# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`ccp` drives an **interactive** Claude Code TUI inside a detached tmux session as if it were `claude -p`. The point is billing: `claude -p` (true headless mode) bills the Agent SDK credit pool, whereas an interactive session bills the subscription pool. So `ccp.sh` automates the interactive TUI — feeding a prompt, auto-answering permission prompts, and scraping the final answer — to get headless ergonomics on the subscription pool. The README tagline is "Headless Claude Code automation without the headless mode."

Pure bash. No build, no package manager, no test suite. Dependencies: `tmux`, `jq`, and the `claude` CLI.

## Commands

```bash
./ccp.sh [-p allow|deny|ask] [-s NAME] [-e KEY=VALUE]... "<prompt>" [-- <claude-options>...]  # run headlessly
./ccp.sh --help                                            # usage
./ccp.sh "say hi"                                          # end-to-end smoke test (see below)
./ccp.sh "review" -- --model opus --add-dir /tmp           # forward claude's own options
shfmt -w ccp.sh hooks/*.sh                                 # format (.editorconfig: 2-space indent, LF)
```

There is no test suite. Verify a change by running the script end-to-end (e.g. `./ccp.sh "say hi"`) — that is the only real test: it exercises the whole launch → readiness → prompt-feed → hook → extract pipeline, and bills a live subscription session (so you must be logged into `claude`).

Before `--`: the prompt is the sole positional arg; everything else is a ccp flag (so a bare `deny` is unambiguously the prompt), and an unrecognized `-flag` is an error. Permission mode (`-p`/`--permission`, default `allow`): `allow` auto-approves every tool call (dangerous Bash is still hard-denied), `deny` rejects everything, `ask` defers to the TUI's normal prompt. `-e`/`--env KEY=VALUE` (repeatable) sets an env var on the launched session via `tmux new-session -e`. `-s`/`--session NAME` names the tmux session (default `cc-<pid>`); it may not contain `.`/`:` and may not collide with an existing session — ccp only ever kills a session it created, never one it didn't.

After `--`: everything is forwarded **verbatim** to the underlying `claude`, so its own options (`--model`, `--add-dir`, `--mcp-config`, …) just work — no per-flag knowledge in ccp, so new claude flags need no ccp change. `--` was chosen over an inline arity table precisely because claude's variadic options (`--add-dir a b c`, `--tools`, `--mcp-config`, …) make inline prompt/value disambiguation impossible. Two passthrough flags are intercepted instead of forwarded: **`--settings <file|json>`** (repeatable) is deep-merged into ccp's generated settings — later values win, and ccp's own `PreToolUse`/`Stop`/`StopFailure` hooks always override the user's for those three events while every other setting (model, env, `PostToolUse`, …) is kept; ccp's `UserPromptSubmit` touch is the lone exception that is *appended* to (not override of) the user's, so a user's own `UserPromptSubmit` hook still runs; **`-p`/`--print`** is dropped with a warning, since claude's headless mode is the very thing ccp replaces (use ccp's own `-p`/`--permission`).

Env overrides: `CCP_READY_TIMEOUT` (default 60s, wait for input box), `CCP_SUBMIT_TIMEOUT` (default 10s, confirm the prompt actually submitted — resending Enter and re-pasting as needed — before giving up), and `CCP_ANSWER_TIMEOUT` (default 0 = wait forever, since prompt complexity is unbounded).

Exit codes: `0` success; `1` runtime failure (session died / answer timeout / bad `--settings`); `2` usage/CLI error (bad args); `4` usage limit reached (quota/credit/429 wall — claude is blocking until reset); `5` turn failed via `StopFailure` (an API error ended the turn); `6` turn needs interactive input (the model called `AskUserQuestion`, unanswerable in a detached run — allow mode only); `127` missing dependency or hook; `130`/`143` interrupted (SIGINT/SIGTERM). Codes `4`, `5`, and `6` each call for a different response from a caller looping ccp: back off until reset (4), retry a transient API error (5), or refine a prompt that needs a human decision (6).

## Architecture

Four files cooperate. `ccp.sh` is the orchestrator; the three hook scripts (plus one inline `UserPromptSubmit` touch, no file) run *inside* the spawned Claude process and communicate back via files.

**`ccp.sh`** — the orchestrator, in numbered steps:
1. Writes a throwaway `--settings` JSON into a `mktemp -d` rundir, wiring four hooks (`PreToolUse` → `auto-permission.sh`, `Stop` → `dump-transcript.sh`, `StopFailure` → `dump-failure.sh`, and `UserPromptSubmit` → an inline `touch <submitted>` that lets step 4 confirm the prompt really reached the model). The user's real `~/.claude/settings.json` is never touched. Hook paths/args are baked straight into the command strings — nothing is smuggled through tmux env. Any passthrough `--settings` is deep-merged underneath this (via `jq`), with ccp's `PreToolUse`/`Stop`/`StopFailure` hooks overlaid last so they win and its `UserPromptSubmit` touch appended.
2. Launches `claude --settings ...` (plus any passthrough args after `--`, each `shq`-quoted so spaces/specials survive the shell tmux runs the command through) in a detached tmux session, injecting any `-e KEY=VALUE` via `tmux new-session -e`. claude launches with **no** positional prompt — interactive — so the prompt is only ever pasted in step 4, never passed as a CLI arg.
3. Polls `tmux capture-pane` until the input box is ready, dismissing the "trust this folder" dialog once if it appears.
4. Pastes the prompt via `load-buffer`/`paste-buffer` (newline-safe, so multi-line prompts don't submit early), then submits — but confirms the submit landed against the `UserPromptSubmit` hook's `submitted` sentinel rather than trusting the pane, resending `Enter` *every* poll (a no-op on an empty box, a submit on a populated one — so it never has to read content out of the box) and re-pasting (after a `Ctrl-U`) only if the box stays *genuinely* empty — empty `❯` and no `[Pasted text` chip — past a grace (a dropped/discarded paste). The prompt is trimmed of leading/trailing whitespace at parse time first. Bounded by `CCP_SUBMIT_TIMEOUT` → exit 1, never a silent hang; see the gotcha below.
5. Blocks until one of four things happens: the `Stop` hook drops the `done` sentinel (success → step 6), the `StopFailure` hook drops the `fail` sentinel (API error → exit 5), the `auto-permission` hook drops the `askq` sentinel (the model called `AskUserQuestion` → surface the question, exit 6), or the pane shows a usage-limit wall (quota block → exit 4). The last is pane-scraped because the subscription session/weekly/Opus walls fire *no* hook (the TUI just blocks until reset), so without it the wait would hang forever.
6. `cat`s the captured answer to stdout.

A single `cleanup` trap (EXIT/INT/TERM) removes the rundir and kills the tmux session — but only one ccp actually started (a `SESSION_STARTED` guard), so dying on a `-s` name collision never tears down a pre-existing session.

**`hooks/auto-permission.sh`** (PreToolUse) — emits a permission decision so the TUI never shows a y/n box, removing any need to scrape the pane for prompts. Even under `allow` it hard-denies irreversible Bash footguns (`rm -rf`, `mkfs`, `dd if=`, fork bombs, writes to `/dev/sd*`). It also intercepts **`AskUserQuestion`**: in **allow** mode it **denies** the call (which suppresses the TUI's multiple-choice box — a plain `allow` only greenlights it and the run then hangs forever on the answer-wait) and touches the `askq` sentinel so the orchestrator aborts with exit 6, recording the question(s) + options to a msg-file for the message; in `deny` mode it is just denied like any other tool (the turn continues); in `ask` mode it defers, since a human attached to the session can answer it.

**`hooks/dump-transcript.sh`** (Stop) — first checks the Stop payload's `background_tasks` array for an in-flight, still-running (`status` `running`/`pending`) task whose `type` is one of the **wake-capable** labels — `subagent`, `workflow`, `shell`, `teammate`, or `cloud session` (the finite kinds that later re-enter the agent with the real answer): if one is present, this Stop is only a *pause*, so the hook exits **without** touching the done-file — the orchestrator waits for the later Stop that fires once the task completes and the agent finishes processing it. The `status` gate (per the schema's `pending|running|completed|failed|killed|paused` enum) is what makes awaiting a `shell` safe: a finished (`completed`/`failed`/`killed`) or `paused` task is *not* awaited, so a finite command the agent ignored never holds the run open (a narrow turn-boundary race remains — a task finishing the same instant the turn ends with its wake still queued can drop done one Stop early — but it's inherent and applies to `workflow`/`subagent` too). Deliberately *not* awaited: `monitor` (an MCP watch), `MCP task` (open-ended async MCP), `dream` (background reflection), and the sibling `session_crons` array — none is this turn's one pending answer, and awaiting them would hang the run. Otherwise it reads the transcript JSONL and extracts "the final answer" = every `assistant` text block after the *last* `user` line (last tool_result, or the prompt). This survives multi-block answers and answers that resume after a tool call; sidechain/subagent lines are excluded. Writes the text to the out-file, then touches the done-file **last** so the orchestrator never reads a half-written answer.

**`hooks/dump-failure.sh`** (StopFailure) — fires *instead of* `Stop` when the turn ends on an API error. Records the `error_type` (`rate_limit`, `billing_error`, `overloaded`, `server_error`, …) to a msg-file, then touches the fail-file **last** (same ordering discipline as dump-transcript). Without it, an API-error turn would never drop the `done` sentinel and the orchestrator would block until the answer-timeout. claude ignores this hook's output/exit code, so the sentinel files are its only effect.

### Things that will bite you if you don't know them

- **Not every `Stop` is the final answer — a backgrounded task parks the turn.** When the agent launches a Workflow, a background subagent, or a `run_in_background` Bash (the tool returns immediately), the turn ends and `Stop` fires while the work is still running; the completing task later wakes a fresh turn with the real answer. `dump-transcript.sh` keys off the Stop payload's `background_tasks` array (verified in the claude binary's hook-input schema: each entry is `{id, type, status, description, command?/agent_type?/server?/tool?/name?}`, with `status` ∈ `pending|running|completed|failed|killed|paused`). The binary's internal task kinds map to friendly `type` labels: `local_agent`→`subagent`, `local_workflow`→`workflow`, `local_bash`→`shell`, `in_process_teammate`→`teammate`, `remote_agent`→`cloud session`, `monitor_mcp`→`monitor`, `mcp_task`→`MCP task`, `dream`→`dream`. The hook withholds the done sentinel while a **wake-capable** task — `subagent`, `workflow`, `shell`, `teammate`, or `cloud session` — is in flight **with status `running`/`pending`**. The await set is an allowlist of labels, so any wake-capable label left off silently drops the answer: the original `workflow`/`subagent`-only list did exactly that to a long-running backgrounded Bash command (→ `shell`), and `teammate`/`cloud session` (backgrounded peer / cloud agents) are in the set for the same reason. The `shell` case is the subtle one: a backgrounded Bash re-enters the agent via a task-notification **only in an interactive session** (claude's own Bash docs say a headless `-p` backgrounded run is never resumed) — and ccp drives the interactive TUI, so it *does* wake. The old code tore the session down at the first Stop before it could wake the consuming turn. The `status` gate keeps this safe: a finished (`completed`/`failed`/`killed`) or `paused` task is not awaited, so a finite command the agent ignored never holds the run open (one narrow exception — a task finishing the same instant the turn ends with its wake still queued can drop done one Stop early; it's inherent and true of `workflow`/`subagent` too, not introduced by the status gate). Still NOT awaited: `monitor` (MCP watch), `MCP task` (open-ended async MCP), `dream` (background reflection), the sibling `session_crons` array (future scheduled work), and a backgrounded process that never exits (a dev server stays `running`, so the run waits on it until `CCP_ANSWER_TIMEOUT` — the deliberate cost of awaiting shells). Older claude builds omit `background_tasks` (reads as empty) or a task's `status` (treated as running, i.e. awaited); both keep the prior behaviour.
- **Re-entrant `Stop` hooks bill the Agent SDK pool — suppress them with `-e`.** A global `Stop` hook that re-enters `claude -p` (spawns a nested Claude session per turn) fires during headless runs and bills the Agent SDK credit pool — the exact thing ccp exists to avoid. `-e KEY=VALUE` sets *any* env var on the launched session (inherited by claude and every hook/subprocess it runs), so set whatever guard var disables such a hook. It injects via `tmux new-session -e`, writing straight into the session env, so it lands regardless of tmux server state — unlike ambient inheritance, which a pre-existing tmux server silently drops (it hands new sessions its own stale env).
- **Readiness detection is signal-based, not "shortcuts"-based.** `ccp.sh` greps for `(shift+tab to cycle)` / `? for shortcuts` / an empty `❯` prompt line, because a custom statusline can hide the shortcuts hint. If the TUI wording changes, this is what breaks — the env timeouts exist as the escape hatch.
- **A submit is confirmed by the `UserPromptSubmit` hook, never by the pane — an empty box does NOT prove the prompt was sent.** Two failure modes leave the prompt unsent after a paste: (a) a single Enter is swallowed by the TUI's post-paste settle window (its "a paste ending in a newline must not auto-submit" guard), and (b) — the one that actually wedged a production `daily-market-scan` run — under CPU contention (two ccp sessions launched the same instant) the paste lands **mangled to whitespace**, which the TUI silently *discards* with no turn. Both empty the input box, so the old "box went empty ⇒ submitted" read advanced to the answer-wait and hung forever (`CCP_ANSWER_TIMEOUT` defaults to 0) on a turn that never started — observed as an idle session with an empty box (the "only spaces got typed" symptom). The fix is ground truth: ccp's inline `UserPromptSubmit` hook touches a `submitted` sentinel that fires (~tens of ms, measured) **only** when a prompt really reaches the model and never on a discarded paste. So `ccp.sh` gates success on that sentinel, and while it is absent keeps nudging within `CCP_SUBMIT_TIMEOUT` (default 10s): it (re)sends `Enter` *every* poll — a no-op on an empty box, a submit on a populated one — and `Ctrl-U` + re-pastes only when the box is *genuinely* empty past a ~3s grace (a dropped/discarded paste) — then exits 1 rather than hanging. A **large/multi-line paste (≥~4 lines) is collapsed by the TUI into a `[Pasted text #N +M lines]` chip on its own line, leaving the `❯` marker line empty** — so an empty `❯` does NOT prove an empty box. This wedged the multi-line `daily-market-scan`/`daily-premarket-brief` runs: the *old* loop sent `Enter` only when the `❯` line looked non-empty and treated an empty `❯` as a dropped paste, so the chip (empty `❯`, content elsewhere) meant Enter was never sent and the loop just re-pasted (→ `[Pasted text #3]`, "paste again to expand") to the 10s `CCP_SUBMIT_TIMEOUT` exit 1 — not pm2 killing the run, despite looking like it (a single-line smoke-test prompt renders inline after `❯` and submits fine, so only multi-line prompts tripped it). The fix is the always-`Enter` policy above (submission never reads the box) plus two backstops so an empty `❯` can't matter: the prompt is **trimmed** of leading/trailing whitespace at parse time (a blank first line can't empty the `❯` of a *non*-collapsed paste; a whitespace-only prompt fails fast with exit 2 instead of a misleading 10s "never submitted"), and the re-paste branch additionally requires no `[Pasted text` chip, so it never re-pastes over a paste that did land. The sentinel check sits at the top of the loop and breaks immediately, so a real submit always wins long before the re-paste grace (~45x the measured ~66ms sentinel latency); the re-paste therefore only ever fires on a genuinely unsent box (no double-submit of a live turn), and `Ctrl-U` makes it idempotent (a slow-rendering original paste can't concatenate with the retry). `Enter` fires every poll, but on an empty box it is a harmless no-op (no turn, no `UserPromptSubmit`), so it can't pick the default on an interactive menu — none renders pre-submit (the trust dialog is already dismissed, `AskUserQuestion` is denied by auto-permission), and once a real turn starts the sentinel breaks the loop within ~tens of ms, so at most one extra Enter ever lands on the cleared/running box. **The homebrew-installed ccp is a separate copy** (`/opt/homebrew/Cellar/ccp/<ver>/`); a scheduled job that calls `ccp` from `PATH` keeps running the old build until it is reinstalled/upgraded, so this fix only protects those daily runs after a reinstall.
- **`Stop` fires before the final JSONL line flushes.** `dump-transcript.sh` re-reads up to ~6s (30 × 0.2s) until the final text block lands; reading once races to an empty result.
- **PreToolUse output schema is `hookSpecificOutput.permissionDecision`** — the legacy `decision: approve/block` is dead for PreToolUse. A hook `allow` cannot override a settings `permissions.deny` rule.
- **`AskUserQuestion` is a normal `PreToolUse` tool, and a plain `allow` does NOT suppress its box.** PreToolUse *does* fire for `AskUserQuestion` (matcher `*` catches it; `tool_input` is a `questions` array — both verified against the binary and a live ccp run), but its multiple-choice box is the tool's *execution*, not a permission gate (its `checkPermissions` defaults to allow — "Permission Required: No"). So a hook `allow` only greenlights the box and the detached run then hangs forever on the answer-wait — which is exactly how it bit a production `daily-premarket-brief` run. Only a `deny` blocks the tool and suppresses the box. So `auto-permission` denies `AskUserQuestion` in **allow** mode and drops the `askq` sentinel → `ccp.sh` surfaces the recorded question(s) and exits 6. The deny does NOT end the turn (the model receives the denial and continues — verified: it went on to answer in text), so the abort is **external**: the orchestrator tears the session down the moment the sentinel appears. In `deny` mode `AskUserQuestion` is just denied like any other tool and the turn runs to completion; in `ask` mode it is left to defer, since a human attached to the tmux session can answer it (the same reason `ask` already warns it will hang detached).
- **Usage-limit walls fire NO hook — only a pane scrape catches them.** The subscription `You've hit your session/weekly/Opus limit` walls make the TUI block until reset *without ending the turn*, so neither `Stop` nor `StopFailure` fires. `ccp.sh` greps the pane for the [documented wordings](https://code.claude.com/docs/en/errors#usage-limits) and exits `4`; the patterns are kept specific (the exact phrases, not a loose `.*limit`) because they run against the *streaming* pane and a loose match would trip on an answer that merely discusses rate limits. API-path errors (429/billing/overloaded) do fire `StopFailure` (→ exit 5), but the same phrases are also in the pane matcher as a backstop for claude builds without the `StopFailure` event.
