# 用户级 Agent 规范

本文件是跨工作区行为的唯一规范来源（canonical user-level Agent instruction source）。工具特定指令文件与本文件冲突时，先读本文件再作判断。

> 这是可公开使用的模板：把 `<尖括号>` 占位替换为你自己的内容，其余结构可直接沿用。

## 语言偏好

- 与用户使用中文交流。（按你的语言偏好修改本条目）

## 全局指令归属

- `~/.agents/AGENTS.md`（即本文件）是唯一规范的用户级 Agent 指令来源。
- `~/.agents/skills` 下的用户级 AgentSkill 资源是唯一规范的用户级技能资源。
- 工具特定文件（如 `~/.claude/CLAUDE.md`、`~/.codex/AGENTS.md`、`~/.copilot/instructions/*.md`）仅为兼容性占位或备份。
- 各工具的用户级技能目录（如 `~/.claude/skills`、`~/.config/opencode/skills`、`~/.codex/skills`）不再维护用户技能副本；需要工具原生加载技能时，配置技能根指向 `~/.agents/skills`（如 OpenCode 的 `skills.paths`）或建立 junction 链接，不得复制技能内容。
- 协作规则需要变更时，先更新本文件。若工具特定备份仍需等价规则，仅同步简短指针或兼容性说明。
- 除非用户明确决定停止使用工具特定冗余，否则不要删除备份指令文件。
- 遇事不决查唯一规范：不确定适用哪条用户级规则时，读本文件并遵循之。

## 跨电脑部署约定

本文件与 `~/.agents`（技能、记忆、原子）设计为跨电脑使用：

- 各机用户主目录下都存在 `~/.agents`，与你的主仓库保持同步（推荐 git clone/pull；网盘或手动拷贝亦可）。
- 本文件内路径一律使用 `~` 相对写法（`~/.agents/...`），不写 `C:\Users\...`、`E:\...` 等本机绝对路径；`~` 在各机均指该机用户主目录。工具特定备份同理使用 `~/.claude/...`、`~/.codex/...`、`~/.copilot/...`。
- 依赖：各机需安装 git；运行记忆检索脚本需 Python（探测顺序：`python` → `uv run python` → 本机已知绝对路径）。
- 机器特定差异（引擎安装位置、Python 安装位置等）不得写入本文件；如需记录，写入对应技能文件的本机裁决注释，跨机部署时替换为本机实际值。

## 用户级 Agent 资源

- Agent 必须参考并遵循 `~/.agents` 下的用户级 Agent 规范与 AgentSkill 资源。
- 已安装的用户级技能位于 `~/.agents/skills`。
- 当工具本地缓存的技能副本与用户级技能同时存在时，优先使用 `~/.agents/skills` 下的用户级技能。

## 技能优先与流程纪律

- 任何任务开始时，agent 必须先检查是否有相关技能适用，再提出澄清问题、探索文件或采取行动；若某技能可能适用，先调用它再继续。
- 流程类技能（如 brainstorming、systematic-debugging）优先于实现类技能；用户显式指令、`AGENTS.md`、`CLAUDE.md`、`GEMINI.md` 及直接请求优先于技能指令。
- 设计、讨论或研究/预研阶段，先使用 Superpowers 工作流；进入计划/设计模式前，在可用时使用 brainstorming/设计工作流。
- TDD 默认禁止：不使用 `test-driven-development` 技能（红绿重构/测试先行）。除非用户明确要求该特定任务使用 TDD，否则遵循本文件并跳过该技能。若某技能推荐 TDD 而本文件禁止，遵循本文件并跳过该技能。自动化测试仅在用户明确要求、或既有项目已要求对进行中变更做特定测试更新时添加。
- 验证偏好：优先编译/构建验证、定向人工检查与项目既有验证方法，而不是为满足某个技能而发明自动化测试套件。

## 协作纪律

- 默认批判性审视每条用户消息；若用户的推理、假设、范围、顺序或取舍有问题，直接、清晰、严肃地指出，而不是默默迁就。
- 明确说明重要假设、风险、边界情况与执行约束。
- 用户与 agent 明确确认的设计决策、执行约束、术语选择或实现方向，执行期间视为有约束力；有新证据表明其不一致、不安全或不可行时，先停下说明冲突再偏离。
- 若输入极不合理，直接给出直白尖锐的反馈，尽快重置讨论。

## 项目初始化排除项

- 初始化或索引项目时，自动跳过以下文件夹及其内容：
- `.idea`、`.vs`、`.vscode`、`.git`
- `Binaries`、`Build`、`Intermediate`、`Saved`、`DerivedDataCache`（含插件子目录下的 `Binaries`/`Intermediate`）

## 领域特有约定（示例：按你的领域改写）

> 本模板为游戏开发者定制，示例保留仅供参考；非游戏领域请整节替换为你的领域规则。

- 游戏项目开发按你的 `unreal-development-workflow`（或等价）技能执行（默认禁 TDD、直接实现 + 编译验证、编辑器自动化不可用时标注人工验证点）。
- 你的语言/引擎的 C++ 文件创建/修改/审查/格式化前：先应用你的编码风格技能；反射宏正确；Tab 缩进、UTF-8 无 BOM、LF 行尾。
- 编译相关（引擎检测、构建工具路径、项目刷新、编译与失败排查）：用你对应的编译技能，不在此重复其命令模板，细节见技能。
- 技能路径基座：`~/.agents/skills/<你的技能仓库>/skills/`。

## 代码与工程惯例

- 命名：类型/函数/变量/字段按实际行为与结果命名；`Resolve` 仅用于从标识符/引用/句柄获取具体对象，其余用精确动词（Evaluate/Calculate、Build/Create、Validate、Apply、Select/Filter、Convert）。
- 注释：必要注释而非逐行；为类型/成员声明、含义不明显的枚举值、多参数函数参数、返回值含义添加注释。
- 组织：`#pragma region` 仅限头文件，`.cpp` 按函数顺序扁平组织；保持代码改动局部化，不重排无关代码。
- 调试：遇到 bug/失败/构建/集成/性能问题，先系统性定位根因再修复；读全错误信息；一次一个假设、最小验证；修复根因而非症状。
- 完成前验证：任何"完成/修复/通过/成功"声明必须有新鲜验证证据（运行检查、读全输出、报告实际结果）；无法验证时明确说明剩余风险。
- 规划：多步实现先给精确计划（文件、步骤、验证命令，无占位符），顺序执行、跟踪进度、受阻即停不猜测；需求不明确时一次问一个澄清问题；方案给 2-3 个带取舍与推荐；行为/架构/能力/工作流变更实现前先获用户批准。
- 并行派发：2+ 独立问题域用并行子代理，每个子代理自包含提示词；失败相互关联、需全系统上下文或会编辑冲突文件时不要并行。
- 评审：重大功能/复杂修复后、合并或交接前执行代码评审；关键结论视为阻塞项；评审者判断有误时用技术证据反驳。

## OpenSpec（可选）

- 若你的项目采用 OpenSpec 契约层：新能力/破坏性变更/架构变更/行为性性能/安全模式变更先提案后实现；bug 修复、拼写/格式/注释、非破坏性依赖升级、配置、既有行为测试通常免提案。
- 提案：动词开头 kebab-case `change-id`；每条需求至少一个 `#### Scenario:`；`openspec validate <change-id> --strict --no-interactive` 通过且评审批准后才实现；`specs/` 是事实来源。
- 提案与既有 specs 冲突：停止，逐项向用户报告冲突（引用路径/需求、冲突内容、实际影响），用户决定前不实现、不静默偏袒新提案。

## 浏览器自动化

- 需导航网站/填表/点击/截图/取数/测试 Web 应用/自动化浏览器工作流时，用 `agent-browser`；OpenCode 下先 `agent-browser skills get core` 加载指令。

## 外部贡献

- 给外部项目开 PR 前：验证问题真实具体、搜索重复 PR/issue、确认变更归属目标项目；一个 PR 一个问题；提交前向用户展示完整 diff 并获明确批准。

## 技能编写与发现

- 创建或修改技能时，使用 `skill-creator` 技能；技能保持简洁、渐进式披露（核心在 `SKILL.md`、详细参考放 `references/`、确定性逻辑放 `scripts/`、输出资源放 `assets/`）；描述应清楚说明何时触发；不得创建误导/意外/恶意/数据外泄技能。
- 用户询问专项任务做法、是否有某技能、或想扩展 agent 能力时，使用 `find-skills` 技能；推荐第三方技能前验证来源信誉、安装量、维护状态。

## Harness 工作流

- 任何实质性任务开始时，agent 必须先调用 `harness-router` 技能，再探索文件或提出澄清问题。此规则与既有技能检查规则同等权重。
- **回答后 TAH 判定** — 每次最终回答前，agent 必须按下述触发清单快速自检（数秒内完成；未命中时保持安静）：
  1. `harness-retro` 触发条件：本次回答覆盖的工作产出了交付物、失败后重试成功、用户纠正了 agent 的判断、做出高影响或不可逆决策、或长任务将尽且存在未关闭检查点。
  2. 检查点纪律：这是长任务且距上次检查点卡已约 5 轮实质交流，或执行蓝图到达 `checkpoint: true` 阶段边界。
  3. 噪音过滤——未命中时静默跳过（绝不提及）：回答为纯查询/琐碎格式调整/单个小文件改动，或本会话刚执行过 retro 且此后无新触发。
  - 命中任一触发：加载 `harness-retro` 并主动提议；草稿卡与记忆写入仍走人工门控——绝不自动写卡。
  - 未命中：静默跳过。绝不等待用户显式请求 harness 检查。
- 任务满足 `harness-retro` 触发条件时，agent 必须提议运行 `harness-retro`（按上述回答后判定）；由用户决定是否继续——这绝不依赖用户显式声明。
- 对话中途任务类型切换时（如从领域 A 讨论切换到领域 B 开发），agent 必须为新任务类型重新运行 `harness-router`。
- 长任务中 agent 必须遵循检查点纪律：在执行蓝图每个 `checkpoint: true` 阶段边界产出检查点卡，或自由讨论中约每 5 轮实质交流产出（作为上述回答后 TAH 判定的一部分检查）。
- `~/.agents/memory/` 下的记忆卡只能通过 `harness-retro` 门控流程写入。绝不自动写卡，绝不删除；用 supersede 取代。
