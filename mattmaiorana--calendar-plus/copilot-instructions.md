## Project overview

- Calendar Plus is an Obsidian plugin: a fork / new plugin based on Liam Cain's Calendar plugin, with integrated periodic note functionality inspired by Periodic Notes.
- Intentionally a **separate** plugin from the original Calendar plugin — both can be installed and enabled simultaneously.

## Important product decisions

- **No backwards compatibility.** Do not write migration code, fallbacks, or compatibility shims for: the original Calendar plugin, the Periodic Notes plugin, Obsidian core Daily Notes settings, or any old data shape. Calendar Plus assumes a clean-slate settings model.
- Calendar Plus owns daily, weekly, monthly, quarterly, and yearly periodic-note settings directly. It does **not** read from Obsidian's core Daily Notes plugin or the Periodic Notes plugin.
- **Dot style product model (1.8.0).** Day and week cells can render dots in one of two modes. Keep this model intact — don't collapse the two modes, don't change the default, and don't move the gate.
  - **`dotMode: "exists"` (default)** — one filled dot when the corresponding daily/weekly note exists. This is Calendar Plus's long-standing behavior. **Must remain the default** for both new installs and existing users (the `loadOptions` spread merge preserves the default for users missing the key).
  - **`dotMode: "word-count-tasks"` (opt-in)** — filled dots based on word count (1 dot per `wordsPerDot`, capped at 5) plus one hollow task dot when the note has `- [ ]` or `* [ ]` open checkboxes. Completed `- [x]` boxes are intentionally excluded.
  - Applies to **daily and weekly cells only**. Monthly, quarterly, and yearly header labels never get dots in either mode.
  - The `has-note` class is emitted on day/week cells in **both modes** as a stable theme hook.
  - Word-count and task sources are **self-gated** inside `src/ui/sources/wordCount.ts` and `src/ui/sources/tasks.ts` — they return empty dots and skip `vault.cachedRead` entirely when the mode is "exists". Don't move the gate into `src/view.ts` or rebuild the source array on settings change; the per-source gate is intentional so toggling modes is reactive without restarting the view.
  - **User-facing copy must not directly reference the original Calendar plugin.** Use descriptive labels ("Note exists" / "Word count and open tasks") in the dropdown, never "Original Calendar plugin" or similar. README + CHANGELOG can mention the plugin in credits/context, but the settings UI stays descriptive.
  - Note-content reads (`vault.cachedRead`) are **only** in the opt-in mode and **only** for visible daily/weekly cells with notes. Do not add new file-content reads outside this gate.
- The plugin must coexist with the original Calendar plugin without collisions (separate view type, separate event namespace, separate manifest id).
- **No `.view-content` padding override.** Calendar Plus intentionally does not target `.workspace-leaf-content[data-type="calendar-plus-view"] .view-content` (or any other `.view-content` selector) for padding, margin, width, or other outer-chrome spacing. The plugin relies on Obsidian's and the active theme's default `.view-content` spacing, matching the original Calendar plugin's baseline. This was investigated and intentionally reverted: a previous attempt to tighten or zero `.view-content` padding produced inconsistent results across themes, leaked spacing into unrelated views, and chased theme-specific renderings (notably Minimal) into a fragile rule. Theme-specific spacing differences should not be addressed by reintroducing a `.view-content` override — any spacing polish should live on internal calendar elements (e.g. `.nav`, `.title-container`, `.quarters`, `.calendar`, `.day`) only.
- **Avoid `!important` in `styles.css`.** The Obsidian community-plugin checker flags every `!important` declaration as a warning ("Avoid !important — override styles by increasing selector specificity or using CSS variables instead"), and accumulating them drops the checker score quickly. 1.7.16 added ~24 `!important`s to force uniform weekend rendering under Minimal; the checker score fell from ~99% to 74%, and 1.7.17 walked all of them back. The standing rule: when a theme conflicts with Calendar Plus styling, prefer (a) modest higher-specificity scoped selectors using the existing `.calendar-plus-wrapper #calendar-container ...` namespace, (b) CSS custom properties (`var(--color-background-day)`, `var(--color-background-weekend)`, etc.) that themes can override cleanly, or (c) a settings toggle that lets users opt out — **do not fight theme internals with `!important`, long view-scoped ancestor chains, or pseudo-element resets**. The **Shade weekend columns** toggle is the canonical example of approach (c): under themes whose `.day` styling makes weekend tinting look busy or inconsistent, the user turns the setting off; Calendar Plus does not try to override the theme.
- **Today button product model.** The Today button in the calendar header is a shortcut to today's daily note, not only a month-navigation reset. Click behavior: (a) always jump the calendar to the current month (`displayedMonth = today.clone()`), and (b) if Daily notes are enabled, route through the same `openOrCreateDailyNote(today, false)` path day-cell clicks use — so confirm-before-create is honored, no-existing-file creates today's note via the configured folder/format/template, and the file opens in the current pane. Plain pane only — modifier state is intentionally not threaded into the Today control (don't add it without a product discussion). When Daily notes are disabled, only (a) runs. Visibility: desktop always shows the Today button; on mobile it is hidden by default and only renders when the user opts in via **Show Today button on mobile** (`showTodayButtonOnMobile`, default `false`). Default OFF is intentional to avoid crowding the mobile header — don't flip the default without revisiting the mobile-layout question. The visibility gate is `{#if !isMobile || showTodayButtonOnMobile}` in `Nav.svelte`; there is intentionally no `.is-mobile .reset-button { display: none }` CSS rule.
- **Active-note highlight model (1.8.3).** Active-file state for the calendar's day/week-num cells is driven by the `activeFile` writable store, populated from two sources: (a) `workspace.on("file-open", onFileOpen)` catches external opens (file explorer, search, link click) via `getActiveFile()`; (b) the per-period existing-file open paths in `view.ts` (`openOrCreateDailyNote` / `openOrCreateWeeklyNote` / `openOrCreateMonthlyNote` / `openOrCreateQuarterlyNote` / `openOrCreateYearlyNote`) call `activeFile.setFile(existingFile)` synchronously immediately after `await leaf.openFile(existingFile)`, and the create-flow callbacks call it from inside the callback. The manual `setFile` after plugin-initiated opens means the highlight updates the moment the note opens, independent of `file-open` event timing — this matters because mobile `file-open` didn't fire reliably enough to drive the highlight in 1.8.2 and earlier, and it matches the original Calendar plugin's daily/weekly pattern (`reference/obsidian-calendar-plugin-1.5.10/src/view.ts:281, 310`). The five periodicities share the same pattern: after `await leaf.openFile(existingFile)`, call `activeFile.setFile(existingFile)`. **Do not casually replace this with a broad `workspace.on("active-leaf-change", ...)` listener** — that approach was tested during 1.8.3 development and introduced a two-click navigation regression because `active-leaf-change` fires on focus-into-calendar before Day.svelte's `on:click` runs, and `updateActiveFile()` → `calendar.tick()` re-renders Day cells mid-click, swallowing the click event. If a future change needs to catch leaf-focus transitions that `file-open` misses, route the work through the manual-`setFile` pattern at the plugin-initiated call site, not through a workspace-wide listener. The initial `updateActiveFile()` sync at the bottom of `onOpen()` (after `new Calendar(...)`) is intentional and should remain — it closes a real lifecycle gap where the constructor's `file-open` listener can't catch transitions that happened before the view mounted (common on mobile when the user opens a file, then reveals the calendar sidebar).
- **Weekend shading product model (1.7.18).** Two orthogonal settings drive weekend rendering, and they are intentionally kept independent:
  - **Week start** (`weekStart`) — controls **column order only**. Choosing Monday vs Sunday vs Locale default rotates the day-of-week header and the body grid; it does not determine which columns are tinted.
  - **Weekend days** (`weekendDays: number[]`, JS weekday numbers 0 = Sunday … 6 = Saturday) — controls **which columns are tinted** when shading is on. Default `[0, 6]` (Sun + Sat). Independent of locale, week start, or any other setting.
  - **Shade weekend columns** (`shadeWeekendColumns`) — master on/off. Defaults to **off**. Opt-in by design: under themes that paint their own opaque background on day cells, weekend tinting can look busy; the toggle is the user-side remedy and the docs make this clear.
  Do not collapse these into a single setting or infer weekend days from `weekStart`. Do not change the default of `shadeWeekendColumns` back to on. Existing users who saved a `shadeWeekendColumns: true` preference under 1.7.16 / 1.7.17 keep it via the existing `loadOptions` spread merge; only users literally missing the key get the new opt-in default.
- **Second Daily Note product model (2.0.0).** A second daily note per day, independent of the primary daily note. Key decisions:
  - Accessed via **right-click on a day cell** (context menu) or **Option/Alt + click** on a day cell. Plain left-click always opens the primary daily note; not accessible via any command.
  - **Option/Alt + click** (`isAltPressed` in `src/ui/calendar-ui/utils.ts`, threaded as an optional 3rd arg to `Day.svelte`'s `onClick` → `openOrCreateDailyNote(date, ctrlPressed, altPressed)`) is dedicated to the second daily note: the Alt branch delegates to `openOrCreateSecondDailyNote(date, ctrlPressed)`, which **opens** it if it exists or **prompts to create** it if it doesn't (same confirm-before-create flow as the right-click "Create Second Daily Note" — 2.1.7 changed this from the earlier no-op-when-missing behavior). When `secondDaily` is disabled, Alt falls through to the normal primary-note flow (Alt ignored). `ctrlPressed` is still honored, so Cmd/Ctrl + Option + click opens/creates the second note in a new tab/split.
  - Has its own `secondDaily: PeriodicNoteSettings` key in `ISettings` (folder, format, template, enabled). Defaults to disabled. The format defaults to `YYYY-MM-DD` (same as daily) — users who want the two note sets in the same folder must use a different format string to avoid filename collisions.
  - **Context menu behavior:** when second daily is enabled, right-clicking a day cell shows a custom `Menu`. The primary-daily item(s) always live in the `calendar-daily` section and the second-daily items in `calendar-actions`, so Obsidian renders a **divider between the two groups consistently** — whether the primary note exists ("Open Daily Note" + "Delete Daily Note") or not ("Create Daily Note"). (Earlier, "Create Daily Note" shared the `calendar-actions` section with the second-daily items, so the divider only appeared when the primary note existed — fixed by moving it to `calendar-daily`.) If a second note exists: "Open Second Daily Note" then "Delete Second Daily Note" (`calendar-actions` section; deletes use `app.fileManager.trashFile` so Obsidian's trash preference is respected). If the primary note exists, its standard file-menu items are still appended below the custom sections. If second daily is disabled: existing behavior unchanged (file menu for primary note if it exists, no-op otherwise).
  - **Dot:** `secondDailyNoteSource` in `src/ui/sources/secondDailyNote.ts` emits one filled dot with `className: "second-daily"` when a second daily note exists, regardless of `dotMode`. `styles.css` sets `opacity: 0.5` on `.dot.filled.second-daily` to visually distinguish it from the full-opacity primary dot without introducing a new color. The `className` is a stable CSS hook if the visual treatment is ever revisited (see `FUTURE_PLANS.md`).
  - **Store:** `secondDailyNotes` in `src/ui/stores.ts` uses `"daily"` as the periodicity for date parsing and UID generation (same granularity as daily notes). No collision with `dailyNotes` because they are separate store objects. Does not add `"secondDaily"` to the `Periodicity` type — the type remains the five calendar periodicities only.
  - **Open/create:** `openOrCreateSecondDailyNote` in `view.ts` calls `createPeriodicNote("daily", date, settings.secondDaily)` directly (passing `settings.secondDaily` for folder/format/template) and handles confirm-before-create inline, so the confirmation dialog correctly says "New Second Daily Note". Does not go through `tryToCreatePeriodicNote` (which indexes into settings by periodicity key).
  - **Active-file highlight (2.1.7):** when a second daily note is the active file, its day cell gets a **distinct grey highlight** (not the purple primary-active fill). A separate `activeSecondDailyFile` store (`src/ui/stores.ts`) holds the active second daily note's UID, set in `CalendarView.updateActiveFile()` alongside `activeFile`. Its detection is **folder-aware** (checks `secondDaily.folder` via `isFileInConfiguredFolder` + parses `secondDaily.format`), so a second daily note is never mistaken for a primary daily note even when the two share a date format — this is why it doesn't reuse `getDateUIDFromFile` (which is basename-only). The store flows wrapper → base → `Day.svelte` as `selectedSecondDailyId`; `Day` renders `.second-daily-active` (a translucent grey `::after` overlay, works over plain and feature-image cells) and **suppresses `.active`** when second-daily-active so the two never stack. The primary `activeFile` highlight still only covers daily/weekly (`getDateUIDFromFile`).
- **Feature Images product model (2.0.0).** Day and week-num cells can show the note's feature/banner image as a cell background. Key decisions:
  - **Scope:** daily cells + weekly cells. Monthly/quarterly/yearly header labels never get background images.
  - **Resolution order:** frontmatter properties (configurable, default `["banner", "image", "cover"]`) are checked first in priority order; the first one that resolves to a vault image file wins. Falls back to the first `![[…]]` embed in `cache.embeds` that resolves to an image. Vault files only — external `https://` URLs are rejected.
  - **Per-note opt-out (2.1.6).** A day's feature image can be hidden individually, stored in **plugin data** as `featureImage.hiddenNotes: string[]` (vault paths) — **not** in note frontmatter. (2.1.5 shipped a frontmatter-flag version that was abandoned: writing `calendar-hide-image` to a note that otherwise had no frontmatter made Obsidian render a Properties box at the top of the note, which users disliked, and the refresh was unreliable. Don't reintroduce a frontmatter flag for this.) The check lives in the **source** (`src/ui/sources/featureImage.ts`): `getDailyMetadata`/`getWeeklyMetadata` return `{}` when `s.featureImage.hiddenNotes.includes(file.path)`, before calling `getFeatureImageUrl` (so it's independent of the URL memoization — the hidden set isn't part of the memo key). Toggled from the **day-cell context menu**: when feature images are enabled and the daily note exists, the menu shows "Hide feature image" (if an image currently resolves via `getFeatureImageUrl`) or "Show feature image" (if the path is already in `hiddenNotes`); `CalendarView.setFeatureImageHidden(note, hidden)` adds/removes the path via `this.plugin.writeOptions(...)`. Persisting through `writeOptions` updates the `settings` store, which the calendar wrapper's `$effect.pre` reacts to (bumps `today`), so the cell refreshes **without** any file write or metadata-cache dependency — this is what made it reliable where the frontmatter version wasn't. The menu item is added by `addFeatureImageMenuItem(...)` in both context-menu paths (the custom second-daily menu and the `showFileMenu` fallback, which takes an optional `addExtraItems` callback). **Known minor gap:** a hidden note's path goes stale if the note is renamed/moved (the image reappears; the orphaned path lingers in `hiddenNotes`) — daily notes are date-named and rarely renamed, so this is deferred (see FUTURE_PLANS).
  - **Implementation:** `src/io/featureImage.ts` exports `resolveFeatureImageFile(note, app, frontmatterProperties)` (2.1.8 renamed it from `getFeatureImageUrl`) which calls `app.metadataCache.getFileCache(file)` synchronously and returns the resolved image **`TFile`** (not a URL) or `null`, memoized on `(path, mtime, propsKey)`. It also exports `invalidateFeatureImageCache(path)` and `isImagePath(path)`. `src/ui/sources/featureImage.ts` exports `createFeatureImageSource(app)` — a factory that returns a self-gated `ICalendarSource`. Its `backgroundFor(note, props)` resolves the image `TFile`, then returns `getThumbnailUrl(file)` when the thumbnail cache is available (falling back to `app.vault.getResourcePath(file)` — the full-res `app://` URL — until the thumbnail is ready or if the cache is unavailable). Gating is inside the source (returns `{}` when `featureImage.enabled` is false, or when the note's path is in `featureImage.hiddenNotes`); do not move the gate elsewhere. `backgroundImage?: string` is added to `IDayMetadata` in `types.ts`; `metadataReducer` propagates it with first-source-wins semantics (`acc.backgroundImage ?? meta.backgroundImage`).
  - **Thumbnail cache (2.1.8).** `src/io/thumbnailCache.ts` is a persistent, file-backed thumbnail cache living in the **plugin folder** (`.obsidian/plugins/calendar-plus/thumbnail-cache/`, via `DataAdapter` so it works on mobile). It exists to remove the full-resolution decode-per-cell-per-render cost (the sidebar-open stutter / typing lag on image-heavy vaults). `initThumbnailCache(app, dir)` is called from `main.ts onload` (`teardownThumbnailCache()` in `onunload`). `getThumbnailUrl(file)` is **synchronous**: returns a ready object URL or `null` and kicks off async preparation (load-from-disk-or-generate). Thumbnails are keyed `hashPath(file.path)-mtime` → `<key>.jpg`; generation uses `createImageBitmap` → `<canvas>` downscale (MAX_DIM 128) → `toBlob` JPEG (quality 0.72), with bounded concurrency (3) and an in-flight dedupe map; generation failures fall back to the full-res resource path. The source `readBinary` runs **inside** the concurrency gate (2.1.9), so a cold month of ~30 images holds at most 3 full-res buffers in memory at once rather than reading all ~30 up front. A debounced (50ms) ready-callback (`setThumbnailReadyCallback`, wired in `view.ts onOpen` to `calendar.tick()`) refreshes cells as thumbnails finish. The day↔image connection is **never persisted** — it's derived live each tick from the note filename + frontmatter/embeds; the cache only maps image-file → thumbnail and is fully regenerable, so per-device differences after folder-sync are expected and harmless. **GC:** `removeThumbnailsForSource(sourcePath)` drops a source image's thumbnails (called from `onFileDeleted`/`onFileRenamed` in `view.ts`, gated by `isImagePath`); `pruneThumbnailsExcept(inUseFiles)` is a mark-and-sweep keeping only currently-in-use thumbnails, driven by `sweepUnusedThumbnailsOnce(app)` (once per session, ~3s after `onOpen`, gated on `featureImage.enabled`) which collects in-use images via `collectInUseFeatureImages(app)` — this clears thumbnails for images that still exist but are no longer a feature image (e.g. the user swapped to a different banner).
  - **Settings:** `featureImage: FeatureImageSettings` in `ISettings` — `enabled` (default `false`, opt-in), `frontmatterProperties: string[]` (comma-separated in the UI, stored as array), `showForWeekly` (default `true`). Settings section added to "Calendar behavior" after the Shade weekend columns section.
  - **Rendering:** `Day.svelte` and `WeekNum.svelte` set `background-image: url("...")` inline and add `has-background-image` when `backgroundImage` is present (the URL is the cached thumbnail when available, else the full-res resource path — see Thumbnail cache). The per-cell `MetadataResolver` resolves the source metadata into reactive `$state` and renders it with `{@render}` (2.1.8 replaced the old `{#await}` block, which produced a *new* promise each tick and so destroyed/recreated each image cell's DOM — forcing the browser to re-decode/re-composite the photo on every render; that was the typing/sync lag). The cell uses `isolation: isolate` to create a stacking context so pseudo-element overlays resolve within the cell. The date/week number is wrapped in a `<span>` (`.day-number` / `.week-num-number`) carrying `position: relative; z-index: 1` — purely for stacking; it has **no** visual styling, so the number's color/weight/today/active behavior is identical with or without an image (a prior attempt to add `color: white` + `font-weight: 600` + `text-shadow` was removed because the user wanted the number unchanged). A `::before` readability overlay (dark gradient `rgba(0,0,0,0.45)→rgba(0,0,0,0.35)`, `z-index: 0`) sits above the image but below the number/dots. The active state suppresses the solid accent fill (`background-color: transparent`) and adds a `::after` accent overlay (`background-color: var(--interactive-accent)`, `opacity: 0.65`, `z-index: 0`) so the photo stays visible while reading as selected. **Hover (2.1.2):** the base `.day:hover` / `.week-num:hover` `background-color` change is invisible behind the image, so image cells instead **lighten the `::before` overlay** on hover (`rgba(0,0,0,0.45→0.35)` → `rgba(0,0,0,0.2→0.1)`, with a `transition: background` on `::before`) to read as hovered, and keep `background-color: transparent` on `:hover` (and `.active:hover`) so hovering doesn't repaint/re-composite the photo (that repaint was the source of hover lag on image-heavy vaults). **Do not reintroduce number styling on image cells** — only the background, the readability gradient, the hover-lightened overlay, and the active overlay should differ.
  - **Cache invalidation:** `view.ts` registers `app.metadataCache.on("changed", onMetadataCacheChanged)` to tick the calendar when a daily/weekly note's metadata changes (e.g. user edits `banner:` frontmatter). `vault.modify` fires before the cache updates, making `metadataCache.changed` the reliable post-update trigger for frontmatter-driven images. **`onMetadataCacheChanged` also calls `invalidateFeatureImageCache(file.path)` before ticking (2.1.8 fix):** the `resolveFeatureImageFile` memo is keyed on `(path, mtime, props)`, and `vault.modify` bumps `mtime` *before* the cache reparses — so a resolve triggered by `onFileModified` can store a stale result under the new mtime, which the later `metadataCache.changed` tick (same mtime) would then return from the memo. This left the image on the cell after removing the last image from a note, until reload. Dropping the memo entry on the authoritative metadata-change event forces a fresh resolve. Don't remove this invalidation while the `mtime`-keyed memo exists.
  - **No new note-index store.** The day↔image *mapping* is not indexed: it's derived on each `calendar.tick()` from the existing `dailyNotes`/`weeklyNotes` stores + `app.metadataCache`. (2.1.8 did add a file-backed *thumbnail* cache — see Thumbnail cache — but that's an image-file→thumbnail cache, not a note/date index, and holds no day↔image association.)
- **Year overview product model (2.0.0).** A compact 12-month navigation grid (inspired by Notebook Navigator's year panel) for jumping between months/years. Key decisions:
  - **Popup, not a stacked panel or mode switch.** `Nav.svelte` renders a `history` lucide icon button in `.right-nav` (before the prev arrow) when `showYearOverviewButton` is true. Clicking it opens `<YearGrid>` as a floating popup (`.year-popup`, `position: absolute` anchored top-right inside the `position: relative` `#calendar-container`, with `var(--background-secondary)` bg, border, `var(--shadow-s)`). The popup overlays the day grid; it neither pushes layout (no stacked panel) nor replaces the grid (no `viewMode`). Both of those earlier iterations were removed — do not reintroduce them. `YearGrid` draws a compact `< YYYY >` year-arrow header and a 4×3 month grid. The existing month/year/quarter header labels are untouched; the year grid is navigation-only (no note creation in v1).
  - **Button gates on the persisted setting; popup open/close is transient local state.** The persisted `showYearOverview` now means "show the history button" (gates `{#if showYearOverviewButton}` in `Nav`). Whether the popup is *open* is a non-persisted `yearOverviewOpen` boolean local to the vendored `Calendar.svelte` — popups shouldn't survive reloads. `toggleYearOverview()` flips it; the button's `on:click|stopPropagation` prevents the open click from immediately bubbling to the `<svelte:window on:click>` handler that closes the popup on any outside click; `.year-popup` also `stopPropagation`s so interacting with the year arrows doesn't close it; selecting a month closes it explicitly. The icon is `var(--text-muted)` (grey) when closed and `var(--text-normal)` (white-ish) when open via a `.active` class — intentionally **not** accent/purple. (An earlier iteration persisted *this* toggle by threading the plugin into the view; that plumbing was reverted since the popup is transient and shouldn't persist. Note `view.ts` *does* take a plugin arg again as of 2.1.6 — but only to persist the feature-image `hiddenNotes` list via `writeOptions`; the year-overview popup state remains transient and is **not** persisted through it.)
  - **`displayedMonth` is the sole state.** No separate "displayed year" and no view-mode state: the shown year is `displayedMonth.year()`, year arrows do `displayedMonth.clone().add(±1, "year")`, clicking a month does `selectMonth(date)` → `displayedMonth = date.clone().month(i).startOf("month")`, which simultaneously moves the day grid and the panel's `.active` highlight (they share `displayedMonth`).
  - **Month dot = any note in that month.** A month cell shows one filled dot (reusing `Dot.svelte`) when it contains any daily, weekly, OR monthly note. Computed by `getMonthsWithNotes(year, daily, weekly, monthly)` in `src/io/yearNotes.ts`, which buckets each store's UID timestamps (`moment.parseZone` of the post-`unit-` portion) into a `boolean[12]`. Weekly notes bucket by their start-of-week month (coarse signal, acceptable). Disabled periodicities have empty stores so contribute nothing.
  - **Store-decoupled.** The vendored `Calendar.svelte` takes `monthsWithNotes: boolean[]` and `showYearOverview: boolean` as props; the app wrapper (`src/ui/Calendar.svelte`) computes `monthsWithNotes` reactively from `$dailyNotes`/`$weeklyNotes`/`$monthlyNotes` + `displayedMonth.year()` and passes it down. The wrapper's reactive uses `(displayedMonth ?? today ?? moment()).year()` because the wrapper's `displayedMonth` defaults to a reactively-assigned `today` that is `undefined` at prop-init time — calling `.year()` on it unguarded threw during the first flush and blanked the entire calendar.
  - **Settings:** `showYearOverview: boolean` in `ISettings` (default `false`, opt-in), toggle in "Calendar behavior" after "Show Today button on mobile". Top-level boolean — the `loadOptions` `{ ...old, ...options }` spread preserves the default; no per-object merge needed.
  - **Styling reuses calendar tokens; intentionally compact.** `YearGrid` cells mirror `.day` (same `--color-background-day`, `--interactive-accent` fill when the cell is the displayed month, `--color-text-today` when it's the current real month, `--interactive-hover`). The framing/elevation comes from the `.year-popup` card (in `Calendar.svelte`), so `YearGrid` itself carries no border/margin. The year number is `0.95em` (not the large `Nav` `.title` size), month labels are `0.8em` (matching `.day`), and cell padding is tight. Year arrows reuse `Arrow.svelte`.

## Current architecture

- **Manifest** (`manifest.json`): id `calendar-plus`, name `Calendar Plus`, minAppVersion `0.9.11`. (Current version is in the Project overview above.)
- **Internal namespaces** (`src/constants.ts`):
  - `VIEW_TYPE_CALENDAR = "calendar-plus-view"`
  - `TRIGGER_ON_OPEN = "calendar-plus:open"` (event external plugins listen on to inject sources)
- **Settings** (`src/settings.ts`): `CalendarSettingsTab` extends `PluginSettingTab`. Periodic-note sections are rendered into per-section wrapper divs via `renderPeriodicNoteSection(sectionEl, ...)`, so toggling Enable re-renders only that section (no full-tab rebuild, no scroll jump).
- **Periodic note helpers** (`src/io/periodicNoteHelpers.ts`): pure path/format/parse helpers + vault scan. Includes `getDateFromFilename`, `getPeriodicNotePath`, `applyTemplateTokens`, `getAllPeriodicNotes`, `getDateUID`, `getPeriodicNote`, `ensureParentFolderExists`, `getTemplateInfo`.
- **Shared creation + open logic** (`src/io/periodicNotes.ts`): `createPeriodicNote(...)`, `tryToCreatePeriodicNote(...)` (confirm-before-create modal), `getLeafForModifierClick(ctrlPressed, settings, workspace)` (returns the destination `WorkspaceLeaf` — plain click → current pane; modifier + `ctrlClickOpensInNewTab` → new tab; modifier + !setting → vertical split), and `tryToCreatePeriodicNoteAndOpen(periodicity, date, ctrlPressed, settings, cb?)` (creates + opens via the modifier-click leaf picker + optional post-open callback). 1.8.1 consolidated the per-period open/create flow here; `view.ts` uses `getLeafForModifierClick(...)` directly for the existing-file open paths so all five periodicities pick the destination leaf the same way.
- **Per-period wrapper files** (`src/io/{daily,weekly,monthly,quarterly,yearly}Notes.ts`): thin one-line delegators to `tryToCreatePeriodicNoteAndOpen("<periodicity>", ...)` after the 1.8.1 consolidation. They remain as named entry points for call-site clarity (`tryToCreateDailyNote`, etc.) and are the only place the `"daily" | "weekly" | "monthly" | "quarterly" | "yearly"` periodicity literal is captured per-file.
- **Stores** (`src/ui/stores.ts`): module-level Svelte writables for `settings`, `dailyNotes`, `weeklyNotes`, `monthlyNotes`, `quarterlyNotes`, `yearlyNotes`, `activeFile`, and `secondDailyNotes`. Each per-period store has a `reindex()` method that rescans the configured folder; the wrapper (`src/ui/Calendar.svelte`) calls these **selectively and debounced** on settings change — only for stores whose own `folder`/`format`/`enabled` changed (2.1.2), and the rescan is debounced ~300ms so per-keystroke folder/format edits coalesce to one walk (2.1.4). The mount reindex stays immediate (calendar populated on open). Don't revert to reindexing all stores synchronously on every settings change. `secondDailyNotes` is created by a dedicated `createSecondDailyNotesStore()` factory (not `createPeriodicNotesStore`) because it reads from `settings.secondDaily` rather than a `Periodicity`-keyed settings entry; it uses `"daily"` as the periodicity for date parsing and UID generation.
- **View / lifecycle** (`src/view.ts`): `CalendarView` extends `ItemView`. Owns the Svelte `Calendar` component, vault file events, settings subscription (registered via `this.register(...)` so it cleans up on view detach), and the periodic-note open/create methods.
- **Plugin registration / commands** (`src/main.ts`): `CalendarPlugin` extends `Plugin`. Registers the view, ribbon icon, and three commands (`show-calendar-view`, `open-weekly-note`, `reveal-active-note`). Commands look up the live view fresh via `getCalendarView()` / `ensureCalendarView()` helpers — no stale `this.view` reference.
- **Calendar UI**: vendored under `src/ui/calendar-ui/` (`components/*.svelte` plus `localization.ts`, `metadata.ts`, `types.ts`, `utils.ts`). Origin: the patched `obsidian-calendar-ui` 0.3.12 source (the patch added quarter navigation, clickable month/year/quarter labels, weekend col classes, and week-num grid borders + active state). The npm dependency and the `patches/obsidian-calendar-ui+0.3.12.patch` file have been removed. `Day.svelte` and `WeekNum.svelte` use the local `getDateUID` from `src/io/periodicNoteHelpers` (with `"daily"` / `"weekly"` periodicity) instead of `obsidian-daily-notes-interface`, which is no longer a transitive dep. Component-internal CSS now lives inside each vendored component's `<style>` block; `styles.css` retains only the wrapper-state-dependent rules (depend on `.daily-enabled`/`.monthly-enabled`/etc. on the outer Calendar Plus wrapper) and the `.calendar-plus-suggest` rule for the document-body-attached settings autocomplete.
- **Autocomplete** (`src/ui/file-suggest.ts`): folder/template path autocomplete in settings. As of 2.1.3, built on Obsidian's native **`AbstractInputSuggest<T>`** (positioning, keyboard nav, popup lifecycle, and keymap scope are all handled by Obsidian) — this replaced a ~150-line hand-rolled `TextInputSuggest` (no-Popper, manual `getBoundingClientRect` positioning + scroll/resize listeners + a keymap `Scope`), ported from the Daily Checklist plugin, which lived in `src/ui/suggest.ts` (now deleted), along with its `.calendar-plus-suggest` rule in `styles.css` (also deleted — the native popup is themed by Obsidian). `FolderSuggest` / `FileSuggest` keep a 2-arg `(app, inputEl)` constructor and override `selectSuggestion` to `setValue(...) + inputEl.trigger("input") + close()`, so the existing `Setting.addText(...).onChange(...)` handlers in `settings.ts` still save on selection with **no call-site changes**. (`AbstractInputSuggest` is available in the pinned `obsidian@1.8.7` types.)

## Important implementation notes

- **Dependency + type-aware lint (added 2.0.1 — do not regress).** The `obsidian` dependency must be the **standard npm package** (`"obsidian": "1.8.7"` in `devDependencies`), **not** a GitHub tarball (`obsidianmd/obsidian-api#…`). The Obsidian plugin-review environment does a **registry-only `npm ci`** and cannot fetch a GitHub-sourced dependency — when it fails to install, the whole dep tree (obsidian, moment, svelte) resolves as `any`/error types and the review's **type-aware `@typescript-eslint`** rules emit hundreds of `no-unsafe-*` warnings across every file (this tanked the 2.0.0 review score ~15%). `versions.json` / `minAppVersion` stay at `1.8.7`, matching `obsidian@1.8.7`. To mirror the review locally, the flat **`eslint.config.mjs`** (2.1.0 migrated `.eslintrc.js` → flat config for ESLint 9 + `typescript-eslint` 8 and removed `.eslintignore`; 2.1.1 renamed it to `.mjs` / ESM and switched from the deprecated `tseslint.config()` to `defineConfig()` + `globalIgnores()` from `eslint/config`, to clear the review's `require()` and deprecated-`config()` warnings) sets `languageOptions.parserOptions.project` + extends `tseslint.configs.recommendedTypeChecked` (with `require-await` / `prefer-regexp-exec` / `restrict-template-expressions` disabled — the review doesn't flag those; **`@typescript-eslint/no-deprecated` is enabled** so local lint mirrors the review's deprecation findings), and its `globalIgnores` covers `reference/`, `main.js`, and JS/MJS/CJS config files (the lint is scoped to `.ts`, replicating the old `--ext .ts`). `@eslint/js` is pinned in `devDependencies` (the review flags imported packages not listed there). Keep `npx eslint .` at **zero** errors. ## UI internals cleanup (landed in 1.7.18)

A small behavior-preserving polish pass landed as part of the 1.7.18 release, alongside the configurable-weekend-days work. Items **kept**:

- **Dot data model trim**: dropped the unused `color` field from `IDot`, made `className` optional, removed the unused `isActive` prop from `Dot.svelte` and its unreachable `.active.filled` / `.active.hollow` CSS rules, trimmed the streak-source dot payload to `{ isFilled: true }`.
- **Dead `th { ... }` block removed from `WeekNum.svelte`** (the component renders only `<td>`, so the rule fired on nothing).
- **`.active` selector in `Day.svelte`** rewritten as `.day.active` / `.day.active.today` for clarity. No behavior change — Svelte-scoped CSS already pinned the selector to elements inside Day.svelte.
- **`Nav.svelte` comment rephrase**: removed the only remaining `!important` mention anywhere in `src/`, so grep / checker output stays clean.

Item intentionally **not kept**:

- **Unused helper parameters** (the `..._args: unknown[]` rest params on `getDaysOfWeek`, `getMonth`, `getDailyMetadata`, `getWeeklyMetadata`) were briefly removed in the same pass, but the cleanup was reverted. Removing the params required `(localeData, getMonth(...))` / `(today, getDailyMetadata(...))` comma-operator expressions in `Calendar.svelte` to keep Svelte's reactive-dependency chain intact. The comma-operator pattern is technically correct but less readable and more surprising than passing `localeData` / `today` as ordinary arguments — a reader shouldn't have to recognize the comma-operator idiom to see the reactive deps. The current code keeps the rest-args; `Calendar.svelte` keeps `localeData` / `today` as ordinary call arguments so reactivity is obvious at the call site. A future pass that wants to clean these up should pick a style that doesn't hide reactive deps from readers (e.g. a named `_trigger?: unknown` param is fine, comma operators are not).

Changelog content guidance:
- Lead with what the user will notice. Group related items under short headings if the section is long (see the 1.6.0 entry as a template).

Proposing version bumps:
- For major user-facing features, major refactors, dependency changes, or other release-significant cleanup, mention in your plan whether a changelog entry and version bump are warranted, and flag the proposed version (major / minor / patch) so the user can confirm.
