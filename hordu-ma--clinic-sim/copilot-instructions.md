# clinic-sim AI 协作总则

- 用户可见回复默认使用中文。
- 先读仓库根目录的 `AGENTS.md`，再读与任务相关的 `skills`、`docs` 与代码文件，最后开始修改。
- 保持 KISS，优先修根因；不要为当前任务引入额外抽象。
- 修改前维护一个不超过 5 步的 TODO；不确定接口、数据模型、行为变更时先澄清。
- 默认做局部修改；仅在新增、升级、移除依赖时更新锁文件。
- 除非用户明确要求，不主动新增 Markdown 文档或脚本文件。
- 禁止硬编码密钥；执行高风险命令前必须确认意图与影响。
- Python 相关终端命令优先使用 `uv run ...`；终端命令保持兼容 Linux/macOS/WSL。
- 完成后报告已执行的验证、未验证项与残余风险。

## 1. 指令优先级

当不同仓库资产存在重叠约束时，按以下顺序执行：

1. 用户明确要求
2. 本文件
3. `AGENTS.md`
4. `.github/skills/<skill-name>/SKILL.md`
5. `docs/` 与代码中的领域说明

如果内容冲突，优先遵循更高优先级来源；如仍存在歧义，先澄清再改。

## 2. 入口索引

### 2.1 通用入口

- 仓库总览与协作规范：`AGENTS.md`
- 场景化执行步骤：`.github/skills/<skill-name>/SKILL.md`
- 文档中心：`docs/README.md`
- 生产部署统一入口：`docs/deployment/生产部署指南.md`

### 2.2 代码与配置入口

- 后端主目录：`src/apps/api/`
- 前端主目录：`src/apps/web/`
- 基础设施主目录：`src/infra/compose/`
- 测试主目录：`tests/`
- 脚本主目录：`src/scripts/`

### 2.3 常见高风险变更入口

- 数据模型与迁移：`src/apps/api/models/`、`src/apps/api/migrations/`
- 身份认证与权限：后端 route/schema/service 及相关 tests
- 部署与生产配置：`src/infra/compose/`、`docs/deployment/`
- 共享契约与前后端联动：后端 schema/route、前端 `src/api`、前端 `src/types`
- 外部依赖与运行环境：LLM、PostgreSQL、MinIO、Nginx、Docker Compose

## 3. 任务执行原则

- 先明确目标，再改实现；先确认契约，再动代码；先验证，再交付。
- 默认采用最小可行改动，避免顺手重构。
- 涉及跨层变更时，优先保持 schema、route、service、model、test 的一致性。
- 涉及前后端联动时，先对齐接口契约，再分别改动两端。
- 涉及部署与安全时，先列出前提、影响范围、回滚路径，再给出执行建议。
- 不依赖口头经验，优先使用仓库内已有文档、技能与命令作为依据。

## 4. 验证分层

### 4.1 最小验证

修改完成后，优先运行与变更最相关的最小验证集。

- 单文件或单模块变更：相关单测或局部检查
- 后端逻辑变更：目标 `pytest` 用例
- 前端页面或接口变更：相关页面构建或类型检查
- 配置与部署变更：对应配置校验与最小启动检查

### 4.2 标准验证

当变更涉及多文件、多层或契约时，补充更完整的验证。

- 后端：相关测试文件、必要的 `pytest`、静态检查
- 前端：构建与类型检查
- 接口契约：后端测试 + 前端构建/类型检查
- 数据模型：迁移逻辑与相关测试
- 部署：配置校验、环境变量核对、回滚路径检查

### 4.3 高风险验证

当变更涉及以下场景时，必须显式说明已验证与未验证项：

- 认证、权限、会话、聊天、评分
- 数据库 schema 或迁移
- 生产部署、Nginx、镜像、Compose
- 外部服务依赖或运行时环境
- 任何可能影响现网可用性的配置调整

## 5. 完成定义

一个任务只有在同时满足下列条件时，才可视为“完成”：

1. 需求目标已实现或已明确说明无法实现的原因。
2. 与当前变更相关的关键约束已检查。
3. 至少完成了最小充分验证。
4. 涉及契约、模型、部署或安全的变更，已同步更新相关约束或测试。
5. 输出中明确列出已运行验证、未验证项与残余风险。

若因环境限制无法完成验证，必须明确写出原因，并说明风险是否可接受。

## 6. 变更范围与回退

- 优先局部修改，避免跨模块无关调整。
- 修改配置、迁移、部署或安全相关内容时，保留可回退路径。
- 删除文件、批量重命名、跨模块重构前必须先确认影响范围。
- 若需要调整文档或脚本，优先复用现有文件，不轻易新增。

## 7. 协作输出要求

- 回答先给结论，再给关键细节。
- 不确定内容必须明确标注“假设”或“待确认”。
- 提供建议时优先说明影响、代价、风险与验证方式。
- 不声称已验证，除非实际执行过相应命令并获得结果。
- 完成时优先报告：
  - 已运行的命令
  - 结果
  - 未验证项
  - 残余风险
