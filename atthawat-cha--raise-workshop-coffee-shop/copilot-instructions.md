# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

This is the **ADT-RAISE Non-Degree Batch 2** workshop project. The stated goal (see `.docs/requirement.md`) is:

> A coffee shop owner needs a tool to take customer orders, so customers can order by themselves from their table (QR-code style self-order flow).

**Current focus of this repository is documentation, not implementation:** producing the Requirement Specification and the Product Backlog for the coffee shop self-order system. There is no application code, package manager, build tool, or test suite in this repo, and none should be assumed or scaffolded unless the user explicitly asks for it — work here is writing/refining `.docs/` content.

## Document Language

`requirement.md` and `system-requirements-specification.md` are written in **Thai**, matching the real audience (a Thai coffee shop owner). All deliverable documents (Requirement, Product Backlog, PDPA/compliance addendum, etc.) should be written in **Thai** unless the user asks otherwise. `CLAUDE.md` itself stays in English, per normal Claude Code convention — don't switch the deliverables' language just because this file is in English.

## Repository Structure

```
.docs/           Requirements and Product Backlog documents (the actual deliverables of this phase)
.docs/spec/      Per-topic requirement documents generated by the requirement-analysis sub agent
.docs/backlog.md Product Backlog (does not exist yet — created/updated by the backlog sub agent)
.design/         Reserved for design artifacts (wireframes, UX, diagrams) — currently empty
.archived/       Reserved for superseded/old versions of documents — currently empty
.logs/           Run logs from sub agents, one file per day — currently empty
.testing/        Reserved for test-related material — currently empty
```

Key documents in `.docs/`:
- `requirement.md` — the original raw prompt plus the workshop's task list ("Need"): create `CLAUDE.md`, build sub-agents/agent skills to help produce Requirement/Backlog documents, use them to actually generate those documents, and extend the Requirement + Backlog with PDPA/legal-compliance considerations. Treat this file as the brief for the whole workshop, not just a one-time input.
- `sub-agents.md` — the spec for the requirement/backlog sub agent: input/output contract, clarifying-question rule, and the file paths it must read/write (`.docs/spec/`, `.docs/backlog.md`, `.logs/`). Implement/update the sub agent to match this file, not the other way around.
- `system-requirements-specification.md` — the baseline SRS derived from the original prompt: objectives, stakeholders, functional requirements (FR-01…FR-09, MoSCoW-prioritized), non-functional requirements, a high-level data model, key use cases, out-of-scope items, and open risks. This is the current source of truth for overall scope — align new per-topic documents with it rather than re-deriving requirements from scratch, and consider syncing new findings back into it.
- `spec/{YYYYMMDD}-{RUNNING_NO}-{SUMMARIZE_TOPIC}.md` — per-topic requirement documents, one per raw requirement the sub agent processes. Doesn't exist yet; created by the requirement-analysis sub agent per `sub-agents.md`.
- `backlog.md` — the **Product Backlog**. Doesn't exist yet. It must be updated (not just created once) every time a `.docs/spec/` document is added or changed, per `sub-agents.md`. Derive items from the SRS/spec documents' functional requirements (one or more user stories per FR, tagged with the FR-ID they trace back to) so requirements and backlog stay traceable to each other.

## Document Conventions

Every deliverable document (Requirement, SRS, Backlog, PDPA addendum, ...) should open with the same metadata header used in `system-requirements-specification.md`, so documents stay comparable and diffable over time:

| รายการ | รายละเอียด |
|---|---|
| ชื่อโครงการ | ... |
| เวอร์ชันเอกสาร | ... |
| วันที่จัดทำ | ... |
| แหล่งที่มาความต้องการ | ... |
| สถานะ | Draft / Review / Approved |

Beyond the header, follow the conventions already established in `system-requirements-specification.md`:
- **Requirement IDs**: `FR-<group>-<seq>` for functional requirements, grouped by feature area (table/QR, menu, ordering, payment, kitchen/KDS, notifications, promotions, reporting, user/roles).
- **Priority**: MoSCoW (`Must` / `Should` / `Could`) per requirement, expressed as a table column.
- **Use cases**: Actor / Precondition / Flow / Postcondition / Acceptance Criteria format.
- **Diagrams**: Mermaid flowcharts for process flows (see the ordering flow in the SRS) when a picture clarifies a flow better than prose.

## Product Backlog Item Format

When `.docs/backlog.md` is created (or added to), each item should carry:
- **Title** — short, action-oriented.
- **Story**: `As a <role>, I want <goal>, so that <benefit>.`
- **Acceptance Criteria**: bullet list, testable, mirroring the AC style used in the SRS use cases.
- **Source**: the FR-ID(s) it implements, e.g. `Source: FR-03.2` — every backlog item must trace back to a requirement; if it doesn't, either the item is out of scope or the SRS is missing that requirement and should be updated first.
- **Priority**: inherit the MoSCoW rating of its source FR (don't re-invent a separate priority scheme).
- **Estimate**: story points or T-shirt size, once the team doing the estimating is established.

## Sub-Agents & Agent Skills

`requirement.md`'s Need list called for building sub-agents/agent skills to help produce these documents. They now exist — use them instead of doing this work ad hoc in the main session:

1. **`requirement-analyst`** (`.claude/agents/requirement-analyst.md`) — sub agent implementing the full `.docs/sub-agents.md` contract: takes a raw requirement, decides whether it's a new `.docs/spec/{YYYYMMDD}-{RUNNING_NO}-{SUMMARIZE_TOPIC}.md` doc or an edit to an existing one, asks clarifying questions (always ≥3 options) when unsure, syncs `.docs/backlog.md` in the same pass, and appends a run summary to `.logs/{YYYYMMDD}-log.md`. This covers both requirement analysis and backlog generation — they're the same contract, not two separate agents.
2. **`requirement-to-backlog`** (`.claude/skills/requirement-to-backlog/SKILL.md`) — the Agent Skill entry point for the above; invoke it (or delegate directly to `requirement-analyst`) whenever the user hands over a new raw requirement.
3. **`pdpa-compliance-reviewer`** (`.claude/agents/pdpa-compliance-reviewer.md`) — sub agent that audits a requirement/backlog document for PDPA / data-handling touchpoints not yet covered by the existing PDPA addendum, and proposes additions (always confirming legally-risky decisions with the user first, ≥3 options).

Before adding a new agent/skill, check these three for overlap first — extend them rather than creating a parallel one that drifts out of sync.

## PDPA / Legal Compliance

PDPA / personal-data-protection compliance is an explicit, still-open requirement (`.docs/requirement.md` Need #4). Any requirement or backlog item touching customer data (orders, payment, contact info) should call out where PDPA applies rather than skipping it. This should land as its own reviewed addition to both the Requirement doc and the Backlog — via the compliance agent/skill above — not folded in silently.

## Definition of Done for the Documentation Phase

This phase is done when:
1. The Requirement/SRS document has been reviewed (status `Approved`, not `Draft`).
2. A Product Backlog exists covering every `Must` (and ideally `Should`) FR from the SRS, each item traceable to its FR-ID.
3. A PDPA/compliance addendum exists and its relevant points are reflected in both the Requirement doc and the Backlog.
4. The sub-agents/skills used to produce the above are committed under `.claude/agents/` / `.claude/skills/`, not just used ad hoc.

## Working in this Repo

- All requirement and backlog documents belong under `.docs/` (`.docs/spec/` for per-topic requirement docs, `.docs/backlog.md` for the backlog), consistent with the existing structure. Don't create new top-level doc folders without checking with the user first.
- Any sub-agent/skill run that creates or edits a requirement/backlog document should log a summary to `.logs/{YYYYMMDD}-log.md`, per `.docs/sub-agents.md`.
- If and when actual application code is started in this repo, update this file with the real stack and the actual build/lint/test commands — do not leave stale or invented commands here.
