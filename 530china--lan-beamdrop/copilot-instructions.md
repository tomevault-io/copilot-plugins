# LAN BeamDrop Agent Instructions

本文件适用于整个仓库。开始工作前先阅读 [README.md](README.md) 和 [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md)；`docs/superpowers/` 下标记为历史设计或历史计划的文档只用于复盘，不代表当前待办。

## 项目定位

LAN BeamDrop 是一个单文件主机服务端与浏览器客户端组成的局域网文件、图片和共享文本工具。产品原则是“一端部署，多端使用”：只在一台主机运行服务，其他设备无需分别安装应用。核心约束是免安装、轻量、局域网直连和跨平台兼容。

- 不把网页共享文本描述为系统剪贴板自动同步；项目不静默监听操作系统剪贴板。
- 多端群聊式时间线是核心交互形态；文本、图片和文件应继续共用统一投递入口与消息流，并保持当前设备在右、其他设备在左的来源区分。
- 不承诺固定传输速度、移动端后台上传或页面刷新后的断点续传。
- 未经明确讨论和批准，不引入数据库、云端文件中转、P2P、原生客户端、重型前端框架或新的生产依赖。

## 工作流程

1. 先理解需求并阅读相关代码、测试和日志，不能根据猜测直接修改。
2. 涉及代码或行为变更时，先说明根因、方案、性能与兼容性影响以及测试计划，得到明确同意后再编辑。
3. 修复必须面向根因和正确状态模型，不能用吞错、延时、重复请求或 UI 遮掩等方式制造临时补丁。
4. 用户可见状态以服务端确认的事实为准。处理前后端不一致时，先通过响应、日志或浏览器现场确认问题位于服务端、传输层还是渲染层。
5. 保持改动范围克制，沿用现有模块和实现方式；不得顺手重构无关代码。
6. 工作区可能包含用户改动。不得覆盖、回退或提交与当前任务无关的文件。

## 方案开发前决策门槛

任何新功能、技术选型、架构演进、打包方式或平台能力变更，在开发前必须完成以下决策门槛。不能把用户不知道的技术影响留到实现或打包完成后才暴露。

1. **先评估必要性**：说明真实用户痛点、现有方案为什么不够、预期减少的步骤或风险，以及不开发是否仍可接受。没有明确收益的新功能默认不进入开发。
2. **对照产品原则**：明确方案是否影响“一端部署，多端使用”、免安装、单文件交付、局域网直连、群聊式时间线、轻量和跨平台兼容。任何一项发生变化都属于产品决策，不能当作技术细节默认接受。
3. **主动披露可预见影响**：至少逐项说明以下内容；不适用时也要明确写明不适用：
   - 用户最终拿到的是单文件、多个文件还是安装包，是否需要安装、管理员权限、开机启动、后台服务、系统托盘、运行时或其他前置环境。
   - 支持和不再支持的操作系统、CPU 架构、浏览器与最低版本，以及可能出现的兼容退化。
   - 可执行文件体积、启动速度、内存、CPU、磁盘、网络和电量影响。
   - 防火墙、证书、系统弹窗、权限申请、安全、隐私和敏感数据风险。
   - 配置、历史数据、共享目录、升级迁移、卸载残留和回滚方式。
   - 新依赖、构建发布、长期维护成本，以及仍然存在的限制。
4. **未知影响必须先查证**：优先查阅官方资料和现有代码；无法确定交付形态、兼容性或性能时，先提出最小验证原型并获得同意。原型必须优先验证最终安装步骤、产物数量、体积、启动和关键平台行为，不能先完成主体开发再验证用户是否接受。
5. **提前定义验收矩阵**：列出自动化测试、浏览器测试、打包验证和必须由用户在真实设备上确认的场景。手机锁屏、系统窗口置前、双显示器、权限弹窗和打包 EXE 等自动化无法可靠覆盖的场景，必须在提交前明确安排。
6. **明确列出确认项**：每次方案讨论结束时，必须单独给出“需要用户确认”清单；如果没有确认项，也必须明确说明“本方案无额外确认项”。用户主动询问“有什么需要确认”时，必须按上述影响清单逐项回答，不能用未经核对的笼统结论带过。用户的方向认可不自动等于接受未披露的安装、兼容性或交付变化。
7. **确认后才能开发**：只有方案影响、验收方式和确认项得到明确答复后才能开始实现。开发中出现新的影响、约束变化或范围扩张时，立即暂停并重新确认。

## 项目结构

- `server.js`：Express 服务入口、启动流程和 API 挂载。
- `config.js`：默认端口、共享目录、容量和历史记录等配置。
- `routes/`：文件、共享文本、设置、资源管理器、测速、诊断和鉴权路由。
- `utils/`：应用数据、日志、网络、二维码、mDNS、WebSocket、上传任务和平台能力。
- `middleware/`：访问控制等 Express 中间件。
- `public/index.html`：主页面结构。
- `public/js/main.js`：前端主流程；其他 `public/js/` 模块负责 API、队列、上传状态和生命周期等独立逻辑。
- `public/style.css`：主页面样式。
- `tests/`：Jest、Supertest 单元与行为集成测试。
- `scripts/build.js`：esbuild 与 pkg 单文件构建流程。

## 工程约束

- 路径使用 `path.join()`、`os.homedir()` 和项目现有 `utils/appdata.js`，不得硬编码本机绝对路径。
- 外部文件名必须防目录穿越，并兼容 Windows 非法字符。
- 大文件必须保持分片落盘和流式合并，不能把完整文件读入内存。
- 文件完整落盘前使用 `.uploading` 或 `.chunks` 隔离，不能提前发布半成品。
- 清理、日志和诊断属于 best-effort 辅助能力，不能推翻已经成功完成的主链路结果。
- 新日志写入结构化文件日志；控制台只保留启动信息、关键事件和异常，禁止恢复高频请求刷屏。
- 修改架构、配置默认值、API、数据生命周期或用户可见行为时，同步更新 README 或架构文档。

## 验证要求

- 修改 JavaScript 后至少运行 `node --check` 检查相关文件，并运行对应的 Jest 测试。
- 影响共享模块、上传主链路、设置、日志或跨平台行为时，提交前运行完整 `npm test`。
- 行为配置必须有行为级测试，不能只断言 JSON 被写入。例如容量限制需要真实请求验证 `413`。
- 修改前端 UI、状态、交互、响应式布局、弹窗或层级后，必须自行使用浏览器完成桌面和移动端验证；覆盖正常路径和相关错误路径，不把可自动完成的验证转交给用户。
- 修改打包、启动或平台能力后运行 `npm run build`，并按受影响平台做可执行文件冒烟或实际操作验证。
- 仅文档或元数据变更至少运行 `git diff --check`，检查本地链接、JSON 解析和描述与实现一致性。
- 测试结束后检查并删除临时脚本、日志、截图、构建中间文件和调试输出。
- 请求提交前必须进行一次覆盖式最终审阅，统一检查完整差异、未跟踪文件、用户可见文案、状态语义、性能、兼容性、安全、数据完整性、测试覆盖、文档同步和临时产物。发现一类问题时应全局搜索同类问题并完成修正，再重新执行完整审阅，不能依赖用户逐轮指出遗漏。

## Git 纪律

- 禁止直接向 `origin/main` 推送；开发和修复在功能分支完成，由仓库维护者通过 Pull Request 合入。
- 暂存或提交前必须检查 `git status`、完整 `git diff` 和 `git diff --cached`，只包含当前任务文件。
- 未经用户明确许可，不执行 `git commit` 或 `git push`。
- 提交类型从 `NEW`、`ENH`、`FIX` 中选择，不使用方括号，格式如下：

```text
TYPE: 精简标题

WHY:  修改原因

WHAT: as follows

- 具体改动

TEST:

验证结果
```

- 提交后核对提交正文编码、工作区状态和远端跟踪状态。
