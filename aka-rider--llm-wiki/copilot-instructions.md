# LLM Wiki — `/wiki-index` + `/wiki-lint`

A compounding, LLM-maintained knowledge base in plain Markdown, following
[Karpathy's LLM-wiki pattern](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f):
you curate sources and ask questions; the model does all the summarizing,
cross-referencing, filing, and bookkeeping. Two Claude Code commands do the work.

Karpathy's original concept has two major flaws: it doesn't work autonomously,
and it needs an Opus+-class model driving it. This wiki solves both. It is
**100% autonomous, dump-and-forget** — drop sources in `_inbox/` and they will
be taken care of — and it is built to run well on **Sonnet-4.6/Opus-4.5-class
models**, not just the frontier tier. What makes both possible is the split
below: deterministic code carries the correctness burden, so the driving model
never has to.

The whole ontology is **PAGE and LINK, nothing else** — no tag/author/broader
frontmatter, no controlled vocabulary file, no hub taxonomy. A tag is a linked
sentence; an author is a linked sentence; a hub is simply a page with enough
inbound links, materialized by code, never pre-declared. **The user provides
content; the LLM only categorizes, places, links, and deduplicates; Python does
everything mechanical.**

**The 80/20 rule of this design: ~80% of the system is discrete, old-school,
predictable if-else code; ~20% is left to the probabilistic LLM.** The LLM is
exceptionally good at summarizing text and rule-based pattern matching — let it
shine there, and let the boring deterministic code do the heavy lifting of
keeping everything consistent (frontmatter, dates, provenance chains, the
index, dedup, link reciprocity). When extending the system, push work toward
the deterministic side: stricter validation and self-correcting tool echoes,
not more LLM judgment.

These are implemented as **slash commands** (not skills) on purpose: you invoke
them deliberately (`/wiki-index <file>`, `/wiki-lint`), one takes an argument, and
`/wiki-lint` is an explicit, sometimes-destructive orchestration you want to
trigger — not something that should auto-fire from a description match. The shared
rules and the scanner live in `.claude/lib/` so both commands stay consistent.

## Layout

```
_inbox/      unprocessed raw drops, and nothing else — kept small
_inbox.fail/ sources whose batch-ingest worker failed — check .logs/<name>.log,
               fix the cause, move the file back to _inbox/ and re-run
.logs/       full stdout+stderr of each batch-ingest worker, one file per source
archive/     immutable originals — moved here on ingest, never edited again
               .sha256/<hash>       code-managed dedup registry (symlink)
               .extracted/<file>.md code-managed extraction/grounding baseline
wiki/<slug>.md  every page — root (archive-backed) and derived — directly in
               wiki/, flat files, no subdirectories, no folder-index
.wiki/       the semantic index's sidecar state (once M2–M4 land): wiki.db
               (embeddings, LLM verdicts, dedup registry, extraction baselines,
               ingest log — portable, git-tracked), cache.db (stat validators,
               FTS5 index — machine-local, gitignored, rebuildable in ~1s),
               models/ (pinned embedding model, ~300MB, gitignored — fetched
               once via `./uv run --project .claude/lib/wiki_mcp
               wiki-model-fetch`)
index.md     vault root, DERIVED — regenerated by housekeep(); outside wiki/ so
               the "index" slug stays free for a real concept page
log.md       vault root, append-only operation log
reports/     lint output — outside the knowledge graph
_user/       user's personal writing drafts — separate from the wiki knowledge graph;
             DO NOT TOUCH files in `_user/` unless explicitly asked to proofread, edit, translate, or similar assistance
_templates/  Obsidian note templates (native and Templater plugin) — do NOT
               read, edit, or generate files here unless explicitly asked to
uv                bootstrap wrapper — installs `uv` into a local venv when the
                     system doesn't have it; use `./uv` instead of `uv` everywhere
wiki-ingest-all.sh  batch ingester — one headless /wiki-index worker per source file
.mcp.json    project-scoped MCP config — defines the `wiki` and `markdownify` servers (committed)
.claude/
  commands/wiki-index.md   /wiki-index
  commands/wiki-lint.md     /wiki-lint
  lib/CONVENTIONS.md        shared rules (page format, provenance, quote-pinning, sizing)
  lib/wiki_graph.py         deterministic read-only health scanner (housekeep's "eyes")
  lib/wiki_mcp/             the `wiki` MCP server — 6 tools: ingest/find/mint/write/
                            merge/housekeep; tests/ holds its pytest suite
  lib/markdownify_mcp/      runs the `markdownify` MCP server (upstream `markitdown-mcp`
                            package, local venv, no Docker) — its own `pyproject.toml`,
                            no first-party code
  settings.json             enables the `wiki` + `markdownify` servers, pre-approves their tools
```

The vault's actual content is git-tracked: `wiki/*.md` and `archive/*` (text merges
cleanly; archive binaries may move to git-LFS if `du -sh archive/` warrants it) and,
once M2–M4 land, `.wiki/wiki.db` (binary, single-writer for now — doesn't merge, but a
fresh clone gets embeddings and judgments for free). `index.md`, `log.md`,
`.wiki/cache.db`, and `.wiki/models/` are derived/machine-local and gitignored — safe
to delete, rebuilt on the next `housekeep()`/tool call.

## `/wiki-index [file]`

Faithful **extractive** ingest of one source (or every file in `_inbox/`):

- `ingest()` archives the raw file (byte-for-byte, SHA-256 deduped), mints its
  bare root page (a thin bibliographic record — content claims live on the
  concept pages), and echoes `mentioned_pages` — existing pages the source's own
  text names, the ingest's link targets — plus `related_pages` (semantic
  cross-corpus weave candidates, when the semantic index is live). A
  deterministic substance gate runs first: incompressible/repetitive effective
  text (zlib-ratio classifier, calibrated on this corpus) is hard-rejected as
  `degenerate_source`; content under the 120-byte measurement floor is rejected
  as `thin_source` unless the caller READS it and re-calls with
  `accept_thin=true` (a bare-URL bookmark is legitimate; a garbage stub is not —
  under the floor only a look can tell). Archived originals are then sealed
  read-only (0444) — `archive/` immutability is filesystem-enforced, not
  doctrine. The root page's source-FORM classification (video/book/image/
  webpage/pdf/…) is **deterministic code, never the LLM's call** — a mechanical
  "Captured as a [[<form>-source]] source." sentence `ingest()`/`write()`/
  `housekeep()` inject and re-inject, never the driver's to write or edit;
- names the **1–4 concepts the source is fundamentally about** (the language/
  product/person/theory — versions and features are *claims filed under* them,
  not their own pages) and `mint`/`write`s a page per concept, every claim
  pinned to a verbatim `> "quote"` that lives on exactly one page per ingest;
- states each concept's category as a linked sentence ("DuckDB is an
  [[analytical-database]]") — **file under existing, coin last, link at first
  use**: lexical AND semantic near-synonym candidates are exhausted before
  coining — an existing near-synonym ALWAYS wins; only then is the category
  minted with `source=<the concept page>` (a coined label, so `mint`
  soft-flags an ungrounded category title instead of rejecting it, and echoes
  near-synonym candidates to merge into);
- links inline in prose freely — an unresolved prose link is downgraded to plain
  text and echoed for repair (only a quote-pin's `([[source]])` attribution still
  hard-rejects), and `unlinked_mentions` echoes name the pages the prose forgot
  to link; a dedicated Phase 4 weaving pass then cross-links root, siblings,
  categories, and — per `related_pages` candidates, when the semantic index is
  live — genuinely related pages elsewhere in the corpus, each judged
  same-concept (merge) / related (one linked sentence, written only on this
  ingest's own page) / spurious (skip) before anything is written;
- flags contradictions; closes out with a scoped `housekeep(scope=<root>)` gate
  that also fails on linkless pages (conceptual links only — provenance no
  longer counts), duplicated quotes, and unacknowledged near-dupes, but never
  on an unjudged weave candidate (that's a report line, not a gate failure).

It seeds **no** hubs — those still emerge later, mechanically, when enough pages
link to one (`/wiki-lint`'s `housekeep()` materializes the listing) — but it DOES
weave: each ingest's own `related_pages` candidates get judged and, where
genuinely related, linked from this ingest's own pages into the existing corpus.
`/wiki-lint` repeats the same judgment at whole-graph scale for what one ingest's
blind spot missed (same-batch parallel mints, later drift).

**Write only what the source says** — hedge uncertainty instead of filling gaps
(e.g. "the talk claims X" when the speaker asserts X without evidence). **Images and
PDFs are read with BOTH Claude's native vision AND `markdownify`
(`mcp__markdownify__convert_to_markdown`, the upstream `markitdown-mcp` package run
locally via `uv` — a plain process with real filesystem access, not the old
Docker-gateway `markdownify` that silently produced nothing usable against local
paths and was the source of ~40 fabricated image pages) — the two are synthesized,
never one used as a blind fallback for the other.** Where they agree that's strong
grounding; markdownify output that's empty/implausible is discarded in favor of what
was directly observed; a conflict is resolved in favor of direct observation, noted.
YouTube URLs also go through `markdownify`, but its transcript output must pass its
own plausibility check first (see Prerequisites) since it can silently return the
generic page shell instead of a transcript. Audio has no extraction path yet — such
sources are parked, never fabricated, until it's verified end-to-end. The
extracted text becomes `ingest()`'s `extracted_text=`, required for any non-text
file (no extraction, no archive move, no page).

## `/wiki-lint [--plan] [--no-subagents] [--batch N] [--weave-cap N]`

The bookkeeping orchestrator — where a pile of linked pages becomes a second brain.
`housekeep()` alone re-derives `index.md`, refreshes `## See also` reciprocity, and
**materializes** a `## Referenced by` listing on any page with enough inbound links
(a hub is just a dense node — never a seeded taxonomy) — all of it now measured on
the **conceptual** subgraph: a `sources:` chain, a quote-pin `([[…]])` attribution,
and a self-link no longer count toward orphan/linkless/dense-node status. Lint then
works `housekeep()`'s returned `judgment_queue` — the LLM-judgment items: near-dupes
(`merge`?), orphans (now rescued via a neighbor's semantic candidates, never the
orphan's own page), abandoned ingests, unverifiable/mismatched quotes, ungrounded
titles, dead links, and — when the semantic index is live — `unlinked_neighbors`
(candidate cross-corpus links: link/merge/unrelated), `uncategorized_category`
(dense-but-unfiled category pages), and `rewritten_page` (a changed page's outbound
links re-verified against its current text). `--weave-cap` (default 150) bounds how
much of the weave backlog one run considers; `0` runs hygiene-only.

Its defining constraint is *not burning its own context window*: a Python scanner
computes all graph facts in one cheap call (so the orchestrator never reads page
bodies up front), and the heavy per-page work (near-dupe judgment, contradiction
sweeps) is delegated to **parallel `Task` subagents** that return terse summaries
only. Subagents get **disjoint file partitions** to avoid concurrent-write
corruption. Nothing is ever deleted — `merge` preserves content behind a redirect
page, and deletion candidates are only *recommended* in the dated report under
`reports/`. Run `--plan` first for a dry run.

```bash
./uv run --project .claude/lib/wiki_mcp python3 .claude/lib/wiki_graph.py --format text   # see what lint sees, anytime (runs under the writer's PyYAML)
```

## Batch ingest

Run `./wiki-ingest-all.sh <source-dir>` to ingest every file in a directory (default
`_inbox/`): one fresh headless worker per file (`claude -p "/wiki-index @<file>"`),
full output logged to `.logs/<name>.log`. Successes are archived by `ingest()` itself;
failed sources are parked in `_inbox.fail/` (skipped for in-place `archive/`-directory
runs, since there's nowhere to park a failure that's already archived). Override
permissions with `PERMS="--permission-mode acceptEdits"` (the default).

## Prerequisites

- **Claude Code** (commands live in `.claude/commands/`; `/wiki-lint` uses subagents).
- **`markdownify` MCP server** — defined in `.mcp.json`, runs the upstream
  `markitdown-mcp` package (MIT, PyPI) locally via `./uv run --project
  .claude/lib/markdownify_mcp markitdown-mcp` — a plain local process, no Docker, so
  it has ordinary filesystem access. One tool, `mcp__markdownify__convert_to_markdown
  (uri)`, handling `file:`/`http:`/`https:`/`data:` URIs — used for images, PDFs, and
  YouTube URLs. An earlier version of this server ran inside a Docker MCP gateway
  with no mount onto this vault's local files, so its image/PDF conversion silently
  produced nothing usable — the root cause of ~40 fabricated image pages found in an
  earlier audit; running it as a local process instead removes that failure mode, but
  `/wiki-index` never trusts a markdownify conversion on its own for images/PDFs — it
  reads the file with native vision too and synthesizes the two, discarding
  markdownify's side wherever it's empty or disagrees with what was directly observed
  (see the `/wiki-index` section above). **YouTube conversion has its own verified
  failure mode**: the
  transcript API it depends on is throttled/blocked by YouTube often enough to hit
  in practice, and on failure it silently returns the generic page shell instead of
  erroring — `/wiki-index` requires a plausibility check on the output before
  trusting it, not just an empty-string check. Audio has no extraction path yet —
  not verified end-to-end, so it stays parked rather than assumed to work. If your
  server exposes different tool names, update the `allowed-tools` line and Phase 1
  in `.claude/commands/wiki-index.md` accordingly.
- **`wiki` MCP server** — defined in `.mcp.json` and enabled via
  `enabledMcpjsonServers` (see `.claude/settings.json`). Six tools:
  `mcp__wiki__ingest` (archive + SHA dedup + root page), `mcp__wiki__find` (the ONE
  identity resolver — exact / redirect / normalized-equivalence), `mcp__wiki__mint`
  (create, with hard L1/L2 title gates), `mcp__wiki__write` (rewrite an existing
  page wholesale), `mcp__wiki__merge` (fold a duplicate into its survivor, never
  deleting), `mcp__wiki__housekeep` (index/reciprocity/dense-node/log/scan) — so
  pages, frontmatter, dates, provenance and the index/log are all written by
  deterministic code, never hand-derived. Runs locally with `./uv run --project
  .claude/lib/wiki_mcp wiki-mcp` — needs [`uv`](https://docs.astral.sh/uv/) and
  Python 3 (deps incl. `pyyaml`, managed by uv). Confirm it is connected with `/mcp`.
- **Semantic index sidecar** (once M2–M4 land) — the `wiki` MCP server also
  maintains a code-managed retrieval index behind `.wiki/`: `wiki.db` (portable,
  git-tracked — embeddings, LLM verdicts, dedup registry, extraction baselines,
  ingest log) and `cache.db` (machine-local, gitignored — stat validators, FTS5
  index). The embedding model itself lives in `.wiki/models/` (gitignored,
  ~300MB, pinned repo+revision) and is fetched exactly once via `./uv run
  --project .claude/lib/wiki_mcp wiki-model-fetch` — never downloaded implicitly
  inside a tool call. **No new driver-facing tools**: this is surfaced only as
  richer echoes on the existing six (`related_pages` on ingest/mint/write,
  semantic `candidates` on find/mint, new `housekeep()` judgment-queue kinds) —
  see `.claude/lib/CONVENTIONS.md`. Absent model → `ingest()` hard-fails with a
  remedy naming `wiki-model-fetch`; `find`/`mint`/`write`/`merge`/`housekeep`
  degrade gracefully (the semantic echoes are simply omitted, with a notice) —
  every prompt instruction that reads one of these echoes carries the same
  degradation clause: absent field, skip the step, never infer a candidate.
- **Python 3** for the scanner — **PyYAML is a hard dependency** (`wiki_graph.py`
  hard-imports `yaml`; there is no lenient fallback parser, deliberately, so the
  scanner and the MCP writer never disagree on what "valid frontmatter" means).
  Run it under the writer's env: `./uv run --project .claude/lib/wiki_mcp python3
  .claude/lib/wiki_graph.py`.
- **No pre-/post-install scripts, mechanically enforced.** Every `pyproject.toml` in
  this repo sets `[tool.uv]` `no-build`/`no-build-package` so uv can only install
  prebuilt wheels for third-party dependencies — never build one from an sdist,
  which is the mechanism that lets a package's build backend run arbitrary code at
  install time. (This repo has no `package.json`, so npm's `ignore-scripts` doesn't
  apply here; `no-build` is the uv/Python equivalent.) Keep this set whenever a
  `pyproject.toml` is added or edited.

## Development & testing

All engine code lives in two files: the MCP server
(`.claude/lib/wiki_mcp/wiki_mcp/server.py` — FastMCP, all 6 `mcp__wiki__*` tools
in one module) and the scanner (`.claude/lib/wiki_graph.py`, which the server
imports). Python ≥3.10; deps (`mcp`, `pyyaml`, dev `pytest`) are managed by uv.

Run tests through uv so imports and PyYAML resolve:

```bash
./uv run --project .claude/lib/wiki_mcp pytest .claude/lib/wiki_mcp/tests      # full suite
./uv run --project .claude/lib/wiki_mcp pytest \
  ".claude/lib/wiki_mcp/tests/test_mint.py::test_mint_rejects_l1_fold_collision"  # one test
```

Tests run against an isolated tmp vault (`conftest.py` sets `WIKI_ROOT`), so they
never touch this wiki. After editing `server.py`, restart Claude Code to reload
the `wiki` server, then confirm with `/mcp`.

Scanner CLI: `--format {json,text}`, `--root <dir>`, and the per-ingest scope:

```bash
./uv run --project .claude/lib/wiki_mcp python3 .claude/lib/wiki_graph.py --scope duckdb-paper
```

`--scope <root-slug>` restricts the report to that root's subgraph and adds a
`scope.clean: true|false` gate (the same one `mcp__wiki__housekeep(scope=...)`
returns). Loop — fix what it lists, rescan — until `clean: true`.

## Design notes

Distilled from ~13 community implementations of the pattern, then rebuilt around a
single mechanism: the terminal state is cross-linked pages, so the only entities
are PAGE and LINK. Three decisions to preserve when extending: a hub is **never
seeded** — it emerges when enough real links point at one page, and code notices;
**provenance is structural, not a convention** — every page's `sources:` chain
must terminate in an `archive/` file, checked mechanically by the scanner on every
`housekeep()` run — during lint, gaps are only flagged, filling them from the web
would break provenance; and **relatedness is only ever a proposal** — the semantic
index surfaces candidates as echoes and judgment-queue items, never as a link. A
link exists only once an LLM judged the pair and wrote a real sentence; a rejected
pair is acknowledged durably (`ack_unrelated`/`ack_unfiled`) so the same judgment is
never spent twice. The same carve-out applies to categories as to hubs:
code-owned mechanical categories (the FORM sentence — "Captured as a
[[video-source]] source.") are minted at first use by `ingest()` itself, not by
LLM judgment; hub listings still emerge only from inbound density, never from a
declared taxonomy.
