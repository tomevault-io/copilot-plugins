# AGENTS.md

本文件只保存 ATT 长期有效的产品方向、架构判断方法，以及知识归属和同步要求。当前命令、
参数、模块名、数据字段、第三方库、完成状态和具体工作流由现行规格、代码、测试或指南负责。

> 总纲：从真实用户结果反推纵向切片，从当前职责推导直接依赖；物理层级不决定依赖，
> 但任何调用都必须经过负责相应规则、状态和不变量的语义所有者；只设计当前目标及其
> 直接依赖，并根据真实调用方的相同语义复用能力和演进数据模型。

## 1. 知识职责与唯一权威

每项知识事实只有一个权威来源，其他材料通过链接或明确引用使用它：

- 本文件保存长期产品方向、架构判断方法、项目边界和知识同步规则；
- 现行规格保存已经确认的产品行为与外部接口契约；
- 指南说明如何调查事实、选择方法和组织验证，不重新定义规格；
- 代码和测试保存已经实现的行为与验证证据，不能反向覆盖现行规格；
- 代表性真实材料、权威说明、实际读写关系和验证记录证明领域事实是否成立；
- Skill 从使用者和执行者视角组织现行能力，负责触发、读取顺序、状态选择、行动、验收
  和恢复；除触发与导航所需的最短稳定摘要外，不复制产品契约和实现细节。

文档必须能够独立阅读和审查，不依赖某个 Skill 才能成立。发现知识缺口时，先由相应
责任方补充并验证事实，再让其他入口引用；缺失的契约不能藏在编排代码或 Skill 中。

只有长期方向、判断方法、项目边界或知识分工发生变化时才更新本文件。当前参数、临时
命名、候选设计、实现进度和详细流程进入各自的现行规格、指南或代码文档。

ATT 只保留当前系统版本。旧实现、旧协议、旧格式、旧配置、旧测试、旧 Skill 和旧工作流
只存在于版本控制历史中，不在当前工作树内另建兼容或历史权威来源。archive/ 只保存与
当前系统版本无关、用于验证领域事实和失败模式的原始材料。

## 2. 产品形态：统一入口，独立纵向切片

ATT 用一个 CLI 聚合多个游戏引擎的翻译能力。统一入口只承担真正跨引擎一致的进程级
职责和路由；每个引擎完整拥有自己的命令域、外部契约、编排、状态、错误语义和演进节奏。
表面相同的命令或流程仍是独立契约，各引擎先准确表达自己的用户意图，再在契约之下复用
语义一致的能力。

一个纵向切片从用户入口延伸到用户能够观察的结果，包含产生该结果所需的业务判断、
状态交接和副作用。项目进度以真实结果衡量；目录、模块、crate 或底层组件的数量不代表
进度。共享能力组成按需连接的网络，服务各纵向切片，不统一控制所有业务流程。

面向用户的入口只表达本次操作意图和确实需要当场选择的事项。已经由项目状态或执行配置
确定的事实直接复用。统一配置只收纳部署环境、外部服务或操作者能够长期选择的策略；
固定产品语义、内部资源参数、调度细节和运行时数据由负责执行它们的模块决定。

## 3. 从结果确定目标与契约

每项任务先明确结果，再决定结构。开始实现前至少回答：

1. 谁在什么场景下需要这个结果；
2. 成功、失败和必须保持的行为是什么；
3. 哪个当前目标对结果负最终责任；
4. 当前目标真正需要哪些直接能力；
5. 本次任务在哪里停止，什么证据能够证明完成。

内部模块任务以上游已经确认的契约和模块自身应交付的行为为起点；技术组件本身不是目标。
当前任务只展开目标及其全部直接依赖，到达直接依赖的公开契约就停止。某个依赖进入后续
实现范围时，再把它作为当前目标重新推导；不一次性设计整棵依赖树。

契约从调用方视角说明意图、结果、成功与失败、提供方承担的复杂性，以及调用方能够长期
依赖的行为。函数、领域类型、模块公开接口或 trait 都可以表达契约，采用满足当前调用关系
的最简单形式；只有存在真实的替换、隔离、独立测试或多实现需要时才引入相应抽象。

接口使用职责语言表达高级意图，算法、存储、第三方类型、资源限制和调度细节留在实现
内部。跨进程、外部服务和扩展协议只提供对方完成当前任务所需的有效事实，不泄露内部
表结构、持久化身份、调度状态或恢复映射。

## 4. 依赖、模块边界与复用

项目依赖是能力网络，不是必须逐层经过的阶梯。判断直接依赖是否成立时确认：

1. 当前模块对该能力是否存在独立需要；
2. 调用是否只依赖对方职责级的稳定契约；
3. 是否绕过其他模块拥有的规则、状态或不变量；
4. 候选中间层是否增加语义转换、策略、保护或生命周期责任；
5. 依赖是否保持单向且不形成循环。

中间层只改名或转发调用时，直接依赖更准确；中间层拥有不可替代的业务含义时，通过它
协作。外部入口和呈现层把业务执行交给责任模块，依赖方向不反转。Composition Root 可以
直接使用具体实现完成构造、配置和生命周期管理，业务执行仍通过相应契约完成。

模块围绕单一、可命名的职责形成，把内部状态、算法、第三方细节和复杂流程留在边界内。
编写具体实现前检查现有完整能力和局部职责，并按语义作出唯一判断：

- 语义、规则、不变量、错误语义和生命周期一致时，直接复用同一实现；
- 只有部分职责一致时，提炼最小、可命名且能够独立验证的公共能力，并迁移现有调用方；
- 只有代码形状或步骤相似时，保持独立并明确真实语义差异。

共享接口只随当前调用方或已经确认的后续调用方的明确需要扩大，不必等待第二份重复代码，
也不根据猜测中的未来场景增加字段、状态或抽象。

新增引擎时，重新检查新切片所需职责对应的现有能力及其当前调用方。相同语义在同一次
改动中提炼成唯一共享实现，并同步迁移所有受影响的当前调用方、配置、测试、规格和依赖图；
引擎特有规则留在各自切片。复制既有切片、在共享模块累积引擎判断分支、保留平行实现或
增加纯转发层，都不能作为完成状态。

拆分只有在以下情况下成立：

- 单元具有独立职责、不变量或变化原因，当前确有调用方需要，并减少调用方必须理解的内容；
- 单元形成必要的依赖、编译、发布或所有权隔离。

文件较长、目录整齐、层级对称、形式上能够拆开或猜测将来复用，都不是拆分理由。共同维护
同一不变量、总是一起变化或离开彼此无法独立理解的代码保留在同一模块。围绕同一职责且
适合共同编译发布的 mod 留在同一 crate；只有隔离边界确实独立时才建立新 crate。

## 5. 数据、格式、版本与配置

代码和数据用尽可能少的概念完整表达当前真实语义。每个类型、字段、状态、接口和中间层
都必须能够说明由谁负责、哪些当前调用方使用，以及它消除了什么复杂性；不为未来需求
预留概念。

进程内部优先使用所有权明确、能够保证不变量的领域类型。互斥模式用枚举表达；组合事实
用字段私有的值类型和构造函数建立不变量。文本树、字符串标签和松散键值只停留在解析、
序列化或持久化边界，进入内部前转换成已经校验的类型。展示文本不充当权威标识或解析协议。

面向人类或模型的外部格式也是产品接口，只保留当前意图需要的字段，并优先使用成熟、
易读且适合批量生成和审核的标准。LLM user message 只携带模型当前输出不可缺少、且尚未
由 system message 或已有上下文确定的事实；能够按顺序、分组或已校验状态稳定推导的内容
不重复编码。只有现有表达无法无歧义地承载嵌套或转义时才改用 JSON。外部不透明字段只有
在当前流程确实读取、写回或原样转发时才保留，并且不进入无需理解它们的业务模型。
任何新增模型内容都必须说明模型当前如何使用它，以及缺少它为什么会使本次任务无法正确
完成。

业务模型、输入输出协议、持久化格式和配置不建立业务版本概念。ATT 只实现现行规格；
确认版本切换后，在同一次改动中替换生产代码、测试、夹具、配置、文档、错误和诊断，并
删除兼容解析、旧字段别名、格式探测、迁移、双读双写、回退和旧版本专用提示。无效输入
只按现行契约处理，不识别或提示其历史身份。已有旧数据在当前实现之外替换、重建或清理；
工具链和构建版本不用于业务分流。

只有外部硬性限制、可复现故障或测量证据，才能支持并发上限、队列、超时、批量、重试、
等待窗口、容量拒绝或磁盘暂存。外部服务限制和操作者真实选择进入配置；固定领域语义由
代码契约规定；并行工作单元数量、窗口、批次、连接复用和缓存由执行代码根据基准和运行
数据决定。没有实际选项的模块不建立配置对象，缺少必填外部选择时明确失败。

ATT 不自行限制项目总量。文件、目录、Lua、SQLite 和 Claim、Unit、Group、Task 等业务
对象都不设置人为上限、拒绝分支或对应配置；活动窗口满时让后续工作等待。真实的文件系统、
操作系统、地址空间、内存、SQLite、外部协议或数据格式错误必须完整报告，不能用一个很大
的常量伪装成“无上限”。

命名优先表达职责和事实。注释解释业务含义、不变量、来源映射及代码本身看不出的取舍，
不复述表面动作；需要保留的原始事实使用原名，不用臆造名称覆盖。

## 6. 语义所有权、信任、错误与扩展

每项业务事实、规则和不变量都有唯一责任方。最了解外部输入的边界负责解析、校验并转换为
能够保证不变量的内部类型；转换成功后，内部模块直接信任该契约，同一事实不重复校验或
解释。会随时间变化的外部状态，由真正执行副作用的模块在操作前重新观测。输入错误、环境
失败和内部不变量破坏保持不同含义。

产生错误的责任边界仍然掌握类型、命令、阶段、路径、字段、实际值、期望值或上限、稳定
错误码和最终状态时，就构造已经按敏感信息规则处理的结构化诊断；只记录当时确实存在的
事实。CLI、日志和其他呈现只读取该记录，不向下
转换任意错误对象，也不解析 Display 文本猜测事实。主错误、相关错误和清理错误分别保留；
泛化错误类别只能补充，不能替代具体原因、状态是否改变、处理办法和恢复位置。

敏感信息清单、替换方式和内容边界只由
[Chat Completions 运行根规格](docs/runtime/chat-completions.md#6-敏感信息闭集唯一权威)
规定，其他代码和文档只引用它。隐藏清单中的值时，仍保留允许公开的阶段、路径、字段名、
状态码、实际值、事务和发布终态。

业务允许的未产出、Partial 和 Unavailable 是正常结果；只有模块无法继续履行契约或保持
状态一致时才返回错误。正常的不完整结果仍带有足够的结构化诊断。

日志、指标、追踪和任务记录默认只是业务行为的附属证据，不参与提交、恢复、重放或副作用
准入。只有现行契约明确要求“证据完整才允许操作或成功”，并说明读取者、权威性、持久化和
失败语义时，记录才成为业务状态。记录失败必须及时产生用户可见诊断，但不改写已经确定的
业务结果、项目状态或业务退出语义；警告或终态自身无法通过 stdout、stderr、worker 或
channel 呈现时，属于独立的进程呈现失败。任何用户可见诊断都不能被空错误分支或无诊断的
退化吞掉。具体行为由[项目日志规格](docs/runtime/project-log.md)负责。

事件名称、正文和字段必须只描述已经确认的事实。阶段完成后才能记录完成事件；统计事件
使用不表示提交或成功的中性含义；事务、发布、取消和结果未知只由相应终态表达，普通进度
或统计不得提前宣称成功。

扩展结果能够由现有核心契约完整表达时，扩展把私有表示转换成该契约接收的数据，并由
语义所有者统一验收、处理冲突和提交，不复制规则或绕过权威状态。现有契约无法表达真实
语义时，扩展可以使用低级能力或保留私有协议，但必须完整承担解析、校验、状态、一致性、
事务、恢复、幂等和往返验证责任；未经核心契约验收的结果不能宣称为核心受管状态。

## 7. 状态、持久化与工作单位

状态模型来自真实纵向行为之间的交接。只有后续行为确实需要跨时间、进程或阶段继续使用的
事实才进入持久化；能够从权威事实稳定推导的数据在使用时计算。

领域上下文范围、耗时工作分配单位、结果验收单位和持久化原子单位分别由各自不变量决定，
不要求相同。相关事实可以整体提供语境，能够独立确认的结果按最小有效单位验收；必须共同
保持一致的传播或状态关系在同一原子事务中提交。批量工作中每项有自己的成败，已确认且
一致的进展及时保存，未完成部分由后续运行根据权威状态重新推导。

批处理和流水线需要真实领域关系、外部协议容量、已经测量的固定成本或吞吐瓶颈作为证据。
必须完整处理的语义单元保持完整，相关语境不无故切碎，无关内容不为了装满批次而拼接。
项目总工作量与同时处理的工作量严格区分：窗口只限制正在读取、计算、等待提交或执行外部
请求的工作，窗口满时排队等待，不把合法总量变成容量错误。

内存可以用于索引、缓存、重排和保存已完成结果。磁盘暂存、逐项消息往返或整条路径串行化
只有在换页、内存耗尽或代表性负载问题得到证实时才引入。并发可以改变完成时间，不能改变
自然顺序、代表选择、分组结果、提交顺序、错误语义或持久化一致性。

每项持久化事实必须明确写入方、读取方、支持的可观察行为、权威位置，以及创建、更新和
失效时机。共享存储可以承载其他领域提供的事实，解释权仍属于原领域。持久化结构直接表达
真实资产、关系、读写和事务边界；只有出现真实的跨领域统一读写需要时才建立通用中间模型。

跨引擎规划的长期架构不变量是：Extract、共享 Planner 和引擎适配器各自承担规格规定的
语义责任；语义一致的 Planner 与模型协议使用唯一共享实现和共同契约测试。文本层次、装箱、
模型责任和临时 ID 的准确先后关系只由 TaskBlock 规划规格定义。

性能是工程完成条件。Rust、异步、线程或缓存只是手段；准确目标和不可放宽的行为由性能
工程要求负责，测量、比较和停止方法由性能验证指南负责。

发行物的精确内容、固定根目录、禁止项和完整验证要求只由发行物规格负责；资源同步脚本只
实现和检查该规格明确列出的资源映射。

公开 Release 只从远端 `main` 上已经存在且不可变的版本标签构建。格式、Clippy、测试、第三方许可
和完整发行检查在标签前完成；Release workflow 只校验标签与版本、构建静态二进制、同步发行
资源、使用最高级别 Deflate 打包并发布。不得上传本机 `dist/`。根许可证、Cargo SPDX、README、发行包与
GitHub 仓库元数据必须表达同一许可和产品范围；旧版本的标签与 Release 保留其当时许可，不追溯改写。

当前版本已经完成约定验证后，用户要求 push、发包或发布时，任务立即进入发行执行模式，
已经验证的提交和版本随即冻结。本地操作应在两分钟内完成，不计远端构建和网络等待；只允许
确认既定提交、版本和标签身份，提交或推送已经确认的改动，创建并推送既定标签，触发 Release
workflow，以及确认公开 Release 页面和固定附件真实存在。Release workflow 保留完成这些动作
所需的最少步骤，不得把上游已经完成的质量验收再次搬入发包过程。

发行执行模式下严禁调用子 agent、重新审查源码或规格、重跑格式、Clippy、测试、性能、许可或
完整发行检查，严禁增加防御性校验、修改业务代码或 workflow、扩大任务范围、擅自提升版本，
也严禁因发包期间新发现的问题自行派生下一个补丁版本。push、标签、workflow 或 Release 创建
失败时，只报告失败动作、具体事实和可重试位置；没有用户新的明确要求，不得自行转入修复、
重新设计发行流程、移动公开标签或改变版本。

## 9. 实现、验证与完成

当前版本的用户可观察契约、持久数据和现有外部调用方决定改动范围，旧版本不带来兼容
责任。既有结构无法表达当前语义、产生重复知识或持续阻碍实现时，进行范围明确的重构，
在同一次改动中更新全部当前调用方、测试、配置、规格和依赖图，并删除失效实现；不保留
转接层、新旧双模型或历史版本专用错误。

继续实现直接依赖时，除根接口外，包含领域判断、状态转换或编排规则的能力都应获得真实
实现。根接口只负责文件、计算、存储、网络、时间和运行时等环境机制；Composition Root
负责转换外部配置、创建具体实现并管理生命周期。

实现顺序与设计顺序一致：

1. 用高层行为固定当前目标的可观察结果和失败语义；
2. 按调用方需要定义直接依赖的最小契约；
3. 实现并验证当前目标，范围外依赖使用测试替身；
4. 依赖进入实现范围后，再以其上游契约为起点实现和验证；
5. 任务要求从入口到结果时，用最小真实样本通过生产入口执行完整路径；
6. 共享能力存在多个调用方时，验证各方依赖同一语义和同一实现。

契约完成、局部测试通过或底层组件就绪，都不能单独证明纵向切片完成。交付时分别说明
业务算法、根接口、真实根适配器和生产入口的完成程度；生产入口只连接已经真实实现并完成
相应验证的能力。

进程级主成功测试和端到端测试使用当前发行配置的正式默认行为；可选行为另设选择测试，
不能为了简化公共夹具而改变主路径的正式默认。

新增或修改配置时，同一次改动完成字段定义、解析、校验、实际应用和生产入口连接，并覆盖
省略后的正式默认、当前契约允许的显式选择和无效值；布尔值或开关才要求分别覆盖显式开启
与关闭。配置控制文件或日志产物时，端到端验证受影响产物的建立、数量、内容、RunId、
零工作量和关闭生命周期。

修改可观测性能力时，只对确认受影响的边界注入建立、序列化、队列、写入、flush、sync、
worker、channel、任务记录或 stdout/stderr 呈现失败。测试断言具体诊断、持久记录、状态影响
和退出码，不只断言没有 panic；必要事件恰好出现一次，统计与实际调用一致，失败路径不能
出现完成、提交或成功文案。重构进程测试时，原有的默认开启、失败可见性、取消和终态证据
必须迁移到新结构，不能随旧夹具或入口一起删除。

性能相关改动按第 8 节路由的现行规格和指南验证。无性能影响的文档改动不运行性能基准。

生产代码和测试套件不得读取、解析或断言 Skill、Markdown 文档、文档示例标记、目录导航、
行数、固定文字、链接或发行副本内容。文档与 Skill 通过审阅和发行资源同步维护；自动化测试
只验证产品可观察行为与数据契约。发现此类测试时直接删除，不用快照、字符串断言或另一种
测试夹具替代。需要评估 Skill 的执行引导时，在仓库外使用不带任务历史的文字场景，不把
评估脚本或夹具提交到项目。

任务完成意味着约定范围内的用户结果或上游承诺成立，失败语义明确，并完成与风险相称的
验证。完整纵向切片还要求生产入口可获得结果，必要状态正确交接，副作用、默认路径、取消
与资源边界得到验证。尚未实现、连接或验证的范围必须明确说明。

架构图、现行规格和测试只描述已经实现并验证的事实，候选设计明确标注为候选。源码、测试
与规格冲突时，先确认当前有效契约，再修正不符合契约的一方；规格不为迁就现有代码而改写。

开始实现前从预期外部结果搜索相关源码、测试、规格、指南、Skill 和发行物，只读取并纳入
确认受影响的内容。外部能力、流程、权限、副作用、环境、成功失败或恢复方式变化时，在
同一次改动中更新负责相应语义的规格、测试、指南、受影响的 Skill 和发行资源。执行者的
阅读、选择、授权、操作、验收或恢复方式没有变化时，不为制造文件差异而修改 Skill，但
交付时说明检查结论。

## 10. Skill、领域事实与同步

Skill 只组织执行。主入口根据当前事实决定下一步，按需读取直接引用；同一个判断只在最
需要的位置出现一次。只有内容具有独立职责并会在明确条件下单独读取时，才拆成引用文件或
模板。命令、参数、schema、字段矩阵、错误语义、完整协议和详细领域规则留在相应权威来源。

任务确实需要跨阶段继续、交接或检查执行质量时，Skill 可以要求维护简短任务清单。清单只
保存稳定宏观阶段和当前事实支持的工作，不提前列出尚未发生的具体任务，并明确唯一写入者、
创建时机、最小格式和更新规则。Skill 和知识入口不绑定具体模型产品或执行平台。

领域模型、自然顺序、关联范围和边界行为，必须由代表性真实材料、权威说明和实际读写关系
共同验证。示例与测试夹具只解释已经确认的事实；字段、关系和命名先来自真实材料，再进入
模型。需要定位、继承或写回的原始字段、精确来源和未经授权的原值必须能够追溯。

源码与测试、规格与指南、受影响的 Skill 和发行物共同描述一个当前版本，但不逐字复制同一
事实。任何位置仍描述旧行为、遗漏当前流程、存在冲突、失效链接或过期导航时，任务尚未完成。

## 11. 每次任务的方向检查

设计、实现和评审至少检查：

1. 当前工作服务什么用户结果或上游承诺，谁拥有其中的规则和不变量；
2. 直接依赖为什么必要，是否绕过语义所有者或保留了纯转发层；
3. 复用和拆分是否依据真实相同语义以及当前或已经确认的后续调用方，而不是代码形状或
   未经确认的未来设想；
4. 新增类型、字段、状态、配置、批处理或资源机制分别由什么真实读写关系、外部限制或
   测量证据证明，是否误设项目总量上限；
5. 外部事实是否只在责任边界校验一次，错误是否保留具体原因、稳定代码和最终状态，
   可观测性是否仍未参与未经契约授权的业务判断；
6. 是否已经读取第 8 节要求的当前规格，并确保受影响范围内没有旧版本实现、数据别名、
   测试和文档残留；
7. 涉及 Planner 时完整装箱是否先于模型责任，涉及性能时是否保持全部正确性并按规定取证；
8. 真实生产入口、正式默认、失败、取消、部分结果、生命周期和副作用是否得到相称验证；
9. 受影响范围内的源码、测试、规格、指南、Skill、导航和发行物是否描述同一个当前结果；
10. 现有证据是否足以证明纵向结果，而不只是局部代码能够运行。

这些问题无法回答时，先缩小目标和边界。任何技术选择都必须能够沿依赖关系追溯到真实需求。
