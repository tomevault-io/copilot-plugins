# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## プロジェクト概要

「どの通信でとどける？」— 通信方式の選択を体験する、科学館向けの教育用Webアプリ（詳細仕様は [Plan.md](Plan.md)）。

「AからBにCを送れ！」という通信ミッションが与えられ、NFC / Bluetooth / Wi-Fi / 5G・LTE / LoRa / 光ファイバー / Starlink / 衛星通信などの通信アイコンをドラッグ＆ドロップでスロットにセットし、適切な通信方式を選ぶ。正解・不正解の二値ではなく「◎○△」のような向き・不向きも表現する。

- 対象ユーザー: 小学校3年生程度（専門用語を避け、平易な言葉でフィードバックする）
- 実展示では手のひらサイズの通信オブジェを使う体験を想定し、Webアプリ版はそのプロトタイプ
- 教育目標: 通信ごとの得意・不得意、距離/情報量/電力/環境による向き不向き、「一番すごい通信」は存在せず目的に応じて選ぶことの理解

## コマンド

Vite + React + TypeScript構成（`npm install`後に利用可能）。

- `npm run dev` — 開発サーバー起動
- `npm run build` — 型チェック（`tsc -b`）＋本番ビルド（`dist/`に出力）
- `npm run lint` — oxlintによるlint
- `npm run preview` — ビルド済み`dist/`をローカルでプレビュー

テストランナーは未導入（Phase 6/7でPlaywrightによる実機・実ブラウザ確認を予定。Step.md参照）。

## ドキュメント構成（3点セット）

[science-app-framework.md](science-app-framework.md) は、この種のScienceMuseum系教育アプリをClaudeと開発する際の共通フレームワーク（他のアプリ開発でも使い回す一般化ドキュメント）。本プロジェクトもこれに従う。

- **CLAUDE.md**（本ファイル）— コンセプト・教育目標・設計方針など、開発中ほぼ変化しない指針
- **Step.md**（未作成・実装開始時に作成）— 実装ロードマップ。企画を「動くものが一つ増える」粒度のフェーズに分割しチェックボックスで進捗管理。各ステップ実装後に一言メモ（何を作ったか・何が分かったか）を追記
- **Findings.md**（未作成・実装開始時に作成）— 開発中に得た知見のログ（通信方式の技術的特性の検証結果など）。機能追加のたびに追記すべき発見がないか自発的に振り返る

## 設計方針

- **ブラウザのみで完結**（サーバーサイド処理なし、GitHub Pagesでホスト可能な静的サイト）
- **TypeScriptベース**
- **PC・タブレット、モバイル/タッチ操作**を前提にUI/パフォーマンスを設計（展示端末・来館者のスマホ想定）
- 通信アイコンは**ドラッグ＆ドロップ**で通信スロットにセットする操作
- **教育効果を最優先**。機能追加や技術的な凝り方より学習目標への貢献度で判断する
- **UIはできるだけシンプル**にし、不要な機能や華美な装飾は追加しない
- 難しい専門用語を避け、小学校3年生でも分かる言葉で結果・理由を伝える（例:「遠すぎてとどかない！」「電池を使いすぎる！」）
- 1回の体験を短くし、複数のお題をテンポよく試せる設計にする
- 通信規格の暗記ではなく「条件に合わせて通信を選ぶ」ことを中心にする
- 技術選定に迷ったら「ブラウザのみで完結」「モバイルで動く」「教育効果」を優先基準にする

## 実装の進め方

- **まず一つの具体的なミッションで全機能を縦に通す**（MVP）。複数ミッション対応などの横展開は縦の筋が動くことを確認してから着手する
- 各フェーズは「動くものが一つ増える」単位で区切り、都度動作確認する
- **各フェーズの最後に実機確認ステップを入れる**（デプロイ→実機でアクセス→確認）。まとめて最後にやらず、フェーズごとに早めにデプロイして確認するサイクルを回す
- ユーザーからの調整依頼は都度Step.mdか実装コメントに反映し、後から経緯を追えるようにする
- 実装終盤に「UIのどの部分がPlan.mdのどの教育目標に対応しているか」を明示的に確認するフェーズを設ける

## テスト・確認の型

- モックではなく**実際にアプリを起動してブラウザで動かして確認**する（Playwright等）
- スクリーンショット・コンソールログ・pageerrorを能動的に確認し、疑わしい挙動は自分で深掘りする
- ドラッグ＆ドロップ、ミッション切り替えなど状態を持つUIは、繰り返し操作してリスナーリークやレースコンディションがないか確認する

## UIの型

- 「体験」（結果を直感的に見るデモ）と「仕組みの理解」を分離した構成が有効（先に結果を体感、スクロールで解説が続く流れ）
- 選択肢UIは、選んだ後の説明文だけでなく選ぶ前の選択肢自体にも短いヒントを入れる
- モバイル一画面に収める意識（スクロールなしで主要体験ができるか）を早めに確認する
