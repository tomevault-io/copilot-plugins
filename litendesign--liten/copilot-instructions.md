Guidance for Claude Code (claude.ai/code) working in this repository.

## What this is

**liten** - *Design-engineered components. Depth, not glow.*

A free, open-source component library shipped as a Fumadocs docs site. Every
component is a single, self-contained copy-paste `.tsx` file documented with a live
preview, its full source, the CSS it needs, and a real usage snippet. The product
*is* the polish: each component holds up in daylight, in both themes, with motion
off, and looks premium doing it.

**Positioning.** The edge is quality, not a use case.
- *Design-engineered* - every component is built on an invisible correctness model
  (layered depth, light from above, top-lit edges, purposeful motion). That craft
  is the differentiator vs. Magic UI / Aceternity / React Bits.
- *Depth, not glow* - the competition ships flat, dark-only neon lit from nowhere.
  Ours is physically honest: light from above, a real elevation ladder, both light
  and dark correct, reduced-motion that renders the settled outcome instead of a
  frozen effect. An effect is copyable; a depth model is not.

The catalog is deliberately broad (text effects, backgrounds, buttons, cards,
navigation, inputs, media, loaders, a globe). The through-line is never the use
case; it is that every component passes the design checklist below. Build the most
beautiful, depth-true version of whatever the component is, product-shaped or
creative. Do not force a SaaS framing onto it.

## Hard rules (these override defaults)

- **Never use the em dash (`—`)** anywhere: not in docs, MDX prose, code, component
  copy, or commit messages. Rewrite the sentence, or use a hyphen (`-`), comma, or
  colon.
- **Zero comment lines anywhere in the repo.** No `//`, no `/* */`, no `{/* */}`,
  no CSS comments in shipped files. Code must read cleanly without them.
- **Never load the font per-component.** Space Grotesk is applied once at the app
  root (`app/layout.tsx`). Do not put `Space_Grotesk(...)` inside a component.
- **Tailwind + `cn` first.** Reach for `className` with `cn` from `@/lib/cn`. Use
  inline `style` only for values that must be prop-driven CSS custom properties
  (e.g. `style={{ '--rb-angle': ... }}`). Do not hand-roll `style={{ borderRadius,
  padding, ... }}` when a class exists.
- **Always use `bun`.** Never npm / pnpm / yarn.
- **Never commit or push unless the user explicitly asks.** No `Co-Authored-By`
  trailers. Keep commits tiny and conventional.
- **Never start or restart the dev server.** The user runs it themselves.

## Commands

```bash
bun dev              # dev server at http://localhost:3000
bun run build        # production build (next build)
bun run types:check  # fumadocs-mdx + next typegen + tsc --noEmit - the verification step
```

There is no test suite or linter. `bun run types:check` is how you verify a change.
The `.source/` directory is generated by `fumadocs-mdx` (on `postinstall` and
`types:check`); never edit it.

## Stack

Next.js 16 (App Router) + Fumadocs 16 (MDX docs) + Tailwind v4 + `motion/react` +
`lucide-react`, React 19. Class merging is `cn` from `cnfast`, re-exported at
`lib/cn.ts` (import from `@/lib/cn`). Package manager: bun.

## Design law (read before touching any component)

This is a dark-first system built on **layered depth, light from above, top-lit
gradient edges, and purposeful motion**. Every component must pass this checklist:

1. **Both themes correct.** Light and dark are each designed, not one derived from
   the other. Canvas is `#fafafa` (light) / `#0a0a0b` (dark). The accent is amber
   `#f0883e`; a component may carry a different single accent through a CSS custom
   property, but only one.
2. **Light from above.** Highlights sit on top edges, shadows fall below. Never a
   glow from nowhere. Borders are brighter at the top (see `.bloom-edge` below).
3. **Elevation ladder.** Surfaces read as raised or recessed through layered
   shadow + top-lit edge, not a flat 1px stroke. Nest panels within panels.
4. **Motion is justified and short.** Animations under ~300ms, eased, purposeful.
   Name and reuse motion constants (`EASE_OUT`, `EASE_IN_OUT`, `SPRING`) inside a
   component rather than scattering magic cubic-beziers.
5. **`prefers-reduced-motion` respected.** With motion off, render the *settled
   outcome* (the final, correct state), not a frozen mid-animation frame.
6. **Focus + press.** Interactive elements get a visible `:focus-visible` outline
   and a subtle press scale.
7. **Exact radius/spacing ladder.** Consistent radii and spacing; no arbitrary
   one-off values.

Shared primitive: the **`.bloom-edge`** utility in `app/global.css` draws the
top-lit gradient border on any element and radius via a masked `::before`. Reuse it
on panels, inner panels, and icon chips rather than reinventing borders.

Component names follow **`Descriptor + Component-type`** (e.g. *Rainbow Button*,
*Tilt Card*, *Sparkle Text*, *Pixel Globe*).

## Architecture: one component = three files + two registrations

### 1. `components/ui/<name>.tsx` - the artifact
The real component. This is exactly what users copy-paste, so keep it
**self-contained**: only `motion`, `lucide-react`, and `cn` as dependencies.
`'use client'` when it has interaction or animation. Tunable/accent values flow
through CSS custom properties set inline via a `vars` object, so a single file
themes per-instance. Any CSS the component needs (keyframes, `@property`, complex
selectors) lives in `app/global.css`, and the doc tells the user to paste it.

### 2. `components/demos/<name>-demo.tsx` - the previews
One or more exported demos (`<Name>Demo`, plus variants like `<Name>CyanDemo`,
`<Name>CustomDemo`). Client components. These render inside `<ComponentPreview>` in
the docs. The default demo's code should match the doc's Usage snippet.

### 3. `content/docs/<name>.mdx` - the page
Follow this exact shape (see `content/docs/rainbow-button.mdx` as the reference):

```mdx
---
title: Rainbow Button
description: One depth-true sentence describing the component.
---

<ComponentPreview>
  <RainbowButtonDemo />
</ComponentPreview>

Docs are **concise, Magic-UI style**, not long essays. Every doc shows BOTH the
full copy-paste source (`<ComponentSource />`) AND a real usage snippet. If the

### 4. Register in `components/mdx.tsx`
Import the component and every demo, then add them to the object returned by
`getMDXComponents`. MDX files can only reference components registered here.
`ComponentPreview`, `ComponentSource`, and the styled `pre` (`CodeBlockWithIcon`)
are also wired here.

### 5. Register in `content/docs/meta.json`
Add the page slug under the correct category divider (`---Text---`, `---Cards---`,
etc.) to place it in the sidebar. Current categories: Text, Animations,
Backgrounds, Special Effects, Buttons, Cards, Components, Navigation, Inputs &
Forms, Media, Loaders & Progress, Maps & Globe.

## CSS strategy (Magic UI style)

Per-component CSS (keyframes, `@property`, `.rainbow-ring`-style selectors,
reduced-motion overrides) is **centralized in `app/global.css`**, grouped per
component. But because each component is meant to be lifted out standalone, the
component's doc reproduces that exact CSS in a ` ```css title="global.css" ` block
so users paste it into their own `global.css`. Keep the two in sync: the block in
the doc must match what actually lives in `app/global.css`.

`app/global.css` layout (grouped top to bottom):
- Tailwind + Fumadocs preset imports.
- `:root` / `.dark` Fumadocs `--color-fd-*` theme overrides (this is how the
  Fumadocs UI is restyled to the depth system).
- `@layer components`: `.bloom-edge`, `.depth-scroll`.
- `figure.shiki` code-block styling (raised panel + `::before` bloom edge + header
  via `> div:has(figcaption)` + `[role='region']` scroll region). `figure.shiki`
  is the class on ALL code-block figures, both `ComponentSource`'s
  `DynamicCodeBlock` and MDX fenced blocks, so styling it once covers everything.
- Per-component blocks below (rainbow `--rb-angle`, tessera, sparkle, marquee,
  liquid-metal `lm-*`, aurora, glow-border `--glow-angle`, footer, brand-reveal).

## Code blocks

Every code figure is styled through `figure.shiki` in `app/global.css`. Language
icons are monochrome (they inherit `currentColor`, gray like text, never colored):
`components/code-icons.tsx` defines `ReactIcon` (for tsx/jsx/react) and `CssIcon`
(simple-icons single path), an `ICONS` map, and two resolvers:
- `iconForLanguage(lang)` - used by `ComponentSource` (`DynamicCodeBlock`).
- `iconForTitle(title)` - used by `CodeBlockWithIcon` in `mdx.tsx`; it derives the
  language from the title's file extension (e.g. `global.css` -> css icon,
  `Example.tsx` -> react icon).

`components/component-source.tsx` reads the real file off disk with a
`cache()`-wrapped `fs.readFile` and renders it via `DynamicCodeBlock`
(`keepBackground: false`), so the shown source is always the actual component.

## Deterministic rendering (SSR)

This is an SSR site: anything that looks random (sample data, jitter, generative
fields, particle positions) must be identical on server and client. **Never call
`Math.random()` during render.** Seed with a pure hash (a `seeded()` helper) so
output is stable. If fresh randomness is genuinely needed, generate it in a client
`useEffect`, not in render.

## Content pipeline

`source.config.ts` defines the `content/docs` collection -> `lib/source.ts` exposes
the `loader()` source -> `app/docs/[[...slug]]/page.tsx` renders pages.
`app/(home)` is the landing page. `app/llms.txt`, `app/llms-full.txt`, and
`app/llms.mdx/docs/[[...slug]]` serve LLM-text routes off the same source.
`app/og/docs/[...slug]/route.tsx` renders per-page OG images;
`app/opengraph-image.tsx` is the root OG image.

`proxy.ts` is the Next.js proxy (middleware): it uses fumadocs-core content
negotiation to rewrite `/docs/*.md` and `Accept: text/markdown` requests to the
`content.md` route, so every doc page has a plain-markdown twin. Route constants
(`docsRoute`, `docsContentRoute`) come from `lib/shared.ts`.

## Brand + site config

- `lib/shared.ts` - single source of site truth: `appName` (`'liten'`, lowercase),
  `siteUrl` (`https://ui.liten.design`), `siteDescription`, and `gitConfig`
  (`{ user: 'litendesign', repo: 'liten', branch: 'main' }`). Use these constants;
  do not hardcode the name/url/repo elsewhere.
- `lib/layout.shared.tsx` - Fumadocs nav: the `LitenMark` glyph + lowercase
  `liten` wordmark, and the GitHub URL derived from `gitConfig`.
- `components/liten-mark.tsx` - the "l" brand glyph (single stroked SVG path,
  `currentColor`). `app/icon.svg` is the favicon: same path, amber stroke.
- The tab title default is just `liten` (`title.default = appName`); other pages
  use the `%s - liten` template.

## OG images (next/og / Satori) gotchas

When editing `app/opengraph-image.tsx` or the dynamic route, remember Satori's
constraints (these have bitten us):
- `inset: 0` is NOT supported. Use explicit `width`/`height` + `left`/`top`.
- A single-line text with `textAlign: 'center'` does NOT center. Either shrink the
  element to its content and center it via the parent's `alignItems: 'center'`, or
  split into separate centered line divs (the root OG uses two line divs).
- Every div with multiple children needs `display: 'flex'`.
- Fonts must be fetched (Space Grotesk 700 woff from the fontsource CDN) and passed
  in the `fonts` option; there is no ambient font.
- The brand mark is embedded as a data-URI SVG `<img>`.

## Working style in this repo

- Build incrementally with small, direct file edits. Write files with the Write/Edit
  tools rather than convoluted shell scripts.
- Match the surrounding code's idiom, naming, and (lack of) comments.
- After a change, run `bun run types:check` to verify.
- When you need the user to run something (a login, the dev server, a commit),
  hand them the exact command to run via the `!` prefix; do not run it yourself.
