# 炒饭会选题台 · 项目说明

给接手这个项目的人(包括未来的我自己)看的。代码怎么写在文件里,**为什么这么写在这里**。

## 这是什么

炒饭会是一档每周三的商业评论课,2022-08-17 开播,截至 2026-09-09 共 200 回,
20972 页课件,126 万字。课件按 `日期+标题/一个pptx` 的结构存在本地。

这个工具把那批课件变成一个选题决策系统。**它不是内容管理系统**——存储本来就没出过问题,
四年 200 期文件夹命名一次没破。真正难的决定只有一个:下周三讲什么。

**v2 起范围扩到全部课程线。** 除了每周的直播课,还有管理大课、操盘手、5W2HMAX、线下课、
超级个体计划、AI小课,合计 273 讲 / 25631 页 / 166 万字。目标从「选题」扩到
「内容 + 新课 + 跨课程复用」,但上面那句仍然成立:它不接管存储,只加索引。

## 同目录下的另一个项目:`studio/` 课程工作台

2026-09-08 起,`studio/` 是一个独立的新项目:帮网课老师生产课件和内容 —— 大纲、单项修改、案例库、
练习库、一节展开成讲稿骨架 + 课件页、从本目录的 `ccm.db` 拉素材(只读)、PPT 模板套版、配图、逐字稿,
多账号 + 每个账号一份老师设定。有自己的 `app.py`、`README.md`(每一版的设计约束都在那里),端口 8430,
数据按账号存在 `studio/users/<uid>/` 下(**已有真实账号,别删 `users/`**)。它只从这里搬走了 `provider.py`,
密钥缺省回退读本目录的 `config.json`。两个项目互不 import,改一边不影响另一边。
下面全部内容只讲选题台。

## 已定的设计决策(不要轻易推翻)

**档案层和资产层物理分离。** v0 的数据全是推导出来的,删了 ccm.db 重扫十分钟就回来。
知识点、案例、方法论、模块、课程编排不是推导出来的,是人写的,丢了就没了。所以:

| | 档案层 `ccm.db` | 资产层 `kb/*.md` |
|---|---|---|
| 谁写的 | 机器从课件抽 | 你写的 |
| 形式 | SQLite | Markdown + YAML frontmatter,一物一文件 |
| `--rebuild` | 清空重建 | **永不触碰** |

资产层用文件不用数据库,理由是这个工具要活四年:文件能 git、能在工具外编辑、
工具死了资产还在。数据库里的 `assets` 表只是缓存,`kb.py index` 随时重建。

**引用锚在 line/folder/页码区间 + 文字哈希上,绝不用数据库自增 id。**
`save()` 是 DELETE + INSERT,`episodes.id` 每次重扫都变。文件夹名是四年没破过一次的键,
那才是稳定锚点。哈希用来发现漂移:改了旧课件,`kb.py check` 会报出哪些知识点的出处动了。

**知识点的最小引用单位是页码区间,不是页。** 平均每页只有 60 字,一个知识点从来不完整地
待在一页里,它铺在连续的一段页里。按页切会得到一堆互相看不懂的碎片。

**只读,不接管。** 绝不改名、不搬家、不要求换存储习惯。任何要求改变存储方式的工具,
三个月内必然废弃。工具只在现有目录之上加一层索引。

**写入端优先于读取端。** 个人知识库的标准死法是检索做得很爽,然后库不再更新,半年腐烂。
成败在于「下周三那期能不能零成本进库」。所以先做守望者,后做界面。

**不做知识图谱。** 认真评估过并否决了。**v2 复核后维持原判**,并把它变成一条可执行的规则:
**关系只能手写,不能自动抽。** 资产层里每一条 `related` 都是人连的,所以永远不会产生
「十条里只站得住三条」的那十条。前端仍然不展示网状图。原文如下 ——200 期会抽出五六千个节点,五千节点的网状图在屏幕上
是一团毛线,放大缩小不产生洞察。而且 PPT 正文是碎句子,从中抽「关系」噪声极大,
十条里能站住三条。图谱只作为内部关联度矩阵存在,前端不展示成网状图。
如果将来一定要可视化,限制在 100–150 个核心概念,那才是人眼读得动的量级。

**不用向量检索、不用图数据库、不要后端。** 数据静态,每周加一条。20 万行页表用 LIKE 查
毫秒级返回。这是个只有一个人用、要活四年的工具,维护成本比功能重要。

**中文不装分词库,用字符二元组。** 搜索和相似度都够用,零依赖。代价是搜单字噪声偏大,
可以接受。

**主界面是 213 个周三格子,不是列表也不是仪表盘。** 数据的本质是四年里的每一个周三,
格子既是导航也是全局图,停更一眼可见。这个选择是有意的,别换成通用的卡片流。

## 数据里的坑(踩过的,别再踩)

**一个文件夹里常有多份 pptx(43 处)。** 因为习惯复制上一期当模板。选文件的规则经过三轮
才对:

- v1「取最大」→ 在 `20230301瑞幸` 抓到了混进来的线下课材料《Day3-数字化时代五大核心能力》
- v2「取最小」→ 在 `20260805生命礼赞4` 抓到了 10 页的附件,真正的 137 页正主被跳过
- v3(当前)先按**首页印着的日期**筛,对得上文件夹日期的才是同一期的多个版本,在里面取最完整;
  全都对不上才说明是从别处复制来的模板,这时才取最小。

首页日期是关键判据,`20260617置身钉内` 里那份副本首页写着 2026.6.3,一比就露馅。

**页数低于 30 的当附件,不计入期数。** 2025-12-24《2026年大模型会走向何方》13 页就是这种。
但注意:附件判定必须在**选文件之前**排除候选,否则会像 v2 那样选中附件。

**`20230333规划` 是个非法日期。** 正确值是 **2023-03-22**(3-15 和 3-29 之间正好空一格,
且首页标注第 27 回)。不要用「前一期加七天」推算,排序后它排在最后,会被推到 2026 年去。
v2 起写在 `sources.json` 的 `date_fix` 里,不改文件夹名。

**其他课程线有另一套坑,和直播课不一样:**

- **学员作业混在课件同一层。** 操盘手的 `课程/` 下面躺着 `（张立松）SuperAI组-作业01.pptx`。
  规则:文件名以括号开头的一律跳过(`exclude_file`),路径含「作业/点评」的目录整个不进。
- **带序号的课程线,序号就是这一讲的身份。** 操盘手 `9-1` 有三份、管理大课 `w11` 有两份,
  同序号即同一讲的多个版本,组内取最完整是安全的 —— 因为序号已经排除了「混进无关文件」
  这个 v1 踩过的坑。不匹配序号的文件(`SuperAI后续经营计划`、`规则1`)不是课件,报出来不收。
- **裸数字结尾不能当版本号。** `超级个体-第一段-加课2` 是另一讲,不是另一版。
  只认显式标记:`[自动保存]`、`v1.2`、`1.0`、`副本`。

**xmind 只有两个用途:读书笔记,和少数线下课的课件。** 写东西的习惯是直接 PPT,
脑图不是第二个写作现场。所以 43 份脑图里只有 6 份线下课的当课件读入,
读书会那 20 份是别人的书,不进知识点库(见资产层的 `origin` 字段)。

**封面回数有 5 处标错**(复制模板忘了改):2022-09-28 写第 1 回、2023-07-26 写第 45 回、
2023-08-09 写第 47 回、2024-12-04 写第 112 回、2025-02-12 写第 120 回。
分析时**一律以日期为准**,回数只用来做交叉校验。

**`20221130三体IP` 文件夹里没有 pptx。** 已知缺失,不是 bug。

**204 个计入的文件夹对应 200 回。** 差额来自同一天讲两场(2022-08-31、2023-07-19、
2023-07-26、2024-01-10、2024-07-24、2025-11-05),以及一个附件和一个缺文件。

## 从档案里跑出来的结论(工具要能复现这些)

这些是人工逐页读出来的,后来工具用相似度算出了同样的结果。**任何重构之后,拿这三条当回归测试
—— 已经写成 `python3 regress.py`,改完代码跑一次:**

1. 第一期《DAO》的折返信号里应出现「生态位」「平台思维」「AI的组织架构」——组织那条线
2. 2023-01-11《ChatGPT》的折返信号里应出现「大模型」「智能体」「2022-11 机器人」——AI 那条线
3. 2026-07-29《散帅和文字的力量》应关联到「超级符号」「斩杀线」——命名与文字那条线

另外三个已验证的数据事实:AI 类内容占比按半年是 6/8/**0**/12/**0**/28/12/29/18(两次归零是真的);
消费与零售从 2022 年的 39% 掉到 2026 年的 3%;200 回里有 30 多期是折返。

**注意:AI 占比这一条,`THEMES` 关键词分类器复现不出来。** 它算出的是
11/20/12/12/8/28/31/46/50,两次归零被抹平了。原因是 `THEMES["AI与技术"]` 里混了
「机器人」「无人机」「芯片」「数字化」这些硬件和泛化词,把《芯片》《无人机》《具身机器人》
《简历》都判成了 AI 类。人工读的时候不算,分类器算。这是 v0 就存在的偏差,不是 v2 引入的
(`THEMES` 和 `classify()` 一字未改)。要复现那条曲线,得把硬件词从 AI 类里拆出去,
或者改用 `ai` 密度加阈值。消费与零售那条复现精确:2022=39% → 2026=3%。

## 路线

**v0(已完成)** 守望者 + 检索 + 折返信号 + 覆盖缺口 + 入库校验。

**v2-A(已完成)地基。** 多课程线索引(`sources.json`)、xmind 当课件读、稳定引用键 +
漂移检查、资产层 `kb/`。折返信号拆成「同线折返」和「跨线复用」两栏。

**v2-B(已完成)采集。** 在课件正文里点两下页码选区间,打个名字回车就沉淀成知识点,
出处和哈希自动填。三下点击加一个名字。

采集的两条设计,不要动:

- **名字实时联想已有条目,命中就切成「追加出处」而不是新建。** 存之前那行字明说回车会做什么。
  这不是便利功能,是「跨课程复用」能被追踪的唯一来源 —— 一条知识点挂着多处出处、
  横跨多条课程线,复用才成立。允许建重名条目,库两个月就废了。
- **选区是页码区间不是单页。** 平均每页 60 字,按页切会得到一堆互相看不懂的碎片。

不要先回填 200 回。让每周的折返信号当回填队列,备课时顺手挖 5–8 期,
二十周之后真正重要的那一百来期就自然挖完了,而你一次都没有「专门去回填」。

**v2-B2(已完成)案例集。** 独立模块,按案例组织的复用视图。三条设计:

- **排序按「用过几次」,不按时间不按字母。** 一条案例的价值就是被复用的次数和跨线数,
  排序要直接说出这件事。
- **案例线索不做自动抽取。** 273 讲的标题原样列出,哪些是案例人一眼能看出来。
  点一条就把采集条预置成「案例 + 标题」。这条守住了「关系只能手写」那条规则 ——
  库里只进你确认过的东西,机器一条都不塞。
- **空状态不是空表。** 案例集是空的时候直接讲清楚从哪儿开始,不是摆一张 0 行的表格。

**v2-B3(已完成)LLM 案例抽取。** `llm.py`,claude-opus-5。这件事在路线图里本来是 v1
(「需要逐页调外部 API 跑 20972 页」),它定的两条要求原样落实了:

- **断点续跑** —— 一讲一条 `llm_runs` 记录,跑完就 commit。改成按讲而不是按页调用,
  是因为平均每页 60 字,单页看不出案例;一个案例铺在连续好几页里。273 次调用约 $10。
- **批次抽检** —— `--limit 5` 先跑五讲。另外加了 `llm.py check`:开跑前一次最小调用,
  验证凭证和请求格式,免得跑到一半发现请求写错了。

两条新的设计约束:

- **抽出来的东西不进 `kb/`,进 `case_candidates` 待定表。** 案例集顶部一键确认才成为资产。
  这条是「不做知识图谱」那条规则在 LLM 时代的等价物 —— 机器负责找,人负责认,分工不能反。
  收下时把这个案例的**全部出处一次写进文件**,否则一条条点还不如不跑。
- **必须跑第二遍 `merge` 归并叫法。** 第一遍会产出「瑞幸」「瑞幸咖啡」「Luckin」三条,
  而案例集的全部价值是「用过几次、跨几条线」—— 叫法不统一,这两个数永远是 1。
  归并只并同一个真实对象,母公司和子品牌不并(字节跳动 ≠ 抖音)。

「案例线索」那一栏(273 讲标题的人工浏览入口)保留,不被抽取取代 ——
不想花钱、或者模型漏了的时候,它是兜底。

**v2-B4(已完成)做成 web app + 多供应商。** 入口收敛成 `python3 app.py` 一条命令,
扫描、抽取、归并、设密钥全在页面上做,不用再开第二个终端。

- **`provider.py` 是唯一调模型的地方。** Anthropic 走官方 SDK(`output_config.format`),
  三方走 OpenAI 兼容协议(标准库 HTTP,不加依赖)。三方对结构化输出支持参差不齐,
  所以是三级降级 `json_schema → json_object → 提示词+容错解析`,降级成功会记住。
- **密钥存 `config.json`,权限 0600,已进 `.gitignore`,永不回传给浏览器**
  —— 前端只拿得到打码版。服务只监听 127.0.0.1。这几条不要为了省事改掉。
- **只有 Anthropic 有价目表,所以只有它显示预估花费。** 三方只报 token 数。
  与其编一个会过期的价格,不如不显示。
- **任务一次只能跑一个**,并发写同一个 SQLite 会打架。任务完成只刷左栏,不整页重绘 ——
  否则会把人从设置页踢回档案页。
- 命令行入口全部保留,`llm.run_cases()` / `run_merge()` 接受 log 回调和 stop 事件,
  网页任务面板和 CLI 共用同一份逻辑,不写两遍。

**v2-C 组装。** 模块 + 课程编排 + 覆盖检查(给一份大纲,告诉你哪几节靠现成模块能拼出来、
哪几节要净新写)。

**v2-D 复用与到期。** 跨课程复用视图 + 判断库到期提醒(原 v1)。

**原 v1(判断库)不取消,被 v2 吸收了** —— 一条「断言」就是带 `expires` 字段的知识点。
下面这段说明依然成立:

**判断库。** 逐页抽出带断言性的句子(「X 会 Y」「本质上是 Z」「未来 N 年」),
存成可追踪条目。每条至少四个字段:断言正文、下判断的日期、涉及对象、**可检验的到期时间**。
最后那个字段是整个系统的意义所在,也最难自动生成。

需要逐页调外部 API 跑 20972 页(已确认可以走外部 API)。必须支持断点续跑和批次抽检——
一次性跑完不校验,错了要重跑全部,代价太大。

**为什么要做这个:** 2023 年 1 月 11 日那期画对了 2026 年的地图,然后被放进抽屉两年,
两年后把人叫回来的是 DeepSeek——一个外部事件。撤退本身不是错,错在撤的时候没有留下
任何回来的路标。判断库就是那个路标:让每年的对账不再是一次考古,而是随时可查。

**v2(设想)** 到期提醒。判断条目到期自动弹出:这条还成立吗。
