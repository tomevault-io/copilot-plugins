## What this is

A Go REST service that decides and serves what an e-ink screen connected to an ESP32 should display. The ESP32 will poll the endpoint hourly; the endpoint renders today's agenda from a single reference Google Calendar next to a right-hand column that itself varies by time of day — the current shopping list at midday, or a visual weather panel for a preconfigured location otherwise — plus the next few days of a weekly menu below both, all from a single reference Google Sheet (calendar and Sheets both via the same one-time-authorized OAuth credential, refreshed unattended — see "Calendar credentials" below; weather comes from Open-Meteo instead, which needs no credential at all). Runs autonomously on a VPS. This is the user's first Go project — prioritize idiomatic, explainable code over shortcuts.

See [README.md](README.md) for usage, endpoint, and binary format details.

## Target hardware

Seeed reTerminal E1001 (GDEY075T7 panel, UC8179 controller): **800×480 px, 4 grayscale levels (2 bits/pixel)**. There's no lightweight standard image format worth adopting for this, hence the custom binary format in `internal/display/codec.go` and the `cmd/preview` CLI to inspect it visually.

## Commands

```bash
go build ./...
go vet ./...
go test ./...
go run ./cmd/server
go run ./cmd/preview --file buffer.bin
```

Unlike other projects of this user, tests **can be run directly here** (`go test ./...`) during implementation — this is a new, small, isolated Go project, without the "don't run tests, give me the command" policy that applies to other repos (that policy belongs to a different, unrelated project).

## Conventions for this project

- **No single-use packages**: don't create an `internal/auth` package just for the token middleware — it lives in `internal/server/middleware.go`, alongside the rest of the HTTP server. If in the future several middlewares are shared across different servers, extracting `internal/middleware` (the `mid` pattern from Ardan Labs Service) would then be justified.
- **`internal/display`, not `internal/eink`**: the package represents *what will be displayed* (image + codec), not the panel driver/firmware. Consistent with the `/api/v1/display` endpoint.
- **Authentication token**: loaded from an environment variable (`AUTH_TOKEN`), with `.env` support in development via `github.com/joho/godotenv`. In production the VPS sets real environment variables (systemd `EnvironmentFile=`), there's no `.env` on the server. Token comparison uses `crypto/subtle.ConstantTimeCompare`.
- **Custom image format**: `internal/display/codec.go` packs 2 bits/pixel with no external standard, meant to minimize memory usage on the ESP32. Any format change must preserve the `Encode`/`Decode` roundtrip and its test.
- **`internal/calendar`, not `internal/googlecalendar`**: represents the domain concept (today's agenda as a list of `Row`), backed by the Google Calendar API client internally. `internal/display` stays agnostic to where its content came from (`Row.TimeLabel()`/`Row.Summary` feed `display.EventLine{Time, Text}`, see "Agenda wrapping" below) — the calendar package owns the formatting logic for its own data, `display` just renders whatever `Section`/`EventLine` it's handed.
- **`internal/shoppinglist`, not `internal/googlesheets`**: same domain-not-API-vendor naming as `internal/calendar`. Reads a fixed spreadsheet's first tab, `A2:A` (no sheet-tab name in the range, so it resolves to the first tab regardless of what it's named; starting at row 2 skips a human-only header row with no special-case code). An item is just its string — no `Row` struct, unlike Calendar, since there's no start/end/reminder classification to model. `parseItems` (pure, tested directly with literal `[][]interface{}` fixtures, same style as `calendar`'s `toRow`/`isVisible`) drops blank rows, non-string cells, and whitespace-only cells.
- **`internal/weeklymenu`, not `internal/sheets2` or similar**: reads the *second* tab of the same spreadsheet as `shoppinglist` — lunch ("comida", rows 2-6) and dinner ("cena", rows 8-12) entries per weekday column (Monday-first, A-G), row 1 being the header. Unlike `shoppinglist`'s tab-agnostic range, a second tab has no implicit A1-notation reference by position, so `FetchWeek` first calls `Spreadsheets.Get` to read `sheets[1].Properties.Title` (the second tab, regardless of what it's actually named) and builds the values range from that title — two API calls per fetch instead of one. The client mirrors `calendar.Client`'s shape (closes over `time.Now().In(loc)` internally so `FetchWeek(ctx)` needs no extra argument), not `shoppinglist.Client`'s, since it has a "today" concept. `parseWeek` rotates the 7 parsed `Day`s to start at today's column (Go's `time.Weekday` is Sunday=0..Saturday=6; `(int(today)+6)%7` converts to this sheet's Monday=0 indexing) and tolerates blanks the same way `shoppinglist.parseItems` does. `Day.Label` is read verbatim from the sheet's header row rather than hardcoded in Go, so the day name's language/format is entirely the spreadsheet's choice.
- **Weekly menu shown 2 days at a time (today + tomorrow), not 7**: `server.DefaultVisibleDays = 2` caps how many of the rotated week's days `menuSections` actually renders — a deliberate first-pass simplification since 7 days × up to 10 entries doesn't fit legibly below the agenda/shopping-list columns. Meant to be revisited (the constant bumped, the layout reworked) once time-of-day-aware phases are designed; not a permanent limitation.
- **Column layout (`display.NewDailyLayout`)**: added for iteration 4 alongside (not instead of) `NewSections`/`NewTextRows`, which keep rendering everything in one column and stay wired to the calendar-fetch-critical-error fallback and `cmd/preview`. `NewDailyLayout` renders the agenda and shopping list as two side-by-side columns (each only as tall as its own content) and the weekly menu as a full-width region starting below whichever column ends lower — sharing an unexported `drawSections(canvas, x, y, sections)` helper (parameterized by x-offset) with `NewSections` rather than duplicating the stacking loop. `drawText` itself still doesn't wrap or clip to a width — a plain `Section.Lines` entry (e.g. a weekly-menu meal line) can still spill past its column boundary, an accepted limitation — but the agenda specifically no longer has this problem, see "Agenda wrapping" below.
- **Agenda wrapping, bold time, bulleted entries**: a user-reported bug — a long event summary at 09:00 would run past the agenda column's right edge and visually bleed into the shopping-list/weather column, since `drawText` doesn't wrap. Fixed with a new `Section.Events []EventLine` (`internal/display/eventlines.go`), an alternative to `Lines`/`Bulleted` that `drawSections` checks first: each `EventLine{Time, Text}` is bulleted (`drawBullet`, reused from the shopping list), `Time` drawn bold (`newBoldFace(rowFontSize)`), `Text` word-wrapped via `wrapText` (greedy word packing, a single word wider than the column is left unsplit rather than broken mid-word) with continuation lines hanging-indented under where `Text` started — so a long summary now stays inside its column instead of spilling into the next one. `internal/server`'s `agendaSection(rows)` replaces the old `agendaLines` helper: builds one `EventLine` per row (`Row.TimeLabel()`/`Row.Summary`, see the `internal/calendar` bullet above) when there are events, or falls back to a plain one-line `Lines` message ("No events today") when there are none, since there's nothing to bullet/wrap in that case. `calendar.Row.TimeLabel()` was factored out of `Row.String()` (which now just calls it) specifically so `agendaSection` could get the time and summary as separate strings instead of re-parsing `String()`'s combined output.
- **Weather panel sizing and layout**: two rounds of user feedback on `internal/display/weathericon.go`'s `drawWeatherPanel`. First, a reported bug — the weather panel's first-pass sizing (96px icon, 40pt temperature, 34px vertical forecast rows) made the weather column taller than the agenda column often enough that the weekly-menu region below (which starts at `max(leftEndY, rightEndY) + sectionGap`, per `NewDailyLayoutWithWeather`) got pushed down far enough to run past the panel's bottom edge — cutting off part of the second visible day, since `drawSections`/`drawWeatherPanel` don't clip to the canvas bounds. Shrunk to 64px icon / 30pt temperature. Second, a visual complaint — the "now" icon+temperature sat left-aligned with the rest of the column empty, and the forecast entries stacked as a left-aligned vertical icon+text list left most of the column's width unused, since neither the icon nor the text needed it. Reworked to: the "now" icon+temperature centered as one block within the column width (`weatherNowGap` between icon and text, block width computed then `x + (width-blockWidth)/2`), and `panel.Hours` laid out as a horizontal row of equal-width slots spread across the full column width, each slot's time label / 32px icon / "temp rain%" text all centered within its own slot (`weatherForecastIconSize`/`weatherForecastLabelFontSize`/`weatherForecastTextFontSize`/`weatherForecastGap`) — both shorter vertically than the original vertical list *and* using the column's actual width, instead of wasting it.
- **Night-phase calendar fetch: day vs. now must stay separate**: a user-reported bug — the night phase's tomorrow-agenda fetch showed nothing even when tomorrow genuinely had events. Root cause: `calendar.Client.FetchForDay(ctx, day)` originally called the package-level `FetchToday(ctx, svc, calendarID, loc, now)` with `day` standing in for *both* of `FetchToday`'s roles for `now` — the 24h window (correct: `time.Date(day.Year(), ...)` derives tomorrow's window from `day` fine) *and* `isVisible`'s past-event cutoff (wrong: `handlers.go` built `day` as `now.AddDate(0, 0, 1)`, i.e. tomorrow *at the current hour*, e.g. 23:00 — so `isVisible` compared every one of tomorrow's rows against "tomorrow at 23:00" and filtered out anything earlier in the day as if it had already happened). Fixed by splitting the package-level function into `FetchDay(ctx, svc, calendarID, loc, day, now time.Time)` (window from `day`, filtering from `now`, kept as two separate parameters) with `FetchToday` now a thin wrapper calling `FetchDay(..., now, now)` since for "today" they're the same value. `Client.FetchForDay` calls `FetchDay(ctx, c.svc, c.calendarID, c.loc, day, time.Now().In(c.loc))` — window from the target day, filtering from the *real* current moment, which correctly never filters anything out on a day that (from right now) hasn't happened yet.
- **Agenda column title + generation-time/battery footer**: `handleDisplay`'s left column now carries `Title: "Eventos"` (Spanish, for consistency with "Lista de la compra" on the right — every other label in this app is Spanish, so "Planning" would be the odd one out). `Section.Title`'s empty-string case now only applies to `NewTextRows`'s single-section wrapper (the calendar-fetch-error fallback) — every section `NewDailyLayout` renders has an explicit title. Separately, `NewSections`/`NewTextRows`/`NewDailyLayout` all take a new `footer string` parameter, drawn right-aligned in the panel's bottom-right corner by an unexported `display.drawFooter` helper (`footerFontSize = 12`, smaller than any other text on the panel, since it's a diagnostic aside). `handleDisplay` builds this string itself (`"15:04:05 - 87%"`-shaped, via `fmt.Sprintf`), keeping `display` agnostic to "battery"/"generation time" as concepts, same as it's already agnostic to calendar/shopping-list/menu content. The battery percentage arrives as a required `?battery=` query parameter (1-100) — a query param, not a header, since headers are reserved for the auth concern in this codebase — parsed by `parseBatteryPercent` in `handlers.go`; missing/invalid/out-of-range values log the specific reason but respond with a generic `400 "invalid battery"`, mirroring `requireAuth`'s generic `401 "unauthorized"` covering multiple distinct causes. The footer is computed once, before the calendar-fetch branch, so it's passed on both the normal (`NewDailyLayout`) and calendar-error-fallback (`NewTextRows`) paths.
- **Reminder vs. event**: the Calendar API has no `reminder` field. The classification rule is: `Start == End` (zero duration) → reminder (show only start time); otherwise → event (show start-end). All-day items (`Start.Date` set instead of `Start.DateTime`) are a third case, shown as "All day".
- **Past-event visibility**: a row stays on the display until an hour after it ends (`visibleAfterEnd` in `internal/calendar/events.go`), so only what's upcoming, ongoing, or just-finished shows up.
- **Calendar credentials**: originally planned as a service account JSON key, but personal (org-less) Google Cloud projects have their `iam.disableServiceAccountKeyCreation` org policy locked with no self-serve override — there's no Organization resource to attach an exception to, and `gcloud ... org-policies disable-enforce` fails with a permission error for the same reason. Pivoted to a **one-time OAuth authorization of the user's own Google account** instead: `cmd/oauthsetup` (see below) turns a Desktop-type OAuth client (from Google Cloud Console) into an `authorized_user`-format credentials file via a single interactive login. `GOOGLE_CREDENTIALS_FILE` (env var, a path not JSON content) points at that file either way — `option.WithCredentialsFile` auto-detects both service-account and `authorized_user` JSON shapes, so `internal/calendar/client.go` needed no code change for this pivot; `internal/shoppinglist/client.go` and `internal/weeklymenu/client.go` reuse the same file and mechanism unchanged. No calendar-sharing step is needed since the authorized account is the calendar owner (same for the spreadsheet). Timezone is a required env var (`TZ`), used both for "today"'s bounds and for formatting event times — there's no other timezone handling in the app.
- **Sheets/Drive scope narrowed to `drive.file`**: originally `spreadsheets.readonly` (read access to every spreadsheet in the authorized account, forever). Narrowed to `drive.file` — access to only the one spreadsheet explicitly picked via the Google Picker widget in `cmd/oauthsetup` — deliberately chosen (not `spreadsheets`, the read+write account-wide scope) because `drive.file` is already read+write on the picked file, so a future iteration that clears/writes weekly-menu cells won't need a second re-consent. `internal/shoppinglist/client.go` and `internal/weeklymenu/client.go` both request `drive.DriveFileScope` (from `google.golang.org/api/drive/v3`) instead of `sheets.SpreadsheetsReadonlyScope`; `internal/calendar/client.go` is unaffected (`calendar.readonly` unchanged).
- **`cmd/oauthsetup`**: a one-time, interactive CLI (not used at server runtime) that exchanges a downloaded OAuth Desktop client JSON for a long-lived `authorized_user` credentials file, via a local loopback HTTP listener catching Google's redirect. Requests `calendar.readonly` + `drive.file` via `google.ConfigFromJSON`'s variadic scope list. Since `drive.file` grants no access until a specific file is picked, the OAuth callback handler exchanges the code for a token, then redirects the same browser tab to a `/picker` route serving `picker.html` (embedded via `//go:embed`, rendered with `html/template` so the injected access token/API key are correctly escaped inside the `<script>` block) — the Google Picker JS widget, restricted to spreadsheets. Routes are registered on specific paths (`/callback`, `/picker`, `/picker-callback`), never on `"/"` — a bare `"/"` pattern in `http.ServeMux` also catches unrelated same-origin requests the browser sends automatically (e.g. `GET /favicon.ico` once `/picker` loads), which would otherwise be misrouted to the OAuth callback handler as a bogus, state-less request. The Picker's `PickerBuilder` must call `.setAppId(<Cloud project number>)` alongside `.setOAuthToken`/`.setDeveloperKey` — without it, `drive.file` doesn't actually grant access to the picked file (the widget still reports success, but the token gets a 404 on that file afterward); the project number is derived from the OAuth client ID's own format (`<project number>-<random>.apps.googleusercontent.com`, split on the first `-`) rather than requiring a separate config value. Picking a file POSTs its id/name to `/picker-callback` on the same listener, which the tool reads before writing credentials; a Picker API key (Cloud Console → Credentials → API key, restricted to the Picker API) is required via `GOOGLE_PICKER_API_KEY` — read from `.env` via its own `godotenv.Load()` call, matching `internal/config`'s pattern, but deliberately kept out of `internal/config.Config` itself since the server never needs it at runtime, only this one-time tool does. Run once per Google account; never touched again afterward, including on the VPS — **except that adding/changing a scope (as Sheets did, and this narrowing did too) requires existing users to re-run it once**, since Google won't silently extend an already-issued refresh token's grant to a newly-requested scope.
- **`cmd/calendarcheck`** / **`cmd/sheetscheck`** / **`cmd/menucheck`** / **`cmd/weathercheck`**: small permanent diagnostic CLIs, one per integration, that dump raw API data as JSON, bypassing `internal/calendar`'s `Row` / `internal/shoppinglist`'s / `internal/weeklymenu`'s / `internal/weather`'s parsing on purpose (they exist to inspect the real shape the upstream API sends, e.g. what a genuinely blank sheet row looks like, debugging unexpected calendar data, confirming `weeklymenu`'s tab-discovery-by-position picked the right tab, or checking Open-Meteo fields `internal/weather` doesn't read).
- **Shopping-list/weekly-menu/weather error isolation**: in `internal/server/handlers.go`, a calendar fetch failure still replaces the whole screen with an error message (unchanged from iteration 2, since the agenda is the primary content) — but a shopping-list, weekly-menu, or weather fetch failure only replaces that section (`shoppingListLines`/`menuSections` return a one-line Spanish error string/Section on `err != nil`; the weather panel falls back to an ordinary error `Section` the same way, via `NewDailyLayout` instead of `NewDailyLayoutWithWeather` — see below) so the rest of the display stays visible. This is a deliberate asymmetry, not an oversight: the content sources aren't treated as equally critical.
- **`internal/weather`, not `internal/openmeteo`**: same domain-not-API-vendor naming as `calendar`/`shoppinglist`/`weeklymenu`. Reads the hourly forecast for one fixed, preconfigured location (`WEATHER_LATITUDE`/`WEATHER_LONGITUDE` env vars) from **Open-Meteo**, chosen over Google Weather API specifically because it needs no API key or billing-enabled Cloud project — a plain `net/http` GET, no `option.WithCredentialsFile`/OAuth at all, unlike every other integration in this app. `weather.Summarize(points, now, maxForecastEntries)` is the "the next 7h won't fit as one row per hour" grouping system: it always returns the current hour as its own point, then either one point per hour if the rest of the horizon (`ForecastHorizonHours = 7`) fits within `maxForecastEntries`, or `maxForecastEntries` representative points — each bucket's *middle* point, not its first — split evenly across the horizon. `IconKeyFor(code int) string` maps Open-Meteo's WMO `weathercode` to one of 7 plain string keys (`"clear"`, `"partly-cloudy"`, `"cloudy"`, `"fog"`, `"rain"`, `"snow"`, `"storm"`) — deliberately a shared string vocabulary rather than a type either package would have to import from the other, keeping `internal/weather` and `internal/display` as decoupled as `internal/calendar`/`internal/display` already are (only `internal/server` translates between domain packages and `display`).
- **Weather panel is icon-based, not text**: an explicit user correction mid-design — a first draft that rendered the forecast as plain text lines was rejected in favor of a Google-Weather-style panel: a large icon + current temperature, then a vertical list of smaller icon + time + temperature + rain% rows below. The 7 icon PNGs (`internal/display/assets/weathericons/*.png`, embedded via `//go:embed`) are simple geometric glyphs (filled circle + rays for sun, overlapping circles + a pill-shaped base for cloud, diagonal lines/asterisks/a lightning-bolt polygon for rain/snow/storm) generated once by a throwaway local script rather than sourced from a licensed set like Material Symbols — swap the PNGs for a different set later if the hand-drawn look isn't wanted, no code changes needed since `drawIcon` just scales-and-composites whatever's under each key. `drawIcon(canvas, key, x, y, size)` uses `golang.org/x/image/draw`'s `BiLinear.Scale` (an already-indirect dependency via `golang.org/x/image/font`) to render one embedded source resolution at whatever size is needed, composited via its alpha channel so the transparent background leaves the canvas untouched; an unknown key is a no-op, not a panic. `display.NewDailyLayoutWithWeather(header, footer, left, WeatherPanel, bottom)` is `NewDailyLayout`'s counterpart for this — added alongside it (not a "right column kind" switch folded into the existing function), same additive precedent as `NewDailyLayout` itself relative to `NewSections`.
- **Time-of-day panel phases (iteration 5)**: `server.phaseFor(now)` splits the day into three phases purely by hour — `phaseMorning` (00:00-15:00) and `phaseNight` (21:00-00:00) both show the weather panel in the right column instead of the shopping list; `phaseMidday` (15:00-21:00) shows the shopping list, **except handleDisplay falls back to the weather panel there too if the list is empty** (confirmed explicitly by the user: an empty shopping list shouldn't waste the screen's most-glanced-at column). `server.WeatherMaxForecastEntries` (currently 4) is the cap `weather.Summarize` groups down to, analogous to `DefaultVisibleDays` for the weekly menu.
- **Night phase references tomorrow, not today**: in `phaseNight`, the agenda and weekly menu both shift to the next day instead of today, and the header reads "Mañana, `<date>`" (`tomorrowHeaderDate`, `spanishHeaderDate`'s format with the weekday name swapped for the word "Mañana" — deliberately ambiguous between "tomorrow" and "morning" in Spanish) instead of `spanishHeaderDate(now)`. This only worked out to a small change because both underlying fetches were already parameterized by an arbitrary reference time/weekday, just wrapped by date-hardcoding convenience methods: `calendar.Client.FetchForDay(ctx, day)` forwards to the same package-level `FetchToday(ctx, svc, calendarID, loc, now)` that `Client.FetchToday` already called with `time.Now()` — for a future day this makes `isVisible`'s past-event filtering a harmless no-op, not wrong, since nothing on a day that hasn't happened yet counts as "past". `weeklymenu.Client.FetchWeekFrom(ctx, day)` similarly forwards to the same package-level `FetchWeek(ctx, svc, spreadsheetID, weekday)` `Client.FetchWeek` already called with today's weekday. The weather panel itself is *not* date-shifted — `weather.Summarize`'s "next 7h from real now" window already reaches naturally into the next day's early hours during the night phase, so there was nothing to change there.
- **`demo_time` query param**: an optional, ESP32-never-sends-it override on `/api/v1/display?demo_time=HH:MM` (parsed by `parseDemoTime`, combined with today's real date in `cfg.Location`) so all three phases can be exercised on demand instead of waiting on the real clock — explicitly requested by the user, who wanted it to hit the real integrations (not a local fixture/demo mode) and to be easy to reach from `cmd/preview`. `cmd/preview --demo-time HH:MM` forwards it as a query param alongside `--battery`, only meaningful together with `--url`.
- **Outgoing day's menu is cleared on entering the night phase**: `weeklymenu.ClearDay(ctx, svc, spreadsheetID, day)` (`internal/weeklymenu/week.go`) is the app's first *write* path to Sheets — everything else in `weeklymenu`/`shoppinglist` is read-only. It blanks one weekday's whole column (rows 2-12: lunch, the blank spacer, dinner) via `Spreadsheets.Values.Clear`, so the user has to re-plan that weekday before it comes back around next week. No new OAuth scope/re-consent was needed: `drive.file` (see "Sheets/Drive scope narrowed to `drive.file`" above) was deliberately chosen originally because it's already read+write on the picked spreadsheet. `handleDisplay` calls this once phase is `phaseNight`, with `now.Weekday()` — the day that's *ending* (captured before `referenceDay` advances to tomorrow) — not `referenceDay.Weekday()`. Because the ESP32 polls hourly and the night phase spans ~3 requests (21:00-23:59), a per-request clear risked wiping an entry the user had just typed in for next week if they filled it in mid-window; `Server.clearOutgoingMenuOnce` (`internal/server/handlers.go`) guards against this with an in-memory, mutex-protected "already cleared today" date key (`menuClearMu`/`menuClearedDate` on `Server`) rather than any sheet-side bookkeeping — resets on server restart, an accepted gap given restarts are rare on the VPS/Raspberry Pi target. A clear failure is logged only, same non-fatal treatment as the shopping-list/weather/menu-fetch errors elsewhere in this handler. No new "no menu" message was needed for the cleared day once it's visible again: `mealLine`'s existing `"(sin planificar)"` per-meal placeholder already covers a day with zero entries.
- **English display literals corrected to Spanish**: `"Could not load calendar"` (the `NewTextRows` fallback header when the calendar fetch fails) and `"No events today"` (the agenda's empty-day fallback line) were the only two panel-rendered strings still in English — found via a full literal audit prompted by the menu-clearing feature above — now `"No se pudo cargar el calendario"` and `"No hay eventos"`, consistent with every other panel string. `display.NewHelloWorld`'s `"Hello World"` was left as-is: confirmed dead code, reachable only from its own test and `cmd/preview`, never from a real request.
- **HTTPS by default, `--insecure` opts out**: `cmd/server` listens with TLS by default, using a self-signed certificate generated once at `secrets/tls-cert.pem`/`secrets/tls-key.pem` (`cmd/server/tls.go`, ECDSA P-256, 10-year validity, SANs from the machine's local interfaces at generation time) and reused unchanged on every later restart — regenerating would change the fingerprint and break any ESP32 client that already pinned the old one. `GET /api/v1/tls-cert` (`internal/server/tlscertpage.go`, gated in `routes()` on `s.tls.Fingerprint != ""`) serves the certificate's SHA-256 fingerprint and full PEM text with copy-to-clipboard buttons, deliberately unauthenticated (no `AUTH_TOKEN`) so it's easy to open from an ordinary phone browser on the same network — this is a diagnostic/pairing page for a human, not e-ink display content, so unlike the display strings above it's in English. Originally this was reversed (plain HTTP by default, `--https` opted in); flipped so the insecure choice is the one that has to be explicitly named (`--insecure`), matching the "make the exception loud, not the default" pattern used elsewhere in this app (e.g. auth token comparison, battery validation).

## Toolchain

The original system Go (apt `golang-1.18`, from 2022) was too old for the current `google.golang.org/api` client (needs Go 1.24+). The user has since replaced it with a system-wide Go 1.26.5 install (via sudo, at `/usr/local/go/bin/go`); `go.mod`'s `go` directive matches. Just use `go` normally.

## Iteration scope

- **Iteration 1**: REST structure, token auth middleware, `/api/v1/display` endpoint with a "Hello World" + current time placeholder, visualization CLI, tests.
- **Iteration 2**: Google Calendar integration — `/api/v1/display` renders today's agenda (events + reminders) from one fixed reference calendar, replacing the placeholder. `NewHelloWorld` is kept around (still used by `cmd/preview`/tests) but is no longer wired into the server.
- **Iteration 3**: Google Sheets integration — `/api/v1/display` renders the current shopping list from one fixed reference spreadsheet, appended below the agenda. Layout is intentionally minimal (just appended rows, sharing `display.NewTextRows`'s single-list rendering) — a real time-of-day-aware layout is future work, not attempted here.
- **Iteration 4**: weekly menu integration — `/api/v1/display` renders today and tomorrow's lunch/dinner menu (`internal/weeklymenu`) read from the same spreadsheet's second tab, below a new two-column top area (agenda | shopping list, via `display.NewDailyLayout`). The 2-day cap (`server.DefaultVisibleDays`) and the column layout are both explicitly first-pass/provisional — validating the integration end-to-end now, with real time-of-day-aware layout tuning deferred to a later iteration.
- **Iteration 5 (current)**: time-of-day panel switching plus a new weather integration (`internal/weather`, Open-Meteo) — the right column now varies by hour (weather panel in the morning/night, shopping list at midday unless it's empty), and the night phase (21:00-00:00) references tomorrow's agenda/menu instead of today's, with a "Mañana, `<date>`" header. See the "Time-of-day panel phases"/"Night phase references tomorrow"/`internal/weather` bullets above for the details. `server.DefaultVisibleDays` (still 2) and the weather panel's forecast-grouping cap (`server.WeatherMaxForecastEntries`) are both still first-pass constants, same spirit as iteration 4's.
- **Next iterations**: ESP32 firmware, VPS deployment.
