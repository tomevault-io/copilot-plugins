# CLAUDE.md — プロジェクト基本ルール

## プロジェクト概要

CodeCommitにMarkdownをpushするだけでWebサイトとして公開される仕組みを構築する。既存のAWSインフラに統合できるため、追加の外部サービス契約や管理が不要になる点もメリットである。

## プロジェクトが解決したいこと

チームの運用ドキュメント（設計書・作業手順書）は現在Markdownファイルとして管理されているが、共有方法はファイルの受け渡しに依存しており、各メンバーがローカルのVSCodeでプレビューしている状態である。

この運用には以下の課題がある。

- ドキュメントの一元管理ができていない
- 最新版がどこにあるか分かりにくい
- 閲覧のためにリポジトリのクローンとエディタが必要
- 作業中にブラウザですぐ参照できない

これらを解決する。

## ユーザー（Yohei）について
- このプロジェクトの開発者を「Yohei」と呼ぶ
- Web アプリケーション開発は初心者のため、教育的な観点での解説やわかりやすい説明を心がける
- 技術的な判断をする際は、なぜそうするのかの背景も添える

### ドキュメント配置

主要ドキュメントは以下に配置する。CLAUDE.md だけはClaude Code が自動読み込みするためルートに置く：

- `CLAUDE.md` — プロジェクト基本ルール（このファイル）
- `docs/` — プロジェクト製作者向けドキュメント
  - `docs/SPEC.md` — 仕様書
  - `docs/DESIGN.md` — 設計書
  - `docs/TASKS.md` — タスク管理
  - `docs/LOGS.md` — 作業ログ
- `steering/steering-t<番号>-<名前>.md` — タスクごとのステアリングファイル

### ドキュメント駆動

- `docs/SPEC.md`, `docs/TASKS.md`, `CLAUDE.md` がプロジェクトの記憶装置になる
- セッションが切れてもこれらのファイルからコンテキストを復元できるので、常に最新に保つ
- 新しいセッションを開始したら、まずこれらを読んで現状を把握する

### プロジェクトの進め方
1. Yoheiとのディスカッションを元に仕様を決めていき、決定事項を `docs/SPEC.md` にまとめる
2. `docs/SPEC.md` の内容を元に、システムの設計を行い、決定事項を `docs/DESIGN.md` にまとめる
3. `docs/DESIGN.md` の内容に従い、実装タスクを計画し、決定事項を `docs/TASKS.md` にまとめる
4. `docs/TASKS.md` の内容に沿って、個別タスクを実施する。
5. 個別タスクの詳細は、タスクごとに、`steering/steering-[タスク番号]-[タスク名].md` のステアリングファイルを作成する
6. 途中必要に応じてYoheiと質疑応答やディスカッションを行い、必要があれば各種ドキュメントを変更して、以降の工程を進める

### 仕様管理：docs/SPEC.md
- 仕様はすべて `docs/SPEC.md` に記載する
- 実装時は常に `docs/SPEC.md` を常に参照し、仕様に従う
- 仕様の変更が必要な場合は、実装の前に `docs/SPEC.md` を更新する

### 設計書：docs/DESIGN.md
- `docs/SPEC.md` の仕様にそって、ワークショップ内で構築するシステムの設計内容を `docs/DESIGN.md` に記載する
- `docs/DESIGN.md` には以下の内容を含む
   - 機能設計
      - 機能ごとのアーキテクチャ
      - システム構成図
      - コンポーネント設計
      - ユースケース図、画面遷移図、ワイヤフレーム
      - API設計
   - 技術仕様
      - テクノロジースタック
      - 開発ツールと手法
   - リポジトリ構造定義書
      - フォルダ・ファイル構成
      - ディレクトリの役割
      - ファイル配置ルール

### タスク管理：docs/TASKS.md
- タスクの計画と進捗状況は `docs/TASKS.md` に記述する
- タスクが進行・完了したら、都度 `docs/TASKS.md` を更新する
- ステータスの凡例：`[ ]` 未着手 / `[→]` 作業中 / `[✓]` 完了 / `[!]` レビュー待ち

### ステアリングファイル: steering/steering-[タスク番号]-[タスク名].md
- 個々のタスクごとにステアリングファイルを作成し、以下の内容を含める
- 今回の作業の要求内容
  - 変更・追加する機能の説明
  - 受け入れ条件
  - 制約事項
- 変更内容の設計
  - 実装アプローチ
  - 変更するコンポーネント
  - データ構造の変更
  - 影響範囲の分析
- タスクリスト
  - 具体的な詳細実装タスク
  - タスクの進捗状況
  - 完了条件

### 作業ログ：docs/LOGS.md
- 各作業の実施内容・決定事項は `docs/LOGS.md` に追記する
- 1エントリは「日付見出し → 実施内容 → 決定事項」の構成で記述する
- 設計判断や仕様の経緯など、コードや差分から復元できない情報を残すことを目的とする

### 設計ナレッジ：docs/KNOWLEDGE.md
- スニペット・ランブック開発のパターンと TIPS を記載している
- 新しいサービスやオペレーションを追加するときは、必ず `docs/KNOWLEDGE.md` を参照して既存パターンに沿うこと
- 新しいパターンや判断基準が生まれた場合は `docs/KNOWLEDGE.md` に追記する

## タスク作業フロー

1. developブランチから作業ブランチを作成する（例：`feature/generator`）
2. 成果物を作成する
3. `docs/TASKS.md` のステータスを `[!]`（レビュー待ち）に更新する
4. ユーザーにレビューを依頼する
5. レビュー承認後、以下を実行する：
   - `docs/TASKS.md` のステータスを `[✓]`（完了）に更新し、進捗サマリーも更新する
   - `docs/LOGS.md` に作業ログを追記する
   - 変更をコミットする
   - developブランチに切り替えてマージする
   - 作業ブランチを削除する

## 成果物のルール

- 明示的に指定しない限り、テンプレートおよび成果物に絵文字は使用しない
- 図はASCIIアートではなく、Mermaidで作図する
