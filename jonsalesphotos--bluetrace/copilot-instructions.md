# BlueTrace Agent 规则

## 语言与事实真源

- 始终使用中文回复，不输出日文。
- 代码中的中文注释和 docstring 使用半角 ASCII 标点。
- 当前代码、当前有效规格和可复现运行结果是事实真源；旧文档、Agent 记忆和 skill 只作为查找线索。
- 宏值、行号、接口状态、功能状态及“某内容不存在”等结论，在据以行动前必须回到当前工作区核实。
- 未提交代码写为“工作区进行中”；未运行的测试、未部署的 APK 和未执行的真机步骤不得写成已通过。

## 执行与授权

- 以最短可靠路径完成用户目标，不用测试数量、检查次数、文档数量或审计轮数代替交付。
- 用户对明确范围作出的修改、清理、定向测试、构建、安装或本地提交授权，在该任务范围内持续有效，不重复确认。
- 仅当目标、范围、不可逆程度、外部副作用或安全边界发生实质变化时重新确认。
- push、merge、release、生产环境操作、真机破坏性写入和范围外删除属于新的授权边界。
- 满足验收标准后停止扩展；范围外问题只记录，不顺手修改。

## 工作区与代码修改

- 先读取一次 `git status` 和相关 diff，区分用户修改与本任务修改；不清理、不覆盖、不回退无关脏文件。
- 代码是真相。skill 和文档中的行号、宏值、设备状态及历史结论必须在当前代码或当前设备重新核实。
- 不为当前需求新增无实际价值的抽象、兼容层、开关或未来扩展；删除被替代的旧路径和无引用资源。
- 设计保持草案/可演进，除非用户明确冻结具体范围；版本基线、测试通过或提交不等于冻结。
- 修改 C/C++ 文件前检查编码；GBK/GB2312 文件按安全转换流程处理。
- 不读取、复制或输出凭据、Token、Cookie、私钥、登录信息、会话记录或个人隐私。

## Android、BLE 与真机

- 把已验证的 ADB transport、已安装 APK、App 数据、目标 GATT 和当前测试阶段视为可复用检查点；只重建失效的层级。
- 固定使用 `C:\Users\260164\AppData\Local\Android\Sdk\platform-tools\adb.exe`，不得依赖 PATH 中的其他 ADB，避免不同版本或用户环境启动另一套 server/key。
- 编译阶段不得调用 ADB。只有 APK 构建成功后才进入部署阶段，安装前只允许用固定 ADB 的 `adb devices -l` 做只读预检。
- APK 构建成功后仍必须尝试同轮部署，但只有恰好一个明确目标且状态为 `device` 时，才允许执行 `adb -s <serial> install -r <apk>`；保留 App 数据，不卸载、不清数据。
- 设备为 `offline`、`unauthorized`、无设备，或存在多个未明确设备时，不得猜测目标或改变 transport。必须保留现场并明确报告“APK 构建成功，但安装阻塞”，不得写成部署完成。
- 无人值守流程不得把 `offline` 自动解释为允许 reconnect。只能用 `adb devices -l` 有限等待并轮询既有状态，超时后报告安装阻塞。
- 自动化流程禁止执行 `adb reconnect offline`、`adb reconnect device`、`adb kill-server`、`adb start-server`、撤销 USB 调试授权，以及删除或重新生成 `.android\adbkey`。
- 上述 transport 恢复命令只有在用户针对本次故障明确授权后才能执行；执行前必须说明它们可能重新触发 RSA 握手和 USB 调试授权弹窗。
- 安装成功后必须核对安装命令返回值和设备端 `versionName/versionCode`；不能只凭 APK 构建成功判断部署完成，也不能只凭安装成功替代本次功能验收。
- 不为“清场”机械执行 `am force-stop`、断开 GATT 或重置 ADB。安装 APK 自然结束旧进程时，按正常流程重新启动 App。
- BLE 连接、自动重连、OTA expected-reconnect、generation、owner 和 Runtime 等结论必须结合代码与 `dumpsys`/logcat/UI 证据，不从页面文案反推。
- 真机写入、OTA、删除设备文件、恢复出厂和关机按用户明确范围执行；只读 ADB 检查不得顺带触发设备操作。

## 测试与验证

- 微小改动只运行最小相关检查；一个逻辑批次完成后运行受影响模块测试。
- 优先使用用户面、黑盒或契约验收。新增测试必须对应用户需求、已有缺陷、公开契约或明确回归风险。
- 不为了测试数量增加测试，不复制生产实现到测试，不为了测试创建生产代码中无实际价值的接口。
- 同一代码和环境未变化时，不重复运行完全相同的检查。
- 完整回归通常只在用户要求、最终提交/合并门禁，或公共 API、协议、schema、依赖、构建系统、并发、持久化、OTA 等基础边界发生变化时运行一次。
- Agent 同次修改编写的测试只能作为辅助证据，不能替代编译、真实调用链或用户面验收。

## 项目工作流与文档

- 开工先读 `Docs/context/BlueTrace项目总上下文.md`，再按任务读取对应的 B2A、UWTP、BLE、采集或 OTA 上下文与当前规格。
- 使用 `.agents/skills/bluetrace-project-workflow/` 恢复状态、选择验证层级和处理脏工作区。
- 实质性改动收尾时更新 `Docs/CHANGELOG.md`；任务线推进时更新 `Docs/context/` 对应活文档；架构性变更同步现有设计文档。
- 正式架构/分析文档按项目文档流程维护；普通修复不新建多余报告。
- 文档必须区分当前规则与历史证据；新规则覆盖旧策略时明确标注历史章节不再代表当前行为。

## 提交与交付

- 未经用户明确授权，不提交、推送、合并、发布或上传。
- 用户授权本地提交时：读取一次状态和相关 diff，完成批准范围清理，运行约定的定向验证；只有门禁需要时运行一次完整回归，然后直接提交。
- 最终报告只列实际修改、实际运行的验证、部署对象和仍未验证的边界，不追加新的自检任务。
