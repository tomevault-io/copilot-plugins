## Project Overview

WOM is a turn-based 2D military strategy game. Supports **free-for-all de 2 a 4 jugadores** (`MAX_PLAYERS = 4` en `wom/core/worldmap.py`): en un jugador es el humano + hasta 3 IAs (cada una con su nivel), sin equipos ni alianzas (cada jugador es independiente; gana el último en pie / el de más banderas o territorio). El núcleo, la IA y las condiciones de victoria ya eran agnósticos a la cantidad de jugadores; mapgen reparte un fuerte inicial por jugador (2: bandas opuestas; 3-4: esquinas) y los colores/banderas por dueño llegan hasta 4 (rojo/azul/verde/amarillo en `theme.py`). **El multijugador en red también es de hasta 4 jugadores** (topología estrella: el host es la autoridad y hace de relay; los clientes solo hablan con él). The game design lives in `idea.md` and the full technical specification in `docs/especificaciones.md` — both in Spanish. The user communicates in Spanish; respond, document, and write docstrings in Spanish. Code identifiers are in English.

**Stack (decided)**: Python 3.13 + pygame-ce, JSON for config and savegames, pytest, PyInstaller for distribution (Windows + Linux + macOS; PyInstaller can't cross-compile, so each build runs on its own OS — WSL2 or CI).

## Commands

The virtualenv is `.venv\` (already created, pygame-ce and pytest installed).

```powershell
.venv\Scripts\python.exe -m pytest tests -v          # run all tests
.venv\Scripts\python.exe -m pytest tests/test_x.py::test_name  # single test
.venv\Scripts\python.exe main.py                     # run the game (pygame window)
.venv\Scripts\python.exe main.py --headless --seed 42            # AI vs AI console game
.venv\Scripts\python.exe main.py --headless --debug-ai           # log AI decisions
.venv\Scripts\python.exe tools\gen_placeholders.py   # regenerate placeholder PNGs
.venv\Scripts\python.exe tools\screenshot_m2.py      # render a game frame to docs/screenshot_m2.png (no window)
.venv\Scripts\python.exe tools\screenshot_menu.py    # render the 3 menu views to docs/screenshot_menu_*.png
.venv\Scripts\python.exe tools\simulate.py --games 30            # AI balance simulation (--detail for per-game)
.venv\Scripts\python.exe tools\llm_client.py --provider ollama --model gemma3   # LLM joins a hosted MP game as a net client
```

Scripts in `tools/` need the project root on `PYTHONPATH` (`$env:PYTHONPATH='D:\dev\WOM'`); `main.py` and pytest do not. UI tests run headless via `SDL_VIDEODRIVER=dummy` (set inside the test files).

## Architecture

Strict three-layer separation — **`wom/core/` must never import pygame** (enforced by `tests/test_smoke.py::test_core_does_not_import_pygame`):

- `wom/core/` — pure game logic: map + random generator (`worldmap.py`, `mapgen.py`), armies (`army.py`), turn engine (`game.py`), auto-resolved battles (`battle.py`), real-time tactical battle model (`tactical.py`), victory conditions (`victory.py`), config loading (`config.py`). Runs headless for tests and mass AI-vs-AI simulation. **`run_turn` está descompuesto** en `begin_turn(orders)` (aplica órdenes + mueve, devuelve la cola de batallas), `resolve_one_battle(a, d, result=None)` (resuelve una batalla; `result=None` ⇒ `resolve_battle` determinista, o aplica un `BattleResult` ya armado) y `finish_turn()` (captura/producción/recuperación/victoria); `run_turn` = la suma de los tres y es el invariante determinista (red/headless/IA). La UI single-player conduce las piezas por separado para intercalar el zoom de batalla. **`tactical.py` (sin pygame)** es el modelo del combate en tiempo real: descompone cada ejército en fichas (con tropas exactas para mapear bajas), las mueve/ataca por `step(dt)` sobre un campo propio (con muralla+puerta si el defensor está en fuerte), y `to_battle_result()` traduce el estado final a un `BattleResult` que el core aplica vía `resolve_one_battle`. NO interviene en el camino determinista; es una capa de UI con RNG independiente (no toca `Game.rng`). El balance táctico vive en `data/config/game.json` → `batalla.tactico`. The map generator paints coherent features over plains (mountain chains as directed walks, forest blobs grown from seeds, lakes, and a river with passable fords every few tiles) targeting `TERRAIN_TARGETS` proportions; connectivity is still flood-fill-verified with retries. Sobre esa base talla tres variantes "livianas" (`_paint_edge_variants`, proporciones en `EDGE_TARGETS`): bosque ralo (`FOREST_LIGHT`/`forest-less`, costo 1, sin penalidad de movimiento pero estorba a caballero/arquero y cubre al partisano) en los bordes de los bosques y suelto; colina (`MOUNTAIN_LIGHT`/`mountain-less`, costo 2, leve para todos, ventaja de combate solo de arquero y partisano) alrededor de las montañas y ocasional; y pantano (`MARSH`/`marshes`, costo 3 salvo partisanos) **solo en la llanura pegada al agua** (su crecimiento se confina a la banda costera y `_drop_orphan_marshes` limpia los que queden sin agua adyacente tras colocar sitios). El costo de movimiento es por-ejército: `costo_terreno` (game.json) más `costo_terreno_clase` (override por clase, p. ej. el pantano cuesta 1 para los partisanos); `army_terrain_costs(base, composition, overrides)` (en `pathfind.py`) calcula el costo efectivo del ejército (máximo por clase presente = ritmo de la clase más lenta) y lo usan el motor de movimiento, la IA, el path del humano y el LLM. Los bonus de combate por terreno viven en `classes.json` → `bonus_terreno`.
- `wom/ai/` — AI players. Same interface as a human player: `decide_orders(game) -> list[Order]`. The three difficulty levels share one codebase (an objective-scoring engine: capture/attack/defend/resupply/garrison, discounted by distance/horizon) and differ only in weights and capability flags from `data/config/ai.json` (`agrupa`, `coordina`, `evita_peligro`, `divide` are dificil-only; `fusiona` is medio+dificil). Two key additions keep the AI from abandoning forts and let it reorganize like a human: a **garrison** objective (`peso_guarnicion`) makes an army on its own frontier fort — enemy within `GARRISON_RADIUS` — value staying, and pulls a free army to an undefended frontier fort; and the AI emits the same **reorganization** orders the human does (but applied through the normal orders flow, not immediately): `MergeArmyOrder` consolidates two adjacent weak rear armies (`fusiona`), `SplitArmyOrder` leaves a garrison and detaches a mobile force from a big army on a frontier fort (`divide`). Each AI also gets a **personality** at game start (agresivo/estratega/moderado, defined in `ai.json` under `personalidades`), chosen deterministically from the seed by `choose_personality(seed, player_id, names)`: it does NOT change the level's skill (horizon/agrupa/coordina/evita_peligro), only modulates character by multiplying weights (`mult_agresividad`, `mult_peso_economia`, `mult_peso_defensa`, `mult_peso_guarnicion`, `mult_umbral_ataque`) and can toggle `fusiona`/`divide`. Balance is validated with `tools/simulate.py` (mass AI-vs-AI, alternating sides); keep dificil > medio > facil when touching AI params. **`tactical_ai.py`** (`TacticalAI`) conduce al bando rival durante el zoom de batalla **según el nivel de su ejército** (`TacticalAI.for_level(owner, level)`, params en `ai.json` → bloque `tactico` por nivel: `prio_rango`/`intervalo`). Todas las fichas empujan al enemigo más cercano (sin estancamiento); la habilidad del nivel está en la selección de blanco: prioriza enemigos de alta amenaza (ataque/defensa alto = arqueros/caballería) dentro de `prio_rango` (facil 0 → sin priorizar; dificil amplio + reasigna rápido). También elige su **formación de despliegue** con `TacticalAI.plan_formation(battle)` según su composición (`formations.recommend`); facil despliega siempre en línea, medio/dificil eligen la conveniente. `GameScreen` le pasa a `BattleScreen` el nivel del jugador rival de esa batalla.
- `wom/ui/` — the only package allowed to import pygame. Produces the same `Order` objects as the AI. Army reorganization is the exception to the orders flow for the human (immediate, outside turn phases — the AI does the same reorganizations through `Merge/SplitArmyOrder` in the normal orders flow instead): Shift+click on two adjacent own armies opens a per-class transfer modal that starts at "Todo" (classic full merge) and calls `Game.transfer_troops`; the HUD "Dividir ejército" button (or D key) opens the same kind of modal and calls `Game.split_army` (new army spawns on a free adjacent tile with no army/fort/town, inherits XP/food, both halves keep ≥1 troop). Both modals are `TroopPicker` in `wom/ui/dialogs.py` (−/+ per class, ×10 with Shift, "Todo"/"Nada", caps at class availability and a global cap). The map view has a camera (`wom/ui/camera.py`, pure Python, unit-testable): mouse wheel zooms in discrete levels anchored at the cursor (level 0 always fits the whole map centered); when zoomed, moving the mouse to the window edges pans (`Camera.edge_pan`, called once per frame from `GameScreen.draw` with the full window as bounds, so the real right edge — not the map/HUD boundary — activates it) and middle-mouse drag grabs the map (view-only, works during animations too); the renderer caches scaled `Assets` per zoom level, clips drawing to visible tiles, and `GameScreen.draw` sets a surface clip on the map area so the zoomed map never paints over the HUD. Path drawing is a "hand-drawn" stroke: Chaikin-smoothed curve with an arrowhead at the destination (`wom/ui/pathline.py`, pure). While tracing a path, double-clicking the destination confirms the route and releases focus (same as clicking the army itself). End-of-turn movement is animated in three phases (march → battle clash → retreat): the core records each army's traversed tiles in `Game.last_moves`, battle pairs in `Game.last_clashes` and who retreated in `Game.last_retreats` (transient, like `last_battles`, not serialized) and `wom/ui/animation.py` (pure Python, no pygame — unit-testable) interpolates them — during the clash both sides lunge at each other with a flash at the contact point, and retreat steps animate only after the clash. The battle result is *revealed* only when the clash ends (`TurnAnimation.result_revealed`): until then combatants show their pre-battle troop counts and the renderer hides this turn's crosses (`hide_new_crosses`); `GameScreen.end_turn` snapshots armies pre-turn so dying armies animate before vanishing (they disappear when their clash ends). The same module computes the spawn-highlight rings that mark the player's initial army during the first seconds of a new game (turn 0 only; dismissed on selection or first end-of-turn). **F1 abre una ayuda visual rápida** (`wom/ui/help_overlay.py`, `HelpOverlay`): modal por encima de todo (incluidos los demás modales y la animación), que `GameScreen.handle_event` atiende antes que nada y dibuja al final de `draw`. Lee los datos en vivo (`game.classes`/`config`/`victory_mode`) — tabla de tropas con vel/atq/def + "brilla en"/"vence a" derivados de `bonus_terreno`/`bonus_vs`, leyenda de terreno con costos, sitios, modo de victoria activo y pasos de "por dónde empezar". Muestra los **sprites reales** (los mismos PNG del mapa) en vez de cuadros de color, cargados con `assets.load_scaled(name, size)` (helper que escala un sprite a un tamaño arbitrario, con el mismo fallback que `Assets`) y cacheados en el primer dibujo. ESC/F1/clic la cierran. Es la versión corta de la guía completa `docs/como_jugar.md`. **Zoom de batalla (`battle_screen.py`, `BattleScreen`)**: en partida individual (nunca en red), tras `begin_turn` cada batalla del humano abre un modal "¿Dirigir batalla (Z) / Auto-resolver (A)?" (`GameScreen._tactical_prompt`/`_advance_tactical_queue`); las de IA-vs-IA se auto-resuelven sin preguntar. "Dirigir" abre `BattleScreen` (modal de pantalla completa que `GameScreen` conduce vía `handle_event`/`update`/`draw`): render del campo táctico con sprites reales **enmarcados en el color del jugador dueño** (rojo/azul/verde/amarillo) + conteo de tropas. Dibuja un **fondo según el escenario** con horizonte (cielo arriba, terreno abajo) y el campo de juego ubicado en el terreno: `fondo-batalla-terreno.png` en **campo abierto** (`HORIZON_OPEN` 0.40, pradera) y `fondo-batalla-fuerte.png` en el **asalto a fuerte** (`HORIZON_FORT` 0.33; muralla+puerta ya dibujadas, no se pintan las celdas grises). Las tropas escalan por **profundidad** (0.8 lejos/arriba → 1.0 cerca/abajo, pseudo-3D barato; se pintan de atrás hacia adelante) con disco translúcido del color del dueño. En el fuerte, `_castle_layout` posiciona muralla/puerta/zonas (atacante en el campo izquierdo, defensor en el patio) calibradas al dibujo, y un **shear de perspectiva** (`SHEAR_FORT`, en `to_px`/`to_cell`) inclina la grilla del modelo —arriba/lejos corre a la derecha— para alinear patio y muralla de colisión con la vista angulada del fuerte (`to_cell` invierte el shear, así los clics siguen siendo correctos). Si falta un asset, degrada al render por celdas. arranca en una **fase de preparación** con cuenta regresiva (10s; las fichas del humano empiezan en "aguantar", no atacan solas) que inicia el combate al llegar a 0 o antes con Espacio/botón "Comenzar". Durante la cuenta el jugador elige una **formación de despliegue** con las teclas 1/2/3/4 — línea/clásica/compacta/en V — que reordena sus tropas (`wom/core/formations.py`, puro y determinista, vía `TacticalBattle.set_formation`; por defecto línea, también para ejércitos chicos); el panel de la cuenta muestra el selector con la activa resaltada y la IA del rival aplica la suya. Luego: selección con clic (una unidad) o caja (grupo), órdenes con clic derecho (mover/atacar) + H (aguantar) + A (todas); los **arqueros** disparan a distancia con efecto de flecha; botón "Auto-resolver", y al terminar aplica el `BattleResult` con `resolve_one_battle`. El ritmo del combate lo fija `batalla.tactico` (`escala_dano`/`escala_velocidad`). "Auto-resolver" usa el camino determinista. Tras procesar todas las batallas, `finish_turn` + la animación de recap normal.
- `wom/ui/editor_screen.py` — **editor de mapas/escenarios** (v0.5.0): misma forma que `GameScreen` (`handle_event`/`draw`/`wants_menu`/`capturing_text`). Mantiene un `Game` interno como buffer de edición (mundo de pura pradera vía `Game.from_setup`) y **reutiliza `MapRenderer`** para el lienzo; tras pintar terreno llama `MapRenderer.refresh_terrain()` (recomputa el autotiling de agua en vivo — antes se calculaba una sola vez en `__init__`). La sidebar es una paleta: terreno (los 6 `Terrain`), sitios (fuerte/pueblo), tropas (ejército) y borrador, aplicados con el **dueño** activo (Neutral/J1…J4, hasta `MAX_PLAYERS`); al guardar, la cantidad de jugadores del escenario la fijan los dueños presentes en el mapa (`_build_doc`: 2 bandos → 2 jugadores, 4 → cuatro); más menú Nuevo (tamaño preset → lienzo en blanco), **Datos del escenario**, Guardar / Guardar como…, Cargar (`ListModal` sobre `list_maps`), Generar aleatorio (confirma; usa `generate_map`) y Volver. **Guardado estilo editor**: recuerda el archivo en edición (`current_path`) y su metadata (`doc_meta`/`doc_image`); "Guardar" sobreescribe ese `.wom` (o abre el formulario `SaveForm` —título/descripción/victoria/IA/imagen— la primera vez), "Guardar como…" crea uno nuevo (nombre derivado del título), Cargar pasa a editar ese archivo y Nuevo lo descarta; el sidebar muestra `Editando: <nombre>` y `Título: <título>`. **El botón "Datos del escenario"** abre el mismo `SaveForm` pero en modo metadata (`_form_mode="meta"`): "Aplicar" vuelca título/descripción/victoria/IA/imagen en `doc_meta`/`doc_image` **sin guardar** (el próximo "Guardar" los persiste), para editar la metadata como parte de la edición y no solo al guardar. La **imagen se elige con el botón "Elegir imagen…"** del `SaveForm`, que abre el diálogo nativo del SO (`wom/ui/filedialog.py` → `pick_image`, tkinter con import perezoso y degradación a None/ingreso manual si no está); el diálogo solo completa la ruta del archivo a importar y el `SaveForm` muestra una miniatura de la imagen actual o la recién elegida. La imagen **no se referencia por ruta: se importa a bytes** (`_read_form_meta` → `Path(...).read_bytes()` → `doc_image`) y queda incrustada dentro del `.wom` al guardar (`image.png` en el ZIP); dejar el campo vacío conserva la ya cargada. Clic de tropas sobre un ejército existente abre `TroopPicker` para editar su composición. Las operaciones de edición (`set_terrain`/`place_site`/`place_army`/`erase_tile`/`new_blank`) mutan el buffer y se testean headless.
- `wom/persistence/` — JSON savegames in `saves/` (`savegame.py`: `save_game`/`load_game`/`list_saves`/`save_info`; all take an optional `directory`, which tests use with `tmp_path`). A savegame stores `format_version`, timestamp and `Game.to_dict()` — including the RNG state and each player's `ai_level` — so a loaded game continues deterministically. Balance config is re-read from `data/config/` on load, never stored. User preferences (music) live in `settings.py` → `settings.json` at the project root (gitignored), saved on every change. **Mapas y escenarios compartibles** viven en `scenario.py` (v0.5.0; **must not import pygame**, in the smoke test; full design in `docs/escenarios.md`): un contenedor `.wom` = ZIP con `scenario.json` (el *setup inicial* — `WorldMap.to_dict()`, tropas sembradas como `army_specs`, jugadores y metadata: título/descripción/`victory_mode`/`ai_level`) + `image.png` opcional. NO es un savegame (no lleva RNG/turno): `build_game(doc)` → `Game.from_setup(world, players, army_specs, victory_mode)` arranca una partida nueva en turno 0. Mismo formato para las dos cosas, distinguidas por tener título o no: un **escenario** (con título; se juega con la IA/victoria que trae) y un **mapa** (sin título; se juega como partida nueva eligiendo IA/victoria). API: `save_scenario`/`load_scenario`/`scenario_info` (lee solo el JSON, sin extraer la imagen)/`list_maps`/`build_game` + el dataclass `ScenarioDoc`. La imagen viaja como bytes crudos (la UI los convierte a Surface). Carpetas: `BUNDLED_SCENARIOS_DIR = data/scenarios/` (distribuidos con el juego) y `MAPS_DIR = maps/` (lo que guarda el editor y comparte el usuario; gitignored).
- `wom/net/` — multiplayer (human vs human over LAN, **2 a 4 jugadores**; **must not import pygame**, in the smoke test). Full design in `docs/multiplayer.md`. Topología **estrella: el host (jugador 0) es la autoridad y hace de relay**; los clientes solo hablan con él. Methodology: **deterministic lockstep** — todos los nodos corren el mismo `Game.run_turn` sobre el mismo conjunto de órdenes + seed. Por turno cada cliente manda sus `Orders` al host; el host las junta con las propias, **valida que cada uno toque solo lo suyo**, y reparte el conjunto completo (`TurnOrders`) a todos; como todos aplican el bundle idéntico, el lockstep no puede divergir por el orden de llegada. `protocol.py` (mensajes + framing por longitud, `FrameDecoder`; `GameSetup` lleva `human_id`, `TurnOrders` el bundle, `Lobby` el roster), `transport.py` (`Connection` con hilo lector; `Server` acepta hasta `max_clients`; `connect`), `session.py` (`HostSession` multi-conexión: handshake, asigna ids 1..N-1, espera a todos, arma el setup con cada `human_id`, arbitra el arranque y relaya órdenes/hash/chat/StateSync; `ClientSession` sigue al host), `orders_codec.py`, `state_hash.py`, `config_fingerprint.py`, `rules.py` (`MatchRules`), y `lockstep.py` (`NetGame`: el host junta+reparte+resuelve, los clientes corren el bundle recibido; cada cliente manda su `Hash` y el host resincroniza al que diverja con `StateSync` → `Game.load_state` in-place). La UI lee el roster de la sesión cada frame. UI: `wom/ui/multiplayer_screen.py` (menú "Multijugador" → hub/crear/conectar/sala; en crear se elige la **cantidad de jugadores** 2..`MAX_PLAYERS` y la sala espera a que se conecten todos; emite `NetGameStart`) y `GameScreen(net=…)` (la AI se reemplaza por las órdenes de los rivales; la reorganización del humano se **difiere como orden** en red; reloj de turno; chat + indicadores en el sidebar; guardar deshabilitado). **Caída/reconexión de jugadores:** si un cliente se cae, el host NO termina la partida — emite `PlayerLeft`, deja el slot reservado (`HostSession._absent`) y la **IA lo controla** (`NetGame.ai_factory` en el host genera sus órdenes y las mete en el bundle; los clientes las reciben ya hechas, sin romper el lockstep). El `Server` sigue aceptando conexiones durante la partida; cuando el jugador **vuelve a conectarse** el host le reasigna su mismo id, le manda el **estado vivo** (`GameSetup` + `Start`, vía `live_state_provider`) y retoma su lugar (`PlayerRejoined`, la IA lo suelta). Solo la caída del **host** (la autoridad) termina la partida para los clientes. Determinism is the load-bearing invariant — verificado turno a turno por `tests/test_net_lockstep.py` (2 y 4 jugadores, más toma por IA y reconexión).
- `wom/llm/` — LLM-controlled player (**must not import pygame**, in the smoke test). Full design in `docs/llm.md`. An LLM plays WOM as a regular **net client** (not an MCP server: that would invert control and clash with the turn-based lockstep). `LLMPlayer.decide_orders(game) -> list[Order]` has the **same signature as `AIPlayer`**, so it's a drop-in (net rival, single-player AI, or local benchmark). Per turn it builds a textual board view (`observation.py`: ASCII map + entity lists, enemies shown only by position/total), asks the model for a JSON array of **high-level intentions** (`actions.py`: move/create/merge/split/transfer/wait — NOT raw paths; it computes routes with the core's Dijkstra and validates owner/adjacency/reachability, dropping invalid actions with a reason), and parses tolerantly (`agent.py`: handles fenced/prose-wrapped JSON, retries once, then passes the turn). Backends (`backend.py`, stdlib `urllib` only, no SDKs): `OpenAICompatible` covers **Ollama + LM Studio + OpenAI**; `Gemini`; `Anthropic` — chosen by `make_backend(BackendConfig)`, API key from env. The system prompt (`prompt.py`) is generated from the live config (classes, victory mode). Entry point `tools/llm_client.py` connects to a human-hosted game (Multijugador → Crear). The LLM's non-determinism stays **outside** the simulation — it only produces orders; both peers still run the same `run_turn`. Tests: `tests/test_llm.py` (units), `tests/test_llm_net.py` (full loopback game in sync).

Music (`wom/ui/music.py` + `music_overlay.py`): `MusicPlayer` builds a playlist from the settings folder (default `data/music`, mp3/ogg), starts on a random track, and advances via `MUSIC_END_EVENT`. The M key toggles a modal player overlay handled at the app-loop level (above any screen); the menu's Opciones mode configures it through the player's setters (each applies and persists immediately). Everything degrades to silent no-ops when the mixer or files are unavailable (headless tests fake `wom.ui.music.mixer`).

Key invariants:
- All randomness goes through the game's seeded `random.Random` (`Game.rng`) — battles and map generation must be deterministic given a seed (replays, tests).
- Game balance lives in `data/config/*.json` (unit classes, battle thresholds, AI weights), never hardcoded.
- Turn phases run in fixed order (see `core/game.py` docstring): orders → movement → battles → capture → production → recovery → victory check.
- Fort production accumulates in `Fort.reserve`; troops enter the map only via a voluntary `CreateArmyOrder` (or the initial spawn). Production order among a player's forts rotates by turn so captured forts also produce when food is scarce. An army parked on its own fort auto-resupplies from the reserve up to `max_army_size` (food refill costs player stock); an army parked on an own town refills food directly, without touching the stock. Capturing a fort destroys its reserve. Each player's cumulative losses are tracked in `Player.troops_lost` (serialized, shown in the HUD).
- Placeholder asset sizes are a contract with future final art: tiles 64×64, units 48×48, icons 32×32 (see `tools/gen_placeholders.py`). The script writes `_<name>.png` always (placeholder reference) and `<name>.png` only if missing — running it never overwrites installed final art. Water uses autotiling (`wom/ui/tiling.py`, pure): 15 shore variants covering all 16 coast combinations (`water_n/s/e/w`, corners `water_ne/nw/se/sw`, channels `water_ns/water_ew`, U-shapes `water_u_n/s/e/w` named by the open side, `water_single`), chosen per tile by which orthogonal neighbors are land. Bridges (`Terrain.BRIDGE_H/V`, passable) are built by mapgen after all water is painted and extend shore-to-shore — a bridge never ends in water; they count as water for shoreline purposes. For movement they are single-axis tunnels: `WorldMap.can_step` rejects lateral entry/exit (BRIDGE_H connects only east-west, BRIDGE_V only north-south) and `neighbors()` enforces it for pathfinding, retreats and the mapgen connectivity check.

**Estilo "pergamino vintage" del mapa** (todo cacheado, sin costo por frame; parámetros en `theme.py`): los tiles secos y de agua se *envejecen* al cargarse en `Assets` (`_age`: desatura hacia gris + multiply sepia; los overlays transparentes —puentes, esquinas de agua— solo se tiñen con `_tint`). Para romper la repetición, de cada terreno seco se hornean `TILE_STYLE_VARIANTS` variantes (solo **espejo horizontal** — el vertical invierte el sombreado de los dibujos; `FLIP_COMBOS` en `texture.py`) y el renderer elige una por tile con un **hash determinista de `(x, y)`** (`wom/ui/texture.py`, puro; **nunca usa `Game.rng`**, así la simulación sigue determinista). El jitter de brillo por tile (`TILE_BRIGHTNESS_JITTER`) viene en 0: un brillo distinto por celda dibuja la grilla en las zonas uniformes. Para fundir los terrenos secos hay un **autotiling de borde** análogo al del agua (`tiling.py` → `TERRAIN_PRIORITY`, `dry_edges`/`dry_corners`: el terreno dominante derrama su textura, recortada por máscaras `edge_mask`/`corner_mask` rotadas, sobre el vecino de menor prioridad). `MapRenderer.refresh_terrain` precomputa, además de la costa del agua, esos bordes secos y los **contornos de tinta** (`ink_group`: segmentos ondulados entre grupos cartográficos —costa, bosque, montaña, pantano—); `draw` aplica al final una pasada de **papel + viñeta + chrome** (`_draw_chrome`: marco de tinta `MAP_FRAME` + rosa de los vientos `compass.png` en una esquina; overlays cacheados por tamaño de área, recortados al mapa). Como todo cuelga de `refresh_terrain`, el editor re-estiliza en vivo por pincelada. Assets nuevos generados por `gen_placeholders.py`: `paper.png`, `edge_mask.png`, `corner_mask.png`, `compass.png` (el usuario puede reemplazarlos por arte fino sin tocar código).

## Roadmap status

All v1 milestones (M1–M6, defined in `docs/especificaciones.md` §8) are **done** and tested: core + headless (M1), playable pygame UI (M2), three validated AI levels (M3), menu + savegames (M4), gameplay/presentation polish — cover art menu, army merging, music, sound/video options (M5), and distributable builds (M6). `main.py` opens the menu (`wom/ui/menu_screen.py`); in-game saving via HUD button or G key, ESC asks for confirmation and returns to the menu. Post-v1 added multiplayer (v0.4.0), the **map editor + scenarios** (v0.5.0) y el **zoom de batalla en tiempo real** (v0.6.0): el único feature del diseño original que faltaba; el jugador puede dirigir cada batalla propia en un mini-RTS o auto-resolverla (solo partida individual; en red siempre se auto-resuelve).

Menu flows (v0.5.0, in `menu_screen.py` → consumed by `app.py`): the main menu added **"Escenarios"** (lista `.wom` con título → modo `scenario_intro` que muestra título/descripción/imagen y emite `ScenarioChoice` → `scenario_game` honra la IA/victoria del `.wom` y, además, monta un `ScenarioIntroOverlay` —modal con título/descripción/imagen que `GameScreen` muestra **sobre el mapa al iniciar la partida** (`wom/ui/scenario_intro_overlay.py`, in-game; se cierra con clic/Enter/ESC y traga el input mientras está visible)—) y **"Editor de mapas"** (acción `"editor"` → `EditorScreen`; el loop lo trata como pantalla propia, vuelve al menú con `wants_menu`). En "Nueva partida" se elige la **cantidad de rivales IA** (`Rivales (IA)`, 1..`MAX_PLAYERS-1`) y el **nivel de cada uno** por separado (`NewGameChoice.ai_levels` es una tupla de niveles; `map_params()` deriva `n_players = 1 + len(ai_levels)` y sube `n_forts` para que haya un fuerte inicial por jugador). También hay un selector **Origen del mapa: aleatorio / archivo**: en "archivo" se elige un `.wom` (modo `pick_map`) y `NewGameChoice.map_path` hace que `new_game` use su terreno+tropas; ahí la cantidad de jugadores la fija el mapa (los dueños presentes, vía `_players_for_map`) y los niveles elegidos se reparten entre los rivales ("Cargar mapa").

Builds: `pyinstaller wom.spec` produces `dist/wom/` (onedir, windowed exe). All resource paths go through `wom/paths.py`: read-only `data/` resolves into the bundle (`sys._MEIPASS`) when frozen, writable `saves/` + `settings.json` sit next to the executable. The executable icon comes from `data/assets/icon.ico` (Windows) or `icon.icns` (macOS), pre-generated from `icon.png` by `tools/gen_icon.py` (needs Pillow, dev-time only) so the build itself doesn't depend on Pillow; the spec selects the format per platform and falls back to the PNG. Linux exes don't embed an icon. `.github/workflows/build.yml` tests and builds Windows + Linux + macOS artifacts on `v*` tags or manually (PyInstaller can't cross-compile; each platform builds on its own runner — the macOS one is `macos-latest`, arm64/Apple Silicon only).

Battle semantics: combat triggers when an army tries to *enter* an enemy's tile — armies never share a tile; each side fights from its own tile (own terrain bonus, defender gets fort/town bonus). Attacker classes with `ignora_bonus_fort` in `classes.json` (the arquero) cancel the defender's fort bonus for their own contribution — they fight the fort's garrison 1:1. Losers/retreaters fall back one tile, except an army standing on a fort: it never retreats (retreat only happens in open field), so a fort holder must be destroyed to dislodge it. En el **zoom de batalla** estas reglas se replican: el bando se "quiebra" (se retira) al caer bajo `umbral_quiebre`, salvo el defensor en fuerte (pelea hasta morir), y el arquero (`ignora_bonus_fort`) dispara por encima de la muralla anulando su bonus.

Site flags are owner-colored: `flag_red.png` (player 0), `flag_blue.png` (player 1), `flag.png` (gray, neutral); the mapping lives in `theme.flag_icon(owner)`.

The menu draws over `data/assets/title.png` (cover art with a central parchment scroll); the scroll's usable area is `SCROLL_AREA` in `menu_screen.py` as image fractions — keep them in sync if the art changes. Without the asset the menu falls back to the flat background.
