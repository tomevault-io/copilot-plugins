# Repository Guidelines

## Project Structure & Module Organization

`index.html` mounts the application and loads `src/hantz-scene.js`, the active Three.js scene. Global UI styling lives in `src/style.css`; `src/main.js` is the earlier prototype and should not be treated as the current entry point. Runtime images and textures belong in `public/assets/`. Design inputs, decisions, and generated references live under `design/`: use `design/scene-spec.json` for structural geometry, `design/design-spec.json` for structured design data, `design/consistency-lock.json` for the final detail lock, `design/reference-set.json` for audited camera-bound images, `design/asset-manifest.json` for asset provenance, `design/input/` for source material, and `design/concepts/` for visual references. `tmp/review/` is working output, while `dist/` is generated by Vite.

## Build, Test, and Development Commands

- `npm ci`: install the exact dependency versions from `package-lock.json`.
- `npm run dev`: start the Vite development server with hot reload.
- `npm run build`: create the production bundle in `dist/`.
- `npm run preview`: serve the production bundle for final inspection.
- `node .codex/skills/floorplan-to-interior-3d/scripts/validate-scene-spec.mjs design/scene-spec.json`: validate dimensions, IDs, rooms, walls, and openings.
- `node .codex/skills/floorplan-to-interior-3d/scripts/enrich-consistency-lock.mjs design/scene-spec.json design/design-spec.json design/consistency-lock.json`: snapshot absolute object transforms, placement rules, and camera frames into every view lock.
- `node .codex/skills/floorplan-to-interior-3d/scripts/stamp-lock-hashes.mjs design/consistency-lock.json`: update scene/design SHA-256 bindings after an intentional source change.
- `node .codex/skills/floorplan-to-interior-3d/scripts/validate-design-package.mjs design/scene-spec.json design/design-spec.json design/consistency-lock.json --require-image-locks`: validate the Stage 2 detail lock and its complete image inventory.
- Add `design/reference-set.json design/asset-manifest.json --require-images` to the previous command to enforce the Stage 3 image gate.

## Coding Style & Naming Conventions

Use native ES modules, two-space indentation, semicolons, double quotes, and trailing commas in multiline JavaScript. Prefer small helper functions over repeated Three.js setup. Use `camelCase` for variables and functions, `PascalCase` for constructors, kebab-case CSS classes, and lowercase hyphenated asset names. Keep stable, descriptive IDs in design JSON. Do not duplicate plan coordinates in JavaScript; update `scene-spec.json` and consume that data.

## Testing Guidelines

No automated test runner or coverage target is configured. Every change must pass the scene-spec validator, the applicable design-package gate, and `npm run build`. Follow the order floor-plan parse -> detail lock -> complete image package -> 3D and final renders. Manually inspect the app at desktop and mobile sizes: confirm a nonblank canvas, loading completion, every locked camera, reference-overlay tolerance, camera controls, view tabs, layer toggles, material and lighting modes, screenshot export, and absence of console errors or UI overlap.

## Commit & Pull Request Guidelines

The repository has no commit history yet, so no existing convention can be inferred. Start with concise imperative Conventional Commit messages, such as `feat(scene): add room camera presets` or `fix(ui): prevent mobile dock overlap`. Pull requests should summarize intent, list affected design/source files, report validation commands, link related work, and include before/after screenshots for visual changes. Explicitly call out geometry changes, assumptions, and design-freeze implications.
