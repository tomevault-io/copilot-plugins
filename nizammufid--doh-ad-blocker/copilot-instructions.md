## What this is (one-liner)

ML-powered automated blocklist generator. Parses DoH/Pi-hole DNS query logs, classifies new ad domains via Random Forest, applies whitelist/FP guards, generates blocklists in 5 formats, auto-pushes to a public GitHub repo that DNS users worldwide subscribe to.

**Production system.** Real subscribers consume the output via `dns.cyberfrost.net` and the published `nizammufid/ad-blocklists` GitHub repo. False positives break random people's internet. Treat changes accordingly.

---

## The two-repo model (read this before anything)

The project lives across **two GitHub repos**:

| Repo | Purpose | Source of truth |
|---|---|---|
| `nizammufid/doh-ad-blocker` (this repo) | **Source code, configs, scripts, docs** | Snapshots from `/opt/doh-ad-blocker` on `cyberfrost.net` |
| `nizammufid/ad-blocklists` (separate) | **Daily-published blocklists** consumed by subscribers | Auto-pushed by `scripts/auto_push.sh` from the server, only `blocklists/*` is committed |

**Server `/opt/doh-ad-blocker/` is currently the canonical environment** — that's where cron runs, where the venv lives, where the model trains, where logs accumulate. This repo is the dev-time mirror; changes here are not live until applied to the server.

The server's `.gitignore` is configured for the `ad-blocklists` repo (ignores everything except `blocklists/`). Don't pull that `.gitignore` here — ours is correct for the source-code repo.

## Operating rules (binding for this project)

These extend the global contract:

1. **Server is canonical.** Code may be edited here, but production runs from `/opt/doh-ad-blocker/`. Pulling state down (this conversation's pattern) is fine; pushing fixes up requires a deliberate sync. Don't assume local-edit and prod-state agree.

2. **Two-repo discipline.** Never push `blocklists/` from this repo. Only `ad-blocklists` publishes blocklists. Keep them decoupled.

3. **FP regression is the safety net.** `scripts/fp_regression.sh` is zero-tolerance for the curated allowlist (anudeepND). Never disable it, never lower the threshold to "just push this one through". A misclassified popular domain → thousands of users' internet breaks.

4. **Diff guard is also a safety net.** `scripts/metrics.sh` aborts pushes on >10% day-over-day list changes. Don't bypass via `METRICS_DIFF_TOLERANCE_PCT=99` casually — first investigate WHY the list shrank/grew that much (usually a broken upstream or model regression).

5. **`data/`, `models/`, `logs/`, `blocklists/` are runtime artifacts.** Gitignored. Never commit them, never edit them locally expecting it to matter — they're regenerated by the server cron each night.

6. **Whitelist additions need a "why" comment.** See `config/config.yaml:whitelist` — entries already have inline comments (e.g. `# *.optimizely.com — A/B testing platform`). Maintain that practice. A future maintainer (probably you) needs to know why each entry exists, otherwise they get pruned and break things.

7. **Credentials handling: SSH keys to the server, never paste passwords/tokens.** A leaked PAT here = supply-chain attack on every blocklist subscriber. (Yes, this happened in the source-import session of 2026-05-09 — see SESSION_LOG.md.)

8. **The build philosophy is *production-tier personal project***: docs are real, decisions get recorded, runbook discipline applies. Not "weekend hacky" — but also not enterprise ceremony. One-maintainer scale.
