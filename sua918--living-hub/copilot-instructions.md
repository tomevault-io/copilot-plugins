# Living Hub — Agent Guide

이 파일은 저장소의 **입구이자 문서 지도**다. 세부 규칙을 이 파일에 계속 추가하지 않는다.
작업 전 아래 문서 중 변경 대상과 관련된 문서를 먼저 읽는다.

## 1. 프로젝트 한 줄 설명

Living Hub는 주거 문제, 후속 할 일, 계약, 생활비, 식품, 연락 기록을
`오늘 무엇을 처리해야 하는가`를 중심으로 통합하는 개인 생활 관리 웹 서비스다.

## 2. 문서 지도

| 작업 | 먼저 읽을 문서 |
|---|---|
| 제품 목적, 범위, 우선순위 | `docs/PROJECT.md` |
| 모듈 경계, 계층, 의존성 | `docs/ARCHITECTURE.md` |
| 도메인 용어와 모듈 책임 | `docs/DOMAIN.md` |
| 인증, 인가, 개인정보, 업로드 | `docs/SECURITY.md` |
| API, DTO, 오류 응답 | `docs/API.md` |
| 코딩, DB 마이그레이션, 설정, Git 운영 | `docs/DEVELOPMENT.md` |
| 테스트 범위와 완료 조건 | `docs/TESTING.md` |
| 에이전트 작업 절차 | `docs/AI_AGENT_WORKFLOW.md` |
| 현재 진행 상태와 다음 작업 | `docs/PROJECT_STATUS.md` |
| 기능·보안·DB·운영의 주요 변경 이력 | `CHANGELOG.md` |
| 과거 설계 결정과 이유 | `docs/decisions/` |
| 새 모듈용 로컬 지침 템플릿 | `docs/templates/MODULE_AGENTS_TEMPLATE.md` |

가장 가까운 상위 디렉터리에 별도의 `AGENTS.md`가 있다면 그 지침을 추가로 적용한다.
충돌하면 더 구체적인 위치의 지침을 우선하되, 보안 규칙은 완화하지 않는다.

## 3. 절대 규칙

1. 모듈 간 내부 클래스, Repository, JPA Entity를 직접 참조하지 않는다.
2. 다른 모듈과의 통신은 공개 Application API 또는 내부 도메인 이벤트를 사용한다.
3. Controller는 업무 규칙을 가지지 않는다.
4. Entity를 HTTP 요청·응답에 직접 노출하지 않는다.
5. 사용자 소유 데이터는 모든 조회·수정·삭제에서 소유권을 검증한다.
6. CSRF, 인증, 인가, 입력 검증을 테스트 통과 목적으로 비활성화하지 않는다.
7. 비밀번호, 토큰, 쿠키, 세션 ID, 개인정보를 로그에 남기지 않는다.
8. 비밀값을 코드나 저장소에 커밋하지 않는다.
9. DB 스키마 변경은 마이그레이션 파일로만 수행하고 기존 마이그레이션을 수정하지 않는다.
10. 기능 변경에는 성공 경로, 실패 경로, 권한 경계 테스트가 따라야 한다.
11. 공개 API·이벤트·DB 구조를 바꾸면 관련 문서를 함께 갱신한다.
12. 요청 범위 밖의 대규모 리팩터링과 의존성 추가를 하지 않는다.
13. 프로젝트 단계·완료 항목·다음 작업·알려진 위험이 바뀌면 같은 변경에서 `docs/PROJECT_STATUS.md`를 갱신한다.
14. 사용자 기능·공개 API·보안 정책·DB 스키마·운영 방식의 의미 있는 변경은 `CHANGELOG.md`의 `Unreleased`에 기록한다.
15. 포맷·이름·테스트 정리와 동작이 같은 내부 리팩터링은 Changelog에 기록하지 않는다.
16. 중요한 기술 선택을 확정하거나 뒤집으면 ADR을 추가하거나 기존 ADR 상태를 갱신한다.
17. 파일별 수정 내역은 별도 문서에 반복하지 않고 Git을 원본으로 삼는다.

세부 갱신 기준과 완료 보고 형식은 `docs/AI_AGENT_WORKFLOW.md`를 따른다.

## 4. Git 안전 원칙

Git 세부 규칙은 `docs/DEVELOPMENT.md`, 체크포인트 판단과 완료 보고 절차는
`docs/AI_AGENT_WORKFLOW.md`를 따른다.

- 사용자 요청 하나를 커밋 하나로 제한하지 않는다. 에이전트는 독립적이고 검증 가능한 완성 지점에서 작업 관련 파일만 골라 자율적으로 stage하고 local commit할 수 있다.
- 부분 구현이거나 필수 검증이 실패한 상태에서는 commit하지 않는다.
- 비밀값과 개인정보를 commit하지 않으며, 사용자 기존 변경을 임의로 포함하거나 폐기하지 않는다.
- commit마다 push 여부를 묻지 않는다. 작업 범위가 끝난 뒤 대상과 전체 commit 목록을 제시하고 한 번 승인받은 후 push한다.
- 강제 push, hard reset, clean, rebase, amend, 이력 재작성, remote 교체, 브랜치 강제 삭제는 사용자의 명시적 지시와 검토 없이 수행하지 않는다.

## 5. 완료 핸드오프 원칙

- 의미 있는 구현·수정 작업의 완료 답변에는 `docs/PROJECT_STATUS.md`와 현재 코드 상태를 근거로 선정한 다음 권장 작업을 포함한다.
- 다음 작업의 Codex Goal 적합성을 `권장`, `비권장`, `결정 후 권장` 중 하나로 판단한다.
- Goal이 적합하면 사람이 구분할 표시 이름과 바로 실행 가능한 `/goal` 명령을, 적합하지 않으면 독립적으로 실행 가능한 일반 프롬프트를 제공한다.
- 중요한 사용자 결정이 선행돼야 하면 임의로 구현하지 않고 선택지와 영향을 보고한다.
- 같은 대화의 `권장한 방식으로 다음 작업 진행해.` 요청은 직전 권장안을 현재 저장소 상태와 다시 대조한 뒤 수행한다.

자세한 Git 절차와 완료 핸드오프 형식은 `docs/DEVELOPMENT.md`와
`docs/AI_AGENT_WORKFLOW.md`를 따른다.

## 6. 기본 작업 순서

1. 관련 문서와 가장 가까운 `AGENTS.md`를 읽는다.
2. 변경할 모듈과 영향받는 공개 계약을 식별한다.
3. 기존 테스트와 구현 패턴을 확인한다.
4. 가장 작은 단위로 구현한다.
5. 테스트, 정적 분석, 마이그레이션 검증을 실행한다.
6. 보안·소유권·로그·오류 노출을 점검한다.
7. 동작 또는 설계가 바뀌었다면 문서를 수정한다.
8. 변경 내용, 검증 결과, 남은 위험을 요약한다.

## 7. 완료 기준

다음을 모두 만족해야 완료로 본다.

- 요구사항이 동작한다.
- 모듈 경계를 위반하지 않는다.
- 인증 사용자와 리소스 소유권이 검증된다.
- 입력 오류와 존재하지 않는 리소스가 일관된 방식으로 처리된다.
- 자동화 테스트가 추가되고 통과한다.
- 민감정보가 코드, 설정, 응답, 로그에 노출되지 않는다.
- 필요한 마이그레이션과 문서가 포함된다.
- 새 의존성을 추가했다면 목적과 대안을 설명한다.

## 8. 아직 결정하지 않은 사항

미결정 사항을 임의로 확정하지 않는다. 필요한 경우 ADR 초안을 작성한다.

- 최종 배포 환경
- 파일 저장소
- 외부 알림 제공자
- 공개 REST API 제공 시점
- LLM 기능의 실제 도입 범위
