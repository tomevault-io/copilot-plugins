## Commands

```bash
swift build                          # debug build
swift test                           # full suite (swift-testing, ~260 tests, sub-second after build)
swift test --filter "TreeActions"    # one suite; also --filter "SuiteName/testFunctionName"
./scripts/package-release.sh         # release .app bundle + zip → dist/ (version from DirWiz/Info.plist)
.build/debug/dirwiz-cli scan <path> [--json] [--min-size N] [--max-depth N] [-q]
.build/debug/dirwiz-cli duplicates|info|benchmark|snapshot|diff <path>
```

CI (`.github/workflows/ci.yml`) runs `swift build` + `swift test` on `macos-15` for pushes to master and PRs.

Release script notes: signs with the first local Apple identity found, else ad-hoc (`DIRWIZ_CODESIGN_IDENTITY` overrides; `DIRWIZ_DIST_DIR` overrides output dir). Grant Full Disk Access to the installed `/Applications/DirWiz.app`, never to `.build` binaries - ad-hoc rebuilds can lose FDA because macOS ties privacy grants to code identity.

## Targets and layering

SwiftPM, swift-tools 6.0, **all targets pinned to Swift 5 language mode** (the test target is not pinned and compiles under Swift 6). macOS 15+. Zero external dependencies - keep it that way.

- `Sources/DirWizCore` - scanner, file tree, duplicate/hardlink detection, analyzers, temporal diff, CLI argument parsing. No UI imports.
- `Sources/DirWizUI` - `AppState` + SwiftUI views + Metal cushion treemap.
- `DirWiz/` (app) and `CLI/` (dirwiz-cli) are executable targets. **The test target can only import DirWizCore and DirWizUI** - logic that needs tests must live in DirWizCore, not the executables (pattern: `CLIArguments.swift`, `TemporalDiffSummary.swift`).

## The file tree - core invariants

`FileTree` (Sources/DirWizCore/Scanner/FileNode.swift) is a flat array of packed `FileNode` structs plus a shared string pool. Everything depends on these rules:

- Nodes reference each other by index (`parentIndex`, `firstChildIndex` + `childCount` = one contiguous child slice). Parent index < child index for any real scan.
- Nodes are appended, never removed - **except `removeSubtree`, which compacts the array and renumbers every index**. Any index held across that call is garbage. That is why:
  - `TreeActions.batchTrash(paths:tree:)` re-resolves each path against the current tree immediately before trashing it; the index-based `batchTrash(nodeIndices:)` is only safe for a single index.
  - After any mutating action, `AppState.invalidateAfterTreeMutation()` (AppState+Analysis.swift) is the single reset point: it clears all index-keyed state (search results, recency factors, temporal-diff arrays) and bumps the treemap layout revision via `scanProgress.publishCounters(forceLayoutRevision: true)`. The treemap only relayouts on tree identity / root index / revision changes - forget the bump and it silently renders stale rects with wrong node indices.
- `FileTree` is `@unchecked Sendable` guarded by an internal mutex. Read through `node(at:)`, `nodesSnapshot()`, `pathBuildingSnapshot()` - do not read `.nodes` directly from concurrent contexts.
- Post-scan analyzers walk snapshots via `FileTree.forEachFileInSnapshot` (single blessed walk with a uniform cancellation cadence) and locate nodes by path components via `FileTree.descendPath`. Do not hand-roll a new whole-tree loop in an analyzer.

## Scanner

`getattrlistbulk` raw-buffer parsing with unsafe pointers (`FilesystemProvider.swift`, hot paths in `FileScanner.swift`) - the parser uses FIXED offsets that depend on `FSOPT_PACK_INVAL_ATTRS` packing every requested attribute, so adding/removing a requested attr shifts every later offset (see the offset constants + parsing contract tests). Symlinks are intentionally skipped. Scans also capture `ATTR_FILE_LINKCOUNT` into the `hasMultipleHardlinks` node flag (`FileTree.linkCountsCaptured` marks the flags trustworthy); hardlink groups auto-populate post-scan/post-mutation via `AppState.refreshHardlinkGroups()` - the Hardlinks tab has no run button. The app path defers bundle sizing to a background pass so first paint is fast; the CLI sizes bundles inline. Env knobs: `DIRWIZ_SCAN_WORKERS`, `DIRWIZ_DEFER_TREE`, `DIRWIZ_SKIP_BUNDLE_SIZES`, `DIRWIZ_BUNDLE_WORKERS`, `DIRWIZ_BULK_BUFFER_BYTES`, `DIRWIZ_NO_WARM_START`. Perf landmine: never `reserveCapacity(count + smallDelta)` on a per-directory/per-item path - it defeats Array's amortized growth and turns scanning into O(n²) (masked below the 500k init reservation, brutal above it; use `reserveNodeCapacity`/geometric growth). Scan-time treemap layouts are deliberately sparse + depth-capped (`ScanTimeLayoutBudget`) so live building doesn't starve the scanner.

**Launch & living view** (waves 6-7): `AppState.restoreOnLaunch()` republishes the cached tree instantly at startup (`staleViewAsOf` drives the sidebar badge and keeps the main pane visible while a refresh runs behind it - ContentView gates on `isScanning && staleViewAsOf == nil`); a cold refresh behind a stale view builds a DETACHED tree and swaps at completion, restoring position via `ExplorationCapture` (path-keyed; indices never survive mutations). Session state (expansion/selection/root) persists per volume via `SessionStateStore`. **Living view is auto-apply now** (living-view-auto-apply, reversing plan 037's "decision 3a: no auto-apply, ever"): FSEvents monitoring auto-starts on every scan completion, and `LiveRefreshPolicy` (DirWizCore, pure + clock-injected like `WarmStartPlanner`) decides when accumulated changes splice themselves in via `applyAccumulatedChanges()` - 2s quiescence, 10s minimum interval, 5,000-changed-dir storm threshold (deliberately the SAME constant as warm start's `unknownDirectoryCountBackstop`, with a test pinning that they match). Guards (pause / scanning / heavy task / temporal-diff overlay) outrank the storm signal and never latch - each tick re-decides, so pending changes apply once a guard lifts. The sidebar Live pill names the current reason; there is no Watch Changes button any more. `SearchView` re-runs its query on `liveRefreshGeneration` because an apply renumbers indices. App cold scans materialize the tree LIVE (immediate mode) - `DIRWIZ_DEFER_TREE` overrides both ways; `ScanProgress` damps early layout bumps until 1,000 files or 20 publishes.

**Warm start** (GUI only; CLI scans stay cold): completed scans persist the tree + FSEvents event id via `TreeCache` (fail-closed binary format - ANY doubt on load returns nil and falls back to a cold scan; any change to `FileNode`'s stored layout MUST bump the cache `formatVersion`). On the next scan, `WarmStart.swift` replays the FSEvents journal since the saved id and `FileScanner.rescanSubtrees` splices only the changed directories into the loaded tree (`removeChildren(of:)` + immediate-mode re-enumeration + `recomputeAggregates()`, which resets non-bundle dir totals then re-sums - never call `propagateSizes()` on an already-propagated tree, it double-counts). Poison flags (MustScanSubDirs/IdsWrapped/RootChanged/Mount), replay timeout, unresolvable paths, or >5k changed dirs all abandon warm and run the unchanged cold path. Equivalence tests (`Tests/SubtreeRescanTests.swift`, `Tests/WarmStartTests.swift`) pin patched-tree ≡ fresh-cold-scan; keep that gate when touching any of this. **Landmine**: the journal-replay stream MUST create with `kFSEventStreamCreateFlagFileEvents` (matching `FSEventsMonitor`'s live-watch stream) - without it, FSEvents can only report at directory granularity, so any file changing directly inside a huge directory gets blamed on that whole directory. On a root-volume ("/") scan this reliably misreports the entire home folder as "changed" (confirmed live: 76% "changed" from ~8 seconds of ordinary background noise), tripping the changed-item-fraction cold-fallback on nearly every launch. `JournalCollector.handleEvents` reduces file-level events to their parent directory (same as `FSEventsMonitor.processChanges`) so `rescanSubtrees` still receives directory targets.

**Firmlinks defeat the `(dev, inode)` guard** - `VisitedDirectories` cannot dedup them, because the two sides report different identities: `stat /Applications` gives the real inode, but the entry `getattrlistbulk` returns while enumerating `/` carries a synthetic firmlink id (`0x0FFFFFFF00000000 + n`). `dev` is identical on both sides, so a `du -x` mount-crossing rule can't catch them either. Unfixed, this both double-counted (`/Applications` and `/System/Volumes/Data/Applications` each fully enumerated) and stranded content (`/Library` reporting 0 bytes with its real 92.6 GB under the Data path) - and which happened was a worker race, so it varied per run. `FirmlinkTable` parses macOS's own `/usr/share/firmlinks` and seeds `VisitedDirectories` with the Data-side paths to skip; `FileScanner.resolveFirmlinkDuplicates` gates it to scans that span both sides (never when rooted at/below the Data volume) and honors `DIRWIZ_NO_FIRMLINK_DEDUP=1`. It fails open - a missing/malformed table means no dedup, never dropped content. **Both** `scan` and `rescanSubtrees` must use it or the warm-start equivalence gate breaks the moment a firmlinked path changes. Parsing landmine: split lines with `whereSeparator: { $0.isNewline }`, not `split(separator: "\n")` - Swift treats CRLF as one grapheme, so the latter silently merges lines.

**Why a scan went cold is never silent** (warm-start-observability): every cold-fallback path - `TreeCache.loadResult`'s `.rejected` case (cache existed but failed to load: corrupt/wrong-version/checksum-mismatched - distinct from `.noCacheFile`, "never scanned"), the planner's own `.coldFallback(reason:)`, and `commitWarmStart`'s mid-patch abandonment (unresolved paths / root-level rescan) - threads a human reason into `beginColdScan`'s `coldFallbackReason` param and `lastScanSummary`. Critically, `restoreOnLaunch` (not just `startScan`) also goes through `loadResult`: it runs on every cold launch and is usually the *first and only* code to see a corrupted cache before its own lookup invalidates the file, so if it used the plain `load()` wrapper the reason would be lost forever with nothing left to explain it later. On `.rejected` it does NOT auto-start a scan (today's empty-launch-state behavior is unchanged) but does set `lastScanSummary` via `ScanSummaryComposer.cacheRejectedAtLaunch`. Any new call site touching `TreeCache.load`/`loadResult` for a scan-adjacent decision must keep this discipline - grep for every caller of the shared primitive, not just the already-obvious ones (this is exactly the gap that shipped once already: `restoreOnLaunch` was missed in the original design, caught only by driving it end-to-end in `LaunchRestoreTests.swift`, not just `startScan`).

`WarmStartHistory` (Scanner/WarmStartHistory.swift) persists the last 20 warm/cold decisions per volume as plain JSON - deliberately NOT `TreeCache`'s fail-closed binary discipline; losing this diagnostic history costs nothing, so a malformed file just reads as empty. Recorded at every `lastScanSummary` write site. Reason strings are logged at `.notice` (not `.info`/`.debug` - those two don't persist to the system log store, so `log show` can't retrieve them after the process exits). In this dev environment specifically, bare `log`/`log show` resolve to a zsh shell builtin that silently no-ops - use `/usr/bin/log show`/`/usr/bin/log stream` explicitly, or the "it's not logging" conclusion will be wrong.

## UI state model

`AppState` and its sub-models (`DuplicateState`, `SearchState`, `NavigationState`, `TemporalDiffState`) are all `@MainActor @Observable`. Background work runs in `Task.detached` and hops back via `MainActor.run` guarded by token counters (`scanToken`, `duplicateToken`, …) - always check the token before writing results so a stale task can't clobber a newer scan. `resetForNewScan()` is the canonical list of per-scan state; new state must be added there.

**Treemap render styles** (`Treemap/CardGeometry.swift`): cushion draws hierarchy with *lighting* (parabolic ridges baked into each leaf's coefficients - costs zero pixels, survives extreme density); cards draw it with *geometry* (rounded corners + gaps, bounded by `CardBudget`). One fragment shader, branching on `CushionUniforms.styleMode` - which was carved out of the old `padding2` so the uniform stride stays 48 and `verifyCushionLayouts()` still covers it. Both styles consume the SAME `SquarifyLayout` output: card radius/gap are computed in the shader from `rectSize`, so the instance buffer is identical and switching style is a pure repaint. **Landmine**: the card inset is a fragment-shader effect only - `SpatialGrid` must keep hit-testing on LAYOUT rects, never inset visual rects, or clicks near a card edge miss and the gaps between siblings go dead (pinned by `CardStyleTests`). Verifying the shader needs an *offscreen Metal render* (`CardStyleRenderTests`), not the repo's headless screenshot technique - `cacheDisplay` does not capture the Metal layer, so a screenshot "diff" of the treemap compares two blank rectangles and passes no matter what the shader does.

**Instance-rebuild cost lives in COLOUR resolution**, not geometry: directory colours walk their children, so re-resolving every instance cost ~70ms of main thread per style toggle on a real volume scan. `CushionRenderer` caches resolved colours keyed on `(colorGeneration, layoutIdentity)` — the view bumps `colorGeneration` for palette/recency/temporal changes and NOT for style, and `layoutIdentity` bumps on every `cachedLayout` replacement. **Both keys are load-bearing**: keying on rect COUNT instead of identity repaints new rects with the previous layout's colours, which ships as a grey wash over the whole map (that exact bug shipped once). Colours are resolved before any culling decision so every layout index has a cache entry. Card culling must stay SUB-PIXEL (`CardGeometry.minVisibleSide`) — culling visible tiles to buy speed punches grey container holes through the map, and the colour cache already bought the speed.

**Folders (card) style borrows three rules from SpaceMonger 1.4** (`seanofw/spacemonger1`, `FolderView.cpp`), and they are the difference between a legible map and confetti: (1) a **subdivide gate** - it only recurses while `w > hmin && h > vmin` (default density row `{32, 24}`, mirrored as `CardGeometry.minSubdivideWidth/Height`), otherwise the folder is ONE block standing in for its contents. DirWiz's layout recurses to a 1pt `minPixelSize`, which is correct for cushions but produces unreadable mush under card decoration, so `CardNesting` collapses below the gate and marks the whole subtree `suppressed`. (2) **Folder chrome is neutral and depth-shaded** (`containerFill(depth:)`, mirroring their `BoxColors[depth & 7]`) - a directory tinted its dominant child's hue competes with the files inside it; extension colour stays on FILES, which is where the meaning is. A COLLAPSED folder keeps its real colour, because it now represents its contents. (3) They steal pixels from children for the title (`y + 12`, `h - 15`); DirWiz's equivalent is `CardGeometry.headerHeight`. **Any chip/label filter must call `headerHeight(width:height:)` itself, never approximate it** - a container between 40 and 56pt tall reserves no strip, and a chip drawn there lands on its first child. Suppression means hit testing must resolve upward: `visibleAncestor(of:)` walks parents until it finds a drawn node, while `SpatialGrid` still indexes full layout rects so card gaps stay clickable.

**Overlays consume DRAWN geometry, not layout geometry.** `updateInstanceBuffer` publishes `onLayoutUpdate(displayRects)` with the post-nesting rects, because Folders (card) style insets children via `CardNesting` — labels or selection borders positioned from `cachedLayout` land in the wrong place, and the folder-name chip collides with the first child's label. Hit testing is the exception and stays on raw layout rects (`SpatialGrid`, built inside the renderer). Folder-name chips render only in Folders style, where the geometry reserves a header strip for them; cushion children fill their parent edge to edge, so a chip there would cover a child.

Tree-table column geometry comes from the shared `TreeTableColumns` constants (TreeRow.swift) - header and rows must consume the same values or columns drift per row.

## Destructive actions

`InstantDuplicateCandidate.id` is derived from its CONTENT (size + name + sorted paths), never a fresh UUID: the living view re-runs instant grouping after every splice, and a random id detaches an already-answered "not duplicates" result from its row. The Duplicates tab is two-tier: `InstantDuplicateFinder` groups by `(size, case-folded name)` purely in memory (no content reads, ~456 ms release for 1M files) and auto-runs on tab open / scan completion / tree mutation, while the exhaustive `DuplicateFinder` content scan stays behind its button. Instant results are `InstantDuplicateCandidate`, a DIFFERENT TYPE from `DuplicateGroup` - every cleanup/trash path takes the latter, so an unverified heuristic result cannot reach deletion; `InstantDuplicateVerifier` (which delegates to `DuplicateContentVerifier.exactGroups`) is the only bridge. Keep that type separation: a `isVerified` boolean would move the guarantee from the compiler to reviewer discipline.

Everything goes to Trash via `TreeActions` → `FileManager.trashItem` - never delete. Duplicate cleanup byte-verifies before trashing (`DuplicateContentVerifier`, opens with `O_NOFOLLOW`) and only proceeds when an unselected byte-identical copy survives. `applyPreset` fails closed: `[]` means "do nothing", and callers must treat it that way. When touching `trashItem` bridging: use the compiler-managed `&nsurlVar` writeback in a synchronous helper - a hand-built `AutoreleasingUnsafeMutablePointer` over strong storage over-releases at pool pop in async contexts (this crashed in production once already; see `performTrash`).

## Temporal snapshots

`SnapshotStore` keeps a per-volume TIMELINE of checkpoints (`DirWiz/Snapshots/v2-<volume-key>/`), replacing the old single `.tdiff` slot that every save overwrote; `DIRWIZ_APP_SUPPORT_DIR` overrides the location (tests), and GUI + CLI (`snapshot`, `snapshot list`, `diff`) share one store per root path. Each checkpoint is the existing `.tdiff` payload inside an LZFSE container (Apple's Compression framework - the zero-dependency rule holds); ~12% of raw, 350k dirs ≈ 2 MB. **The container has a stored-uncompressed mode byte and it is load-bearing**: LZFSE expands small/high-entropy input and `compression_encode_buffer` then returns 0, so without it small snapshots cannot be written at all. **`index.json` is a cache, never the truth** - it is rebuilt from the `.dwcp` files when missing or corrupt, and recovered entries are marked pinned since the store cannot tell which mattered. Anything that lists the store before writing to it must read the index FIRST: `list()` self-heals by adopting every `.dwcp` on disk, so listing after a write re-adopts the file being written. Retention thins unpinned checkpoints (30 dailies / 12 weeklies / 12 monthlies, 500 MB budget) and NEVER evicts a pin. Auto-checkpoints happen on scan completion behind a 6h/1%-growth throttle; the camera action pins.

## Website (docs/)

`docs/index.html` is the dirwiz.app landing page, tracked via a `.gitignore` exception (`docs/*` is otherwise ignored). **`docs/` also holds internal working docs (`strategic-analysis.md`, `performance-loop.md`) that must never be published** - deploy an explicit allowlist of referenced files, never the whole directory. Deploy: `wrangler pages deploy <dir> --project-name dirwiz` (Cloudflare Pages project `dirwiz`; wrangler's OAuth token can attach custom domains but CANNOT write DNS records - that needs the dashboard or a scoped API token). Screenshotting the page headlessly requires `--force-prefers-reduced-motion`: `.rv` elements sit at `opacity:0` until an IntersectionObserver fires, so without it you capture a blank page. Download facts (version, checksum, signing, architecture) must be verified against the actual released asset - `shasum -a 256`, `codesign -dv`, `spctl -a -vvv`, `lipo -archs` - not the release notes. The live-demo treemap embeds a real pruned `dirwiz-cli scan --json` (`const REAL_SCAN`); regenerate it from real scans rather than hand-editing, and keep it to system paths so no personal filenames ship.

## Test hygiene: never write to the real defaults

Preferences MUST go through `AppState`'s injected `defaults`, never `UserDefaults.standard` directly - and tests must construct an isolated suite (`UserDefaults(suiteName:)` + `removePersistentDomain`, reusing ONE name rather than a fresh UUID per call, which litters `~/Library/Preferences`). This is not hypothetical: `treemapRenderStyle` and the Insights collapse store originally read/wrote `.standard`, so a test run and a headless screenshot run silently changed the developer's own installed app (it started opening in card style with three Insights sections collapsed). If you add a persisted preference, wire it to `defaults` in `init` and assert in a test that `.standard` is untouched.

## CI is correctness-only; heavy machinery runs locally

Heavy benchmark suites (`PerformanceSensitiveSuites`, `SnapshotStoreSizingTests`) carry `.enabled(if: runHeavyBenchmarks)` (TestHelpers.swift): they run on a local `swift test`, skip automatically when `CI=true` (GitHub Actions always sets it), and `DIRWIZ_HEAVY_TESTS=1/0` forces either way. Rationale: free-plan macOS runners bill at 10x, and a loaded shared runner produces timing numbers this repo has already been burned by twice - so CI asserts correctness (~14s test step) and wall-clock claims are only ever made from local/release runs. A new benchmark or timing gate MUST go under one of the gated suites, not at top level.

## Testing conventions

swift-testing (`import Testing`, `@Suite`/`@Test`/`#expect`/`#require`) - not XCTest. Real-filesystem fixtures via `createTempTree` (Tests/TestHelpers.swift); tree shapes a real scan can't produce are hand-built through `@testable` internals (`setRootPath`/`addNode`/`addChildren`). Tests run in parallel; any suite touching `DIRWIZ_APP_SUPPORT_DIR` (via `withTemporaryAppSupportDir` or inline `setenv`) MUST be declared as `extension AppSupportEnvSuites { @Suite(...) ... }` - `.serialized` on the suite itself is NOT enough (it only orders that suite's own children, not against other top-level suites), and this is the first suspect if CI flakes intermittently. When refactoring an analyzer or scan path, write characterization tests pinning current outputs *before* the refactor (pattern: `Tests/AnalyzerWalkTests.swift`).

Warm-start tests need a fixture with BOTH shapes: ~300 padding dirs so the changed-item fraction stays under the planner's threshold (keeping it warm-eligible), AND real churn (~40 dirs × 100 files) so the patch runs long enough to observe mid-flight - padding alone yields a near-instant patch that polling tests race (`warmPatchIsCancellableMidFlightBody` is the reference fixture). `TreeCache.loadResult` invalidates a structurally-corrupt cache as a side effect, so a test asserting on the rejection reason must call it FIRST and once - calling `load()` first deletes the evidence.
