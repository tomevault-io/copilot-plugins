## fablekin

> Manages the synthesis and lifecycle of high-fidelity character profiles and secondary entity capsules.

# Fablekin: AI-Powered Narrative Simulation

Fablekin self-contained environment for building and experiencing dynamic, long-form narratives. It combines a multi-agent AI system with a persistent world-brain to ensure long-term continuity, logical consistency, and evolving character arcs.

This project was born from a desire to solve common limitations in AI role-playing (RP) systems:
- **SillyTavern/RisuAI**: While powerful, these often rely on a single, monolithic LLM call for every interaction, which can lead to instruction drift, lost context, and "flat" characters in multi-NPC scenes.

Fablekin solves this by employing a **Multi-Agent Specialization** strategy. Each turn is processed by a pipeline of specialized agents (Director, Writer, Extractor), ensuring every aspect of the narrative—from prose quality to world-state accuracy—is handled with maximum attention and thematic coherence.

## The TurnContext Capsule

The **TurnContext** is the single source of truth for every turn in the Fablekin engine. It is a state-heavy object that encapsulates the entire narrative lifecycle—from user input to final LLM output and visual novel assets.

### 1. The Skeleton & Inflation Pattern
To maintain high performance during project navigation (e.g., scrolling through the timeline), Fablekin uses an **Explicit Lazy Loading** doctrine:
- **Skeleton Mode**: When browsing the story history, only metadata-heavy fields (DB ID, Turn Number, Thumbnail, Title, Synopsis, Summary) are loaded.
- **Inflation**: The full state (including processing logs, prompt components, and raw LLM responses) is only loaded ("inflated") from the database when a specific turn is expanded for deep inspection or used as context for a new turn.

### 2. The Symmetric Prompt Registry (Slots)
TurnContext maintains a hierarchical `promptComponents` registry, organizing data into:
- **Pillars**: `root` (shared), `writer` (prose-specific), `director` (guidance-specific).
- **Slots**: `protocol` (rules), `canon` (lore), `dynamic_knowledge` (RAG/KG), `simulation` (state), `history` (narrative), `directives` (overrides).
This structure allows plugins to inject data into precisely the right context without polluting other areas of the AI prompt.

### 3. Serialization & Security Safeguards
- **Path Protection**: The `rootDirectory` is explicitly protected during `fromSnapshot` restoration. This prevents old snapshots (potentially from different machines) from overwriting the current session's active workspace paths.
- **Serialization Deny-List**: Transient or circular data (e.g., internal module handles, chat history arrays) is stripped during saving via `RUNTIME_PERSIST_DENY_LIST`.
- **MAX_SNAPSHOT_SIZE Safeguard**: If a turn snapshot exceeds **5MB**, the engine engages "Emergency Stripping." It progressively discards heavy transient data (Director CoT steps, performance logs) until the snapshot is safe to store, ensuring database stability.

### 4. Fidelity Tiers (The Memory LOD)
TurnContext supports dynamic fidelity levels for prompt assembly:
- **FULLTEXT**: The verbatim narrative output.
- **SUMMARY**: A condensed version of the turn's events.
- **SYNOPSIS**: A highly compressed, poetic overview.
- **Dynamic Overrides**: Plugins can use `historyOverrides` to force high-fidelity (Fulltext) injection for distant but narrative-critical turns (e.g., a "boss fight" from 50 turns ago).

## The AI Director & Cinematographer

Fablekin utilizes a dedicated **AI Director** (`vn_cinematographer`) to transform raw narrative prose into a sequence of cinematic visual novel events. This process occurs after the Writer AI completes its work, hooked into `HOOK_POST_VN_GENERATION`.

### 1. The Director Track
The Director Track is a structured set of instructions generated by the AI to control the "Camera," "Animation," and "VFX" layers of the VN Viewer. It ensures that the visual presentation matches the narrative intensity and emotional beats.

### 2. Atomic Command Grammar (UCP)
Cinematic commands follow a strict **Universal Cinematic Protocol (UCP)**, allowing for precise control:
- **Camera (`cam:`)**:
  - `cam:auto`: Default logical framing.
  - `cam:char:[Name]`: Focuses on a specific character.
  - `cam:wide`: Wide shot of the background.
  - `cam:zoom:[Name]`: Close-up of a character.
- **Animations (`anim:`)**:
  - `anim:shake:[Name]`: Shakes the character sprite (impact/surprise).
  - `anim:pulse:[Name]`: Subtle pulsing effect.
  - `anim:hop:[Name]`: Character jumps up and down.
- **Emotes (`emote:`)**:
  - `emote:[type]:[Name]`: Spawns a floating bubble above the character.
  - Types: `heart`, `anger`, `sweat`, `idea`, `exclamation`, `question`.
- **Titles (`title:`)**:
  - `title:[preset]|[text]`: Triggers high-impact on-screen text.
- **VFX & SFX (`vfx:`, `sfx:`)**:
  - Triggers named effects from the `vn_pixijs_vfx` and `vn_sfx` plugins.

### 3. High-Impact Title Presets
The `vn_cinematographer` includes logic for "Super Sentai" style title card presets:
- `character_intro`: Cinematic splash for new major characters.
- `locationchange`: Stylized text for entering a new area.
- `boss`: Heavy-impact layout for antagonistic encounters.
- `newitem`: Discovery of a valuable artifact or inventory item.
- `major_event`: "Chapter Finish" or "Important Decision" style cards.
- `discovery`: Finding a secret path or hidden lore.
- `landmark`: Approaching a significant geographical location.

### 4. Hook Integration
The cinematographer does not work in isolation. It aggregates prompts from other plugins:
- **`vn_pixijs_vfx`**: Injects lists of available weather, particle, and overlay effects.
- **`vn_sfx`**: Injects lists of available soundscapes and one-shot effects.
- **`character_classifier`**: Provides gender and importance data to ensure correct sprite prioritization.

## The Fablekin Plugin Ecosystem

Fablekin is built on a "Plugin-First" architecture. Almost every engine feature—from relationship tracking to the visual novel renderer—is a plugin. This ensures the core engine remains light and the narrative logic is fully modular.

### 1. The Hook Lifecycle & Execution
The `PluginManager` orchestrates data flow through a sophisticated hook system:
- **Execution Modes**:
    - **Sequential**: Plugins receive the output of the previous listener, allowing for a pipeline of transformations (e.g., `HOOK_D_writerBrief`).
    - **Parallel**: Independent modules run concurrently to maximize throughput (e.g., `HOOK_POST_PROMPT_BUILDER`).
- **Priority System**: Hooks are executed in integer-based priority order (0-100). Core plugins typically occupy the `P10` and `P20` slots.

### 2. Story Scripts (Project-Level Plugins)
Creators can extend the engine using **Story Scripts**—Markdown files containing JS code blocks.
- **Security model**: Evaluated in a `vm` context with a "Trust-On-First-Use" (TOFU) and hash-based approval gateway.
- **Scope**: Story Scripts have the same access to the `tools` toolkit as standard plugins.

### 3. The Inter-Plugin Bridge (`callPluginFunction`)
To facilitate cross-plugin communication, plugins can export functions that are callable by others via a standardized bridge, allowing for complex emergent behaviors (e.g., the Story Card system triggering effects in the Relationship Tracker).

### 4. Dynamic View Portals
Plugins register frontend extensions through two mechanisms:
- **Full Views**: Dedicated tabs in the renderer (e.g., the Lore Browser).
- **Documentation Portals**: Markdown help files dynamically aggregated into the engine's central Docs system.

### 5. Secure Secret Synchronization
The engine automatically handles masked synchronization of sensitive values between the UI and backend `SecureStorage`, ensuring API keys are never exposed in log files.

### 6. The Plugin Toolkit (`tools` Library)
Each plugin receives a massive `tools` object providing standardized APIs:
- **`tools.llm`**: Multi-provider LLM interface with retry logic.
- **`tools.memory`**: Semantic and SQL search across project databases.
- **`tools.gui`**: Interactivity suite (GUI Injection & Intercept).
- **`tools.project`**: Filesystem operations and asset resolution.
- **`tools.logger`**: Unified logging for performance profiling.

### 7. The `emitReceive` Protocol
To facilitate a request-response pattern over the naturally asynchronous Socket.IO layer, the engine utilizes a custom `emitReceive` utility. It allows the backend to "ask" the frontend for data (e.g., `get-selected-files`) and wait for a corresponding `-response` event with a configurable timeout (default: 5000ms), bridging the gap between event-driven and procedural logic.

## The Orchestrator (Director)

Fablekin employs a multi-agent system where the **Writer** is guided by a high-level **Orchestrator** (Director).


### 2. The Orchestrator's Cognitive Framework
The Director agent follows a sophisticated two-call execution protocol:
1. **The Analysis Phase**: Reviews Canon Lore, Simulation State, and Narrative History to generate a "Writer's Brief."
2. **The Ledger Phase**: Updates its own **Director's Ledger**—a persistent relational memory stored in SQLite. It tracks active plot IDs, hidden NPC motives, and long-term narrative tension.
- **Prompt Components**: The Director's prompt is surgically assembled from multiple slots (Foundation, Chronicles, Simulation) to ensure maximum context density without exceeding token limits.

### 3. Direct AI Control Protocol (emitReceive)
The backend-frontend bridge is powered by a custom `emitReceive` pattern over Socket.IO. This pattern transforms event-driven communication into a pseudo-procedural flow, allowing the backend to request information or actions from the UI and wait for a response, effectively treating the frontend as a participant in the narrative generation.

## VN Transformation Pipeline

The `vn_manager.js` orchestrates the conversion of raw narrative text into a structured visual novel sequence. This pipeline is highly parallelized to minimize user latency.

### 1. Dialogue & Emotion Analysis
- **Parsing**: The engine breaks narrative blocks into atomic dialogue lines and narration.
- **Emotion Classification**: Uses optimized LLM calls or regex patterns to detect character moods.
- **Sprite Mapping**: Resolves the best-match sprite based on `Name + Emotion`, handling overlays for talking and blinking.

### 2. Orchestration Stages (Blocking Tasks)
The following tasks halt scene delivery until completion:
- **Asset Selection**: Competitive selection of the best background and OST using the `AssetSelector`.
- **Character Bootstrapping**: Identifying new characters and triggering `HOOK_NEW_CHARACTER_IDENTIFIED` for initial relationship/personality extraction.
- **Sprite Positioning**: Calculating optimal XY coordinates and depth (Z-index) for character sprites based on scene density and dialogue focus.

### 3. Background Orchestration (Post-Delivery)
Non-critical tasks are deferred to ensure the user sees the scene as fast as possible:
- **Summarization/Synopsis**: Generating high-performance narrative capsules for long-term memory.
- **Thumbnail Generation**: Composing a 320x180 thumbnail of the scene's top 3 characters on the current background.
- **TTS Provisioning**: Triggering audio generation hooks while the user is already reading.

### 4. Cinematic Event Grammar
The `vn_manager` translates narrative beats into **Client Events** (e.g., `scene:transition`, `vn:ost-change`) that the frontend PixiJS engine consumes to trigger visual transitions.

## Visual Novel Simulation Layer

The VN Simulation Layer is where raw AI narrative is visualized. It utilizes a custom PixiJS-based engine to manage layered sprites, dynamic backgrounds, and cinematic effects.

### 1. Modernized Settings & Global Configuration
Fablekin has transitioned to a **Centralized Configuration Model** for the viewer experience:
- **Global `settings.json`**: All persistent configuration is stored in the root workspace using a strictly hierarchical `snake_case` schema. It is divided into two primary namespaces: `infrastructure` (Global/API) and `narrative_agents` (Specialized Agent parameters).
- **Player Character Handlers**: Globally registered `playerHandlers` that manage protagonist interactions across all projects.

### 2. The Layered Sprite Animation System
Sprites are dynamic organisms managed by the `SpriteAnimator` class:
- **Base Texture**: The core emotion-specific sprite (e.g., `Skirk_Annoyed.png`).
- **Dynamic Animation Layers**: The engine detects and overlays secondary assets:
    - `[name]_talk`: Toggled during dialogue playback for synchronized lip-sync.
    - `[name]_blink`: Intermittently activated to provide narrative "life."
- **Asset Resolver**: A case-insensitive, extension-agnostic pipeline that prioritizes the best match from the project's internalized `assets/` directory.

### 3. High-Fidelity VFX & SFX
Simulation depth is provided by specialized plugins:
- **`vn_pixijs_vfx`**: Manages weather effects, particle showers, and cinematic screen overlays.
- **`vn_sfx`**: Handles spatialized soundscape transitions and one-shot feedback.

- `1_Directives` -> **Directives**
- `2_Lore_Book` -> **Lore Book**

If a file is locked, the operation is queued in the project's config as `__pending_renames__` and executed during the next application boot, ensuring filesystem integrity without interrupting the user's flow.

## Recent Architecture Updates (Interludes, Intercepts, Dynamic Events)

### 1) Interludes (Virtual Turns) as First-Class Runtime
- Interludes are generated with dedicated run profiles and persisted in `chat_interludes`, not canonical `chat_turns`.
- Canonical numbering does not advance during interludes; they are attached to a parent chapter with an ordinal (`parent.ordinal`).
- Interlude mode naming is backend/internal; user-facing naming is Interlude.

### 2) Writer Prompt Snapshot Restore for Interlude Runs
- Canonical turns now persist a compressed `writer_prompt_snapshot` payload.
- Interlude prompt assembly restores from that snapshot so interlude generations inherit the same full prompt context that produced the parent chapter.
- This avoids context loss when plugin execution is reduced/opt-in for interlude flows.

### 3) Managed Plugin Storage Keying
- Plugin physical storage now uses a turn storage key rather than plain turn number:
  - Mainline chapter: `53`
  - Interlude of chapter 53: `53.1`, `53.2`, etc.
- This prevents interlude artifacts from colliding with parent chapter artifacts.
- Rewind/delete behavior removes both the base chapter folder and all `${chapter}.*` interlude folders.

### 4) GUI Intercepts: Robust Degrade Behavior
- Stale or unresolved intercept descriptors are treated as recoverable.
- Overlay fallback paths auto-resolve and return control, rather than trapping the viewer in a blocked state.
- Non-blocking intercept overlays are cleaned up when navigating context to avoid persistent stale UI.

### 5) Dynamic Event Pipeline Simplification
- Dynamic event opportunities are now always available when capabilities are registered.
- Writer receives a dedicated pacing section (always-on) with natural-language guidance and "last seen" context per dynamic event type.
- Director focuses on repetition/cadence steering (encourage overdue event families, suppress repetitive ones).
- Scene phase classifier resolves based on written scene output and uses Director deny signals only when explicitly present in `--- WRITER_BRIEF ---`.

### 6) Interlude UX Language
- User-facing text is now standardized:
  - "Turn" -> "Chapter"
  - "Interlude" -> "Interlude"
- Backend identifiers remain unchanged for compatibility with existing modules and storage contracts.

## Architectural Overview

The engine is a modular, event-driven architecture—designed for resiliency and extensibility. The backend processes are managed in Node.js and communicate with the Electron frontend via Socket.IO multi-webview.

### 1. The Backend Hub (Electron Main)
The `main.js` process serves as the central nervous system of Fablekin. It hosts an **Express server** on port 14541 for serving internalized assets and plugin resources, and manages the global application lifecycle:
- **Project Bootloader**: Orchestrates the transition between projects, including database initialization (`FactManager`, `StaticDataManager`), hook execution (`HOOK_PROJECT_LOADED`), and player metadata synchronization.
- **Process Isolation**: Manages a frameless, context-isolated Electron window with a custom IPC bridge for window controls (minimize, maximize, close).
- **Socket.IO Event Registry**: Acts as the primary event bus, routing over 60+ unique events between the UI tabs and the backend modules.

### 2. Frontend Injection & Caching
To optimize performance during the "startup storm" (where multiple webviews connect simultaneously), the engine utilizes a **Frontend Injection Cache**. Payloads for `HOOK_FRONTEND_INJECTION` (HUD) and `HOOK_FRONTEND_TIMELINE_INJECTION` (Timeline) are pre-computed and stored in memory, then served instantly to new connections. The cache is surgically invalidated only when plugins are toggled or projects change.


-   **Core Application**: The UI is managed by an Electron shell. The main process is Node.js. All inter-process communications are handled as real-time events using Socket.IO.
-   **Plugin-Enabled Architecture**: The engine features a robust hook-based plugin system. This allows developers to intercept and modify the narrative generation and visual novel transformation processes at various stages (e.g., pre-dialogue parsing, post-asset selection), enabling modular extensions like the Story Cards system.
-  ### 2. The Frontend UI Shell (Renderer)
The `renderer.js` processes orchestrate the UI composition and inter-webview communication:
- **Dynamic Tab Orchestration**: Beyond fixed tabs (Project, Content, Log), the engine dynamically generates tabs for active plugins by querying their views and mounting them inside isolated `<webview>` tags.
- **Tab Persistence**: Active tab states are maintained in `localStorage`, allowing the engine to restore the user's exact workspace context between restarts.

## Chapter Persistence & SQLite Architecture

Fablekin utilizes a robust SQLite-based persistence layer for narrative history, managed by `chaptermanagement.js`.

### 1. The `chat_turns` Database Schema
Every narrative turn is stored in a project-specific `.db` file (Campaign) with high-speed query optimization:
- **`id` (PK)**: The permanent, chronological anchor for the turn.
- **`creation_turn_number`**: An identifier used for internal consistency during generation.
- **`turn_context_snapshot` (Gzip BLOB)**: The full `TurnContext` capsule, serialized as JSON and gzipped to save up to 80% on disk I/O.
- **Metadata Columns**: `title`, `synopsis`, `summary`, `thumbnail`, and `dialogue_count` are stored as flat columns to allow for ultra-fast UI rendering without decompressing the main context blob.

### 2. State & Integrity Mechanisms
- **Skeleton vs. Inflation**: The UI initially loads only "skeletons" (metadata columns). Full context objects are lazily "inflated" only when deep inspection or world-state reconstruction is required.
- **Viewer State Persistence**: The `viewer_state` table tracks the user's exact position across restarts, enabling "Pick-Up-And-Play" continuity.
- **Arc Compression**: For stories spanning hundreds of turns, the engine utilizes a specialized `arc_compression_cache` to store LLM-synthesized summaries of ancient history blocks, bypassing context limits.

## Project Structure & Content Management

Fablekin utilizes a strictly zoned file structure within each project to organize the "Story Bible" and the "Chronicles."

### 1. Portable Project Configuration (`.config`)
Directory settings are stored in sibling `.config` files (e.g., `Lore_Book.config`).
- **Relativization**: All file references are stored as relative paths, ensuring project portability across machines and OSs.
- **Sticky Mode & Lineage**: Files can be assigned "Structured Personas" (e.g., `charsheet`). Once assigned, the system utilizes a `none:[modeId]` convention in the config. This creates a "Sticky Lineage" where the file remembers its data type and restricts available editor modes, even if it is excluded from the active prompt.
- **Automatic Migration**: The engine detects legacy absolute paths in `.config` files and automatically relativizes them upon the first load.

### 2. Core Project Zones
- **`1_Directives` (Protocol)**: High-level system prompts and writing style guides.
- **`2_Lore_Book` (Canon)**: Character sheets, world-building, and static history.
- **`3_Chronicles` (Campaigns)**: Reserved exclusively for narrative `.db` files. These are explicitly ignored during static lore RAG passes to prevent narrative pollution.
- **`4_Important` (Overrides)**: High-priority rules injected at the absolute bottom of every prompt.

### 3. Internal Directory Processing & Caching
The `directory_processor.js` manages the physical-to-logical mapping of the project:
- **Depth 2 Isolation**: To maintain UI responsiveness, directory scanning is capped at a depth of 2.
- **System Exemptions**: `plugins`, `vectors`, and `assets` folders are treated as system-internal and excluded from the standard Content Manager display.
- **Cache Hashing**: The `CacheManager` generates unique cache identifiers by Base64-hashing the absolute directory path. This ensures that lore summaries and synopses remain collision-free even for projects with identical names in different locations.
- **Token Estimation**: The engine employs a 4:1 character-to-token ratio for high-speed budget estimation in the UI.

## AI Memory & Vector Architecture

Fablekin utilizes a hybrid memory model to achieve both semantic depth and factual reliability.

### 1. Vector Memory Subsystem (LanceDB)
The engine utilizes **LanceDB** for high-performance, local-first RAG operations.
- **Project-Isolated Storage**: Every project maintains isolated `/vectors` partitions (e.g., `memory_store`, `static_lore`, `summaries_cache`).
- **Unified RAG Pipeline**: Uses `RecursiveCharacterTextSplitter` for predictable chunking and Ollama for local embeddings.
- **MongoDB-to-SQL Filter Bridge**: Allows programmers to use MongoDB-style filters which are procedurally translated to LanceDB SQL.
- **LLM Relevance Scoring**: A secondary "reflection" pass where a fast LLM prunes low-quality RAG results.
- **Graceful Degradation**: Proactive checks for the embedding service; if offline, the engine falls back to metadata/keyword filtering without crashing.

### 2. Relational Memory (SQLite)
Relational memory answers, "What is technically true?" Stored in project-specific `.db` files, it tracks:
- **World State Facts**: High-speed lookup for Location, Time, and Inventory.
- **Character Bonds**: Symmetrical relationship vectors (Friendship, Romance, Trust, Fear, Respect).
- **Evolutionary Personality**: Numerical trait tracking using the OCEAN model.

## The Memory LOD & History Reconstruction

The engine reconstructs narrative history using a tiering logic defined in `memory_lod.js` and `chaptermanagement.js`.

### 1. The Sliding window of Fidelity
Fablekin balances context richness with token limits through four distinct tiers:
- **Living Memory (Fulltext)**: The most recent turns are provided with verbatim dialogue and narration.
- **Mid-Range (Summaries)**: Older turns are compressed into 150-character narrative capsules.
- **Distant Past (Synopses)**: The furthest turns are reduced to poetic, one-line summaries.
- **Mechanical History**: Outcome injections (e.g., injuries, relationship shifts) are preserved with high-priority context even for synopsized turns.

### 2. Emergency Serialization Guard (5MB Limit)
If a turn snapshot exceeds 5MB, the engine engages "Emergency Stripping," purging non-critical transient data (like raw performance logs or large CoT blocks) before committing to the SQLite blob to ensure database stability.

## The Prompt Component Registry (Slots)

The `turnContext.promptComponents` object serves as the single source of truth for context assembly. It is located at the root of the `TurnContext` for maximum visibility. All slots are **arrays of strings**, allowing multiple agents and plugins to contribute data without overwriting each other.

-   **systemInstructions**: Base persona and fundamental operating rules.
-   **writerCoT**: Thinking framework (Writer only).
-   **worldLore**: Static lore from Building directory.
-   **staticLore**: Static lore from Lore directory.
-   **retrievedContext**: RAG results and Knowledge Graph insights.
-   **knowledgeGraph**: Relational data extracted from history.
-   **mechanicalContinuity**: Outcomes from previous turns (Injected Outcomes).
-   **worldStateSnapshot**: Programmatic situational snapshot (Location, Time, Weather, Inventory).
-   **personalitySnapshot**: Natural language summary of current character internal states.
-   **relationshipSnapshot**: Active dynamics and reaction guidance between characters.
-   **relevant_world_entities**: Dynamically discovered secondary characters (via Social Probe) including their latest Brief and ALIVE/DEAD status.
-   **narrativeHistory**: Processed Synopsis/Summary/Full-text chain.
-   **directorBrief**: The Orchestrator's Writer's Brief.
-   **importantDirectives**: Hard constraints or overriding system instructions.

## The Prompt Component Architecture (Part 1-4)

The final prompt sent to the LLM agents is assembled from the `promptComponents` registry, organized into a four-part document structure.

The final block that triggers the creative generation.

# Project Overview: LLM-Powered Narrative Generation System

## 1. Detailed Feature List

- **Narrative Generation:**
    - Generates story text using Large Language Models (LLMs).
    - Integrates with lore files and chat history for contextual generation.
    - Supports "Turn 0" proactive orchestration for initial scene setup.
    - Incorporates "Writer's Brief" feedback for narrative adjustments.
- **Visual Novel (VN) Transformation:**
    - Transforms generated story text into visual novel sequences, with status updates now managed by a simplified popup GUI.
    - **Advanced Sprite Animations:** Characters feel more alive with an automatic, layered animation system.
        - **Blinking & Talking:** If sprites with `_blink` and `_talk` suffixes are provided, characters will automatically blink at random intervals and animate their mouths when they are speaking. This is handled by the frontend `SpriteAnimator` class.
        - **Smart Entrance Animation:** A character entering a scene for the first time (or replacing another character) will animate with a smooth slide-and-fade effect. Emotion changes on an already-present character will not re-trigger the entrance animation, ensuring a seamless experience.
    - **Seamless Chapter Navigation:** Integrated floating navigation cards appear on the left and right edges of the VN viewer. These cards provide visual previews (thumbnail + title + synopsis tooltip) of the preceding and succeeding turns, allowing users to traverse the entire story history chronologically without leaving the main viewer. 
    - **Context-Aware Input Visibility (Creator Mode):** The engine dynamically manages the visibility of user input. Inputs are strictly hidden when viewing historical turns or intermediate dialogue lines, appearing only at the "creative tip" of the story (the final dialogue of the latest turn). If a "Next Chapter" exists, the input section is replaced by a navigation card to enforce narrative linear continuity.
    - **Manual Dialogue Editing (Creator Mode):** To ensure absolute narrative control, creators can edit any line of dialogue or narrative text directly within the VN viewer. A "pencil" icon appears on hover over the dialogue box, enabling localized corrections. These edits are stored in a "dirty" state locally and are only committed to the project's SQLite database upon clicking the "Save Changes" button. This batch commit process performs an atomic update to the `TurnContext`, synchronizing the visual sequence, the processed dialogue metadata, and the raw text used for long-term memory (RAG).
    - **Synchronized Audio Keys (CRCs):** During a manual edit commit, the engine automatically recalculates the CRC32 hash for the modified text. This ensures that the frontend immediately recognizes the line as "new" and fetches the corrected audio instead of playing a cached version of the old dialogue.
    - **Post-Edit Hook (`HOOK_TURN_UPDATED`):** Once a batch edit is finalized and the turn is saved, the engine triggers the `HOOK_TURN_UPDATED` hook. This allows auxiliary systems (like the Knowledge Graph, Relationship Tracker, or TTS engine) to react to the narrative changes in parallel with the background re-generation of the turn's summary and synopsis.
    - **Navigation Protection:** To prevent data loss, the VN viewer includes a "dirty" check. If a creator attempts to navigate to a different turn or generate a new one while uncommitted edits exist, the UI prompts for confirmation, ensuring manual corrections are either saved or intentionally discarded.
    - **Dynamic Thumbnail Generation:** Using the `sharp` library, the engine automatically composites a 320x180 thumbnail for each turn. It overlays the top 3 most prominent character sprites onto the selected background, mirroring their in-scene positions. This is processed as an asynchronous background task to minimize user-perceived latency.
    - Automatic asset selection (sprites, backgrounds, OST) based on narrative context. The system now supports a detailed sprite object in the turn data, allowing the backend to specify which animation layers (`hasBlink`, `hasTalk`) are available for a given sprite.

## The Knowledge Graph World Brain

Fablekin utilizes a sophisticated Knowledge Graph (KG) to maintain a persistent, traversable "World Brain." This system ensures that the AI stays grounded in the story's emergent facts, social ties, and causal history.

### 1. Hybrid Retrieval (The Four-Phase Search)
When a turn is processed, the KG Manager executes a multi-tiered search to find the most relevant facts:
- **Phase 1: Librarian Intent**: A fast LLM analyzes the current turn and context to generate 3-5 specific search queries (e.g., "What is Skirk's opinion of the player?").
- **Phase 2: Thematic Probe (Vector)**: Standard cosine similarity search against the embeddings of all Subject-Predicate-Object triples.
- **Phase 3: Social Pathfinding (Weighted BFS)**: Uses a "Narrative Energy" budget (100) to find deep connections between active characters. Different relationship types have varying costs (e.g., Family: 5, Social: 40).
- **Phase 4: Bridge Hunter (Triangles)**: SQL-based discovery of common entities or "triangles" between two or more active NPCs to surface shared history.

### 2. Scored Re-ranking
Candidates are ranked using a multi-factor formula: `(VectorSimilarity * 0.4) + (TemporalAnchor * 0.3) + (Recency * 0.2) + (Centrality * 0.1)`. This ensures that triples linked to recent "Anchor" chapters and core social nodes are prioritized.

## Agentic Lore Research & Slotted RAG

Fablekin moves beyond simple RAG by employing an **Agentic Lore Researcher** to manage the "Story Bible."

### 1. Slotted Injection
Retrieval Augmented Generation (RAG) results are not simply dumped at the top of the prompt. Instead, they are "slotted" into the chronological history. If a memory about a specific turn is found, it is injected back into that turn's context, preserving temporal continuity for the AI.

### 2. The Librarian Query Expansion
The engine uses a dedicated `query_generator.js` to expand a single user intent into a high-fidelity search plan. This prevents the "shallow retrieval" common in basic RAG systems.

## The TurnContext Architecture

Every discrete "turn" in Fablekin is encapsulated within a `TurnContext` object—a transient, stateful capsule that orchestrates the flow of data from user prompt to visual novel sequence.

### 1. Data Schematics
The context is partitioned into logically isolated namespaces:
- **`input`**: Contains the raw user prompt, director instructions, and relativized file references.
- **`processed`**: The "working memory" where LLM outputs, extracted facts, and plugin-specific data (e.g., relationships, personality states) are stored.
- **`output`**: The materialized visual novel sequence, including asset paths, AI-generated titles, and synopses.
- **`runtime`**: Ephemeral, non-persisted data (e.g., performance metrics, asset indices) used only during the active generation pipeline.

### 2. The Skeleton & Inflation Pattern
To optimize UI responsiveness, the engine utilizes a **Skeleton Pattern**. When browsing history, only lightweight metadata (Skeletons) are loaded into memory. When a specific turn's details are needed (e.g., for reprocessing or script viewing), the `ensureFull()` method performs a "lazy inflation," fetching the high-fidelity JSON blob from the database.

### 3. Symmetric Hierarchical Registry (Slots)
The engine utilizes a `promptComponents` registry to build complex prompts from multiple sources (core engine + various plugins). This registry is partitioned by **Target** (Root, Writer, Director) and **Category**:
- `protocol`: System rules and structural formats.
- `canon`: Lore, world data, and project-specific knowledge.
- `simulation`: Current world state and character dynamics.
- `history`: Narrative context and past dialogue.
- `directives`: High-priority overrides and specific turn instructions.

## The Prompt Assembly Engine

The engine utilizes a "Foundation" gathering system to procedurally build prompts for both the **Orchestrator (Director)** and the **Writer**.

### 1. The Hierarchical Slot System
Prompts are not static strings but are assembled from a multi-dimensional registry (`promptComponents`). This allows the engine and plugins to inject context into specific "pillars" with guaranteed priority:
- **Root Pillar**: Data shared by both Orchestrator and Writer.
- **Writer Pillar**: Instructions and context exclusive to the narrative prose generation.
- **Director Pillar**: High-level guidance exclusive to the creative orchestrator.

### 2. Slot Categorization & Multi-Source Injection
Within each pillar, data is slotted into functional categories. This ensures that a plugin adding a "Relationship Rule" (Canon) doesn't interfere with the "Writer's Formatting Process" (Protocol):
- **Protocol**: System-level formatting and behavior rules.
- **Canon**: Static world knowledge, lore, and character sheets.
- **Dynamic Knowledge**: Context retrieved via RAG (World Knowledge RAG).
- **Simulation**: Programmatic state snapshots (World State, Personalities).
- **History**: Historical narrative context (Sliding Window).
- **Directives**: Turn-specific instructions and high-priority overrides.

### 3. Instruction Precedence (Folder Priority)
The engine respects folder-based urgency when gathering files:
- **`1_Directives`**: Files in this folder are treated as core protocols.
- **`4_Important`**: Files in this folder are treated as **Final Execution Directives**, injected at the absolute bottom of the prompt to ensure the LLM follows them over all other context.

### 1. The Performance Waterfall
The Log Inspector features a sophisticated **Waterfall Visualization** tab that parses synchronized console logs into a Gantt-style graph:
- **Subsections & Markers**: Every major process is explicitly enclosed in `>>>` (start) and `<<<` (end) markers, categorized by subsystem.
- **Greedy Packing Algorithm**: To visualize parallelism, the waterfall uses a greedy packing strategy to stack overlapping asynchronous tasks into separate horizontal lanes, identifying the actual "Critical Path" of a turn.
- **Interactive Metrics**: Hovering over a bar reveals exact millisecond durations, memory usage deltas, and the individual log messages that triggered the event.

### 2. Session Integrity & Pseudo-Turns
Narrative engines often "miss" logs that occur during boot or background processing. Fablekin solves this via **Pseudo-turns**:
- **Startup Sessions**: Activity that occurs outside a narrative turn (e.g., project loading, vector store initialization) is logged under a unique `startup` pseudo-turn ID.
- **Unified Log Stacks**: In the UI, these logs are presented with the same fidelity as narrative turns, ensuring no system "black boxes" exist.

### 3. State Continuity (Snapshots vs Inflation)
Every turn is persisted with a Gzipped context snapshot. The engine uses a lazy **Skeleton/Inflation** pattern:
- **Fast List**: Turn lists only load "Skeleton" metadata (titles, turn numbers).
- **Deep Zoom**: Full context "Inflation" only occurs when a specific turn is selected or used as a RAG anchor, significantly reducing memory overhead for long-running stories.

### 4. The Sliding window (History Fidelity)
To balance context richness with token limits, history is managed via a **Sliding Window of Fidelity**:
- **Recent Turns (Fulltext)**: The most recent chapters are provided as full narrative dialogue (or `metaDialogue`).
- **Mid-Range (Summaries)**: Older turns are compressed into concise summaries.
- **Distant Past (Synopses)**: The furthest turns are reduced to one-line synopses.
- **Mechanical History**: "Outcome Injections" from previous turns are preserved as high-priority context to ensure continuity of consequences (e.g., injury or inventory loss).

### 5. Emergency Serialization Guard (5MB Limit)
To prevent database bloat and ensure fast project loads, the engine implements an **Emergency Strip** mechanism during serialization. If a single turn's data exceeds 5MB, the engine automatically purges heavy transient data (like raw LLM chat logs and full prompt components) before committing to the SQLite blob, prioritizing narrative integrity over metadata storage.

## Fablekin Coding & Architecture Standards

To maintain the engine's integrity and portability, all core and plugin development must adhere to the following standards:

### 1. The Decoupled Philosophy
- **Engine Logic (`/engine/`)**: Contains pure application code. No project-specific data or hardcoded paths should ever reside here.
- **Workspace Data (`/workspace/`)**: Contains all user projects, assets, and databases. The engine treats this as a black-box storage layer.

### 2. File Pathing & Resolution
- **Absolute vs Relative**: **NEVER** use hardcoded root-relative strings (e.g., `../../assets/`). 
- **The Standard**: Use `path.join(__dirname, ...)` for internal engine resources. For project assets, derive paths from the `turnContext.runtime.rootDirectory` or the `tools.project.absolutePath` helper.
- **Case Sensitivity**: While the filesystem might be case-insensitive (Windows), the engine's asset resolver enforces case-sensitivity in its internal logic to ensure cross-platform compatibility.

### 3. State Management (TurnContext)
- **Immutability**: The `processed` object in TurnContext should be treated as append-only. Never delete data from previous plugins unless performing an explicit "State Collapse."
- **Serialization Safety**: Ensure all data injected into `runtime` is serializable. Heavy objects (e.g., Buffer, Socket, DB Handles) must be excluded from storage via the `RUNTIME_PERSIST_DENY_LIST`.

- **Application Startup:** `main.js` initializes Electron window, starts Socket.IO server, and sets up core modules.
- **Project Selection:** User selects a project via `views/project_selector/`. `main.js` sets `rootDirectory`, loads `index.html`, and emits `project-changed` event. `FactManager` is initialized for the selected project.
- **Client-Server Communication:** Socket.IO is used for real-time, event-driven communication between `main.js` (backend) and renderer processes (frontend).
- **Narrative Generation (VN Turn):**
    1.  Frontend (e.g., `views/vn_viewer/`) sends `generate-vn-turn` event to `main.js`.
    2.  `main.js` calls `vnHandlers.generateVNTurn`.
    3.  A `TurnContext` object is initialized and passed throughout the workflow, encapsulating all turn-specific data and replacing the need for multiple, messy parameters.
    4.  `narrativeengine.js` begins the narrative generation sequence, sending status updates via `utils.js`.
    5.  **GUI Intercept**: `main.js` executes the `HOOK_GUI_GATEKEEPER`. If a plugin intercepts, the generation pauses until the plugin resolves the bridge.
    6.  `narrativeengine.js` orchestrates the call to the AI Orchestrator...
    7.  `narrativeengine.js` builds LLM prompts and generates story text...
    8.  `vnmanager.js` orchestrates asset selection...
    9.  **Frontend Delivery**: The scene is sent to the UI. The frontend then triggers `HOOK_VN_GUI_READY` and `HOOK_VN_GUI_LAST_DIALOGUE` at the appropriate times in the scene lifecycle.
    10. `vnmanager.js` calls various extractors...
    11. `chaptermanagement.appendMessage` is called to save the turn.
- **File Management (Content Manager Integration & Chat Conversion):**
    - When a user marks a Markdown file as 'chat' in the UI, `main.js`'s `fileHandlers.convertMdToChatDb` is triggered.
    - This function reads the content of the Markdown file, parses it, and then uses `chaptermanagement.appendMessage` to insert each turn into a new SQLite database file (e.g., `Chat.db`) located in the same directory as the original Markdown file.
    - After successful conversion, the original Markdown file is deleted.
    - The `fileHandlers.saveFileConfig` now identifies the active chat database file and initializes `chaptermanagement` with its full path.

## 3a. Example of a Full System Flow

To illustrate how all the components work together, here is a step-by-step walkthrough of a single turn, from user input to final output.

**1. Setup & Configuration (The Creator's Workflow)**
-   The user first selects their project. In the "Content Manager" view, they see their project's file structure.
-   Using the dropdown next to each file, they assign a "persona" or "mode" to their lore files. `my_characters.md` is set to `charsheet`, `world_history.md` is set to `summary`, and `important_rules.md` is set to `full`. This tells the engine how to process these files later.

**2. User Action (The Spark)**
-   In the Visual Novel viewer, the user is presented with a scene. They type their action, "I draw my sword and inspect the strange altar," and press "Go."

**3. Turn Inception (The Backend Awakens)**
-   The `generate-vn-turn` event is sent to `main.js`. A new `TurnContext` object is created, which will act as a "capsule" carrying all data for this turn.

**4. The Director's Review (Orchestration)**
-   The **Orchestrator** (`orchestrator.js`) is executed.
-   It analyzes the story's history, character arcs, and the current world state to ensure long-term coherence.
-   It generates a "Writer's Brief"—a set of high-level instructions and suggestions—and places it into the `TurnContext` for the next agent to use.

**5. Prompt Assembly (The Great Gathering - *Now Highly Parallel*)**
-   The **Prompt Builder** (`prompt_builder.js`) immediately calls the **Query Generator** utility, which makes a single LLM call to create 5-10 variations of the user's prompt ("I inspect the altar," "What is on the altar?", "A close look at the strange altar," etc.).
-   With this array of queries, it launches a `Promise.all` to fetch all context **simultaneously**:
    - It searches the static lore database for information related to "altars" or "rituals."
    - It searches the history of past chapters for any previous encounters with similar altars.
    - It generates KG insights about entities related to the last turn.
    - It synthesizes a personality snapshot for any new characters who just entered the scene.
-   Once all these parallel tasks complete, the Prompt Builder rapidly assembles the fetched data, the Director's brief, and the static files into the final, context-rich prompt.

**6. Narrative Generation (The Creative Act)**
-   The **Writer AI** (`narrativeengine.js`) receives the prompt and generates the story for the current turn, describing the character drawing their sword and what they see at the altar.

**7. Parallel and Asynchronous Processing (The Transformation)**

-   The moment the raw text is generated, the **VN Manager** (`vnmanager.js`) begins its work, splitting tasks to minimize latency:

        - **Blocking Parallel Tasks:** It simultaneously runs all processes required to immediately display the scene to the user. This includes structuring dialogue, selecting assets (backgrounds, OST), classifying emotions, **generating the turn thumbnail**, and extracting facts critical for the world state. The system waits for all these to complete.

    -   **Asynchronous Background Tasks:** As soon as the blocking tasks finish and the scene is sent to the user, the system triggers "fire-and-forget" background tasks.

 These now include requesting **Text-to-Speech (TTS) generation**—with a payload enriched by the character's guessed gender for accurate voice selection—alongside generating the turn's **summary** and **synopsis** and updating the story's **knowledge graph**. The UI notifies the user that these tasks are running and when they complete.

**8. Final Assembly & Display (The Showtime)**
-   Once the parallel tasks are complete, the `vnmanager` assembles the final scene:
    -   It finds the correct sprite (`player_curious.png`).
    -   The `sprite_positioner` arranges it on the screen using the "heat" system.
    -   The final sequence of dialogue, sprites, background, and music is finalized.
-   This final sequence is sent to the **VN Viewer** UI, and the user sees the scene they created, complete with visuals and music.
-   **Optional: Manual Correction:** If the user notices a minor dialogue error or wishes to tweak the prose, they use the **Manual Dialogue Editing** feature to correct the line instantly, ensuring the story remains exactly as intended before moving to the next turn.

**9. Committing to Memory**
-   The entire, fully-populated `TurnContext` object—containing the user's input, all the intermediate data from every agent, and the final VN sequence—is saved as a single, atomic record into the project's SQLite database. The turn is now a permanent part of the story's history.

## 6. Known Issues/Fixes (Example)

- **LLM-based World State Synthesis Replaced with Programmatic Generation:**
    - **Issue:** The previous implementation used an LLM to synthesize the world state snapshot, which was often verbose and didn't always provide the concise, actionable information needed for prompt construction.
    - **Resolution:** The LLM call for world state synthesis in `fact_manager.js` was replaced with a programmatic approach. The system now directly constructs a summary from the extracted facts (locations, time, weather, inventory), ensuring a more direct, consistent, and efficient world state representation for the AI. The configuration for the LLM-based synthesizer was removed.

- **Intermittent Voice Playback Failure:**
    - **Issue:** Voice lines would occasionally fail to play in the visual novel viewer, or fail to load from the local archive even when files existed.
    - **Root Cause 1 (Hash Mismatch):** The frontend was independently re-calculating the CRC32 hash, leading to mismatches for certain strings. Resolved by making the backend the single source of truth for audio filenames.
    - **Root Cause 2 (Path Resolution):** The frontend was using absolute-style paths (e.g., `/projects/...`) which Electron's `file://` protocol resolved to the disk root instead of the project directory.
    - **Resolution:** Refactored the data pipeline to use the backend's CRC hash directly and updated the frontend to use relative pathing (`../../projects/...`) to ensure correct resolution within the application's working directory. Additionally, enhanced the TTS plugin with detailed diagnostic logging to trace archival paths and API payload sizes.
- **Complex Parameter Passing & Module Interdependencies:**
    - **Issue:** Previously, the narrative generation pipeline involved numerous cascading function calls, each requiring a large number of parameters to be passed. This led to code complexity, made debugging challenging, and hindered modularity and extensibility.
    - **Resolution:** The introduction of `modules/turncontext.js` as a central "capsule" object has significantly streamlined the data flow. By encapsulating all turn-specific data and related module functionalities within a single `TurnContext` object, the system now benefits from reduced parameter clutter, improved code readability, easier diagnosis of issues, and enhanced modularity, allowing for more efficient implementation of new features and inter-module dependencies.
- **Chat History Storage Migration:**
    - **Issue:** Initial chat history was stored in monolithic Markdown files (`.md`), which became inefficient for access and management.
    - **Resolution:** The chat history storage was fully migrated to a performance-optimized SQLite database. `chaptermanagement.js` was refactored to handle database operations, schema migrations, and high-speed metadata queries. `main.js` was updated to orchestrate the conversion and correctly initialize the system with the full database path. The conversion process now correctly creates the `.db` file in the same directory as the original `.md` file, providing a robust foundation for long-form narrative persistence.

- **Thumbnail Generation Race Condition:**
    - **Issue:** Thumbnails were often failing to generate or were missing sprites/backgrounds because the generation task was running in parallel with asset selection, leading to empty fields during the thumbnail build process.
    - **Resolution:** Moved thumbnail generation from the blocking parallel pipeline to the asynchronous background tasks. The task now triggers only after the `finalBackground` and `prominentSprites` have been definitively determined and assigned to the `TurnContext`. The database record is then automatically "patched" with the new base64 thumbnail via the `updateTurn` method.

## Plugin Development Guide

The Dynamic Narrative Engine features a robust, reactive plugin system designed for deep integration with both the backend narrative logic and the frontend visual novel interface.

### 1. Plugin Structure
A plugin resides in a subdirectory of `/plugins` and must contain an `index.js` file.
```javascript
module.exports = {
    id: 'my_plugin_id',
    views: [ // Optional: Register custom tabs
        { id: 'my_view', label: 'My Plugin', entry: 'ui.html' }
    ],
    exports: { // Optional: Export functions to be called by other plugins
        'my_function': async (context, tools, ...args) => { ... }
    },
    hooks: {
        'HOOK_NAME': {
            priority: 10,       // Lower numbers run first
            mode: 'sequential', // 'sequential', 'parallel', or 'background'
            run: async (context, tools) => { ... }
        }
    },
    socketListeners: { // Optional: Handle frontend events
        'my-custom-event': (data, tools) => { ... }
    },
    settingsSchema: { // Optional: Declare UI-configurable settings
        apiKey: { type: 'text', label: 'API Key', description: 'Your secret key', default: '' },
        maxRetries: { type: 'number', label: 'Max Retries', min: 0, max: 10, default: 3 },
        modelType: { type: 'select', label: 'Model', options: ['fast', 'smart'], default: 'smart' },
        enableFeature: { type: 'checkbox', label: 'Enable Feature X', default: true }
    }
};
```

### 2. The Lifecycle
1.  **Initialization**: `PluginManager` loads all plugins at application startup.
2.  **Socket Binding**: When a new frontend client connects, all `socketListeners` are automatically bound to that socket instance.
3.  **Hook Execution**: During the narrative pipeline, the `PluginManager` executes registered functions. Sequential and Parallel hooks are awaited; Background hooks are fire-and-forget.

### 3. Comprehensive Hooks Reference

#### System & Project Lifecycle
- `HOOK_NARRATIVE_START`: Fired when the narrative engine starts.
- `HOOK_PROJECT_LOADED`: Fired when a new project is selected or loaded.
- `HOOK_CHAT_DB_INITIALIZED`: Fired when the active story database (Chat.db) is ready.

#### Narrative Generation Pipeline (Ordered)
- `HOOK_GUI_GATEKEEPER`: Fired at the very start of a turn. This is the primary hook for `tools.gui.intercept`.
- `HOOK_PRE_PROMPT_BUILDER`: Fired before any prompt components are gathered.
- `HOOK_EXTRACT_ENTITIES`: Fired during prompt building to allow plugins to extract search terms.
- `HOOK_POST_FILE_PROCESSING`: Fired after each static lore file is processed for RAG/KG.
- `HOOK_POST_PROMPT_BUILDER`: Fired after all components (RAG, KG, state) are gathered but before final LLM message assembly.
- `HOOK_PRE_ORCHESTRATOR`: Fired immediately before the Orchestrator AI runs.
- `HOOK_POST_ORCHESTRATOR`: Fired after the Orchestrator generates the Writer's Brief.
- `HOOK_PRE_WRITER`: Fired immediately before the main Writer AI runs.
- `HOOK_POST_WRITER`: Fired after the Writer AI generates the narrative text.

#### Visual Novel Transformation Pipeline
- `HOOK_PRE_VN_GENERATION`: Fired before the raw text is transformed into VN scenes.
- `HOOK_PRE_DIALOGUE_PROCESSING`: Fired before the text is parsed into dialogue/narrative blocks.
- `HOOK_POST_DIALOGUE_PROCESSING`: Fired after dialogue parsing is complete.
- `HOOK_NEW_CHARACTER_IDENTIFIED`: Fired when a new character is detected in a scene. Used for bootstrapping personality/relationships.
- `HOOK_VN_BLOCKING_TASKS`: Parallel-blocking hook for tasks required for the initial scene render (asset selection, etc.).
- `HOOK_POST_BLOCKING_TASKS`: Fired after blocking tasks finish but before the scene is sent to the frontend.
- `HOOK_POST_ASSET_SELECTION`: Fired after backgrounds/music/sprites are chosen.
- `HOOK_PRE_SPRITE_POSITIONING`: Fired before sprites are arranged on the screen.
- `HOOK_POST_VN_GENERATION`: Fired when the entire VN transformation is complete.
- `HOOK_VN_BACKGROUND_TASKS`: Background hook for non-critical tasks (TTS generation, world state extraction, KG updates).

#### Frontend & UI Hooks
- `HOOK_FRONTEND_INJECTION`: Fired to gather HTML/CSS/JS snippets to inject into the main VN viewer.
- `HOOK_VN_GUI_READY`: Fired from the frontend when the scene has finished rendering and is waiting for the user.
- `HOOK_VN_GUI_LAST_DIALOGUE`: Fired from the frontend when the user reaches the final line of a scene.

### 4. Developer Tools Suite
Every plugin function receives a `tools` object containing:
-   **`tools.turnContext`**: Access to the current turn's full state and history. This includes the `processed.slottedRAG` registry, allowing plugins to inspect or manually inject memories into specific historical chapters during the prompt assembly phase (e.g., via `HOOK_POST_PROMPT_BUILDER`).
-   **`tools.llm.call(messages, options)`**: Make resilient LLM requests.

## Core Plugins Reference

In addition to the components described below, the current active plugin set includes `adventure_book`, `arc_cinematics`, `camp_rest_interludes`, `cg_generator`, `lore_book`, `memory_recall`, `narrative_architect`, `output_size_controller`, `post_writer_consistency_checker`, `quest_tracker`, `sprite_shading`, `story_arc_tracker`, `vn_alive_bg`, `vn_cinematographer`, `vn_hud`, `vn_pixijs_vfx`, and `vn_sfx`.

### **Grand Story Planner (`grand_story_planner`)**
The "World Architect" of the narrative simulation.
- **Strategic Roadmap**: Generates and maintains a "Grand Story Plan" that defines high-level arcs, hidden mysteries, and off-screen machinations.
- **Git-like Updates**: Reviews narrative history every 5 turns and performs a "Reality Check" and "Simulation Advance," updating the plan using fuzzy SEARCH/REPLACE patches.
- **Orchestrator Guidance**: Injects the plan exclusively for the Orchestrator AI via `HOOK_PRE_ORCHESTRATOR`, allowing the Director to guide the Writer without revealing the "master blueprint" to the main narrative agent.
- **Dual-Memory Persistence**: Stores a master cache in `project.db` (based on static lore) and a dynamic, evolving version in each story's `chat.db`.

### **Character Sheets (`character_sheets`)**
Manages the synthesis and lifecycle of high-fidelity character profiles and secondary entity capsules.
- **3-Tier Character Triage**:
    - **Tier 1: MAJOR (Full Sheet)**: Protagonists/Antagonists with 11-layer "Pyramid of Persona" and git-style evolution.
    - **Tier 2: MAJOR (Light Capsule)**: Named secondary characters with a concise `Brief` and `STATUS`.
    - **Tier 3: MINOR**: Generic NPCs (e.g., "Guard") excluded from long-term tracking.
- **Character Evolution Engines**:
    - **Full Sheet Evolution**: Every X turns, applies git-style patches to Major character mutable layers.
    - **Light Capsule Batch Evolution**: Every X turns, performs a parallel batch update for all active secondary characters, summarizing recent developments and updating their `ALIVE`/`DEAD` status in a single LLM call.
- **Hybrid Social Probe (Discovery & Truth)**: 
    - Employs a **Pointer-based RAG strategy** to inject relevant characters into the prompt.
    - **Discovery Phase**: Uses Noun-Matching (deterministic) and Thematic RAG (probabilistic via `social_registry` vector collection) to identify character names relevant to the user prompt and scene context.
    - **Truth Phase**: Fetches the "Ground Truth" (latest Brief and Status) from the SQL database for the discovered names, ensuring narrative consistency even if RAG retrieval returns outdated content.
- **Layered Immutability**: Protects core character identity (Appearance, Background) during evolution.
- **Plugin Interoperability**: Integrates with `personality_tracker` and `relationship_tracker` to populate character sheet layers.
- **Interactive Manual Editor**: Dedicated UI for manual persona modification, with automatic synchronization to the `social_registry` vector store.
- **Prompt Injection**: Dynamically injects synthesized character data and discovered social entities into the prompt slots.

### **Character Classifier (`character_classifier`)**
The central agent for character attribute identification and narrative triage.
- **Proactive Classification**: Analyzes character sheets and narrative dialogue to determine genders and importance (Major/Minor) using a fast LLM.
- **Narrative Triage**: Enables performance optimization by identifying minor NPCs, allowing complex trackers (Relationship/Personality) to skip redundant processing.
- **Shared Registry Integration**: Immediately populates the `TurnContext.characterGenders` registry, ensuring absolute consistency across TTS and Sprite selection pipelines.

### **Knowledge Graph (`knowledge_graph`)**
Manages the structured factual memory of the world, combining vector semantic search with narrative pathfinding.
- **Architecture**: Stores facts as Subject-Predicate-Object triples with associated causal context and high-dimensional embeddings.
- **Hybrid Retrieval (The Cartographer)**:
    1.  **Librarian Intent Generation**: Generates specific search queries based on immediate context.
    2.  **Thematic Probe (Vector Search)**: Performs semantic search against triple embeddings.
    3.  **Social Pathfinding (Weighted BFS)**: Uses a "Narrative Energy" budget to discover deep connections between entities.
    4.  **Bridge Hunter**: SQL-based discovery of common entities or "triangles" between participants.
- **Scored Re-ranking**: Candidates are ranked using a multi-factor formula: `(VectorSimilarity * 0.4) + (TemporalAnchor * 0.3) + (Recency * 0.2) + (Centrality * 0.1)`.
- **Deduplication & Persistence**: Uses cosine similarity (>0.95) to detect duplicate facts, updating the `turn_created` timestamp of existing records to maintain a living memory.
- **Resilient Transaction Management**: Implements exponential backoff retry logic and performs embedding pre-calculation outside of SQLite transactions to mitigate database locking issues in parallel environments.
- **60/20/20 Investigation Strategy**: When utilized by the Researcher, the KG follows a balanced "Dossier" (direct lookup), "Bridge" (pathfinding), and "Chain" (Butterfly Effect random walk) effort allocation.
- **Unified Schema**: All KG tables (Chat and Lore) utilize a standardized schema including `turn_created` and `context_embedding` for consistent cross-database querying.
- **Visualization**: Provides an interactive Sigma.js-based graph viewer to explore the emergent world web.

### **Personality Tracker (`personality_tracker`)**
Maintains dynamic character development profiles.
- **Vector Tracking**: Quantifies character personalities across 16 traits (OCEAN, Maslow-like needs, and various prowess/might axes).
- **Rolling Narrative Ledger**: Periodically consolidates personality history into a "Internal Development" summary, ensuring the AI is aware of how characters have changed over time.
- **Evolution**: Updates these traits incrementally based on their actions and dialogue in each turn.
- **Initial Bootstrapping**: Automatically identifies new NPCs and establishes their baseline personality from character sheets or initial scene context, utilizing a project-level cache to avoid redundant extractions.

### **Relationship Tracker (`relationship_tracker`)**
Tracks complex, symmetrical bonds between characters.
- **Five Vectors**: Friendship, Romance, Trust, Fear, and Respect.
- **Symmetrical Modeling**: Ensures consistent feelings between character pairs through a canonical ordering system.
- **Rolling Narrative Ledger**: Periodically (default every 5 turns) consolidates relationship history into a "Narrative Evolution" summary, providing the AI with deep context of shared history and intimate developments.
- **Archetype Engine**: Synthesizes scores into high-level dynamics (e.g., Honorable Rivals, Unshakable Comrades, Soulmates).
- **Reaction Guidance**: Injects an "Active Relationship Dynamics" block into the prompt, predicting character reactions and interpretations of events based on their current bond.
- **Agnostic HUD Integration**: Dynamically pushes a "Relationships" section to the VN HUD, categorizing bonds into "Top Bonds," "Contacts," and "World Dynamics." Includes an interactive "Full Relationship Mapping" modal with search, origin stories, and evolution history.

### **TTS Core (`tts_core`)**
The central Text-to-Speech integration, optimized for real-time responsiveness and narrative consistency.
- **Background Generation**: Triggers TTS requests for dialogue lines as a non-blocking background task using a centralized, gender-aware extraction pipeline.
- **Selective Audio Regeneration**: Utilizing the `HOOK_TURN_UPDATED` hook, the plugin intelligently manages manual edits. It compares the current narrative CRCs against the existing audio archive, surgically deleting orphaned `.wav` files and requesting new TTS only for the modified lines.
- **Centralized CRC Protocol**: CRC32 calculation and text sanitization logic are centralized in the core `utils.js` module. This ensures perfect synchronization between the backend's audio filenames and the frontend's playback requests.
- **Narrator Support**: Can voice narrative lines using a dedicated narrator persona, with robust detection for lines missing explicit character tags.
- **Real-time Monitoring & Archival**: Employs a namespaced dynamic route (`/plugins/tts_core/callback`)—registered at system boot to ensure availability—to receive progress updates and trigger the download of completed audio files.
- **Unified Status Reporting**: Provides detailed visual feedback (e.g., "TTS Regeneration: 2/5 (40%)") via the core UI Notification system.
- **Intelligent Playback**: Prioritizes local archived audio files, falling back to the live TTS server or an emulated mouth animation timer if necessary.

### **Plugin Example Suite (`example_*`)**
Thirteen disabled reference plugins provide clean starting points for third-party authors.
- **Beginner**: Settings, terminal commands, documentation, secret storage, and exported plugin APIs.
- **Intermediate**: Custom file types, custom views, VN client events, structured alias-routed LLM calls, plugin interoperability, and scoped state/facts.
- **Advanced**: Minimal PixiJS takeover and scenario-rich VN GUI intercepts with separated manifest, backend, and frontend payload modules.
- **Release Contract**: Every example uses an `example_*` ID, an `Example:` display name, complete metadata, `isExamplePlugin: true`, and a local README.
- **Safety**: Examples are disabled by default, never persist an LLM provider, and demonstrate lifecycle cleanup and explicit failure handling.

### **World State Tracker (`world_state_tracker`)**
Tracks the "ground truth" of the simulated world.
- **Hard Facts**: Manages Location, Time, Weather, Safety Level, Crowd Density, and Inventory.
- **Elapsed Time**: Calculates total days, hours, and minutes since the beginning of the adventure.
- **Agnostic HUD Integration**: Proactively injects "World Status" (Time, Elapsed, Location, Weather, Safety, Crowd) and "Inventory" sections into the Agnostic VN HUD.
- **Inventory Management**: Tracks item quantities, icons, and descriptions. Includes an interactive "Full Inventory" modal with search capabilities and origin tracking (where/when each item was acquired).
- **Programmatic Synthesis**: Constructs a concise situational brief for every turn, ensuring environmental consistency and including the total elapsed time for the AI's temporal awareness.

### **World Location Tracker (`world_location_tracker`)**
Provides a high-performance interactive map for situational awareness.
- **Dynamic Localization**: Automatically identifies the party's starting location on Turn 1 via an LLM call and tracks movement through subsequent turns via an automated update cycle.
- **Parent-Anchor System**: Supports high-fidelity narrative locations (e.g., "Throne Room") while anchoring them to coordinate-providing "World Nodes" (e.g., "The Palace City"). This ensures the map marker remains accurate even when the party is in a specific sub-location not explicitly defined in the nodes list.
- **Intelligent Movement & Transit**: Analyzes narrative output to determine if the party has stayed, arrived at a new node, or is "In Transit". Employs a "Stayed-by-Default" priority rule to prevent location drift during purely descriptive scenes.
- **Decoupled Logic & GUI**: Separates technical instructions intended for the AI (Prompt Logic) from clean, formatted status readouts for the user (GUI Text). The HUD displays a player-friendly "Adventure Journal" style summary of the current location and nearby points of interest.
- **Configurable World Scale**: Travel distances and times are calculated using project-specific constants (pixels per km, walk speed, winding factor) defined in the `.world` file's `meta` section, allowing for different map scales across projects.
- **Prompt Injection**: Utilizes `HOOK_POST_PROMPT_BUILDER` to inject the current location (coordinates and name) and a list of nearby points of interest into the `worldStateSnapshot`.
- **Large-Scale Mapping**: Utilizes a sophisticated tiling pipeline powered by `sharp` to handle ultra-high resolution (e.g., 10k+) map assets.
- **Interactive Leaflet UI**: Integrates a Leaflet.js-based map viewer into the VN HUD, featuring custom coordinate scaling, smooth panning/zooming, and reactive markers for world nodes and the party's current position.
- **Persistence**: Location state (status, origin, destination, progress, specific location, and anchor node) is stored within each turn's `TurnContext`, ensuring perfect history seeking and continuity.

## The Narrative Generation Lifecycle (The Turn)

Every turn in Fablekin follows a strict, 10-step orchestration pipeline to ensure consistency and performance:

1.  **Turn Inception**: User input is captured and wrapped in a new `TurnContext` (Capsule).
2.  **Prompt Assembly (Parallel Phase)**: The `PromptBuilder` gathers data from multiple slots (RAG, Facts, Chronicles) in parallel.
3.  **Orchestration (Director)**: The AI Orchestrator reviewers the context and generates the "Writer's Brief".
4.  **Generation (Writer)**: The Writer agent generates the narrative response, adhering to the Brief and Canon Lore.
5.  **VN Transformation**: The `VNManager` parses the text into a sequence of sprites, backgrounds, and dialogue steps.
6.  **Simulation & Ledger Update**: The engine extracts new facts (relationships, personality shifts) and updates the SQLite ledgers.
7.  **VFX & Asset Selection**: Assets are automatically resolved based on the narrative context (matching filenames to sprites/BGM), utilizing CRC32 for dialogue-audio synchronization.
8.  **Frontend Broadcast**: The turn is emitted to the UI via `generate-vn-turn-response`.
9.  **Persistence & Diagnostics**: The turn is Gzip-compressed and stored in SQLite, while dual-stream diagnostics (JSON Turn Logs + Console Raw Logs) are written to `workspace/logs`.

## Technical Summary of Fablekin v2.0 (The Refactored Engine)

Fablekin represents a shift from a flat file-based storytelling tool to a high-performance, **state-sensitive narrative simulation engine**. The core architectural pillars are:
1. **Isolated Context (Capsules)**: Every narrative turn is a self-contained object, enabling perfect serialization and history-seeking.
2. **Multi-Agent Orchestration**: Decoupling higher-order narrative "Direction" from immediate "Writing."
3. **Evolutionary Persistence**: Character growth and social dynamics are modeled as numerical vectors that proceed along non-linear curves.
4. **Diagnostic-First Design**: Built-in Waterfall engines and real-time cost auditing treat narrative creation as a technical orchestration process.
