# AGENTS.md

Guidance for AI coding agents working in this repository.

## What this is

Trau is an autonomous, ticket-driven development loop shipped as a single static Go binary (`CGO_ENABLED=0`). It picks a ready tracker ticket (Linear/Jira/GitHub Issues, or an internal issue when no external tracker is configured), drives it through **build → handoff → verify → commit → PR → CI → merge** with one fresh AI-agent subprocess per phase, checkpoints after each phase, and resumes after any interruption.

Read `CONTEXT.md` first — it defines the domain vocabulary (**Provider / Model / Route / Fallback provider / Provider override**) and which near-synonyms to avoid. Use those terms exactly in code, comments, and tickets.

## Language

- **Write in ASD-STE100 Simplified Technical English.** This applies to everything you write: code, comments, commit messages, PR bodies, tickets, and replies to the operator. Keep one idea per sentence, prefer the active voice, use an approved word only in its approved part of speech, and never reach for a synonym of a term you have already used.
- **Read every `CONTEXT.md` before you write, and use its ubiquitous language.** The terms it defines beat any near-synonym, in prose and in identifiers alike. A term the domain model does not define is a term you must not invent on the spot.

## Commands

```bash
make build                 # compile to bin/trau
make reset                 # rebuild + `trau hub restart` — humans only; refuses inside a trau run (TRAU_ACTIVE=1)
make test                  # go test -race ./... — the pre-PR gate; run it locally, nothing runs it for you (TESTFLAGS='-timeout 8m'; see the Tests bullet)
go test -race ./internal/pipeline -run TestVerifyPause   # single test
make vet                   # go vet ./... (runs the make windows gate first)
make windows               # GOOS=windows go build ./... — native-Windows compile gate (ADR 0023)
make lint                  # golangci-lint (installed separately)
make fmt                   # gofmt -w .
make dist                  # cross-compile release matrix into dist/
```

**Rebuild after every feature or ticket** so the change is actually testable. `make build` refreshes `bin/trau`. A running `trau serve` is a port-locked singleton with the SPA compiled into the binary, so it keeps serving the old code until restarted — autostart *reuses* a stale hub, it does not replace it. The web UI's footer shows `web`/`cli` versions; after a rebuild, confirm they reflect the new build (hard-refresh the browser, since the bundle's asset names are not content-hashed).

**The web bundle is generated, never committed.** `internal/webserver/dist` is git-ignored. A tracked bundle made every two deliveries that touch `web/` collide on a binary file that no merge can resolve, which is why it is out of the index now. A fresh clone needs one step: `make build`. It runs the SPA build (`npm ci && npm run build`) and then links the binary, so the hub it produces serves the web UI. `make test` builds the SPA first for the same reason. Only `internal/webserver/dist/.gitkeep` stays tracked, because `//go:embed all:dist` must match one file to compile; the SPA build writes the placeholder back, so a build no longer dirties the working tree. A binary from a bare `go build ./...` still compiles and runs — it answers each page route with a 503 that names `make build`. The release path does not change: `.goreleaser.yaml` rebuilds the bundle in its `before` hooks.

**The hub on :8728 is off-limits during agent runs.** If you are an agent spawned by trau itself (a build/verify/repair/cleanup phase — `TRAU_ACTIVE=1` is in your env), the hub on :8728 is the orchestrator that owns your run: restarting or killing it destroys the run's data channel and pauses the whole loop. The only supported restart is `trau hub restart`, which asks the running hub to re-exec the on-disk binary — never `kill`, never a port grab. `make reset` is `make build` plus that command and refuses outright while `TRAU_ACTIVE=1`; `trau hub restart --force` (the escape hatch for a hub whose API has wedged) refuses in the same situation, and while any loop is live. Both refusals are by design — do not work around them. To QA hub/web changes live, start an **isolated** hub from the dev binary and drive only that instance:

```bash
iso=$(mktemp -d) && TRAU_HOME=$iso/.trau HOME=$iso ./bin/trau serve --port 8799
```

Override BOTH `TRAU_HOME` and `HOME` so the isolated hub cannot see the real `~/.trau` databases. When done, kill only that pid. Never stop, restart, or "clean up" any process listening on :8728 — it was not started by you, even if a port probe makes it look recent. `make reset` is for humans doing interactive dev outside a run.

**QA repos must never impersonate a real one.** The real hub refuses heartbeat roots under the temp dir and prunes the temp-dir and vanished ones it already holds at every startup (COD-1466), but `known_repos` still has no TTL: a clone anywhere else is adopted permanently and the next restart mints a project for it — a clone named `shipflock` becomes a second `shipflock` project the hub then syncs against the real tracker on the shared API budget, and same-named repos render as one wedged row in the repo picker (COD-1465). When QA needs a working target repo:

- Run trau against a clone **only under the isolated hub above**. Anything that heartbeats or registers — `trau serve`, a run, a drain, `--requeue` — pointed at :8728 from inside a clone pollutes the real hub's state permanently.
- Name throwaway clones distinctly — `qa-<ticket>-shipflock`, never the donor repo's own name — so an isolation slip produces identifiable junk instead of a doppelgänger project.
- To exercise *real* hub state (a real quarantined ticket, the real queue), drive the real registered repo itself; do not substitute a clone.
- Delete clones when finished. If one ever reached the real hub anyway, remove it through the web UI's repo management before ending the session.

A hub running a *released* trau (Homebrew, say) cannot be moved onto a checkout by `make reset`: `trau hub restart` re-execs the binary the running process resolves to, which is the release one. For that, Settings → Updates has a **build channel** switch — it rebuilds a registered repo with `HUB_RELOAD_BUILD_CMD` and restarts onto `HUB_DEV_BINARY`, gated on that repo setting `HUB_SELF_RELOAD=1` (ADR 0024). The same section takes a dev hub back: **Rebuild & restart** is `make reset` without the terminal, and **Switch to release** restarts onto the first `trau` on PATH that no registered repo owns. A hub under `trau hub supervise` switches too: the LaunchAgent is rewritten to the chosen binary and handed back to launchd, so its respawn stays on that build. Same rule as above: humans only, never during a run.

Commit messages follow Conventional Commits (`feat(scope):`, `fix:`, …) — release notes are generated from them (ADR 0002). Ticket IDs in commits/comments reference the project's own tracker tickets and act as the design changelog: in a commit that is the change record, in a comment only as a cross-reference to where a decision lives (see the comment policy under *Conventions and invariants*).

## Architecture

`cmd/trau/main.go` is the composition root (~2100 lines): flag parsing, layered config, and the builders (`buildRouter`, `buildTracker`, `buildPipeline`, `buildFallback`) that wire everything through injected interfaces. All modes (TUI session, headless, `--once`, `--dry-run`) converge on `runLoop(ctx, engine, ...)`, tested against the small `engine` interface. Subcommands: `doctor` (preflight) and `watch` (read-only transcript tail via `internal/vterm`).

The target repo is never the trau source tree — it resolves via `--repo` flag → `TRAU_REPO_ROOT` → cwd's git toplevel (ADR 0001). All `git`/`gh` operations act on the resolved target.

### Package seams (internal/)

- **pipeline** — the phase chain. Verify is a *cold, adversarial* pass: the verifier agent sees only the handoff brief (the `handoff` + `rubric` artifacts in the hub store) and the code on disk, never the build agent's reasoning. A mechanical test gate (`testgate.go`) stands between the build tail and verify and spawns no agent: it routes the run straight to repair when the rubric names a test that does not exist, or when a package whose tests the slice changed does not survive `go test -race -count=3`. Everything it cannot measure — a rubric naming no tests, an unlistable diff, a missing toolchain, its own exhausted budget — reads as a pass, so no delivery is ever blocked on the gate's instrumentation. On verify failure: up to `MaxRepairs` repairs, then `MaxBugfixes` bugfixes, then quarantine. Error taxonomy is the core invariant (`classifyPhaseErr`): `GiveUpError` → quarantine + `needs-human` label; `PausedError` → provider rate-limit, work stays at checkpoint; `FaultError` → WIP pushed, resumable, loop stops; `CrossProjectError` → ownership refusal, nothing touched. Epic flow (`epic.go`) stacks sub-issues on an `epic/<ID>-*` integration branch. `lessons.go` keeps an append-only per-repo lessons ledger in the hub store (ADR 0008; the file-era `runs/memory/` JSONL survives only as the one-shot legacy importer's read side), recalled into later verify/repair prompts.
- **agent** — provider abstraction. `Runner.Run(ctx, prompt, label)` spawns a **fresh subprocess per call, never a resumed session** (that's what keeps verify cold). Providers register via `Spec` in `provider.go`; **nothing branches on provider name outside this package**. `router.go` dispatches per canonical phase key (`build/handoff/verify/repair/bugfix/cleanup/lintfix/commit/pick`); dynamic labels like `verify-retry2` collapse by prefix — new phase labels must keep their canonical prefix or they route to `pick`. Execution mode is **per provider, not a project-wide rule**: the claude pipeline provider is `ClaudeInteractive` — a real in-process PTY (`aymanbagabas/go-pty`, no tmux) with a result-file contract, never `-p` (the PTY transcript feeds `watch`/vterm, the auth sniffer, and terminal takeover, ADR 0018) — while codex/kimi run headless `-p --output-format stream-json`.
- **tracker** — hybrid direct-API + MCP-via-agent. Linear uses direct GraphQL when `LINEAR_API_KEY` is set, else the tracker's MCP through an agent prompt with sentinel-line parsing. Jira uses direct REST v3; with full REST credentials the tracker is deliberately rest-only (runner nil) so it can never silently switch to the MCP's different Atlassian identity. GitHub issues are MCP-only; PR/CI operations live in `pipeline` shelling to `gh`. The `internal` provider (ADR 0007) is the default when no external tracker is configured: it drives internal issues through the serve hub's HTTP API (`internal/hubclient`) — pick, status, labels, and comments — so the loop never opens the hub database; `buildTracker` autostarts the hub for it (ADR 0004).
- **state** — the per-ticket phase ranking (building→built→handed_off→verified→pr_open→merged, quarantined=9) and resume logic. Checkpoints are now DB rows the hub owns and migrates forward (ADR 0008); the file-era `.trau/runs/<ID>/state` `KEY=value` store survives only as the one-shot legacy importer's read side. **The phase ranking must stay stable across versions.**
- **config** — precedence: defaults < user layer < `./trau.ini` < project layer < env (`TRAU_<KEY>` alias wins over bare `KEY`) < CLI flags (ADR 0016: repo config beats the machine baseline). The project and user layers are rows in the hub database's `config_values` table, keyed by repo root and by machine (ADR 0051); the ini files they used to be — `<repo>/.trau.ini` and `~/.trau.ini` — are no longer read or written by anything. `./trau.ini` (or `TRAU_ENV`) is the one config file layer left, parsed KEY=value, never executed. All knobs are documented in `trau.ini.example`. Monorepo knobs resolved after a slice's diff is known (e.g. `LINT_FIX_CMD`) additionally check `<workspace>/.trau.ini` for the workspace owning the changed files (`config.WorkspaceOverride`, `agent.OwningWorkspaceDir`; ADR 0019) before falling back to the repo-root value — that per-directory file is not the retired project layer, and `config.Declared` still falls back to it so a Folder repo's child can declare its own `FORGE`/`BASE_BRANCH`. Both surfaces write the same rows: the hub through the handle it already owns, the CLI (`WriteConfigLayer`/`DeleteConfigLayer`, the TUI settings editor, `trau setup`, `trau hub remote on`) by opening `trau.db` read-write for the length of one upsert and creating it when this machine has never started a hub — a deliberate amendment to ADR 0007 §1. Resolution reaches the rows through `config.UseHubConfigLayers` — the hub points it at its own handle, everyone else opens `trau.db` read-only the way `trau doctor` does. On every serve start the hub imports the file era's two layers into the rows once — `~/.trau.ini` and every tracked repo's `<repo>/.trau.ini`, a joining repo at registration time — taking only catalog keys, never clobbering a row already there, and renaming each source file to `.trau.ini.migrated` rather than deleting it; keys the catalog does not list and lines that are not `KEY=VALUE` stay in that file and are named in the hub log and by `trau doctor`. A `.trau.ini` still under its live name decides nothing, so the hub logs it at serve start and `trau doctor` warns about it.
- **event** — one JSON line per significant action to `.trau/runs/events.jsonl`; the durable source of truth. The TUI is display-only on top of it.
- **tui** — Bubble Tea **v2** (`charm.land/bubbletea/v2` imports, not `github.com/charmbracelet`). Two modes: `New` (dashboard renderer for headless-launched runs) and `RunSession` (persistent menu shell). The TUI talks to the backend only through the `tui.Actions` interface and never imports pipeline/tracker/agent wiring; the pipeline talks to displays only through `console.Renderer`.
- **webserver grill (Inbox Interview / Ask ahead)** — the one place hub code **deliberately runs `claude -p` headless** (`grillrunner.go`); do not "fix" it to interactive/PTY. Interview children are short-lived hub-spawned processes whose only I/O is their per-session MCP endpoint (`/api/v1/grill/{sid}/mcp`, tools `ask_user` + `ask_round` + `finish_session`, `grillmcp.go`/`grillround.go`) — the web Inbox panel *is* their terminal, so there is nothing for a PTY to wrap, and the built-in AskUserQuestion tool doesn't exist in print mode. Turns chain via `--resume <session-id>`; a blocked `ask_user` streams SSE keepalives, parks on idle, and the user's later answer fires the resume turn. `ask_round` is the same machinery over a numbered set of independent questions answered as one form: its answers live in `grill_round_answers` keyed by the question's position, so auto-accept can settle the recommended ones before the user sees them and a session parked mid-round resumes on the remainder alone. Every grill prompt default interviews round-by-round at the frontier — one `ask_round` per frontier, `ask_user` only for a genuine single follow-up. First-turn prompts + rule blocks are hardcoded in `grillprompt.go` (not in the ADR 0017 prompt catalog). Mechanism spec: `tasks/grilling-prd.md` (COD-865/877 research, verified on CLI 2.1.207).
- Supporting: **budget** (spend ceilings), **checks** (pluggable verify checks from `.trau/checks` YAML, executed by the verify agent), **folderrepo** (a Folder repo's Child repos — a registered folder that is not a git repository itself, scanned at run time for the git repos directly inside it, which are the run's ship targets; ADR 0030), **forge** (which code host a repository's own remote points at and which branch that host calls default — read per repo and per Child repo, never inferred from the tracker and never taken from the checked-out branch; delivery reaches GitHub via `gh` and Bitbucket Cloud via `forge/bitbucketapi`, and a repo elsewhere — or a Bitbucket repo with no `BITBUCKET_EMAIL`/`BITBUCKET_API_TOKEN` — is refused before a run spends anything, ADR 0032 + ADR 0036), **skillrules** (repo-owned per-skill routing rules from `.trau/skills-rules.json` — `always`/`auto`/`manual` scopes matched against the ticket text at build and the slice's changed files after it; `agent.SkillResolver` folds them together with the config pins and the never-empty fallback chain, ADR 0021), **tokens** (normalized per-call token/cost JSONL; "Input" = non-cached portion so totals compare across providers; `CostUSD *float64` nil = unmetered), **usage/probe** (rate-limit windows for the HUD), **teamsync** (opt-in `TEAM_SYNC` sharing of lessons and settled-run summaries over the target repo's own git remote: the hub — never a loop child — force-pushes this machine's records as a parentless snapshot to `refs/trau/team/<writer-id>` and mirrors the teammates' back into `refs/trau/remotes/team/*`; refs only, never the working tree, and every failure is recorded for doctor rather than raised. Teammate runs are served from their own `team-runs` resource, never folded into `/runs`, so nothing that means *this machine's work* — the picker, the queue, the drain, the attention counts — can pick them up), **vterm** (reconstructs legible screens from raw PTY transcripts), **launchd** (the opt-in macOS LaunchAgent that keeps the hub up — `trau hub supervise` installs it with KeepAlive, the plist's `TRAU_SUPERVISED=1` makes a self-restart exit instead of racing launchd's successor for the port, ADR 0022), **sanitize**, **doctor**, **notify**, **timelog**, **logger**, **console**.

### Conventions and invariants

- **stdout is byte-stable** — all diagnostics (`--verbose`, `--debug`) go to stderr only; `--json` output must not change.
- Best-effort operations (logging, notify, timelog, gitignore maintenance) must **never abort the loop** — swallow-and-continue is the convention.
- Quarantine is idempotent.
- **The queue reconcile sweep never launches anything** (`drainer.reconcileQueue`, ADR 0022): on hub boot and on every drain arm it settles a paused, failed, or awaiting-merge item *done* only on proof its work already shipped — a merged checkpoint, a tracker Done, or a merged PR — and leaves everything else exactly as it was. Auto re-attempts are a separate, opt-in path (`QUEUE_AUTO_RESUME`) and fire only for a blameless pause, never for a fault or a deliberate Stop.
- **`trau serve` exposure is fail-closed** (`internal/webserver`): a loopback bind is open and tokenless; any non-loopback bind requires `SERVE_TOKEN` — the server refuses to start exposed without one, and the whole API is gated behind `Authorization: Bearer <token>` (401 otherwise). Repo (un)registration is gated a second time: on a non-loopback bind it also requires `SERVE_ALLOW_REGISTER=1` (403 otherwise, naming the key), so a leaked token cannot widen the hub's startable-repo set. The blessed remote path is a private network / Tailscale, never a public port — `SERVE_REMOTE=tailscale` automates exactly that path (`trau hub remote on` writes it; `reconcileServeRemote` re-establishes the tailnet forward on every hub start) and widens nothing: the bind stays loopback, so the exposure policy above is untouched, and a tailnet that cannot carry the hub is a startup warning rather than a refusal to serve locally.
- Tests: table-driven with subtests; hand-rolled fakes shared across the package — `fakeGit`/`fakeRunner`/`fakeTracker`/`newTestPipeline` live in `internal/pipeline/verify_pause_test.go` and other test files embed/extend them. Golden files only in `internal/state/testdata`. **No test may reach a real external API, and this is enforced rather than assumed** (ADR 0027): `internal/netguard` installs a deny-by-default `http.DefaultTransport` in every test binary — a request to anything but a literal loopback address prints the offending URL and exits the binary non-zero, with no env var, build tag or setter to turn it off. Every package with test files carries a `netguard_test.go` holding nothing but the package clause and `import _ "github.com/RomkaLTU/trau/internal/netguard"`; `make test` runs `internal/netguard/check` first and refuses to run any test when a package omits it or when production code imports the guard. Everything else goes through the interface seams. Two more things keep a test binary independent of the machine running it. The hub database schema is stamped into each test's home from a template migrated **once per test binary** (`internal/hubdb/hubdbtest`, a drop-in for `hubdb.Open`), so a test's cost no longer scales with the 56-file migration ladder — packages exercising migration itself still call `hubdb.Open` and keep that coverage. And every package whose tests shell out to `git` wires `internal/gittest` into its `TestMain`, pinning `GIT_CONFIG_GLOBAL`/`GIT_CONFIG_SYSTEM` at a fixed identity: the production code under test inherits the plain process environment, so without it the developer's `~/.gitconfig` decides whether a commit made by that code succeeds. Measured 2026-08-03 in a two-core `golang:1.25` container, the whole `-race` suite runs in **3m30s**; the slowest packages are `internal/webserver` (128s), `internal/hubstore` (36s) and `internal/hubdb` (25s, the migration ladder it deliberately still pays). `-timeout` is per package, not per suite, and the gate passes `8m`.
- **Spawned children carry no ambient memory** — every spawn seam builds its environment with `agent.ChildEnv`, which strips the host Claude Code session markers *and* sets `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`. Auto-memory is keyed to the git repo, not the session, and is shared with the operator's own sessions: a memorizing child would hand the build phase's reasoning to the cold verifier and persist prompt material (QA credentials) to a plaintext store trau doesn't own.
- **Every decision assumes Windows, Linux and macOS** — trau is developed on all three. OS-divergent behavior goes behind a shared contract with `*_unix.go` / `*_windows.go` implementations (`internal/proc`), never an OS branch at the call site; ADR 0023 requires unix behavior stay byte-identical while Windows reaches the same contract by a different mechanism. Never fix a Windows failure by skipping the test on Windows or by changing darwin/linux behavior — triage as production bug vs unix-assuming test and fix in the right layer. Acceptance criteria are "green on all three OSes." **There is no PR-triggered CI** — GitGuardian's secrets scan is the only check a PR gets — so run `make fmt && make vet && make test` locally before opening a PR: that covers the suite on your own OS plus the native-Windows *compile* gate (`make vet` runs it first); nothing runs the suite on the other two OSes before merge, so say "unverified" for those rather than implying they passed (`make -n <target> HOST_GOOS=linux` proves only the emitted command).
- **A migration's version number is claimed by its filename, so parallel branches collide silently.** `internal/hubdb/schema/NNNN_<name>.sql` — two branches both taking the next free `NNNN` merge cleanly and produce a tree no binary can open the hub database from (`migrateAll` refuses duplicate versions outright). Renumbering the later one is safe and is the fix: migrations are tracked by name, not version, so a database that already ran it under the old number is not asked again. `TestEmbeddedMigrationsAreUniquelyNumbered` catches the collision in CI.
- **Comments must earn their place — why, never what.** The house style favors dense editorial doc comments carrying invariants, concurrency notes, design rationale and ADR/ticket cross-references; keep writing those, in that voice. Never add: narration that restates the adjacent code, section-banner comments, change-log narration (what the code previously did, now does, or which ticket changed it), commented-out code, or name-restating doc comments on trivial unexported declarations. Terse godoc on exported identifiers is Go convention and stays. Ticket IDs and ADR numbers appear in comments only as design cross-references — where a decision lives — never as change narration. The `no-low-value-comments` check in `.trau/checks/checks.yaml` gates this over a slice's own diff.
- **Web UI tooltips & labeling** — an icon-only control is an `IconButton` (`web/src/components/trau/icon-button.tsx`): `label` is required and becomes both the `aria-label` and the default hover text, `tooltip` overrides the hover text when it should differ from the name (`Editor: VS Code`), and a control the user cannot press explains itself through `disabledReason` rather than going silent. Every other hover explanation goes through `ui/tooltip.tsx` — never the native `title=`, which no touch or keyboard user ever sees and which cannot be styled or themed. One `TooltipProvider` at the app root owns the timing (300ms, instant between neighbours); do not mount a second. Icons stay `aria-hidden` — the label on the control is the accessible name.
- Architecture decisions live in `docs/adr/`; add an ADR for decisions of that scope.
