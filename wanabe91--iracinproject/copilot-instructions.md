## О проекте

Анализатор мастерства пилота для iRacing: читает бинарные файлы телеметрии
`.ibt`, режет сессию на круги, находит повороты трассы автоматически, считает
метрики круга/поворота и сравнивает каждый круг с эталоном (лучшим чистым
кругом), выдавая текстовые подсказки о том, где и почему теряется время.
Есть CLI для импорта/анализа и FastAPI-бэкенд, отдающий JSON дашборду
(маршрут `/analysis`). Сайт открывается входом: на `/` —
страница входа по макету Claude Design. Дальше развилка `/main`:
живая телеметрия (`/live`) и разбор прошлых заездов (`/analysis`). Вход не
обязателен — на развилку ведёт и ссылка «без входа», потому что локальный
анализ учётки не требует.

Требует Python >= 3.14, менеджер пакетов — `uv`. Фронтенд — Vite + Vue 3 SFC + TypeScript + Pinia + vue-router в `frontend/`.

## Команды

```bash
uv sync                                    # установить Python зависимости
cd frontend && npm install                 # установить frontend зависимости
cd frontend && npm run build               # собрать фронтенд в web/dist
cd frontend && npm test                    # запустить Vitest тесты фронтенда
uv run pytest                              # все Python тесты
uv run pytest tests/test_laps.py -v        # один файл тестов
uv run pytest tests/test_laps.py::test_name -v   # один тест
uv run iracing-coach import [путь]         # импорт .ibt (файл или папка), по умолчанию Documents/iRacing/telemetry
uv run iracing-coach analyse               # пересчитать повороты/эталоны/подсказки без нового импорта
uv run iracing-coach stats                 # сводка по базе
uv run iracing-coach sync                   # синхронизировать онлайн-кэш iRacing (нужна учётка)
uv run iracing-coach gen-types              # перегенерировать web/api-types.d.ts из pydantic Response-моделей
uv run pyright web/app                      # проверка типов фронта (strict; pyright ставится через uv, без npm)
uv run uvicorn iracing_coach.api:app --reload --port 8712   # HTTP API + дашборд (см. .claude/launch.json)
```

Реальных `.ibt` в репозитории нет (десятки МБ); юнит-тесты собирают
синтетический файл той же двоичной раскладки через `build_ibt`/`synth_ibt` в
[tests/conftest.py](tests/conftest.py). Тесты, помеченные
`requires_real_telemetry`, пропускаются, если в `~/Documents/iRacing/telemetry`
нет настоящих файлов.

## Архитектура

### Конвейер импорта — два независимых прохода ([ingest.py](iracing_coach/ingest.py))

Это ключевой инвариант, который нельзя нарушать:

- **`import_file`** — разбор одного `.ibt`: круги, метрики круга. Зависит
  только от самого файла. Идемпотентен по `file_hash` (blake2b от содержимого).
- **`analyse`** — разметка поворотов трассы, выбор эталонного круга,
  пер-поворотные метрики, подсказки. Зависит от *всей* накопленной базы —
  эталон улучшается с каждой новой сессией.

Смешивать проходы нельзя: первый же импорт разметил бы повороты по случайному
кругу, и все последующие сравнения унаследовали бы эту случайность.
`ensure_turns` при этом никогда не переписывает уже размеченные повороты —
как только пилот (`source='manual'`, см. `PATCH .../turns/{turn_no}`) или прошлый
прогон их зафиксировал, автоматика их не трогает. Повороты размечаются на
**связку трасса+машина** (`turns.car_id`), а не только на трассу: границы и точка
торможения зависят от машины. Поэтому разметка и `_turn_ids` идут внутри цикла по
машинам в `analyse`.

### Хранилище: SQLite + Parquet ([db.py](iracing_coach/db.py), [traces.py](iracing_coach/traces.py))

- **SQLite** (`data/iracing.db`) — только метаданные и метрики: `tracks`,
  `cars`, `sessions`, `laps`, `turns`, `refs`, `findings`. Метрики (`lap_metrics`,
  `turn_metrics`) хранятся в длинном формате ключ-значение, а не колонками —
  набор метрик растёт с каждой идеей, и не хочется гонять миграции схемы под
  каждую.
- **Parquet** (`data/laps/<session_id>/<lap_no>.parquet`) — сама трассировка
  круга, приведённая к сетке из 1000 точек по дистанции. Круг всегда читается
  целиком и колонками, поэтому здесь Parquet эффективнее строк в БД.

### Версия схемы и миграции ([db.py](iracing_coach/db.py))

Форма схемы пронумерована, номер лежит в самом файле базы (`PRAGMA
user_version`). Причина: `CREATE TABLE IF NOT EXISTS` создаёт недостающие
таблицы, но ничего не знает о недостающих *колонках* — база, созданная до
появления `turns.car_id`, молча оставалась старой формы, и запрос к
несуществующей колонке падал уже в API, а фронт показывал это как «нет
эталона».

Правила:

- `SCHEMA` — форма **текущей** версии, применяется только к пустому файлу.
  Существующие базы доводятся до неё шагами из `MIGRATIONS`.
- Новая колонка = новый шаг в `MIGRATIONS` **и** +1 к `SCHEMA_VERSION`. Правка
  одной только `SCHEMA` до существующих баз не доедет; это стережёт тест
  `test_migrations_end_at_schema_version`.
- Снимки формы внутри шага (`_TURNS_V2` и т.п.) скопированы, а не собраны из
  `SCHEMA`: миграция описывает переход между двумя зафиксированными формами, и
  следующая правка `SCHEMA` не должна задним числом менять смысл старого шага.
- Пилотское не пересоздаётся: `turns.source='manual'` и `turn_notes` миграция
  обязана сохранить (перестройка таблиц идёт с сохранением `id`, поэтому ссылки
  остаются валидными). `turn_metrics`, `findings`, `refs` и авторазметка —
  производные, их всегда пересоберёт `ingest.analyse`.
- Мигрируют **только пути записи**: `connect(ensure_schema=True)`, то есть CLI.
  Читающим (HTTP-слой) нужен `check_version` — он только читает и потому не
  берёт блокировку записи. Несовпадение версии — 500 с текстом «что делать»,
  а не пустой ответ; расхождение видно и в логе uvicorn при старте.

### Общая ось сравнения: сетка по дистанции ([laps.py](iracing_coach/laps.py), [grid.py](iracing_coach/grid.py))

Сравнивать круги по времени бессмысленно — один и тот же поворот в разные
моменты. Поэтому `resample_lap` приводит каждый круг к единой сетке `dist_pct`
(1000 точек, интерполяция `np.interp` с подмешиванием контекста соседних
кругов на краях, чтобы не зажимать интерполяцию к константе на границе). Все
последующие метрики и дельты — операции «точка трассы к точке трассы».
`grid.py` — общая арифметика по кольцевым участкам (когда `start_idx > end_idx`,
т.к. участок пересекает линию старт-финиш); ей пользуются все модули метрик,
чтобы не переоткрывать этот случай.

### Поиск поворотов ([turns.py](iracing_coach/turns.py))

Признак поворота — кривизна траектории `κ = |YawRate| / Speed`, а не боковое
ускорение (которое сливает быструю пологую дугу и медленную шпильку в один
сегмент). Апексы — пики кривизны, отобранные по prominence, число подгоняется
под `TrackNumTurns` из session info. Дистанция между апексами задаётся в метрах
(`MIN_TURN_SEPARATION_M`), а не в долях круга, иначе короткие трассы теряют
повороты. Авторазметка — только стартовая точка: границы можно поправить руками
(`PATCH`-ручка), и такие повороты (`source='manual'`) переживают повторный
`analyse`.

### Метрики и подсказки ([metrics/](iracing_coach/metrics/), [coach.py](iracing_coach/coach.py))

- `metrics/lap.py`, `metrics/turn.py` — числовые метрики (точка торможения,
  скорость в апексе, доводка тормоза, реверсы руля и т.д.), все доли времени
  считаются взвешенно по `sample_intervals`, а не по числу точек сетки (иначе
  прямая и шпилька весят одинаково).
- `metrics/delta.py` — `per_turn_delta` режет круг на участки «вход в
  поворот → вход в следующий» так, чтобы участки покрывали круг целиком и сумма
  дельт точно равнялась отставанию круга; потеря на выходе из поворота
  засчитывается повороту, а не следующей прямой. `ideal_lap_time` тем же разрезом
  собирает «идеальный круг» — лучший участок из всей выборки чистых кругов, с
  указанием круга-источника; отдаётся ручкой `/api/laps/{id}/ideal?scope=all|session`.
- `coach.py` превращает метрики в `Finding` (правило + сообщение + `time_loss_s`).
  На поворот выдаётся не более одной подсказки: если бы каждое сработавшее
  правило несло полную дельту поворота, сумма по списку была бы кратно больше
  настоящего отставания.

### Формат `.ibt` и session info ([ibt.py](iracing_coach/ibt.py), [session_info.py](iracing_coach/session_info.py))

`IbtFile` мапит файл через `mmap` и читает нужные каналы (`DEFAULT_CHANNELS`)
одним `np.frombuffer` со structured dtype — поканальные seek'и на ~283 каналах
и десятках тысяч записей неоправданно медленные. Session info у iRacing
называется YAML, но им не является (имена пилотов ломают строгий парсер),
поэтому `session_info.py` — точечное регэксп-извлечение нужных полей, а не
YAML-парсер.

### HTTP-слой ([api.py](iracing_coach/api.py))

FastAPI отдаёт JSON под `/api/*` и собранный SPA из `web/dist/index.html`. Соединение с БД
открывается на каждый запрос через контекст-менеджер `_conn()` и закрывается
после — иначе хэндлы утекают и импорт блокируется. Читающие ручки не создают
схему БД (`ensure_schema=False`), чтобы `executescript` не брал блокировку
записи и не мешал параллельному импорту; вместо этого `_conn()` зовёт
`db.check_version` (только чтение) и отдаёт 500 с диагностикой, если форма базы
не та.

На стороне фронтенда клиент API (`frontend/src/shared/api/client.ts`) обязан проверять
`response.ok` — у ошибки FastAPI тело тоже JSON (`{"detail": …}`), и без
проверки оно уезжает дальше как данные. 404 гасится где применимо, всё остальное показывается баннером.

### Фронтенд: Vite + Vue 3 SPA ([frontend/](frontend/))
### Response-модели и TypeScript-типы ([api_models/](iracing_coach/api_models/), [codegen.py](iracing_coach/codegen.py))

Каждая ручка `api.py` с dict/list[dict]-ответом несёт `response_model=` —
OpenAPI на `/api/docs` показывает реальные ответы, а не «объект неизвестной
формы». Модели живут в пакете `iracing_coach/api_models/` (6 подмодулей по
группам ручек: метрики, сессии, повороты, инженер, настройки, auth/live),
`__init__.py` реэкспортирует все 45 имён через `__all__`. Входные
pydantic-модели (`ImportRequest`, `TurnEdit`, `LoginBody` и т.д.) остались
в `api.py` — это Response-этап, не реорганизация входных схем.

`uv run iracing-coach gen-types` перегенерирует `web/api-types.d.ts` из
этих моделей — контракт, по которому фронт тайпается в редакторе (JSDoc
`@typedef {import('/static/api-types').X}` + `// @ts-check`). Файл
коммитится; снапшот-тест `tests/test_codegen.py` падает, если модели и
`.d.ts` рассинхронизировались — после любой правки `api_models/` надо
перегенерировать и закоммитить `.d.ts`.

Генератор самописный, без `pydantic-to-typescript`/`json2ts` (npm): тот
пакет под капотом зовёт Node, что ломает инвариант `uv sync` как
единственной установки. Рендерер обходит `model_json_schema()` (чистый
pydantic v2) и пишет `interface`-ы с сортировкой по имени модели —
идемпотентно, порядок полей внутри interface = порядок определения модели.
SSE-кадры (`EngineerEvent`, `LiveFrame`) описаны в нижнем блоке `.d.ts`
вручную: стримы отдают `dict` напрямую через `_sse()`, pydantic их не
знает, и в OpenAPI их нет.

**Сознательное отклонение от строгого 1:1**: опциональные поля моделей
(`ProviderView.error`, `ProfileResponse.career`, `reference_lap_id` без
эталона и т.п.) после постановки `response_model=` сериализуются как
`null` даже в ok-ветках, где раньше их не было. `exclude_none` не подходит
глобально (убрал бы легитимные `None`). В TypeScript это даёт `T | null`
вместо `T | undefined` — фронт с optional chaining обрабатывает их
идентично, но при желании фиксится точечно. `TurnNoteRow.created_at` —
`string`, не `datetime` (sqlite хранит дату через пробел, не ISO).

**Проверка типов фронта в CI** — `uv run pyright web/app` (strict,
конфиг в `pyrightconfig.json`). `pyright` ставится через
`uv add --dev pyright` и тянет `nodeenv` — Node под капотом ставится
сам, без отдельной `npm install`, поэтому инвариант `uv sync` как
единственной установки не нарушается: пользователь не видит второго
тулчейна, только `uv run pyright web/app` как еще одну проверку рядом с
`uv run pytest`. `web/app/*.js` тайпятся через `// @ts-check` + JSDoc
`@typedef {import('/static/api-types').X}`; `paths /static/*` в
`tsconfig.json` резолвит импорты к `web/api-types.d.ts`. Команда не
блокирует основной `pytest` — это отдельный шаг; снапшот `.d.ts`
(`tests/test_codegen.py`) страхует контракт даже без pyright.


### Фронтенд: Vue без сборки ([web/](web/))

Фронтенд собран в Vite 8 + Vue 3 (SFC `<script setup lang="ts">`) + Pinia 4 + vue-router 4 + TypeScript.
Результат сборки отдаётся из `web/dist`.

- Марка (svg-логотип с дугами и красным апексом) вынесена в `shared/ui/BrandMark.vue`.
- Стили разбиты на дизайн-систему: `tokens.css` (единственное объявление `:root`), `base.css`, `motion.css`, `chrome.css`.
- Токены расхождений разведены по именам: `--ink` (`#f2f2f2` для тёмного фона витрин) / `--ink-2` (`#e8e8e8` для интерфейса), `--ink-dim` (`#8a8a8a`) / `--muted` (`#9c9c9c`).

**Страницы отдаются только через `_page()`** (`api.py`), то есть с
`Cache-Control: no-cache`. Голый `FileResponse` шлёт `last-modified`/`etag` и
ни одного `Cache-Control`, а без него браузер берёт эвристическую свежесть
(долю возраста файла) и отдаёт страницу из кэша, вообще не сходив на сервер.
Правка вёрстки после этого часами не видна — причём молча. `no-cache` не запрещает хранить, а требует переспроса. Стережёт `test_pages_are_revalidated_by_browser`.

**Вход и гейт профиля:**
За входом стоит один профиль — `/profile` без учётки уводит на `/?next=/profile`.
Гейт двухслойный:
1. Серверный редирект в `api.py` (ловятся прямые переходы по URL).
2. Клиентский guard `attachAuthGuard` в `app/router/index.ts` (ловятся внутри-SPA клики по `router-link`).

Два неочевидных требования к гейту:
- `/profile` идет с `no-store` (`_NO_STORE`), запрещая хранение в кэше браузера.
- `next` на стороне `LoginPage.vue` фильтруется от Open Redirect (`safeNext`).

### Realtime-слой: живая телеметрия ([realtime/](iracing_coach/realtime/))

**Live-дельта** (`realtime/delta.py`, `realtime/reference.py`). Эталон берётся
из `refs` по связке трасса+машина — той же, на которой размечены повороты.
Идентичность спрашивается у источника **на каждый заход** в него, а не один раз
при старте процесса: за обрывом почти всегда новая сессия, а с ней другая
трасса, и однажды прочитанная идентичность считала бы дельту к чужому эталону.
Это осознанное ограничение, а не баг: смена машины или трассы **в течение
одной сессии без обрыва связи** (тестовый день, гараж) идентичность не
перечитывает, и дельта продолжит считаться к эталону прежней связки до
следующего переподключения источника.
Кривая эталона замыкается точкой `(1.0, duration_s)`: сетка `resample_lap`
кончается на 0.999, и без замыкания `np.interp` зажала бы последний 0.1% круга
к константе — ровно там, где на дельту и смотрят. Провайдер работает на
**отдельном** sqlite-соединении: то, что у `TextChannel`, пишется ещё и из
воркера LLM. Любой отказ (нет эталона, битый Parquet, непригодная схема,
сломанный session info) — это состояние `no_ref` на экране, а не упавший
фоновый поток.

### Онлайн-слой: webdata/ ([webdata/](iracing_coach/webdata/))

`webdata/` — строго надстроечный пакет, по образцу `ai/`: ядро (`ingest.py`,
`ibt.py`, локальный CLI-анализ) его не импортирует и не знает о нём, а SDK
`iracingdataapi` подгружается лениво изнутри `client.py`, а не на импорте
пакета — оба инварианта проверяет `tests/test_webdata_isolation.py`.

Вход — OAuth2, grant `password_limited` (легаси-вход по паролю iRacing вывел
2025-12-09). Пароль пользователя нигде не хранится: он нужен ровно один раз,
чтобы получить токены. В `keyring` лежат только `client_secret` приложения и
одноразовый refresh-токен; email и `client_id` — не секреты, в `settings.json`
(`credentials.py`). `oauth.py` — нижний слой: грант и рефреш к
`oauth.iracing.com/oauth2/token` через `requests` (без SDK), с маскировкой и
пароля, и секрета по схеме iRacing `base64(sha256(secret + id.strip().lower()))`
(id — email для пароля, `client_id` для секрета). `client.py` ужат до носителя
bearer-токена: сам SDK 1.4.4 никакого OAuth не делает, только шлёт готовый
`access_token` заголовком.

`auth.py` держит access-токен (~600 с) только в памяти процесса и рефрешит по
истечении. Refresh одноразовый — новый сохраняется **сразу, до** использования
нового access-токена, иначе обрыв между «старый использован» и «новый сохранён»
рвёт цепочку и требует повторного входа. `invalid_grant` (refresh истёк или
отозван) стирает refresh-токен и уводит на вход; сетевой сбой — просто `None`,
учётку не трогаем. Вход при этом мягкий шлюз, а не жёсткая блокировка:
`auth.client()` при отсутствующей учётке или недоступном iRacing отдаёт `None`
вместо исключения, и HTTP-читатели (`/api/catalog/*`, `/api/profile`)
деградируют до того, что уже есть в базе, а не падают.

`sync.py` тянет каталог машин/трасс и профиль пилота через живой клиент и
складывает их в БД (схема v5); `match.py` сопоставляет онлайн-каталог с
локальными `tracks`/`cars` по имени. CLI-команда `sync` (см. `cli.py:cmd_sync`)
— единственный путь записи из этого слоя; пароля она больше не касается вовсе, а
логинится через `auth.client()` по сохранённому refresh-токену. Остальной CLI
(`import`, `analyse`, `stats`) как был, так и остался account-free.

**Заморозка регистрации OAuth-приложений.** С декабря 2025 iRacing не выдаёт
новые пары `client_id`/`client_secret` (Account → OAuth2 Applications недоступен
для новых заявок). Из этого следует: текущий refresh-токен в `keyring` —
дефицитный, невосполнимый ресурс, пока регистрация не откроется вновь.
`invalid_grant` (протух или отозван) стирает его — это конец онлайн-доступа для
этой учётки, а не временный сбой: повторный `login()` по паролю ничего не
починит без валидного `client_id`/`client_secret`, которых больше негде взять.
Поэтому `auth.client()` (см. выше) различает сеть и `invalid_grant` не только
ради корректности, но и чтобы транзиентный сбой сети не спровоцировал
случайную потерю токена — контракт закреплён тестами в `test_webdata_auth.py`
(`clear_tokens()` вызывается только на `invalid_grant`, никогда на
`WebDataError`). `TokenResponse.refresh_token_expires_in` (когда iRacing его
присылает) переводится в абсолютное ISO-время и лежит в
`settings.iracing_refresh_expires_at` (не секрет); `cmd_stats` печатает
предупреждение о дедлайне, если он известен, и молчит, если нет. Локальный
анализ (`import`/`analyse`/`stats` без сетевой строки, дашборд `/analysis`) от
этого слоя не зависит вовсе и продолжит работать, даже если online-доступ
кончится насовсем.

### Онлайн-слой: garage61/ ([garage61/](iracing_coach/garage61/))

`garage61/` — второй онлайн-источник рядом с `webdata/`, по тому же инварианту:
ядро (`ingest.py`, `ibt.py`) и `api.py` его не импортируют на уровне модулей
(импортируют только `from .garage61 import auth as garage61_auth`, как
`webdata_auth`), а `garage61api` подгружается лениво изнутри `client.py`.
Проверяет `tests/test_garage61_isolation.py` — зеркало `test_webdata_isolation.py`.

Главная ценность слоя — **внешние эталоны**: сегодня коуч сравнивает круг только
с собственным лучшим, а Garage61 даёт телеметрии кругов тиммейтов/друзей под
сопоставимыми условиями, и коуч становится полезным с первого дня. Три потока
ценности: community-эталоны (лучший круг тиммейта как `refs.kind='community'`),
статистика пилота (`me/statistics` в `garage61_profile`), чужие сетапы под связку
(`community_setups`, ранжированные по близости условий к текущей сессии).

**OAuth — authorization_code + PKCE** (RFC 7636), а не iRacing-овский
`password_limited`: браузер пилота уходит на `garage61.net/api/oauth/authorize`,
возвращается на `/api/garage61/callback`. `code_verifier`/`state` живут в
кратковременном in-memory кэше процесса (`auth._pkce`, TTL 300 с); на диск их
писать нельзя (verifier — половина секрета PKCE). Маскировки секрета НЕТ
(standard OAuth, в отличие от iRacing `base64(sha256(...))`). CLI-only вход
(`garage61 login`) — out-of-band: печатает URL, читает `code` из stdin, обмен тем
же `oauth.exchange_code` (риск R1 — смягчён). `invalid_grant` → стирает refresh и
`None`; сеть → `None` без чистки (мягкая деградация, как `webdata`).

**Источником кругов идут только чужие** (`drivers=['following']` без `'me'`):
мои круги на Garage61 дублируют локальный `best` и не несут ценности. Если
faster-than-me нет среди following/тимейтов — фича молча спит. Сетапы — топ-N под
связку с условиями (температура/влажность/топливо круга-источника), и
AI-инженер получает ранжированный по близости условий список через инструмент
`community_setup`, а не один «самый быстрый» (сетап зависит от условий).

**Схема v7** (аддитивная миграция): `community_laps` (топ-N чужих кругов,
`g61_lap_id` UNIQUE, не в `laps`/`sessions` — иначе замутятся списки и сводка),
`garage61_profile` (синглтон `id=1`, JSON-снимок), `community_setups`, и две
колонки `refs.lap_time`/`duration_s` (nullable — у best дублируют `laps`, у
community единственный источник времени, т.к. `lap_id=NULL`). `compare`/`ideal`
читают эталон **только из `refs`** (R6 — унификация пути: не джойнят `laps` для
эталона). Ресемплинг CSV (`csv.resample`) — зеркало `laps.resample_lap`, но без
Lap-объекта: нормирование `dist_pct` на собственный `LapDist.max()` (R5 —
эффективная длина круга и `length_m` из каталога расходятся на пару метров).

**Мягкая деградация на каждом уровне**: нет учётки / нет Pro-плана / нет сети /
нет following под условия / мост ID не сработал — `fetch_top_n`/`fetch_setups`
возвращают `0`, `auth.client()` отдаёт `None`, фича молчит, локальный анализ не
страдает (зеркало контракта `webdata`). Регистрация OAuth-приложений Garage61
открыта (в отличие от iRacing), поэтому `invalid_grant` здесь — конец онлайн-доступа
до повторного входа, но не невосполнимая потеря.
