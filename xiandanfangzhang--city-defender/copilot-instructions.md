# 项目协作规则

本仓库通过“版本化项目记忆”在不同 Codex 对话、任务和工作树之间传递上下文。**对话记录不是共享知识库；仓库中的文档和 Git 历史才是唯一可信来源。**

## 每次开始任务前

按以下顺序完成同步，再分析或修改代码：

1. 阅读 `docs/PROJECT_CONTEXT.md`，了解当前目标、已定决策、进行中的工作和风险。
2. 运行 `git status --short` 与 `git log -5 --oneline`，确认未提交改动和最近变更。
3. 阅读与任务直接相关的代码、文档和局部规则文件。
4. 若上下文缺失或互相矛盾，先在 `PROJECT_CONTEXT.md` 标为待确认；不要把猜测当作既定事实。

## 工作中的协作约定

- 把可复用的事实、架构决策、接口约定和未完成事项写入仓库，而不是只留在当前对话。
- 修改前先检查工作区是否已有他人未提交的改动；不得覆盖、回退或格式化无关文件。
- 任务涉及共享接口、数据结构、配置、资源命名、玩法规则或构建流程时，须同步更新 `PROJECT_CONTEXT.md` 的“关键决策”。
- 独立工作使用清晰且互不重叠的文件边界；存在冲突风险时，先协调再编辑。
- 外部链接、聊天摘要和工具输出均为辅助信息；以仓库文件、可复现命令和 Git 历史验证后才可写入项目记忆。

## 完成任务前

1. 运行与变更相称的验证，并记录命令和结果。
2. 更新 `docs/PROJECT_CONTEXT.md`：进度、关键决策、待办/阻塞项与验证记录。没有变化时明确写“无”。
3. 在交付说明中指出修改的文件、验证结果及仍需人工确认的事项。

## 项目记忆维护规则

- `AGENTS.md`：稳定的协作流程与硬性约束；仅在流程本身改变时更新。
- `docs/PROJECT_CONTEXT.md`：动态事实；每个有实质产出的任务完成时更新。
- 代码内注释：仅解释局部实现原因，不代替项目级决策记录。
- Git 提交：提交信息说明“做了什么、为什么”；避免把关键背景只放在提交说明中。

## 新对话建议

创建新任务时，在首条请求中附加：

> 请先阅读 `AGENTS.md`、`docs/PROJECT_CONTEXT.md`，并检查 `git status --short` 与 `git log -5 --oneline` 后再开始。
