# Repository Guidelines

## Project Structure & Module Organization

`lyca/` contains the Python implementation. Core runtime components live in `lyca/core/`, skill interfaces and examples in `lyca/skills/`, and inspection helpers in `lyca/debug/`. The runnable entry point is `lyca/demo.py`. Architecture and behavior specifications are under `docs/`; consult the matching versioned document before changing a core contract. `data/` holds demo/runtime state, including memory JSON, the append-only Chronicle, blob content, the Skill Registry, and the model-facing compact Skill Catalog projection. Docker Compose bind-mounts this host directory to `/app/data` by default; override it with `LYCA_DATA_HOST_PATH`. The Agent workspace is a separate `/workspace` Docker volume. Treat generated data as state, not source code.

The separate Admin BFF and OneBot bridge may share `data/chronicle/chronicle.jsonl`; Admin BFF read/write request boundaries explicitly refresh the Chronicle reader, which incrementally absorbs complete external JSONL appends by inode and byte cursor. This synchronizes Chronicle visibility only; Task, Memory, and Agent worker projections remain process-local until distributed reconciliation exists.

## Documentation Synchronization

Every completed code change must update the relevant documentation in the same change. For core runtime or contract changes, update the matching versioned design document and `docs/IMPLEMENTATION_STATUS_V0.1.md`; for channel or integration changes, update the corresponding integration document. Keep `AGENTS.md` and `CLAUDE.md` aligned when commands, architecture boundaries, recovery behavior, or repository workflow changes. Document remaining limitations explicitly instead of describing planned behavior as implemented.

## v2.0 Multi-Agent Workflow

The complete rules are in `docs/MULTI_AGENT_WORK_RULES_V2.0.md`. Sub-agents must use a disjoint write set; plans, analysis, and task breakdowns are not implementation, and completion requires written and verified changes. v0.2 core truth and authority remain controlled by Chronicle, Policy, Effect Broker, and Verification; no sub-agent may bypass them or treat model output as state. Changes to code, contracts, or workflows must update the relevant documentation and keep `AGENTS.md` and `CLAUDE.md` aligned. Dangerous operations require explicit confirmation and minimal scope; credentials must stay out of source, logs, and commits; runtime `data/` is persistent state and must not be casually edited or cleaned; uncertain Effects remain auditable and require receipt/reconciliation/verification, never blind retry or a claim of completion.

Tool Registry lifecycle is persistent by default. Startup may migrate only the exact current-digest built-in Chat delivery dependency from `DEPRECATED` to `ACTIVE`; `REVOKED` and mismatched definitions remain closed, and the migration is Chronicle-audited.

Skill routing is two-stage: the model sees only the stable category/number/purpose entries in `data/skills/skill_catalog.md`; the runtime resolves the submitted catalog ID through `catalog.json`, checks lifecycle/digest/live binding, and reads the full Skill Manifest only after selection.

OneBot proactive text sending is a separate `channel.message.send_to` Tool. It is visible only to owner-authenticated admin Chat, requires a numeric `user_id` or `group_id`, and must use the Effect Broker and bridge receipt; QQ nicknames are never treated as addresses. Bridge send routes accept loopback callers by default or require the shared `ONEBOT_BRIDGE_TOKEN` across hosts. Inbound events are raw-logged first, then `onebot.private_user_ids` and `onebot.group_ids` gate Agent/model access; unauthorized events do not create Chronicle/Task work. Group Agent access additionally requires an exact bot `at` by default (`onebot.require_group_mention`); the bot mention is retained in metadata but removed from canonical command/model text, so `@bot /help` parses as `/help`. The bridge starts and reconnects its configured forward OneBot WS listener with bounded backoff, logs the user/group reason for each drop, and normalizes `at` plus attachment/group-upload metadata. Docker Compose starts the bridge as a separate `onebot-bridge` service; `scripts/start.sh` selects its bridge and authenticated OneBot WS routes for Docker or WSL host networking, with HTTP `:3000` only as fallback.

Admin Chat attachments use `lyca.core.attachments.AttachmentStore` under `data/chronicle/blobs` plus `data/attachments/manifest.jsonl`; the browser gets opaque refs through `/admin/v1/chat/attachments`, Chat messages persist canonical attachment metadata, and ReAct capability profiles may declare `channel.attachment.send` consistently even when the current Turn has no attachment. Dispatch still accepts only an exact current-turn inbound ref. The BFF and bridge enforce 25 MiB per file, 50 MiB total, and 8 files, and never accept local paths or external URLs as attachment refs.

The Admin Configuration gateway control writes `data/gateway_state.json` atomically. OneBot reads that shared kill switch at inbound and outbound boundaries: disabled events remain in raw inbox evidence but cannot reach Chronicle, Agent/model processing, or provider sends. The switch defaults to enabled when the state file is absent; malformed state fails closed. QQ Official Bot and Feishu remain explicitly unavailable until their adapters exist.

Chat tool execution is bounded per user Turn: `tool_loop_max_iterations` limits Chat/ReAct model-tool rounds, `max_tool_calls_per_turn` limits individual tool proposals, and `max_plan_steps` is capped at 10 for static ToolPlans. Pre-action structured reasoning uses the separate `reasoning_tool_loop_max_iterations` budget (default 1, loader cap 4) and only the PURE reasoning scope; an all-non-retryable rejection batch stops that loop before another proposal. Ordinary Chat PURE/OBSERVE tool failures are returned as structured tool errors and do not abort the other calls or the Turn; exhausted Chat budgets use one final text request with the same declarations and `tool_choice=none`. Chat and structured `think()` provider failures may walk the ordered config-file-only `llm.fallback_models` chain; a successful Chat fallback remains active for the rest of that Turn and is recorded in the checkpoint. When the chain is exhausted, the call returns an explicit failure and structured reasoning cannot be replaced by a simulated success artifact.

Chat uses one byte-identical stable system contract across text and action modes. A governed, bounded Agent Context containing Ego cognition, Language Style, the compact Skill Catalog, and current Environment is placed before canonical history; model-facing Soul/Environment text strips inline `sources` and `valid_from` audit fields while Chronicle projections retain them. Volatile Workspace, channel, immutable conversation interaction policy, a non-authoritative pre-action planning proposal, the Harness-derived current Action tool list, and Skill Visa are a separate Turn Context beside the current request. Text omits the Turn Context and tools, while action Chat exposes the fixed identity/channel capability profile; declarations change only when that profile, Tool/Skill lifecycle, digest, or governing policy changes. Native declarations and the mirrored current Action tool list are authoritative for tool availability; tools omitted from the pre-authorization decision scope are not evidence that they are unavailable during Action. Action Chat is count-unbounded by default (`chat_history_max_messages=0`) and uses a configurable 1,000,000 estimated-token context budget. At 90% pressure it deterministically compacts older complete protocol groups to a 70% target while keeping a configurable recent exact tail (64 messages by default); compaction is a lossy, non-authoritative user-role projection, makes no extra LLM call, and emits a deduplicated `context.compacted` Chronicle event. The current request and retained tool protocol groups stay exact; impossible mandatory-context budgets fail explicitly. The provider wire remains frozen and append-only within a Turn until compaction or source divergence causes an explicit rebase, and fallback carries the same wire into the active model scope. This disposable state is process-local and non-authoritative. Chronicle-backed Usage cache statistics remain grouped by emitted `purpose`/`think_type`; one interactive Chat event accumulates every successful provider call in its `initial`, `continuation`, and `finalization` phases. The assistant message projection separately rolls up every durable LLM reasoning phase in the whole Chat Task/Turn, including decision and post-action review when ReAct uses them, and counts only the latest cumulative interactive Chat snapshot after recovery. AgentCycle context-window refreshes use deterministic event summaries, so optional trace-only activity-summary calls cannot add hidden provider work to request or ACK paths. Chat ACK records delivery and returns without synchronous memory consolidation; a later non-Chat terminal task may process the pending consolidation window. Prompt layout delta state is reserved for one structured think type's continuous tool loop; decision, skill selection, and post-action review use separate scopes, and review sends a canonical prompt.

Chat and opt-in task Skills share `lyca.core.react_loop.ReActLoop`. Every model Action is durably checkpointed before `ToolDispatcher`, every Observation is checkpointed before the next model call, and hidden provider reasoning is excluded from ReAct events. `runtime.react_enabled` controls only task Skills declaring `execution.mode=react|hybrid`; Chat always uses the extracted loop. Task ReAct currently exposes PURE/OBSERVE tools only. `conversation.reply` keeps final delivery in its static ToolPlan, and `workspace.read` is the first opt-in task Skill.

Admin Chat has an Auto/Short/ReAct segmented control whose selected `interaction_mode` is locked by the first persisted message for the whole conversation. `auto` is the UI default: the first Chat call sees the fixed capability profile, final text ends immediately, and an actual tool proposal enters ReAct; after the final tool-loop text it skips the separate LLM post-action review. `short` forces one no-tool response and never upgrades; `react` forces the full cognitive/action profile including review. Legacy `chat` inputs normalize to `short`. The policy is persisted in the inbound event and Task checkpoint, participates in request-id idempotency, is echoed on the assistant message, and is not reset by `/new`; create a new conversation to choose another policy. This selector does not grant capabilities; dispatcher and policy checks remain authoritative.

User slash commands are a control-plane path shared by Admin Chat and allowlisted OneBot Chat. `lyca.core.commands` parses `/help` and `/new` before any model call; command replies still use the governed `conversation.reply` delivery path. Follow-up messages in one conversation reuse the Chronicle-derived active `event_session_id`; `/new` appends a `CONVERSATION_RESET` history boundary carrying the next session id, and never deletes Chronicle, memory, task, or transcript state. Command parsing is distinct from the model-facing `execute_command` sandbox.

Inbound channel adapters write an adapter-owned `payload.source_header` containing the platform, transport, source identity, and same-conversation reply target. The Agent sees this metadata in both text and action prompts; the harness derives `reply_conversation_id` from the trusted inbound event envelope, so model output cannot redirect a reply. Deterministic `/help` and `/new` use the same governed route without an LLM call. OneBot is implemented; Feishu remains unavailable until its adapter exists. See `docs/EXTERNAL_GATEWAY_INTEGRATION_V0.1.md`.

The command sandbox permits `curl` and `wget` as bounded HTTP(S) read clients for content such as public GitHub pages and APIs. `curl` writes only to stdout; `wget` requires `-O -`; upload, POST, file-output, non-HTTP(S) URLs, URL/header/netrc credentials, and proxy/config credential flags are rejected. This is an HTTP-read policy, not a complete public-network/SSRF classifier. Results distinguish policy validation from DNS, connection, timeout, TLS, and certificate failures and report whether a credential-free proxy was configured. Child processes receive only credential-free proxy settings plus workspace metadata, never LLM credentials.

Admin Web `/sandbox` monitors the live Workspace descriptor, sandbox enabled/status, `workspace.inspect` allowlist, limits, and blacklist rule count. Its direct terminal submits only browser-parsed argv through `POST /admin/v1/system/sandbox/execute`; BFF revalidates `execute_command@0.1.0` through Tool Dispatcher, an owner-only short-lived Capability, and Effect Broker, then records the Tool/effect lifecycle in Chronicle. The console is read-only: no shell session, file write, host absolute path, parent traversal, Git mutation, or credential argument is exposed.

## Build, Test, and Development Commands

The v0.1 demo supports Python 3.10+ and uses only the standard library.

```bash
python3 -m lyca.demo
python3 -m compileall lyca
LLM_AUTH_TOKEN=... python3 -m lyca.demo --test-connection
python3 -m lyca.demo --model gpt-4o   # any OpenAI-compatible model
python3 -m lyca.demo --no-llm         # force the simulated reasoner
python3 debug/run_llm_workflow.py --dry-run  # inspect the live five-turn scenario
python3 debug/run_llm_workflow.py      # opt-in real LLM/Docker validation
python3 debug/run_llm_integrations.py  # default dry-run for future external integrations
python3 -m lyca.debug.sandbox_network  # no-LLM HTTP sandbox/proxy diagnostics
```

Run the first command for the deterministic local workflow. Use `compileall` as a quick syntax/import check. The LLM backend is on by default (`LYCA_USE_LLM=1`) and reads `.env` from the project root; any OpenAI-compatible API works via `LLM_BASE_URL`/`LLM_AUTH_TOKEN`/`LLM_MODEL` (`DEEPSEEK_*` kept as legacy aliases, default base `https://api.deepseek.com`). Same-endpoint Chat/structured-think failover is configured separately as ordered `llm.fallback_models` in the local `lyca.config.json`; the list does not switch credentials or judge answer quality.

## Coding Style & Naming Conventions

Follow the existing Python style: four-space indentation, type annotations, concise docstrings, and `from __future__ import annotations`. Use `snake_case` for modules, functions, and variables; `PascalCase` for classes and enums; and uppercase names for enum members and constants. Prefer dataclasses for domain records and frozen dataclasses where state is intended to be immutable. Keep external effects behind the Effect Broker and record state transitions through Chronicle events. No formatter or linter is configured, so keep imports grouped and changes consistent with nearby code.

## Testing Guidelines

Tests live under `tests/`; there is no coverage threshold. Before submitting, run `python3 -m compileall -q lyca services tests`, `python3 -m unittest discover -s tests -t .`, and `LYCA_DATA_DIR=/tmp/lyca-demo-check python3 -m lyca.demo --no-llm`; confirm the demo ends with `DONE` and reports success and delivery verification. Add tests as `test_<feature>.py`, using deterministic reasoners and temporary data directories so tests do not call external APIs or modify checked-in runtime state.

The five-turn live workflow is opt-in because it uses the Docker-configured provider and consumes quota. Run `python3 debug/run_llm_workflow.py` after prompt, ReAct, Tool, or Chat contract changes when live credentials are available; use `--require-cache-hit` only for providers known to report cache usage. Its evaluator must remain covered by deterministic unit tests.

`python3 debug/run_llm_integrations.py` defaults to a no-network readiness/scenario check for DeepResearch, Skill installation, and Codex Tool integration. Use `--live` only after the corresponding ACTIVE bindings and adapters exist; its evaluator and readiness probe must remain local and fail-closed by default.

`python3 -m lyca.debug.sandbox_network` is the explicit public-network probe for the model-facing command sandbox. It runs read-only `curl` against example.com and the GitHub API, then verifies that a POST is rejected before network execution. The probe does not invoke an LLM or write runtime state; `NETWORK_CONNECT_FAILED`, `REMOTE_DNS_FAILED`, proxy failures, HTTP status failures, and policy rejection remain separate results.

## Commit & Pull Request Guidelines

Git history is currently too small to establish a convention. Use short, imperative commit subjects, optionally scoped, such as `core: validate capability leases`. Pull requests should explain the behavior change and rationale, list validation commands, link relevant issues or design documents, and call out schema or persisted-data changes. Never commit API tokens, credentials, or private runtime records from `data/credentials/`.
