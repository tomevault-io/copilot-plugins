## Server vs Client Components

Default to **Server Components**. Add `'use client'` only when the component
needs browser APIs, event handlers, hooks, or TanStack Query.

| Use Server Component for | Use Client Component for |
|---|---|
| Data fetching | Forms with controlled state |
| Page layouts | Interactive UI (dropdowns, sheets) |
| Static content | TanStack Query consumers |
| Auth checks | Zustand consumers |

Never fetch data in a Client Component with `useEffect`. Use Server Components
or TanStack Query with a prefetched initial value.

## Supabase Client Rules

| Context | Client to use | Import from |
|---|---|---|
| Server Component / Server Action / Route Handler | `createServerClient` | `lib/supabase/server.ts` |
| Client Component | `createBrowserClient` | `lib/supabase/client.ts` |

Never import the server client into a Client Component. Never import the browser
client into a Server Component.

The server client reads cookies via `next/headers` — it must be called inside
an async function context.

---

## Mutations

All mutations are **Server Actions** in `lib/actions/`.
Use Route Handlers only for operations that stream, require multipart form data,
or call external APIs (OCR).

Server Action pattern:
```ts
'use server'
export async function createExpenseWithItems(input: CreateExpenseInput) {
  const supabase = await createServerClient()
  // validate, call RPC, return { data, error }
}
```

Never call Supabase RPCs directly from Client Components.

## Auth + Household Gate

`middleware.ts` runs on every request:
1. No session → redirect to `/login`
2. Session, no household membership → redirect to `/onboarding`
3. Session + household → allow through

The household check queries `household_members` for the current `user_id`.
Cache the result in the middleware cookie (`household_id`) to avoid a DB round
trip on every request.

Every user belongs to **exactly one household**. This is enforced by a
`UNIQUE (user_id)` constraint on `household_members`. The onboarding flow is
the only path that creates or joins a household. Attempting to join a second
household returns an `already_in_household` error from the RPC.

## Conventions

### TypeScript
- `strict: true` always
- No `any`. Use `unknown` and narrow.
- Generate DB types with `supabase gen types typescript` — never hand-write DB types.

### Naming
- Files: `kebab-case.ts`
- Components: `PascalCase.tsx`
- Server Actions: verb + noun (`createExpense`, `joinHousehold`)
- DB columns: `snake_case` (Supabase default)

### Error Handling
- Server Actions return `{ data: T | null, error: string | null }`
- Never throw from a Server Action — return the error
- Client components display errors from the returned object, not try/catch

### Styling
- Use Tailwind utility classes directly
- Use shadcn/ui components for all interactive primitives (Button, Sheet, Dialog, etc.)
- Do not write custom CSS unless Tailwind cannot express it

### Comments
- Write no comments unless the WHY is non-obvious
- No JSDoc blocks. No TODO comments committed to main.

## Critical Domain Rules

These rules come from `docs/spec/product.md` — never violate them:

1. **One household per user.** Enforced at DB and middleware level.
2. **Every expense has at least one item.** Validate before saving.
3. **GST is per-expense**, not per-item. Rate defaults to 9%.
4. **Item names are always normalized** before being stored or looked up in
   `item_category_mappings`. Use `lib/utils/normalize.ts`.
5. **Category suggestions always run before allowing new category creation.**
   Never let users create a category without seeing existing matches first.
6. **OCR API key lives only in the Route Handler.** Never in client code or
   environment variables prefixed `NEXT_PUBLIC_`.
7. **Amounts are stored as `numeric(10,2)`** — no floating point arithmetic on
   monetary values. Use integer cents in intermediate calculations if needed.

## What NOT to Do

- Do not use the Pages Router (`pages/` directory)
- Do not use `getServerSideProps` or `getStaticProps`
- Do not use `useEffect` for data fetching
- Do not call OpenAI from the client
- Do not store monetary amounts as JavaScript `number` floats
- Do not allow category creation without first showing fuzzy-matched suggestions
- Do not add features not in the current phase scope
- Do not write backwards-compatibility shims for removed code
