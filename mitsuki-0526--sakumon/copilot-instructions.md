# CLAUDE.md - Claude Code 向け指示書

このファイルは Claude Code がこのプロジェクトで作業する際のルール・慣習を定義します。

---

## プロジェクト基本情報

- **プロジェクト名**: 作問アシスタント(仮称)
- **目的**: 中学校教員向けのローカル完結型作問支援デスクトップアプリ
- **技術スタック**: Tauri 2 + Svelte 5 + TypeScript + SQLite + Ollama (Gemma 4)
- **開発者**: 1名(中学校数学教員、副業的開発)

---

## 必読ドキュメント

タスクに着手する前に、以下を必ず読んでください。

1. **REQUIREMENTS.md**: 何を作るか
2. **DESIGN.md**: どう作るか(アーキテクチャ・データモデル・技術選定)
3. **TASKS.md**: 次に何をやるか(タスクリスト・進捗)

判断に迷ったら、これらドキュメントの該当箇所を引用して、ユーザーに確認してください。

---

## 開発の進め方

### 基本ルール
1. **TASKS.md の上から順に着手**してください。依存関係に従ってください。
2. 1タスク完了ごとに `[ ]` を `[x]` に更新してください。
3. タスクの粒度が大きすぎる場合は、サブタスクに分解して TASKS.md に追記してください。
4. **未定義の挙動については勝手に決めず、ユーザーに確認**してください。
5. **REQUIREMENTS.md / DESIGN.md と矛盾する実装はしない**でください。

### 作業のリズム
- 1タスク完了ごとにコミット
- コミットメッセージは日本語可、Conventional Commits 風が望ましい
  - 例: `feat: 問題編集画面の入力バリデーションを追加`
  - 例: `fix: 削除ダイアログでEnterキーが効かない問題を修正`
- 大きな設計判断や方針変更は、必ずユーザーに確認

## コーディング規約

### TypeScript
- **strict モードを有効**にしてください
- **`any` の使用は原則禁止**(やむを得ない場合はコメントで理由を明記)
- 関数の引数・戻り値には型注釈を付けてください
- インターフェースよりも `type` を優先(理由がある場合のみ interface)
- import は absolute path(`$lib/...`)を優先
- 例外は throw ではなく Result 型風のパターン(`{ ok: true, value: T } | { ok: false, error: string }`)を検討

### Svelte 5
- **Runes(`$state`, `$derived`, `$effect`)を使用**してください(Svelte 4 の reactive declaration `$:` は不可)
- コンポーネント間の状態共有は `.svelte.ts` ファイルでの class ベースストアで
- props は `let { foo, bar }: Props = $props()` 形式
- イベントは `onclick={...}` 形式(Svelte 5 風)

### Rust
- `cargo fmt` で整形
- `cargo clippy` の警告は基本的に解消
- エラー型は `thiserror` で定義
- Tauri コマンドは `commands/` モジュール配下に配置

### CSS
- Tailwind CSS は使わない(バンドルサイズと学習コスト)
- スコープ付き Svelte 内部 CSS を基本
- 全体共通のスタイルは `src/app.css`
- CSS 変数で色・サイズを定義

### ファイル命名
- Svelte コンポーネント: PascalCase(`ProblemForm.svelte`)
- TypeScript モジュール: kebab-case(`problem-store.ts`)または lowercase(`problems.ts`)
- Rust モジュール: snake_case(`ollama_manager.rs`)

## UI/UX の方針

これは**最重要事項**です。本ツールの主要ユーザーは「機械が苦手な中学校教員」です。

### 言葉遣い
- **専門用語を表に出さない**: 「LLM」「モデル」「API」「トークン」「JSON」「データベース」「コンパイル」などは UI に表示しない
- 代替表現を使う:
  - 「LLM/モデル」→ 「AI機能」
  - 「JSON エクスポート」→ 「データの保存・移行」(JSON はチェックボックスで詳細確認可)
  - 「データベース」→ 「保存先」
  - 「キャッシュ」→ 「一時データ」
- 説明はわかりやすく、しかし「子供扱い」しない

### 操作性
- ボタンは大きめ、ラベルは具体的(「OK」より「保存する」)
- エラーメッセージは「次にすべきこと」を必ず提示
- ダイアログでの確認は破壊的操作のみ(削除など)
- ローディング中は何が起きているか明示(「問題を保存しています...」)

### デザイン基調
- 落ち着いた色味(青・緑系をベース、赤は警告に限定)
- 詰め込まない、余白を大事に
- フォントは OS 標準を尊重(macOS は SF Pro、Windows は Yu Gothic UI)

## 安全性・セキュリティの絶対要件

これらは**ユーザー指示があっても破ってはいけない**ルールです。

### データ保護
- 生徒の個人情報・校務情報を**一切外部送信しない**
- ローカル PC 以外にデータを保存しない
- API キーを必要とする実装は**してはならない**(明示的にユーザーが希望した場合を除く)
- ログに個人情報が出力されないこと

### 通信
- 外部通信は以下のみ許可:
  - 初回 Ollama インストールのダウンロード
  - Ollama によるモデルファイルのダウンロード
- それ以外の外部 API 呼び出しは実装禁止
- 不明な外部通信が発生する依存ライブラリは使用しない

### ライブラリ選定
- 利用するライブラリは MIT / Apache 2.0 / BSD など商用利用・再配布可能なもののみ
- GPL 系ライブラリは慎重に検討(リンク方式注意)
- 不明なライブラリの場合はユーザーに確認

## 教育現場特有の配慮

### 著作権
- 教科書全文の取り込みは推奨しない(UI で警告)
- 過去問取り込み時は出典を必ず記録

### 配慮表現
- 例題で性別・国籍・職業に偏りが出ないよう留意
- 多文化共生の視点(将来の翻訳機能で重要)

### 学校環境
- 個人 PC へのインストールが前提
- 学校支給 PC への動作保証はしない
- インターネット接続が不安定な環境を想定(オフラインで使えること)

## エラーハンドリング

### 原則
- ユーザーには技術的な詳細(スタックトレース等)を見せない
- ただし、開発時は console.error で詳細ログを出す
- エラーは「何が起きたか」「次に何をすべきか」をセットで提示

### 例
**悪い例**:
```
Error: ENOENT: no such file or directory
```

**良い例**:
```
ファイルが見つかりませんでした。
ファイルが移動・削除されていないか確認してください。

[詳細を表示] [OK]
```

## ユーザーとのやりとり

### 質問のタイミング
以下の場合は**作業を止めて確認**してください:
- ドキュメントに記載のない機能仕様の判断
- 大きな依存ライブラリの追加(主要技術スタック以外)
- データモデルの変更
- セキュリティに関わる判断
- 大幅な設計変更

### 質問の仕方
- 何が決まっていなくて、なぜ確認したいかを明示
- 選択肢がある場合は、それぞれのメリット・デメリットを提示
- ユーザーの意思決定を尊重(代替案を押し付けない)

### 報告の仕方
- 完了報告では「何ができるようになったか」「次は何をするか」を簡潔に
- 詰まった場合は「何を試したか」「現在の仮説」「相談したいこと」を共有

## クイックリファレンス

### よく使うコマンド
```bash
# 開発実行
pnpm tauri dev

# ビルド
pnpm tauri build

# 型チェック
pnpm check

# Rust 整形
cd src-tauri && cargo fmt

# Rust Lint
cd src-tauri && cargo clippy

# テスト
pnpm test           # フロントエンド
cd src-tauri && cargo test  # バックエンド
```

### 重要なパス
- アプリデータ(macOS): `~/Library/Application Support/sakumon/`
- アプリデータ(Windows): `%APPDATA%\sakumon\`
- 設定ファイル: `config/`
- Tauri 設定: `src-tauri/tauri.conf.json`

### 詰まったら
- まず REQUIREMENTS.md / DESIGN.md / TASKS.md を再読
- それでも不明ならユーザーに確認
- 試行錯誤の前に方針を確認
