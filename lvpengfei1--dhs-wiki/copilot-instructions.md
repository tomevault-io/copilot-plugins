# DeepSeek Harness 中文业务 Wiki 维护规则

本目录采用 [LLM Wiki](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f) 的三层方法：项目源码与项目文档是只读原始来源，`wiki/` 是由 Agent 维护的综合知识层，本文件是 Wiki 的结构与维护规则。Wiki 不复制源码，也不把自身页面当作事实依据。

## 目标与读者

Wiki 面向希望理解 DeepSeek Harness 产品、Agent 行为和设计原理的中文读者。正文按业务问题、Agent 生命周期、系统提示词、平台能力和设计取舍组织，不按软件包或源码目录组织。源码目录只出现在证据、覆盖台账和附录中。

每个主题优先回答六个问题：系统解决什么问题；谁在什么场景使用；一次工作如何发生；各能力如何协作；为什么采用当前设计；失败、限制和取舍是什么。

## 原始来源

事实依据按以下顺序使用：

1. 当前实现、运行配置、提示词、工具定义和可执行示例；
2. 测试、快照与不变量，它们证明外部可观察行为；
3. 当前架构文档、软件包 README 和仍有效的 Agent Note，它们解释约束与设计理由；
4. 用户本次明确陈述，仅用于确定 Wiki 范围与表达重点。

`vendor/` 是外部引入的 Cordis 源码，本轮只记录其位置、上游身份和对 Harness 的基础作用，不读取其内部文件来推导 Harness 的业务结论。`.agents/notes/archived/` 是冻结历史，不作为当前行为的权威来源。`node_modules/`、`lib/`、`dist/`、`coverage/`、缓存和其他构建产物不纳入分析。

## 页面正本

一个可独立判断真假的核心结论只在一个主题页面完整解释，其他页面使用双向链接引用，不复制整段结论。页面职责如下：

- `index.md`：全库入口和内容目录；
- `log.md`：按时间追加的资料接入、综合、校验和维护记录；
- `00-阅读指南/`：阅读路径、证据规则和范围；
- `01-业务全景/`：产品定位、参与者、业务价值和能力地图；
- `02-Agent运行机制/`：从输入到完成的 Agent 工作原理；
- `03-系统提示词/`：提示词组装、指令层级和模型行为约束；
- `04-平台能力/`：面向业务用途解释模型、工具、运行环境和集成能力；
- `05-设计原理/`：解释跨能力共享的架构原则及其取舍；
- `06-典型业务流程/`：按真实使用场景串联多项能力；
- `07-边界与验证/`：失败恢复、安全边界、已知限制和行为证据；
- `99-附录/`：术语、外部依赖位置、证据索引和逐文件覆盖台账；
- `_meta/`：机器可读清单、覆盖映射和生成状态；
- `_ops/`：只维护 Wiki 的脚本与说明，不承载业务结论。

## 页面格式

主题页面使用 YAML frontmatter，至少包含：

```yaml
---
title: 页面标题
page_type: overview | mechanism | prompt | capability | principle | flow | boundary | appendix
status: draft | verified
updated: YYYY-MM-DD
source_scope:
  - 项目相对路径或路径前缀
---
```

正文根据主题选择以下章节，不为凑模板保留空章节：

- `本页回答什么`：明确业务问题和阅读收益；
- `业务位置`：参与者、触发条件、输入与结果；
- `工作原理`：用业务动作和状态变化说明机制；
- `为什么这样设计`：仅保留可由源码、当前文档或 Agent Note 支持的理由；
- `边界与失败方式`：说明不保证什么、如何失败和如何恢复；
- `与其他主题的关系`：链接其他正本页面；
- `源码证据`：列出直接支持本页结论的项目相对路径、符号或配置项及其支持范围。

正文使用中文业务表达。产品名、项目名、协议名、类型名和通用技术缩写可保留英文。代码细节只在解释行为所必需时出现。

## 结论与证据

每项核心结论属于以下一种性质：

- **来源事实**：实现、配置、提示词、测试或当前文档直接表明；
- **推导判断**：综合多个来源得到，必须写明推导依据和适用边界；
- **待核验**：证据不足或来源冲突，不写成确定事实。

`源码证据`必须链接到 `wiki/` 之外的原始来源。其他 Wiki 页面只能帮助导航，不能成为新结论的唯一依据。测试快照和生成文件属于派生证据，应回链到产生它们的场景或实现。

## 逐文件覆盖

`_meta/source-files.jsonl` 是逐文件分析状态的机器正本，`99-附录/源码覆盖台账.md` 与 `99-附录/逐文件/` 是其派生视图。每个纳入范围的文件必须具有以下状态之一：

- `pending`：已登记，尚未完成语义分析；
- `inspected`：已读取并确认职责，但尚未进入主题综合；
- `synthesized`：已读取，相关业务结论已写入指定主题页；
- `supporting`：作为文档或设计理由来源读取，不承担逐代码文件完成要求；
- `derivative`：锁文件、快照或生成结果，只用于结构或行为交叉验证；
- `position-only`：按用户要求只保留位置，本轮不分析；
- `not-applicable`：不是代码、配置、提示词、测试或业务证据，并记录原因。

只有全部必分析文件都达到 `synthesized`，或达到 `inspected` 且明确记录“没有独立业务结论”及理由，才能声称完成“逐个文件解析”。目录级映射只能在该目录内每个文件都已实际读取后使用。

## 操作流程

### 接入与综合

1. 运行 `_ops/build-source-inventory.mjs` 更新原始来源清单；
2. 从 `index.md` 和覆盖台账确定下一个业务主题与尚未读取的来源；
3. 逐文件读取，先更新 `_meta/analysis-map.json`，再更新唯一主题正本；
4. 同步 `index.md`、证据索引和受影响的交叉链接；
5. 在 `log.md` 追加一条记录；
6. 重建清单并检查必分析文件、孤立页面、失效链接和重复主张。

### 查询与沉淀

回答问题时先读 `index.md`，再读相关主题页及其原始证据。对证据充分、具有持续价值的新综合，可更新现有正本或新建具有唯一职责的页面；临时回答和无来源推测不写回 Wiki。

### 健康检查

定期检查待分析文件、孤立页面、无原始来源页面、同义重复、互相冲突的结论、源文件哈希变化和过期推导。冲突无法由当前来源解决时，保留冲突与待核验状态，不替来源做决定。

## 写作与验证要求

一个物理段落写在一行内。使用相对 Markdown 链接。正文保持当前状态，不记录实现过程、评审对话或代码阅读流水。完成声明必须同时由覆盖清单、实际正文、有效链接和源文件回链支持。由于当前工作区没有 Git 元数据，恢复和变更识别使用 `_meta/` 中的文件哈希及写后回读结果。
