# AI Graph Engineering + Multi-Agent Coding Assistant

A **project-independent** multi-agent coding system, plus a target application
to exercise it against.

| Path | What it is | Reusable? |
|---|---|---|
| `.claude/agents`, `instructions`, `prompts`, `workflow` | the AI engine | **yes — copy to any repository unchanged** |
| `.claude/project/` | facts about the repository being worked on | no — generated per repository |
| `library-management/` | the current target application | no — a sample workload |

## The architectural rule

> **Layer A contains zero project facts. Layer B contains nothing else.**

A *project fact* is anything true of one repository and not of repositories in
general: languages, frameworks, architecture, conventions, test commands,
tooling, business rules, file locations.

Nothing in `agents/`, `instructions/`, `prompts/` or `workflow/` may name a
technology, a command, or a domain concept as a requirement. Those files define
*behaviour*: how to reason, what to verify, what never to do.

Everything specific lives in `.claude/project/`, generated by
`repository-setup-agent` from repository evidence, with a `source` and a
`confidence` on every fact.

**The portability test:** copy the four Layer A directories into an unrelated
repository, run project initialisation, and the system works with no edits. If a
copied file needs changing, a project fact leaked into the engine.

## Two workflows

**Project initialisation** — once per repository. Two agents, disjoint scopes:

* `repository-setup-agent` inspects the repository and generates the project
  configuration Markdown plus `metadata.yaml`.
* `graph-agent` then builds the repository graph into
  `.claude/project/graph/`, consuming that configuration.

Neither writes the other's artifacts, and neither touches application source,
tests, or build files.

**Development** — once per ticket. Twelve agents run in sequence, consuming
`.claude/project/` as fact. It does not start until project configuration exists
and is marked ready.

## Instruction and project-context loading

Each agent's frontmatter declares what it needs:

```yaml
tools: Read, Grep, Glob                    # runtime-enforced by Claude Code
instruction_context: [instructions/global.md, ...]   # declared only
project_context: [architecture.md, testing.md]       # declared only
write_scope: []                                      # declared only
capabilities_required: [filesystem.read]             # declared only
```

**Only `tools:` is runtime-enforced.** The rest is metadata Claude Code does not
read. The orchestrator, when built, must load and enforce it explicitly — see
[`.claude/workflow/orchestrator-contract.md`](.claude/workflow/orchestrator-contract.md)
§6–7.

Precedence is defined at the top of
[`.claude/instructions/global.md`](.claude/instructions/global.md): global safety
rules outrank project configuration, always.

## Conventions for working here

**Changing the engine (Layer A)**

* Add a rule to `instructions/`, never to an agent or a prompt.
* **Never name a technology, command, or domain concept as a requirement.** Use
  a labelled example if one aids clarity, and make the project-configuration
  path the actual source.
* Changing an agent's Inputs table means updating
  [`prompt-inputs.md`](.claude/workflow/prompt-inputs.md) and
  [`agent-handoff.md`](.claude/workflow/agent-handoff.md) in the same change.
* Changing task state means updating
  [`task-state.schema.yaml`](.claude/workflow/task-state.schema.yaml) first — it
  is authoritative — then the prose.
* Never claim two steps run in parallel unless both steps' declared inputs
  permit it. The Inputs tables are the arbiter.
* Run the consistency audit in
  [`orchestrator-contract.md`](.claude/workflow/orchestrator-contract.md) §8.

**Changing project configuration (Layer B)**

* Regenerate it with the initialisation workflow, or edit by hand and mark the
  entry `source_type: manual` or `verified` — those survive a refresh.
* Every fact needs a `source` and a `confidence`. `unknown` is a valid value; a
  plausible guess is not.

**Changing the target application**

`library-management/` contains **intentional defects** — bugs, architectural
violations, insecure code, documentation gaps, and failing tests. They are the
material the agent system exists to find.

Do not "fix on sight". Do not repair a failing test to make the suite green.
