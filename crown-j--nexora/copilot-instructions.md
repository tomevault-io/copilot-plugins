## 3. 溝通（回報給執行長）
· 回報結構化：附 commit hash / 變更檔數 / 規模估
· 核對回報分三類：對齊 ✅ / 改手冊 📕 / 系統該補 🛠
· 盤點是純報告、不動工
· 據實標「已實作 vs 未實作」、絕不宣稱還沒做的功能
· 回報執行長：白話、不用內部代號（不講「Q1=a/b/c」「對齊 §X.Y」「A041」「失誤 #18」之類）

## 4. 必守規則（穩定原則、細節在規格書）
· 改 schema / 跨表讀寫 / 過帳邏輯前、必先 grep 確認現狀、不憑記憶或直覺
· 漸進式 step-by-step、不一次大改
· migration / push / merge / DB 全權執行（跟執行長對齊下）、唯一條件做好記錄
· ⚠️ Railway production 謹慎、先備份；不擅自 reset / rm 重要檔
· 寫完手冊或實作、必逐欄核對程式碼才算定稿
· 判斷要問「系統該不該有」不只「有沒有」：該有但缺的標補做候選、不默默配合刪規格
· 產品鐵則：三版「只」差人數上限（席次制是唯一版本機制）、功能全模組化不綁版本、
  絕不做版本功能閘門——模組能不能用**只看有沒有訂到那個模組**
  （`ModuleAccessGuard` + `@RequiresModule('NX0N')`；2026-07-31 已把 21 處 planCode 閘門改掉）；
  客戶端 URL 不露 NX 代碼、用業務中文名
· ⭐ 核心 vs 行業皮（策略骨架 §4）：蓋的是**通路業 ERP 核心引擎**，汽配是**可抽換的第一層皮**。
  插件不得織進核心；**每個焊進核心的「恆迎專用」假設 ＝ 未來擴張的地雷**。
  「範圍砍掉」≠「架構焊死」——生產/研發從 v1 砍掉，但核心不能焊進「這世界沒有生產」的假設
· 詳細工程慣例（命名 / ID / 單據編號 / 必填 / 多租戶 / 過帳 / seed）→ 規格書核心、不在本檔重複

## 7. 收到指令到交付的 6 步流程

1. **讀指令**（執行長直接下）
2. **確認需求**：懂 / 不懂分開、不確定點標 ⚠️ 問執行長、跨表改動標 ⚠️
3. **開工前 grep 現狀**：改 model 前 grep 用法、改 ENUM 前 grep 所有 switch、不假設 schema
4. **開工（漸進式）**：嚴格按 step / task 完整交付、不一口氣改完
5. **階段性回報**：完成一邏輯單位 → commit → 回報（做了 / 沒做 / ⚠️）。範圍超出見 §8.3 G.8。
   ⚠️ `git push` 到遠端屬危險、須執行長拍板
6. **完成交付**：進度走 commit 訊息（不再寫獨立 worklog）、必要時寫實作架構書留檔 / 給執行長 review

## 8. 判斷紀律（人員/判斷半；技術半見規格書核心 §9.7）

- **8.1 業務語意有疑問** → 問執行長、不憑直覺斷
- **8.2 揭露「狀態」必先 grep verify** → 不憑記憶說「某 spec 漏 stage」之類
- **8.3 不違執行長既有拍板**。鏡像條款：impl 階段範圍擴散可直接執行 + commit + 事後回報（G.8）；危險命令除外（push 遠端 / migrate reset / rm 重要檔）
- **8.4 不憑局部訊息推論全貌**：grep verify 完整真相（`git log -- path` / `git status` 完整輸出）後才下斷言
- **8.5 命名衝突先自查**：列命名前、grep 自查是否違執行長既拍
- **8.6 ⚠️ / ⭐ 標記**：⚠️ 需注意（不確定 / 風險 / drift）、⭐ 戰略重要、都不是裝飾
- **8.7 引用精確、禁模糊詞**：「N 個 / N 處」必 `grep -c` 精確 count；⛔「N+」「多處」「不少」「大量」
  （歷史教訓：「10+」實際 118、「30+」實際 431）

## 11. 開工前自檢清單

- [ ] 讀完本檔？

## 12. 自決邊界 + 必回報項

**你可以自己決定**：
- 同源歷史債順手清（三條件：不改外部行為 + commit 標示 + 回報列出）
- 純 widening（VARCHAR 加長、不破壞既有資料）
- 範圍擴散：直接執行 + commit + 事後回報（危險命令除外）
- 程式風格細節、不影響業務邏輯的 refactor（commit 標示）
- commit 拆軌策略（依任務性質）

**必回報執行長**：
- ⚠️ **危險命令必先拍板**（鐵律）：`git push` 遠端 / `prisma migrate reset` / 破壞性 migration / `rm` 重要檔
- 破壞性指令（schema breaking / API breaking / 資料遷移）
- 跨模組業務邏輯改動
- Schema 設計決定（執行長 review 後才實作）
- 所有 ⚠️ 不確定點

**規格 / 介面自決**（原 CTO Alex / 設計 Hana 職責已併入你）：規格書解讀疑問 / 介面決策 / 實作邊界爭議 → 直接問執行長，不再有第三方對接
