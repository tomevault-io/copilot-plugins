# Prototype Instructions

Run the local server yourself and open the preview in the in-app browser. Do not give the user server-start instructions when you can run it.

Before making substantial visual changes, use the Product Design plugin's `get-context` skill when the visual source is unclear or no longer matches the current goal. When the user gives durable prototype-specific design feedback, preferences, or decisions, record them in `AGENTS.md`.

When implementing from a selected generated mock, treat that image as the source of truth for layout, component anatomy, density, spacing, color, typography, visible content, and hierarchy.

Authentication decisions: Enterprise WeChat is the only supported login method. Every client route except `/login`, including the 404 route, must require a persisted Enterprise WeChat user identity. Keep the detailed Enterprise WeChat user in the Zustand auth store and initiate OAuth automatically when the app is opened inside Enterprise WeChat.

Authentication flow decisions: centralize Enterprise WeChat user-agent detection in `client/src/utils/wecom.js`. When an unauthenticated user opens the app inside Enterprise WeChat, start OAuth automatically and render `LoginFailed.jsx` through the public `/login?status=failed` state if automatic login fails. Outside Enterprise WeChat, unauthenticated users remain on the standard `/login` QR-code flow.

Navigation decisions: the protected workbench uses `/recorder`, `/records`, and `/detail` for the recorder, recording list, and recording detail views. Preserve the selected recording in the detail route query string. The records header exposes the current Enterprise WeChat user through a compact avatar menu with logout.

Record preview routing decisions: drive `RecordPreviewOverlay` from the dynamic `/records/:recordingId` route. Opening a recording card navigates to that route, while closing the overlay returns through router history; do not use component-local expanded-recording state as the source of truth.

Recording name editing decisions: keep recording names read-only on `RecordCard`. Edit a recording name only from `RecordPreviewOverlay`, using the pencil control beside the preview title to enter edit mode.

Routing implementation decisions: `App` is the protected workbench layout and renders child routes with React Router's `Outlet`. Route declarations render dedicated page-level components directly (`/recorder` → `Recorder`, `/records` → `Records`, `/detail` → `Detail`). Do not pass route-name strings into `App`, conditionally render route pages in `App`, or move page-only properties and methods into `App` or a broad context. Keep page-specific state and behavior in the owning route component; only layout behavior genuinely used by `App` belongs there.

Router ownership decisions: `client/src/AppRouter.jsx` owns `BrowserRouter`, route guards, redirects, and all route declarations. Keep `client/src/main.jsx` as the application bootstrap only, and do not move the global router provider into the workbench layout `App`.

Shared constant decisions: keep cross-route persistence keys and storage identifiers in `client/src/constant.js` and import them explicitly after moving code between route components. Page-only tuning values may remain in their owning module.

Server official-identifier constant decisions: keep Tencent Meeting webhook event names and similar externally defined server-side identifiers in `server/constant.js`; do not scatter their string literals through routes, services, cron jobs, or utilities. Preserve every official identifier value exactly as the provider defines it, including spelling, punctuation, separators, and casing. Constant names must use the uppercase form of the official name and must not translate, paraphrase, normalize, abbreviate, alias, or otherwise rename the provider-defined identifier. When punctuation in an official name is not valid in a JavaScript identifier, represent the uppercase official name as a quoted object key while keeping its value byte-for-byte equal to the official name.

Database startup decisions: `docker-entrypoint.sh` selects the Prisma schema strategy with `PRISMA_SCHEMA_MODE`. Use `push` for development schema synchronization and `migrate` for checked-in production migrations; missing or unknown values must fall back to `prisma migrate deploy`, never to a destructive push option.

Recording persistence decisions: Prisma is the only data-access implementation for `Recording` and `TranscriptSegment` reads, creates, updates, soft deletes, restores, and permanent deletes. Legacy aggregate helpers may remain temporarily for non-recording entities, but they must delegate recording persistence to the Prisma repository and must never issue raw `SELECT`, `DELETE`, or `INSERT` statements against `recordings` or `transcript_segments`.

Database access decisions: prefer Prisma for all new or reworked database reads and writes. Do not introduce new raw SQL when Prisma can express the operation; when touching legacy raw-SQL persistence, migrate the in-scope operation to Prisma where practical.

Prisma migration review decisions: all newly written server-side database queries and mutations must use Prisma. Whenever an existing server persistence path is changed, migrate the in-scope legacy database access to Prisma as part of that change instead of extending aggregate helpers or raw SQL. After any existing logic has been migrated to Prisma, explicitly call out the migrated operations and files in the user-facing handoff and remind the user to review the persistence behavior; never leave an in-scope Prisma migration unmentioned.

Test deployment decisions: `py_server` is intentionally disabled because the current application flow does not use it. `start_test.sh` must not build, start, wait for, or report `py_server`, and must not remove or otherwise manage stale Compose orphan containers.

Records menu decisions: the avatar dropdown uses a compact, content-driven width with mobile viewport bounds instead of a fixed width, and its icon-only action buttons center their icons.

Detail component decisions: `client/src/pages/Detail/Detail.jsx` is the route-level owner and page orchestrator; do not reintroduce a broad `DetailView` wrapper. Split cohesive visual regions and message/composer parts into `client/src/pages/Detail/components`, and keep route loading in focused hooks under `client/src/pages/Detail/hooks`. Keep the chat-history panel as a controlled component: its owner controls visibility through `open` and `onClose`, while panel-only state such as the history/favorites tab remains inside the panel.

Client styling decisions: Tailwind CSS is the primary styling approach for new or substantially refactored client components. Prefer utility classes for layout, spacing, typography, color, borders, responsive behavior, and interaction states; retain shared semantic CSS only for behavior or complex reusable presentation that is materially clearer than repeated utilities. Do not expand the global stylesheet for component-local styling when Tailwind can express it cleanly.

Client date-time decisions: use `dayjs` for frontend date parsing, validation, comparison, and display formatting in new or substantially refactored code. Do not add new ad-hoc `Date` formatting helpers or locale-string formatting when `dayjs` can express the same behavior consistently.

Client request decisions: all new or substantially refactored client HTTP requests must use `client/src/utils/request.js` as the transport implementation. Define endpoint-specific functions under `client/src/api` and call those functions from pages, hooks, stores, and components; do not add direct `fetch`, Axios, or legacy `utils/index.js` `api()` calls in feature code. Keep URL construction, HTTP methods, parameters, and request payload mapping inside the API module rather than the consuming UI.

Daily brief scheduling decisions: schedule the daily meeting brief with `node-cron` at 00:00, 14:00, and 19:00 in `Asia/Shanghai`, with the fixed expression, timezone, and schedule hours exported by `server/config.js`; these values are code configuration and must not be exposed as environment variables. The windows are previous-day 19:00 to current-day 00:00, current-day 00:00 to 14:00, and current-day 14:00 to 19:00. Select recordings only by Prisma `Recording.createdAt` using half-open ranges, and do not fall back to upload, share, or update timestamps. Keep one daily brief row per date and owner; later windows append into that row and merge its recording IDs. Keep startup compensation and overlapping-run coalescing, and do not reintroduce minute-based `setInterval` polling.

Transcription recovery decisions: recover interrupted local API transcription jobs with a dedicated `node-cron` task every minute and run one recovery sweep immediately at server startup. Query candidates with Prisma, verify that the local audio artifact exists, coalesce overlapping sweeps, and enqueue at most 10 recordings per sweep. Do not reintroduce the legacy 30-second `setInterval` recovery loop.

Server router dependency decisions: functions needed by server routes should be imported directly from focused utility modules whenever practical. Do not pass importable utility functions through router `configure()` dependency objects; reserve configuration injection for behavior that genuinely belongs to the application composition root or would otherwise create circular dependencies.

Pure-function dependency decisions: do not bind, inject, or pass stateless pure functions into child routers or child modules through `configure()`, dependency objects, closures, props, or equivalent wiring when they can be imported directly. Export them from a focused module and import them at the point of use; dependency injection is reserved for stateful runtime services, replaceable side effects, composition-root behavior, or genuine circular-dependency boundaries.

Reusable utility placement decisions: move functions with a high likelihood of reuse into the utility folder owned by their execution boundary or domain instead of leaving them embedded in a route, page, component, or composition file. Client-only utilities belong under `client/src/utils`, server-only utilities under `server/utils`, and agent-specific utilities under that agent's own `utils` folder. Keep narrowly domain-specific helpers in a focused utility module within the corresponding boundary, and do not create cross-boundary utility imports.

Tencent Meeting webhook payload decisions: handle the canonical `payload.event`, `payload.trace_id`, and `item.token_info` fields only; do not add aliases for alternative event, trace, or token-info field names. Recording-file extraction must read only the canonical `payload.payload`, `item.recording_files`, `file.record_file_id`, `item.operate_time`, and snake_case meeting/file fields documented by Tencent Meeting; do not add camelCase, capitalization, alternative-container, generic ID, or cross-level fallbacks in that extractor. When a canonical field is absent or invalid, return the zero value of the expected output type instead of guessing another field: `""` for strings, `0` for numbers, `[]` for arrays, `{}` for plain objects, `false` for booleans, and `null` only when the domain model explicitly defines a nullable value.

Tencent Meeting webhook documentation decisions: treat the subscription documents under `docs/tencentMeetingWebhook` as the sole source of truth for Tencent Meeting callback event names, payload shapes, field names, field locations, types, and required nesting. Before implementing or changing callback parsing, read the relevant document and follow it exactly. Do not add undocumented compatibility behavior, including camelCase-to-snake_case or snake_case-to-camelCase conversion, capitalization aliases, fallback field names, cross-level lookup, alternative container lookup, or treating a documented plain object as an array (or an array as a plain object). If the received payload does not match the documented shape, use the expected typed zero value or reject/ignore the invalid event as the documented processing path requires; never guess a compatible shape.

Tencent Meeting canonical recording callback decisions: treat `recording.audio-completed` as the recorder callback with the exact shape `{ event: "recording.audio-completed", trace_id, payload: [{ operate_time, recording_files: [{ record_file_id }] }] }`. This callback does not contain meeting information; do not infer `meeting_id`, `meeting_code`, subject, creator, meeting-record ID, duration, or other meeting fields from aliases, neighboring events, or generic IDs while parsing it. Treat `recording.completed` as the cloud-recording callback with the exact shape `{ event: "recording.completed", trace_id, payload: [{ operate_time, recording_files: [{ record_file_id }], meeting_info: { meeting_id, meeting_code, media_set_type, subject, creator: { userid, user_name }, meeting_type, start_time, end_time } }] }`. A callback may contain multiple `payload` items and multiple `recording_files`; read only these canonical snake_case paths, deduplicate files only by non-empty canonical `record_file_id`, and apply the typed zero-value rule to missing fields. Calculate cloud-meeting duration only as `meeting_info.end_time - meeting_info.start_time` after converting both canonical timestamps to milliseconds; if either timestamp is absent or invalid, or `end_time <= start_time`, return `0` and do not use file-, container-, event-, or current-time fallbacks.

Tencent Meeting recording identity decisions: use the canonical `record_file_id` as the only Tencent-side recording identifier for normalization, lookup, download-address requests, deduplication, and Recording persistence. Do not derive, query by, persist, or use `meetingRecordId`/`meeting_record_id`, and do not recreate legacy placeholder-replacement logic keyed by that value. The existing nullable Prisma column may remain temporarily as an unused compatibility column until an explicit schema-removal migration is requested.

Tencent Meeting transcript sync decisions: automatically query `/v1/records/transcripts/details` for the canonical `smart.transcripts` webhook event and for the recorder-specific canonical `recording.audio-completed` event. Recorder completion performs an immediate attempt followed by a bounded retry window because recorder transcripts do not emit `smart.transcripts`, and it may fall back to TXT transcript files exposed by the single-recording detail response. Do not poll transcript details from `recording.completed`, audio-download completion, cloud discovery, or pending-import sweeps, and do not fall back to per-paragraph detail fan-out.

Tencent Meeting webhook routing decisions: expose `/api/tencentMeeting/webhook` as the canonical callback and dispatch only by canonical `payload.event`. Persist callback payloads and processing status with Prisma. `recording.started` only provides persisted recorder-owner context, `recording.completed` imports cloud-recording metadata and queues audio, `recording.audio-completed` imports each canonical `record_file_id` and queues its audio download, `smart.transcripts` alone queues transcript synchronization, and `common.sts-token` only stores the Redis token before resuming pending audio imports.

Tencent Meeting STS token decisions: Redis is the only persistence store for STS token data; do not persist tokens in local files or use a process-local token fallback. Run the token validity check from `server/cron/tencentMeeting.js` immediately at startup and every five minutes, and use a Redis distributed request lock so multiple application instances do not submit duplicate token requests. Persist canonical `token_info` fields from the `common.sts-token` webhook with a Redis TTL derived from `expire_ts`.

Recording ownership decisions: `ownerName` is an immutable producer-name snapshot, not a client-editable label. Manual uploads must derive `userId`, `ownerClientId`, and `ownerName` from a server-signed Enterprise WeChat identity obtained during OAuth; never trust name or user-ID request headers for ownership. Tencent Meeting imports use the creator/owner display name returned by Tencent Meeting and may resolve a missing name from the verified Enterprise WeChat directory using the creator userid. A recorder `recording.audio-completed` import must prioritize the owner name carried by that same canonical event, including when updating an existing recorder Recording, and must never inherit ownerName from an adjacent `recording.completed` event. Only when the current event has no usable identity may the nearest preceding `recording.started` context from persisted webhook history act as a fallback; one started context may apply to multiple subsequent audio-completed files until a newer started event arrives or the context expires.

Visual direction: login and not-found screens follow the recording-list reference style—cool gray-blue atmospheric background, oversized heavy black display type, translucent white cards with generous radii, near-black primary actions, coral secondary accents, circular outline-icon controls, and soft low-contrast shadows.

Code comment decisions: add concise comments for non-obvious compatibility handling, business constraints, and implementation choices that future maintainers could otherwise accidentally remove. Do not add comments that merely restate the code.

Server logging decisions: format server call-flow log names exactly as `[call] {functionName} step {index}` without a trailing colon. Keep variable details in structured metadata or `message`, use stable incrementing step indexes within each function, log guard-clause exit reasons, and do not dump complete request, webhook, token, or other sensitive payloads merely for tracing.

Recording sequence decisions: allocate every new `Recording.seq` with Redis `INCR` using the fixed key `recording_current_seq`; do not derive a new seq by querying the latest Recording or by incrementing the legacy aggregate counter. During server startup, before listening or starting background jobs, query the maximum persisted Prisma `Recording.seq` and set that Redis key to the maximum, using `0` when the recordings table is empty. Sequence gaps after a failed database write are acceptable; duplicate allocation is not.
