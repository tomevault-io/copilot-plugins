# 项目协作规范

## 编码与审查

- 所有类、变量和方法都需要提供必要的中文注释，说明其职责、含义或关键约束。
- 实施需求前必须审核其合理性、可行性及潜在影响，不能盲目接受；发现风险或更合适的方案时应明确说明。

## 验证职责

- Agent 负责代码审查、自动化测试和构建验证；构建成功后可以安装应用，但不主动启动或操作真机，也不执行真机视觉验收。
- 需要真机验证时，Agent 应整理清晰的验收步骤和预期结果，由用户负责执行并反馈问题。

## Git 提交规范

- 每个 commit 必须是一个原子提交，只对应一个明确的修改点；不相关的功能、修复、重构或文档调整必须拆分为不同 commit，禁止为了省事混合提交。
- 同一修改点所必需的生产代码、配套测试和直接相关说明应放在同一个 commit 中，避免把不可独立验收的实现机械拆散。
- 提交标题必须采用 `<type>: <中文摘要>` 格式，例如 `fix: 修复设置开关文字切换不同步`。
- `type` 使用 Conventional Commits 类型，常用值包括 `feat`、`fix`、`refactor`、`test`、`docs`、`build`、`ci`、`perf`、`style` 和 `chore`。
- 中文摘要应简洁、准确地描述提交结果，禁止使用只有英文说明的提交标题。
- 除仅修改拼写等极小变更外，提交必须包含详细正文。标题与正文之间保留一个空行。
- 正文应根据实际情况说明变更背景、核心实现、影响范围和验证结果，避免只重复标题。
- 存在不兼容变更时，在类型后添加 `!`，并在正文末尾使用 `BREAKING CHANGE:` 说明迁移方式。

推荐模板：

```text
fix: 修复分段选择文字与高亮区域不同步

- 问题：选中状态变化时整段文字会提前切换颜色。
- 实现：使用同一动画边界裁剪选中文字，只改变与高亮重合的字形像素。
- 影响：不改变公共 API 和无障碍语义。
- 验证：通过单元测试、Lint 和 API 门禁；真机回归由用户验收。
```
