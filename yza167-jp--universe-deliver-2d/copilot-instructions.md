# AGENTS.md

本文件是仓库级长期指令。它应保持短、稳定、可执行。当前产品细节以 `CODEX_GOAL.md`、`DEVELOPMENT_TASKS.md`、`Docs/08_DECISION_LOG.md`、`Docs/M1/06_M1_DECISIONS.md` 和任务引用文档为准。

## 1. 每次任务的必读顺序

开始修改前必须阅读：

1. `AGENTS.md`
2. `CODEX_GOAL.md`
3. `DEVELOPMENT_TASKS.md`
4. `Docs/08_DECISION_LOG.md`
5. `Docs/M1/06_M1_DECISIONS.md`
6. 当前任务引用的 `Docs/*.md`
7. `git status`、近期相关提交和当前实现

不要只根据聊天提示工作，也不要跳过仓库现状检查。

## 2. 当前范围

- 当前里程碑是 **M1：Four-Planet Demo**。
- M0 已于 2026-07-24 完成，是冻结的回归基线。
- 只实现 `DEVELOPMENT_TASKS.md` 中状态为 `Ready` 或由主 Agent 明确选定的一个任务。
- 一次只允许一个 `In Progress` 任务。
- 未完成 Planet/Order/Character Packet 与任务依赖前，不批量制作新星球。
- M1 允许：赤砂星回访、白噪星、穹林星、群潮星、3 个必做支线、1 个可选扩展支线、低空投放、关系/许可/图鉴、飞船与站点初步成长。
- M1 不加入：完整敌人战斗、多飞船购买、程序生成路线、多单同时配送、复杂贸易、Steam SDK、云存档或大型基地经营。
- 每个任务都必须遵守其“明确不做”。

## 3. M0 基线保护

除非当前 M1 任务造成明确回归，不得重新设计或无理由重调：

- 大厅、驾驶舱、赤砂星首单与完整返航闭环。
- T-036 已通过的基础飞行手感。
- T-045 已通过的赤砂星路线、canonical AGL、检查点和有限平台规则。
- 护盾优先的统一飞行伤害入口。
- 持续 Beam 激光、有限倒车、倒车禁用 Boost。
- 场景级模态协调、通用对话整段跳过、版本化存档与备份恢复。

发现回归时，在当前任务内做最小修复；不要借机推倒 M0。

## 4. 不可擅自改变的产品事实

- 中文标题：`《我在宇宙送快递》`；英文工作名：`Universe Deliver`。
- 玩家是来自地球的人类，是银河外卖公司的快递员。
- 老皮是会说话、直立行走的外星水豚，从开场起就是固定伙伴。
- 不同文明通过同声传译器交流。
- 快递站为 2D 俯视角；星际旅行为 2D 第一人称可交互驾驶舱；星球进入/配送为横向侧视飞行。
- 主线是基本线性的单人叙事流程，不是 Roguelike。
- 玩家长期使用同一艘飞船，通过模块、数值和剧情功能升级。
- M1 中激光炮仍只用于陨石/明确环境物；星球目的地剧情无战斗。
- 主线失败不得造成经济死档或强制维修债务。
- 货物是剧情物件，不是随机词条集合。
- 角色名、物种细节、货物显示名等候选内容必须遵守 Canon Status；`PROVISIONAL` 不得静默升级为 `LOCKED`。

## 5. M1 内容规则

- 推荐主线顺序：赤砂回访 → 白噪星 → 穹林星 → 群潮星。
- 每颗新增主线星球必须同时具备自然、人文、冲突、独特飞行、剧情货物、核心 NPC、目的地区域、纪念品/图鉴和回访种子。
- 必做支线为白噪星、穹林星、群潮星各 1 份；赤砂星额外支线是范围允许时的扩展项。
- 支线可以失败、减报酬或失去额外关系收益，但不能造成主线死档。
- 穹林星的低空投放是 M1 第二种正式交付方式。
- 穹林星武器封存选择与群潮星控制权选择只改变关系、对白、路线便利和结尾变量，不创建指数级主线分叉。
- M1 只揭示：中继网早于公司、多个文明都曾接触它、老皮可感知普通设备无法识别的信号。不得自行揭示创造者、真实用途或最终结局。

## 6. 技术基线

- Godot `4.7.1-stable`，未经独立升级任务不得变更。
- GDScript；新增脚本默认静态类型。
- Compatibility renderer。
- 2D、16:9、内部视口 640×360、`viewport + keep + fractional fit`；像素纹理 nearest。
- 首要开发与验证平台：macOS / Apple Silicon；M1 收尾验证 Windows 导出。
- 输入必须通过 Input Map action。
- 飞船主体继续使用 `CharacterBody2D` 与显式积分。
- 只保留少量真正跨场景的 Autoload；不要创建万能 Manager 或默认全局 EventBus。
- 数据优先使用可验证 Resource/结构化文件；稳定 ID 使用英文 `snake_case`。
- M1 存档使用 schema v2，并必须迁移 M0 v1 存档，不静默覆盖旧档。

## 7. 代码与文档规范

- 文件、目录、类、变量、信号和资源 ID 使用英文 Godot 命名约定。
- 玩家可见文本使用本地化 Key，不把长段中文硬编码进脚本。
- 中文为源语言；英文列可占位，但 Key 必须稳定。
- 单个脚本职责清晰；优先小组件、信号和 Resource。
- 不为尚未出现的需求搭建复杂框架。
- 关键手感与系统参数集中配置，不散落魔法数字。
- 新的产品/范围决定更新相应 M1 文档与决策记录；普通实现历史由 Git 和任务结果表达。

## 8. 依赖与资产

- 默认不引入第三方插件、SDK 或运行时服务。
- 引入前先更新 `Docs/09_DEPENDENCY_LOG.md`，记录目的、版本、许可证、替代方案和移除成本。
- 外部/生成式素材记录到 `ATTRIBUTION.md`。
- 生成式素材默认为 placeholder/candidate，不自动视为最终资产。
- 不提交 `.godot/`、导出构建、缓存、本机设置或来源不明素材。

## 9. 测试与完成条件

除纯文档任务外，完成前必须：

1. 运行相关单元测试。
2. 运行关键场景/流程烟雾测试。
3. 运行 `./scripts/check_project.sh`。
4. 检查 `git diff --check` 与 `git status`。
5. 对受影响的 M0 路径执行必要回归。

自动测试重点覆盖数据引用、订单状态、v1→v2 迁移、星球解锁、关系/许可、支线计时与奖励、交付方式、飞行纯数学和关键场景实例化。

视觉节奏、角色语气、星球差异、飞行手感和音乐氛围不能伪装成完全自动验收。

## 10. Git 规则

- 只由主 Agent 提交；子 Agent 不提交。
- 一个提交对应一个完整、可解释的增量。
- 提交前通过适用检查。
- 提交信息优先中文。
- 不修改、覆盖、删除用户未提交工作。
- 不使用破坏性 Git 命令或重写未经确认的历史。
