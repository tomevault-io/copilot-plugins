# AGENTS.md

这是 `research-agent` 的开发与 Review 规则。当前代码和正式规格优先于历史计划与参考笔记。

## 沟通与执行节奏

- 解释陌生概念时，先用大白话说明“解决什么实际问题、在当前项目里会发生什么”，再补术语和接口；
  不得让项目所有者根据字段名猜业务含义。
- 默认小步开发。开始前说明目标、数据流、文件、持久化位置和验证方法；完成后报告修改、原因、验证、
  未完成内容和下一步。未经确认，不扩大范围或进入下一项大型 Task。
- 不自动提交、合并、删除工作区或执行破坏性操作。
- 工作区可能已有用户或其他 Agent 的修改。不得 reset、checkout、覆盖或顺手整理无关改动。

## 阅读路由

- 修改代码、依赖、数据库或目录前，主 Agent 先读 `docs/development/collaboration-guide.md` 和
  `docs/specs/0001-minimum-mvp.md`；改动系统边界、上下文、记忆或论文库时，再读
  `docs/architecture/system-overview.md`。
- 只有核对历史方案时才读 `docs/reference/obsidian-design-notes/`；文档入口和权威级别见 `docs/README.md`。
- Worker 默认只读根 `AGENTS.md`、Task Brief、相关代码和测试；边界改变、Brief 有歧义或主 Agent 明确要求
  时，才继续读完整规格。
- 不得把计划中的模块或调用关系描述成已经实现。

## 修改前必须明确

涉及两个或以上模块时，修改前先画基于当前代码的实际调用图：

```text
入口 → 调用函数 → 输入/投影 → 判断与副作用 → 持久化边界 → 输出消费者
```

每个箭头都必须能在当前代码中找到调用点。Task Brief 至少写清：目标、负责文件、输入、处理、输出、
持久化边界、验证方式和明确排除项。

涉及模型响应、Tool、外部输入、并发顺序或状态变化时，先确认产生了哪些不可重建事实、首次保存位置、
重启恢复方式，以及审计/Compact/回放是否需要其身份、顺序和因果关系。模型调用 ID、轮次、批次位置和
请求/结果对应关系必须首次产生时持久化；摘要、索引和前端投影不能代替原始事实。

## 项目硬边界

- SQLite 是结构化权威存储；Long-term Memory 正文以 `data/memory/**/MEMORY.md` 为权威，SQLite 只保存
  可重建投影。Session Memory、Daily Summary、Long-term Memory 和 Working Context 不能混成同一层。
- Transcript 只能追加；Compact 不能删除原始事实。
- 所有数据访问先校验 `project_id`，禁止跨项目读取。
- Tool Call 与 Tool Result 必须成对并保持批次完整；外置结果只向模型暴露稳定 `result_id` 和预览，
  不暴露文件路径。
- Memory、Artifact、Evidence、Research State 和运行状态职责分离。外部输入、Tool 参数和模型结构化输出
  都不可信，必须校验 Schema、作用域和来源。
- `memory/session/`、`memory/long_term/`、`memory/recall/` 保存业务实现；根目录同名文件只做兼容导出。

## 开发与测试

- Python 3.12；依赖只通过 `uv`、`pyproject.toml` 和 `uv.lock` 管理。
- 数据库结构通过 Alembic 迁移修改，不能依赖启动时隐式改表。
- 缺陷修复先写可复现失败测试，再做最小生产修改。
- 异步操作必须说明超时、取消和异常传播；长任务与重试路径必须幂等。
- 不提交密钥、真实隐私论文数据、本机绝对路径或大型模型文件。

每个代码开发切片都必须有与风险相称的集成测试。涉及 `AgentRuntime`、`loop`、Context、Transcript、
Tool Result、Compact、Memory、恢复、事务或重试时，测试必须覆盖真实入口、真实调用关系、关键输入输出和
最终持久化状态；只测 helper 或 mock 调用方不能证明接线完成。

跨模块测试还要覆盖新旧组合的主流程、失败、取消、重试、重启恢复和异步时序插入，证明中间字段不丢失、
持久化事实与真实请求/输出一致、副作用只发生一次，且新失败不会误触发旧终态或恢复分支。

主 Agent 累计集成范围至少覆盖 `API/AgentRuntime → Run/Transcript → Main ModelCall → Tool →
Context/Compact/Memory → 下一轮 Main ModelCall → 最终数据库、Transcript 和文件状态`。

提交前先跑全量回归，再跑当前改动的定向测试。全量回归若被环境或既有问题阻断，交接中必须列出具体
失败、受影响的旧链路和测试缺口；不能用定向测试通过代替完整验收。

## Review 与交接

正式 Review 前，Agent 先独立完成异常边界检查，不把发现遗漏的责任交给项目所有者。Review 按顺序提供：

1. 精简实际调用图：入口、关键投影、外部副作用、持久化写入和输出消费者，标明文件与函数；
2. 不变量：必须始终成立的唯一性、完整性、预算和作用域规则；
3. 反例矩阵：并发、重复调用、取消、崩溃、数据库失败、重试耗尽、跨作用域和非法输入；
4. Findings：真正发现的问题、修复位置和验证证据；
5. 涉及恢复、取消或复杂终态时，再给端到端状态图。

项目所有者确认产品策略和状态归属；Agent 负责接线、事务、恢复、越权、预算和测试。带项目所有者读代码
前，先说明文件职责、依赖和实际调用方向；不能把计划中的 Pipeline 当成已接通，也不能让项目所有者自行
猜异常边界。函数名不得隐藏副作用。

## 代码注释规则

- 新增或修改的模块说明必须写清：文件作用、入口函数、主要调用方、输入、输出和持久化边界。
- 复杂函数、事务、状态转换、异步边界和恢复逻辑按可阅读阶段写中文注释。保留“第一段、第二段”等阶段
  标题，再说明该阶段读取什么输入、读写哪个权威对象、成功产生什么，以及每个关键失败分支为什么发生、
  由谁重试、回滚或收口。
- 校验函数先说明“要验证什么事实或回答什么问题”，再写路径、字段和类型规则。
- 注释解释“为什么”和“输入怎样变成输出”，不逐行翻译语法，不给简单赋值加噪声。补充分支说明时不得
  删除阶段标题。

## Plan 编写规则

涉及第三方工具、模型输出、文件格式、数据库投影或两个以上模块时，Plan 在列问题和 Task 前，必须按顺序
提供项目所有者无需读代码也能理解的白话数据说明：

1. **真实输入和输出：** 用当前代码、真实命令输出或去隐私样本说明数据形状；没有真实样本时明确标注
   “推测”或“人工 fixture”。
2. **最小具体样例：** 展示一份缩短后的同结构数据，逐项解释关键层级和字段的业务含义。
3. **采用与不采用：** 对每类上游文件或字段说明“直接使用、只供诊断、完全不使用”及原因。
4. **转换映射：** 写清“上游内容 → 内部保存 → 下游消费者”，标出权威原件、SQLite 写入点和可重建投影。
5. **完整实例链路：** 选择一条具体记录，从输入画到内部对象、数据库、检索/模型消费者和最终回查。

白话区使用“页面大块、原始位置编号、文件清单、状态更新”等业务含义。术语第一次出现时必须用具体例子
解释；类名、字段名、表名、错误码和函数调用放到“实现和代码 Review”部分。段落保持短小，问题、选择、
验证分开写。

每个实施 Task 的产品 Review 部分必须保留三个标题：

1. **这一步要得到什么：** 写完成后用户或下游实际得到的结果，不能只写“完成某模块”。
2. **为什么现在做：** 写当前问题和不处理的具体后果，不能只写“保证一致性”。
3. **你只需要确认什么：** 只列产品行为、失败边界或工程取舍；没有新选择时明确写“本步没有需要额外
   确认的产品决策”。

随后必须单独写：

> 以下是给执行 Agent 的技术清单，产品 Review 可以跳过。

这句话之后才列文件、类、字段、数据库结构、错误码、测试命令和实现步骤。新的产品取舍不能藏在技术清单
里，必须回到白话区说明影响并单独确认。

技术区的策略必须明确：谁读取什么输入、按什么顺序处理、写入或返回什么、怎样防止重复或遗漏、失败在
哪里停止、由什么测试证明。只写“增加校验”“记录 audit”“保证一致性”不算策略。

涉及架构、协议、状态、并发、持久化或安全边界的 Plan，还必须写：当前问题、最终选择、一个替代方案、
工程取舍和可复述的面试表达。

## 子 Agent 使用

- 低风险文档、注释和机械修改由主 Agent 完成，做匹配的最小验证。
- 中风险普通业务、Repository、API 或局部数据库修改可由一个 Worker 实现，主 Agent 检查 diff 和测试。
- 迁移、并发、持久化恢复、安全边界或外部副作用等高风险改动，由一个 Worker 实现，再由新的 Agent 独立
  Review；不可逆操作还必须明确审批点和回滚方式。
- Worker 只接收必要的 Task Brief，必须知道工作区还有其他操作者，不得撤销无关修改。
