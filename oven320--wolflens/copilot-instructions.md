# WolfLens 开发规则

本文件适用于整个 WolfLens 仓库。后续开发应采用“小步修改 + 文档接力”：每轮只解决一个边界清晰的问题，完成后更新 `CODEX_HANDOFF.md`，避免同时改动 schema、pipeline 和 UI 而难以验证。

## 项目定位

WolfLens 是一个狼人杀阶段化复盘工具，不是在线对战平台，也不是直接猜身份的 AI 玩具。

目标流程：

```text
输入对局文本
  -> 结构化事件抽取（用户不可见）
  -> 可视化修正
  -> 阶段化复盘输出
```

## 1. 禁止偷看未来信息

- 当前阶段页面只能使用当前阶段及之前的 `visible_events`。
- 阶段图、右侧面板、风险提示、局面识别、策略建议和报告结论不得读取未来阶段事件。
- 最终完整复盘可以使用 `all_events`，但必须明确区分：
  - 当时可见信息：只基于该阶段及之前的事件；
  - 事后复盘信息：允许使用完整事件链和最终结果。
- 新增分析器时，优先接收显式事件切片，不要默认读取整局事件列表。
- 测试必须覆盖：切换到较早阶段时，未来死亡、未来投票和未来发言不会影响当时页面。

## 2. Schema 必须统一

- `wolflens/schema.py` 是 Python 核心数据结构的唯一事实来源。
- event 至少应统一包含：
  - `event_id`
  - `phase_id` 或 `phase_index`
  - `type`
  - `actor`
  - `target`
  - `content`
  - `source_text` 或 `evidence_span`
- 当前历史结构仍使用 `round_id` 与 `phase`。后续迁移必须小步进行，先定义兼容字段和迁移影响，再逐个修改 parser、tracker、UI 和测试。
- 不要维护多套含义相近但字段不同的 event 结构。若前端需要适配，使用单一 adapter 转换核心 schema。
- 新增字段时，在 `CODEX_HANDOFF.md` 说明：
  - 为什么需要；
  - 哪些模块读取或写入；
  - 是否向后兼容；
  - 需要补哪些测试。

## 3. UI 必须来自 Pipeline

- 不允许在 UI 中硬编码 `P1`、`P2`、`P4` 的结论、玩家风险、箭头或样例报告。
- 阶段切换、圆环玩家图、事件列表、证据详情和报告内容必须来自真实结构化事件或 pipeline 输出。
- 没有数据时显示空状态，不展示假结论。
- 示例数据可以存在，但加载示例后也必须走同一条 parser -> pipeline -> UI 链路。
- `frontend/` 当前是 React 原型。接入后端前，mock 数据只能用于原型展示，不得被误认为真实分析结果。

## 4. 证据链必须可追溯

- 每个关键判断必须能追溯到：
  - `event_id`
  - 阶段
  - 玩家
  - 原文片段
- 不允许生成没有 `evidence_id` 的强结论。
- 面向普通用户时，可以隐藏内部 ID，但必须保留可展开的证据详情。
- 证据解释不是模型隐藏思维链。界面统一使用“证据详情”“分析依据”“来源事件”等名称。

## 5. 玩家画像必须克制

- 只能称为“游戏风格”或“策略画像”。
- 只能基于本局当前可见行为。
- 不允许推断现实人格、智商、恶意或心理动机。
- ToM 层用于评估游戏内表达可能如何被理解，不用于对真实玩家做心理诊断。

## 6. Local-first 与 LLM Fallback

- 无 API key 时必须可运行。
- LLM 增强必须使用现有可配置接口，不硬编码外部模型。
- LLM 输出必须经过 schema 校验；解析失败时退回规则实现。
- 不上传、不保存用户对局文本，除非用户明确选择保存或导出。

### 记忆库 UI 约束

- 记忆库只能展示用户主动保存到本地的摘要与画像。
- 没有记忆时显示空状态，不注入演示局或硬编码画像。
- 历史玩家信息只能称为“游戏风格 / 策略画像”。
- 历史画像不能直接改变本局身份概率、风险颜色或定罪结论。
- 画像证据必须展示来源对局、`evidence_id`、可见范围和可见阶段。
- UI 只读浏览与主动保存应保持分离；保存入口必须明确提示本地持久化，默认关闭。

## 7. 每轮交付要求

- 优先修改最少的文件。
- 不顺手重构无关模块。
- 不覆盖工作区中来源不明的已有改动。
- 运行与改动范围匹配的测试。
- 更新 `CODEX_HANDOFF.md`，至少记录：
  - 本轮修改文件；
  - 影响范围；
  - 测试结果；
  - 已知风险；
  - 下一步建议。

## 8. 三线程协作边界

为避免 schema、推理逻辑和 UI 同时漂移，后续工作分为三个线程。每个线程默认只修改自己的责任范围；需要跨界时，先在 `CODEX_HANDOFF.md` 写清接口变化和影响文件。

### A. 推理架构线程

负责：

- 核心 schema 与兼容迁移；
- parser、阶段识别、状态追踪；
- `visible_events` / `all_events` 契约；
- 证据卡、belief、局面路由、ToM、策略、反事实；
- Python pipeline 的数据流正确性。

默认不负责：

- 页面美化；
- React 组件布局；
- 用 UI 临时逻辑绕过 pipeline。

### B. 数据与评测线程

负责：

- `examples/` 与 `examples/eval_cases/`；
- `scripts/evaluate_cases.py`；
- parser、阶段隔离、证据追踪、报告质量的自动评测；
- 公共数据 adapter 方案与 license 记录；
- 回归结果文档。

默认不负责：

- 直接重写 pipeline；
- 为了提高分数在 UI 中硬编码样例结论。

### C. 全栈产品与 UI 线程

负责：

- 整体集成与用户流程；
- Streamlit 页面和组件；
- React 原型、页面结构和创新交互；
- pipeline 输出到 UI 的 adapter；
- 空状态、错误状态、加载状态和证据展开体验。

必须遵守：

- UI 只消费真实 pipeline 输出；
- mock 仅用于明确标注的原型展示；
- 不在 UI 中新增推理事实；
- 不自行发明第二套核心 event schema；
- 发现后端接口不足时，把需求写入 `CODEX_HANDOFF.md`，交由 A 线程处理。

### 共享规则

- `AGENTS.md` 与 `CODEX_HANDOFF.md` 是共享协作文档。
- 修改共享接口前先记录数据契约，再改代码。
- 单轮尽量只由一个线程修改同一文件。
- 合并前优先验证：阶段隔离、证据追踪、无数据空状态、无 API key fallback。
