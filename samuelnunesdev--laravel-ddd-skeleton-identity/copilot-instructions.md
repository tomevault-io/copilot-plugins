# Project Guidance

## Purpose

This repository is a cloneable Laravel DDD Skeleton with an embedded Identity Platform. Preserve its ability to serve as the starting point for other modular Laravel systems.

## Architecture

- Organize code vertically under `app/Modules/<Module>`.
- Use hexagonal architecture by default.
- Use lowercase kebab-case for static URI path segments, for example
  `/oauth-clients` and `/password-reset`. Keep Laravel route names in dotted
  notation and route parameter names in lowercase snake_case.
- Keep Domain independent of Laravel, Eloquent, HTTP, queues and infrastructure.
- Put use cases and DTOs in Application.
- Put Ports In and Ports Out under `Application/Ports`.
- Put controllers in `Infrastructure/Http/Controllers`.
- Put persistence adapters in `Infrastructure/Persistence/Adapters`.
- Keep Eloquent Models in Infrastructure.
- Never put repository interfaces in Domain.
- Do not create repositories by ceremony. Prefer `make:port` and `make:adapter` when a real boundary exists.
- Use `make:repository` only when explicitly justified.
- A module must not use another module's Eloquent Model or tables directly.
- Communicate through application contracts or versioned integration events.
- Keep `app/Shared` small and free of business concepts owned by a module.

## Mandatory domain rules

- Identity is global; authorization is scoped by organization and module.
- Never trust an `organization_id` or `module_id` directly from a Request.
- Organizational use cases require a validated `OrganizationContext`.
- Module access requires all of:
  - active identity;
  - active organization;
  - active membership;
  - active module;
  - module enabled for the organization;
  - at least one active role;
  - at least one effective permission.
- Effective permissions are `(inherited union direct grants) minus direct denials`.
- A direct grant or denial cannot exist without an active role in the same context.
- Direct grant and denial are mutually exclusive for the same identity, organization, module and permission.
- Permissions belong to one module and may be reused across organizations.
- Global module roles may be reused; organizational roles cannot leave their organization/module.
- Creating permissions, creating roles, assigning roles and changing direct effects are separate capabilities.
- Client Credentials represents an OAuth Client, never a human identity.

## Data lifecycle

- Protected entities use deactivation, soft delete, revocation or ended validity.
- Do not implement hard delete for identities, organizations, memberships, modules, organization-module links, OAuth Clients, service authorizations, roles, permissions, role compositions, assignments or overrides.
- Do not use destructive cascades for security/audit data.
- Audit events are append-only.
- Purge is allowed only for categories and retention periods defined in ADR-007 and the TRD.
- Migrations must preserve historical and referential integrity.

## Security

- Never log passwords, full tokens, OAuth secrets, TOTP secrets or recovery codes.
- Use server-side authorization on every administrative operation.
- UI capability checks are not authorization.
- Require exact Redirect URI matching and PKCE `S256`.
- Password and Implicit grants are forbidden.
- Use parameterized queries, contextual escaping and allowlists.
- Keep secrets outside the repository.
- Treat security failures as closed by default where the TRD requires it.
- A Psalm suppression must be local and justified; do not create a taint baseline for the skeleton.

## Implementation workflow

- For complex work, follow `docs/implementation/IMPLEMENTATION-PLAN.md` as a living execution plan.
- Work on one authorized milestone at a time.
- Before editing, inspect the repository and relevant module documentation.
- Keep `Progress`, `Discoveries` and `Decision Log` in the plan current.
- Do not implement later milestones merely because their files are nearby.
- Do not version empty module directories merely to advertise a future layer.
  Add a directory when its first real implementation file is introduced, and
  remove obsolete `.gitkeep` placeholders as the module evolves.
- If behavior is unclear, consult the PRD and TRD before inferring.
- If a durable architectural choice is missing, propose an ADR.
- Keep changes focused; preserve unrelated user changes.
- Do not commit, push, merge, publish or release unless explicitly requested.

## Testing expectations

Every behavior change needs the lowest appropriate test and, when applicable, an integration or E2E test.

Prioritize negative tests for:

- cross-organization access;
- cross-module permission use;
- privilege escalation;
- missing roles or zero effective permissions;
- disabled and soft-deleted records;
- token issuer/audience/nonce/PKCE failures;
- service principals used in human-only routes;
- secret leakage;
- hard-delete attempts.

Run the applicable commands before declaring work complete:

```bash
composer validate
php artisan ddd:check
vendor/bin/pint --test
vendor/bin/phpstan analyse
composer security:taint
# M12: uncomment after implementing the controlled vulnerable fixture.
# composer security:taint-self-test
vendor/bin/phpunit
npm run lint
npm run typecheck
npm run build
npx playwright test
composer audit
npm audit
```

If a required command does not exist yet, create it in the milestone responsible for project tooling. Do not claim a check passed when it was skipped.

## Definition of done

A task is complete only when:

- behavior matches PRD acceptance criteria;
- code respects the TRD and accepted ADRs;
- module boundaries pass `ddd:check`;
- migrations and data lifecycle are safe;
- server-side authorization is present;
- relevant tests pass;
- static analysis and taint analysis pass;
- documentation and the implementation plan reflect material changes;
- the final report names checks run, checks not run and remaining risks.

## Laravel DDD Toolkit

This project uses Laravel DDD Toolkit.

Architecture defaults:

- vertical modules under `app/Modules`;
- hexagonal architecture by default;
- pragmatic tactical DDD;
- `make:module`, not `make:domain`;
- ports live in `Application/Ports/In` and `Application/Ports/Out`;
- adapters live in `Infrastructure`;
- Domain must not depend on Laravel, Eloquent, HTTP, Jobs, Infrastructure or external SDKs;
- Application must not depend on Controllers, Requests, Eloquent models or Infrastructure adapters;
- Infrastructure may depend on Application and Domain;
- Eloquent is allowed in Infrastructure;
- repositories are optional and should only be generated when they add value.

Recommended command before finishing architectural changes:

```bash
php artisan ddd:check
```

Module-level AI docs:

- New modules may include their own `README.md` and `AGENTS.md`.
- Module-level `AGENTS.md` files provide more specific instructions for that module and should be respected over generic project-level guidance when editing files inside the module.
