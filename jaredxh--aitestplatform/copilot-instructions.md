## Agent Rules

- 每次实现需求或修复 bug 前，必须单独创建 git worktree 和分支。
- worktree 统一创建在项目目录下的 `.worktree/` 中，例如 `.worktree/feature-name`。
- 开发、测试、提交应在对应 worktree 和分支内完成，避免直接在主工作区改动需求代码。
- 分支名称应清晰描述任务范围，例如 `feature/preview-ui` 或 `fix/file-recovery`。
- 编写 plan 后进入执行阶段时，应尽量创建 subagent 并行处理可独立推进的任务。
- plan 编写完成后自动合并worktree 和分支到主分支

# 项目语言规范

请严格遵守以下规则：

1. 所有对话、解释、建议必须使用**简体中文**。
2. 代码注释必须使用中文。
3. 生成的 Commit Message 必须使用中文。
4. 严禁出现大段未翻译的英文技术名词（保留专业术语如 API、SDK 除外）。

# 项目指导准则

这些准则用于减少常见的 AI 编码失误。请在执行任务时与本仓库的具体约定合并使用。

1. **先思考，再编码**：不要隐藏不确定性。实现前说明关键假设；如果存在多种解释，先指出差异；如果有更简单方案，主动说明；如果需求不清楚，先停下来提问。
2. **优先简单方案**：只实现用户明确要求的内容。不为单次使用场景抽象，不添加未被要求的配置项，不写投机性功能。如果实现明显可以更短、更直观，就先简化。
3. **保持改动外科手术式精准**：只改必须改的地方，不顺手重构无关代码，不替用户删除既有死代码。若当前改动造成未使用的导入、变量或函数，需要一并清理。
4. **围绕目标闭环验证**：把任务转换成可验证目标。例如「修复问题」应尽量补充复现测试并让测试通过；「重构」应确认重构前后的测试都能通过。多步骤任务需要给出简短计划和验证方式。
5. **把模型用于判断型任务**：分类、草拟、总结、提取可以交给模型；路由、重试、确定性转换优先交给代码处理。代码能稳定回答的问题，不要用主观判断替代。
6. **关注上下文预算**：当任务或会话上下文接近上限时，先总结当前状态并重新组织上下文，不要静默超限。
7. **显式处理冲突**：如果两种代码模式互相矛盾，选择更新、更稳定或测试覆盖更好的方案，并说明原因；不要把冲突模式混在一起。
8. **写之前先读**：新增或修改代码前，先查看导出、直接调用方和共享工具。若不确定现有结构为何如此，先查清或提问。
9. **测试表达意图**：测试不只验证行为结果，也要体现行为为什么重要。业务逻辑变化时不会失败的测试，通常不是好测试。
10. **重要步骤后做检查点**：阶段性说明已完成内容、已验证内容和剩余风险。若无法准确复述当前状态，应先停下来整理。
11. **遵循仓库约定**：在代码库内部，一致性优先于个人偏好。如果认为既有约定有害，应先说明风险，不要私自引入另一套风格。
12. **明确暴露不确定性**：「已完成」必须意味着没有静默跳过的工作；「测试通过」必须说明实际运行过哪些验证。默认公开不确定性，而不是隐藏它。
