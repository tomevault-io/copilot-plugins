## livinghinge2

> レーザー加工用カーフベンディング/リビングヒンジパターンを生成するWebアプリ。

# リビングヒンジ ジェネレーター — 開発引き継ぎ資料

レーザー加工用カーフベンディング/リビングヒンジパターンを生成するWebアプリ。
現状は単一HTMLファイル(`index.html`)として完結し、WordPressのuploads配下に置くだけで公開できる。

- 公開URL: https://laser-kakouki.com/wp-content/uploads/2025/12/livinghinge.html
- 作業ファイル名は `index.html`(公開時に `livinghinge.html` へリネーム)
- 現行サイズ: 約66KB / 1,431行
- **実行時の外部依存: ゼロ**(v6でGoogle Fonts読み込みを削除。フォントはOS標準のみ)
- 開発時の依存: 検証ツールのみ(Playwright / Chromium。`tools/*.mjs`)

## 方針(v8で転換)

**仕様の安定と出力データの正確性のためなら、「手書きの単一ファイルであること」「ビルドレスであること」は犠牲にしてよい。**

ただし勘違いしないこと ——
**配布物としての単一HTMLとオフライン動作は放棄しない**。ビルド(`vite-plugin-singlefile` 等)で
1枚のHTMLに畳めば、WordPress uploads運用もCDN障害耐性もそのまま維持できる。
実際に手放すのは「手書きの単一ファイルで開発すること」だけである。

---

## 1. 絶対に壊してはいけない契約(Hard Contract)

1. **DXF出力**: 単位mm実寸、レイヤー名 `CUT`。Y軸は反転して出力(`y' = H - y`、DXFはY上向きのため)。
   現行はR12形式(AC1009)で、2点線分は `LINE`、多点は `POLYLINE`+`VERTEX`+`SEQEND`。
   LightBurn / Illustrator / Fusion 360 / Inkscape で読めることを維持する。
   (バージョンの引き上げは §8 P1-5 で検討中。**mm実寸とレイヤー名は形式を変えても不変**)
2. **SVG出力**: `width="{W}mm" height="{H}mm" viewBox="0 0 W H"`(=1ユーザー単位が1mm)、
   `stroke="#FF0000" stroke-width="0.1"` fill無し。テキスト要素は含めない。
3. **配布物は単一HTML・実行時ゼロ依存**。CDNやWebフォントを実行時に読みに行かないこと
   (CDN障害・オフラインで壊れるため。過去に明示的に不採用を決定済み)。
   ビルドで達成するのは可(v8以降)。**ソースが単一ファイルである必要はもう無い**。
4. **設定共有URL**: `location.hash` にJSONを `encodeURIComponent` して保持。
   後方互換を守ること(古いキー、例: 廃止済み `p.web` が入っていても無視して動くこと。テスト済み)。
   新キーを足す場合は、そのキーが**無い**古いhashでもデフォルトにフォールバックすること
   (v6で `mat` を追加。旧hash読み込み時は `mat` 未定義→デフォルト適用をテスト済み)。
5. ブラウザストレージ(localStorage等)は使わない。状態共有はhashのみ。
6. **出力を変える変更は必ずゴールデン照合を通す**(§6.0)。
   `node tools/golden.mjs check` が通らない変更は、出力仕様を意図的に変えた場合を除いてマージしない。
   意図的な変更なら `capture` で採り直し、**差分を必ずレビューしてから**コミットする。

## 3. パターン生成仕様

### 3.1 共通(列ベース: straight / wave / diamond / cross / arc)
- `columnXs(x0,x1,pitch)`: 領域内に対称配置した列中心X群。
- `centerYs(y0,y1,period,offset)`: period = `cut + gap`。偶数列はoffset 0、奇数列はperiod/2ずらし(千鳥)。
- 生成後は必ず `clipRect` で余白内にクリップ(開ポリライン対応の半平面クリップを4回)。
- diamond/crossは形状幅を `pitch - 0.6〜0.8` で自動制限。

### 3.2 hex(ハニカム)
尖頭六角形(pointy-top)。各六角形を左右2本のポリラインで描き、上下頂点の隣接辺を
`gap/2` ずつトリムしてブリッジを残す。colStep=`√3R+hs`、rowStep=`1.5R+hs*0.87`、奇数行は半列オフセット。

### 3.3 spiral(メアンダー)★最重要
**[4,2] 2Dメアンダーパターン**(Dujam Ivanišević / koFAKTORlab 2014年考案)の忠実な実装。
形式化の出典: Zarrinmehr et al. "Kerfing with Generalized 2D Meander-Patterns" (CAADFutures 2017)。

構造の要点(実装を触る前に必ず理解すること):
- 正方形クワッド格子。各クワッドに**同キラリティの矩形スパイラル2本**を対角アンカーで絡ませる。
- カットは格子頂点で合流し「4本枝のスパイラルツリー」になる。頂点は市松2彩色され、
  片方の色(ツリー頂点)からだけ渦が生え、もう片方(エッジ中点相当)は**無傷のソリッド固定点**として残る。
- ウェブ(セル間の枠)は**存在しない**。材料は固定点同士を結ぶ蛇行アームのみ。これが二重曲率の柔軟性の源。

実装詳細(`GEN.spiral`):
- アーム幅 `sw` はセルサイズ `cs` の**奇数分割に自動スナップ**: `N = round(cs/sw)` を奇数化(最小5)、`p = cs/N`。
  → 渦間隔が全域で完全に均一になる数学的条件。
- 基本パスA(アンカー(0,0)、自ピッチ2p)の頂点列:
  `(0,0) → (S-p,0) → (S-p,S-p) → (2p,S-p) → (2p,2p) → (S-3p,2p) → (S-3p,S-3p) → (4p,…) …`
  (k%4でR/U/L/D、インセットは1周ごとに2p増。線長がp以下になったら終了)
- B = Aの180°回転(同一クワッド内で絡む相手)。
- 奇数パリティのクワッドは `rot90: (x,y)→(S-y,x)` を適用(**ミラーではなく回転**。キラリティを全クワッドで統一するため。ここをミラーに変えると本物と異なる構造になる)。
- 偶数クワッドは水平辺上に、奇数クワッドは垂直辺上にカットを持つため、共有辺のカットは重複しない(設計済み)。

### 3.3.5 bone / hexslit / ehex / tri(v7で追加、fequalsf再現)
fequalsf.com の "parametric kerf" テストフォブDXF(#6/#7, #8, #9)を解析して再現したもの。
DXFはR13(AC1012)・SPLINE主体。**スプラインは短い断片の連鎖なので、端点連結(join)して
初めて本当のモチーフ形状が分かる**(断片単位のbbox統計では誤同定する。v7初版はこれで
縦の鼓形と誤実装し、やり直した)。手順は§6.7。

- **bone**(#6/#7): 参照モチーフは **幅1.205×高さ0.133の滑らかな閉曲線** =
  中央レンズ(半幅A≈0.055×全長) → 細い首(≈0.13A) → 両端の丸バルブ(r≈0.7A)。
  半幅プロファイルを円弧+コサイン補間で構成し、`straight` と同じ列/千鳥配置。
  レンズ内部は脱落する(仕様)。パラメータ pitch/cut/gap/**br**(=レンズ半幅)。
- **hexslit**(#8): **フラットトップ・縦0.8スカッシュの六角形**。各セル =
  **完全に閉じた内六角形(芯は脱落する。参照フォブも同じ)** + 外郭線 + セル間の帯 `hs`。
  パラメータ hr/hs/**rw**(リング幅=外郭−内六角)/gap(ブリッジ幅)。
  参照比率: 内/外 ≈ 0.73 → rw標準1.2(hr=5時)。
  - **外郭は左右2本の長いポリライン**で、切れ目は**上辺・下辺の中央だけ**(各セル2箇所)。
    こうすると左右/上下の鏡対称が保たれ、参照フォブ#8と同じ規則的な織り目になる。
    v9までは角3箇所で切って2辺ずつ3ピースに割っていたため、3回対称の風車状になり、
    短い括弧が散らばったノイジーな見た目だった(v10で修正)。
  - リング帯(内六角と外郭の間)は上下2箇所のブリッジでウェブに繋がる。脱落するのは
    **各セルの芯だけ**で、これは仕様(§7.1)。連結成分数は修正前後で完全に同一
    (margin=2 で soft/std/firm = 153/99/46)であることを実測確認済み。
- **ehex**(#5): **横長に伸ばした六角形のハニカム格子**。参照フォブ#5の再現。
  パラメータ el(全長)/eh(高さ)/es(セル間隔)/gap(ブリッジ幅)。
  - **向きが最重要。フラットトップ(左右が尖端 / 上下が水平な平坦辺)である。**
    `hex` は尖頭六角形(上下が尖端)なので、`hex` の式をそのまま横に伸ばすと
    **90°違う向き**になる(v12で実際に踏んだ。§9参照)。頂点は
    `L(-A,0) UL(-F,-B) UR(F,-B) R(A,0) LR(F,B) LL(-F,B)`、`A=el/2`・`B=eh/2`。
  - **平坦部の比率 `FR=0.6`**(`F=A*FR`。正六角形なら0.5。参照フォブは平坦部が長く
    尖端が短い)。この比率が格子ピッチにも効く: `colStep=A*(1+FR)+es*0.87`、
    `rowStep=eh+es`、**奇数列を `rowStep/2` だけ縦にずらす**(フラットトップ格子は
    列オフセットであることに注意。行オフセットではない)。
  - 各セルは上下2本のポリラインで描き、左右の尖端で `gap/2` ずつトリムしてブリッジを残す
    (トリム比 `t=(gap/2)/hypot(A-F,B)`)。尖端は隣列のセルと向き合うので、参照フォブの
    ロゴに見える「六角形の上下に斜め線対」= 隣列セルの尖端が平坦辺の中央に来る形になる。
  - **何も脱落しない**(§6.2適用可)。実測: margin=2 で全プリセット+ソルバー両端
    (el=8/eh=2/es=0.7、el=24/eh=7/es=2.5)+非整数比(el=13/eh=3.3)すべて連結成分1。
    margin=0 でも最大0.79%(外周クリップ由来の軽微な欠け)。
    ただし **es が 0.5mm を切ると 0.3mm カーフでウェブが消えて崩壊する**
    (es=0.4 で連結成分2688 / 脱落42%を実測)。ソルバーの柔らかい端は es=0.7 で止めてある。
  - 目標半径ソルバーの到達域は板厚3mm・MDFで **R ≈ 15〜25mm**(構造上つねに柔らかい)。
- **tri**(#9): 三角格子(辺 **ts**)。**格子の辺自体もカットする**(両端を `gap/2` 縮めた
  1本の直線 → ブリッジは格子頂点に集まる)。各セル(上向き/下向き三角形の両方)に
  同心の内接三角形リング(間隔 **td**)。**各リングは切れ目1箇所だけの開ポリライン**で、
  切れ目を置く角をリングごとに回す(`(k-1)%3`)。
  - **リングごとの切れ目が1箇所であることが見た目の要**。参照シート#9の特徴である
    「全幅に渡る水平線」「シート全体を貫く長い斜線」「格子頂点の星状の集中」は、
    格子辺を頂点でだけブリッジすることと、リングを3分割せず1本で描くことから出る。
    v8までは各リングを3ピースに割り、偶数/奇数で角/辺中央に切れ目を置いていたため
    全体が短い破線の集合に見え、参照とは別物だった(v9で修正)。
  - 連結性: リング間の材料は切れ目を通って渦状に繋がり、最外周のリング帯は
    格子頂点のブリッジ経由で外側へ繋がる。**内部は何も脱落しない**(§6.2適用可)。
    ただし margin=0 だと外周クリップで小片が落ちる(標準設定で約8%)ため余白2mm推奨
    (警告実装済み。margin=2 で全プリセット+極端値 ts=8/td=0.6、ts=60/td=5、ts=19/td=1.1 の
    連結成分1を確認済み)。パラメータ ts/td/gap。

### 3.4 パターン追加の手順
1. `GEN` に生成器を追加(mm座標ポリライン配列を返す。最後に `clipRect`)。
2. `PARAM_DEFS` にパラメータ定義、`state.p` にデフォルト、`PATTERNS` に登録。
3. `PRESETS` 3種に**そのパターンの全パラメータキー**を追加(§7の既知欠陥を増やさないこと)。
4. `renderStats` の `charLen`(柔軟性ヒューリスティック)と `renderWarnings` に分岐を追加。
5. サムネイルは同じ生成器で自動描画される(`thumbSVG` のパラメータセットに追記)。
6. **`tools/golden.mjs` の `PATTERNS` 配列にも id を足す**(ここはページ側の `PATTERNS` とは別の
   ハードコード配列。足し忘れると新パターンだけゴールデンの対象外になる。v11で実際に踏んだ)。
   `tools/smoke.mjs` はページから `PATTERNS` を読むので追記不要。
7. §6の検証バッテリーを通し、**ゴールデンを採り直す**(`node tools/golden.mjs capture`)。

## 4. 3D曲げプレビュー(v8で削除済み)★再実装しないこと

v3〜v7に存在した自前Canvasレンダラーによる3D曲げプレビューは、**v8で機能ごと削除した**。

削除理由: **板を曲げた「見た目」を出すだけで、カットしたパターンが実際に曲げに耐えるかは
何も検証していなかった**。円筒/ドーム/サドルへのマッピングは純粋な幾何変換であり、
カットパターンの剛性も破断も一切考慮していない。UIに「※形状イメージです」と
注記しなければ誤解される機能は、その時点で価値より負債が勝っている。

削除で消えた負債:
- JS約220行 + CSS約24行 + HTML約20行(index.html は 74,922 → 64,022 bytes)
- §5 のポインタキャプチャ問題(viewport内の唯一のインタラクティブ要素がbendbarだった)
- §4旧版の性能予算「build3d+render3d ≤ 25ms」という制約
- E2EでのCanvasピクセル解析(§6.3.5のハング問題の温床だった)

**「曲がるかどうか」に答える正しい経路は視覚化ではなく数値**である:
材料プロファイル(§6.5)→ 推定最小曲げ半径 → テストピース面付け(§7.5)で実物を切って実測 →
係数のキャリブレーション(§8 P1-9)。ハリボテの3Dより、実測に裏打ちされた
「最小曲げ半径 ≈ 42mm」の一行のほうが情報量が多い。

本物の曲げシミュレーション(FEA等)を実装するのでない限り、3Dプレビューを復活させないこと。

## 5. 入力系の重要な落とし穴(実際に踏んだバグ)

`viewport` の pointerdown で `setPointerCapture` を呼ぶため、**viewport内に置いたUIへの
実クリック/実ドラッグが全て奪われて死ぬ**。v7までは3D操作バー(bendbar)がこれを踏み、
`if(e.target.closest(".bendbar")) return;` で除外していた。

**v8で3Dを削除した結果、viewport の中身はプレビュー用SVGだけになり、除外リストは不要になった**
(コードにも注意書きのコメントを残してある)。viewport内にインタラクティブ要素を復活させる場合は、
必ず同じ除外処理を入れること。

教訓: `dispatchEvent(new Event('input'))` のような**合成イベントのテストではこのバグは検出できない**。
UIテストは Playwright の `mouse.down/move/up` による実ポインタ操作で行うこと
(`tools/smoke.mjs` はこの方針で書かれている)。

## 6. 検証バッテリー(リリース前に必ず実行)

このプロジェクトでは「上位工程=判断・受け入れ基準の設定、下位工程=実装・自動検証」の分離で開発してきた。
v8で 6.0 と 6.4 を実行可能なコードとして実体化した。残り(6.1/6.2)は未整備。

### 6.0 出力ゴールデン照合 ★最優先・v8で実装

```sh
node tools/golden.mjs check     # 出力が変わっていないか検証（差分あれば exit 1）
node tools/golden.mjs capture   # 出力を意図的に変えたときだけ採り直す
```

実ブラウザ(Chromium)で `index.html` を読み込み、アプリ本体の
`regenerate()` → `makeDXF()` / `makeSVG()` / `buildTestSheet()` を**そのまま呼んで**
出力を `tests/golden/` に保存してある。ユーザーがダウンロードボタンを押すのと同一経路なので、
抽出用の再実装がズレる心配がない。

採取マトリクス(94ケース × DXF/SVG = 188ファイル)—— 詳細は `tests/README.md`:

| 区分 | 件数 |
|---|---|
| 全11パターン × 3プリセット × 縦横(120×70mm) | 66 |
| 余白2mm(外周クリップの端条件) | 11 |
| 外枠なし | 1 |
| メアンダー極端値 cs=5/sw=0.8, cs=40/sw=5, cs=13/sw=1.7 | 3 |
| サイズ極端値 20×20 / 400×300 | 2 |
| テストピース面付け | 11 |

`manifest.json` には sha256 に加えてポリライン数・総カット長・柔軟性スコア・推定R_min・
使用パラメータも記録してある。**ファイル差分が出たとき「何がどう変わったか」の当たりが数値で付く**ため。

リファクタリングのついでに `capture` を回さないこと。安全網が消える。

### 6.1 幾何(未整備・要vitest)
- 全パターン×両方向で: NaNなし、境界外座標なし、ポリライン数・総カット長が妥当。

## 6.5 材料プロファイルと目標半径モード(v6)

`state.mat = {kind, thick}`。素材係数 `MATERIALS[kind].k` は MDF 1.0 / シナベニヤ 0.85 / アクリル 1.7。

- **半径推定**: `R_min ≈ 9 × k × 板厚 / effScore(柔軟性スコア)`。
  `effScore` はスコア1.5を膝として傾き0.4に圧縮する。**この圧縮は必須**で、
  無いとメアンダーのような高カット密度パターンで推定半径が非現実的に小さくなる。
- **逆算ソルバー** (`#btnSolve`): 「かたい端」と「柔らかい端」のパラメータ集合の間を
  線形補間し、**実際に生成して実スコアを測りながら18回二分探索**する。
  閉形式の逆関数を使わないのは、ゲージ表示と逆算結果を必ず一致させるため。
  端でクランプした場合はトーストでその旨を伝える(無言で外れた値を返さない)。
- 補間レンジ: 列系 = pitch/cut/gap、hex = hr/hs/gap、spiral = **sw のみ**
  (csも動かすと渦の見た目が別物になるため、セルサイズはユーザーの指定を尊重する)。
- 板厚は `setThickness()` に一本化(v7までは3Dプレビューと共有していた。v8で材料パネル専用)。

精度は主要域(R=25〜150mm)で誤差10%程度。パターンによっては到達できない領域があり、
特にメアンダーは構造上つねに柔らかく、R≈10〜15mm付近から上に動かせない(仕様)。

**係数はいずれも理論値ではなく手当てである**(§8 P1-9でキャリブレーション予定)。

## 6.6 加工時間の目安(v6)

総カット長 ÷ 加工速度(5/10/20/40 mm/s から選択)。加減速・移動時間は含まない旨をtitle属性に明記。
警告は従来の「カット数 4,000本超」に加え、**総カット長 20m超**でも出るようにした
(メアンダーは本数が少なくても長大になるため)。

## 6.7 外部DXFの解析手順(v7で確立)

参考パターンのDXFから形状を読み取って再現するときの手順。実際に fequalsf の
"parametric kerf" シート(R13/AC1012, SPLINE 3357本+POLYLINE 1544本)で使った:

1. group code をペアで読み、code 0 の値でエンティティを分類(SPLINE/POLYLINE/VERTEX/MTEXT等)。
2. **SPLINEは De Boor で評価**(次数71/制御点10,20/knot 40)。制御点を直線で結ぶと曲線が潰れる。
2.5. **評価済み曲線を端点で連結(join)してから形状を判断する**。CADのスプラインは1本の
   モチーフが多数の短い断片に分かれており、断片単位のbbox統計で判断すると誤同定する
   (v7でこれを踏み、boneを一度誤実装した)。連結後に閉/開・寸法・周長を測る。
3. **PNGに手書きラスタライズして Read で目視**。純Python(zlib+struct)でPNGを書けば
   画像ビューア不要。単位はインチのことが多いが、本ツールは自前mm寸法で再生成するので
   単位は無視してトポロジーと比率だけ取る。
4. MTEXT(code 1/3)にタイトルや出典が入っていることがある(今回 "fequalsf.com" 判明)。

## 7. 既知の制約・仕様上の注意

### 7.1 仕様として意図的なもの
- **閉ループを切るパターンは内側が脱落する**。これはパターン本来の意図であり不具合ではない:
  diamond 約12%(連結成分81) / bone 約24%(レンズ内部) / **hexslit 約46%(六角形の芯。参照フォブ#8も同じ設計)**。
  §6.2の「連結成分1」基準を適用してよいのは **メアンダーと tri(margin≥2)** のみ。
  hex/tri は margin=0 だと外縁クリップで小片が出る(triは余白2mm推奨の警告を実装済み)。
- メアンダーのツリー頂点では4本のカットが1点で合流し、近傍の材料が先細りになる。
  これは本物のパターン固有の性質であり不具合ではない(ただし極小sw時は脆い)。
- メアンダーはカット総長が他パターンの約2倍以上(120×70mm標準で **6,140mm**)。
  総カット長ベースの警告と時間見積りで対応済み(§6.6)。
- 柔軟性ゲージはヒューリスティック(カット密度×√特性長)。目安表示に留めること。
- ブラウザの `hex` パターンで外部クリップにより稀に短い断片が出るのは `polyLen>0.3` で除去済み。

### 7.2 直すべき既知の欠陥(v8時点、未修正)
- **`PRESETS` が `amp / wlen / cw / bulge / dw` を持っていない**。このため
  ウェーブ・アーチ・クロス・ひし形では「しなやか/標準/しっかり」を押しても
  形状固有パラメータが変わらない。→ §8 P2-10
- **`bone` のDXFが異常に大きい**(総カット長は straight の約2倍なのにファイルは約100倍の335KB)。
  モチーフ1個を72分割の固定折れ線で書き出しているため。他も分割数が形状精度と無関係で、
  **arc は `cut` や `bulge` に関わらず常に n=14 固定**(大きな `bulge` でカクつく)、
  **wave は `n = max(8, ceil(cut/1.2))` でカット長にしか比例しない**(`amp` が大きく
  `wlen` が短いと谷が潰れる)。→ §8 P1-6
- **DXF R12 の `$INSUNITS` は規格上無効**(R14以降の変数)。つまり現状のmm実寸は
  「読み手が 1unit = 1mm と解釈してくれる」前提に依存している。→ §8 P1-5
- **`state.p` が全パターン共有のプール**。パターンを切り替えると前のパターンで触った値が
  持ち越される。→ §8 P2-12
- **廃止済みの `web` パラメータが `state.p` / `PARAM_DEFS` に残存**(hash互換のためだけ)。
  → §8 P0-4 のスキーマ版管理で削除

## 7.5 テストピース面付け(v6)

70×30mm の小片を、主要パラメータを現在値の ×0.6〜×1.4 で5段階に振って縦に面付けする
(`buildTestSheet()`)。振るパラメータは 列系(bone含む)=`gap` / hex・hexslit=`hs` / ehex=`es` / tri=`td` / spiral=`sw`。

- 左右に `grip` 8mm の掴みしろを残し、その間にパターンを生成する。
- **識別はテキストではなく切り欠きの本数**(下辺から3mmの切り込み × 1〜5本)。
  SVG契約(§1-2)がテキスト要素を禁じているため。ここをtextに変えないこと。
- 出力は `makeDXF/makeSVG` に polys と寸法を渡して再利用する(本体出力の契約と同一)。

**この機能は §8 P1-9(半径推定のキャリブレーション)の実測データ取得手段でもある。**
