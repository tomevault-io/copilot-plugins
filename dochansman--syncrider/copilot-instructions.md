## Project overview

**SyncRider** — a smarter Fahrradcomputer (bike computer): the phone is the "brain" (GPS, routing, storage), an ESP32-S3-AMOLED board is a dumb display/input device, connected via BLE. Two sub-projects live in this repo:

- `app/` – Android app (Kotlin, Jetpack Compose).
- `firmware/` – ESP32-S3 firmware (ESP-IDF v5.4.4, C, NimBLE + LVGL). BLE GATT peripheral (`RideData`, `RouteData`, `NavStatus`, `ControlEvent`, `DeviceStatus`, `PhoneStatus`, `SetTime`, `MediaStatus`, `DeviceCommand`, `DisplayConfig`, `RideSummary`) and AMOLED display bring-up (5-screen carousel: Datenübersicht, Navigation, Musik-Steuerung, Fahrtsteuerung, Statistik) both working on real hardware (see below).

The spec docs in `docs/` are the source of truth for architecture and protocol decisions and should be consulted (and kept in sync) when working on BLE or navigation code:

- `docs/wiki/` — the reader-facing documentation (hardware, build, app, board, internals, troubleshooting). Superseded the original spec/mockup/scaffolding notes, which now live in the untracked `docs/archiv/`.
- `docs/fahrradcomputer-ble-protokoll.md` — exact BLE GATT service/characteristic byte layout
- `docs/gestaltung.md` — the design system shared by app and board (seven principles, colour tokens,
  type scale, icon language), the **metric-ID catalog** (stable cross-device numbering used by
  `metrics/Metric.kt`, `DisplayConfig` and the planned `BoardInfo.metric_mask` — append-only), the
  app's information architecture, and the data-model/charting decisions. Code comments cite it by
  section number, so renumbering its sections orphans those references. Mockups live in
  `docs/mockups/` (board screens, round-display safe area + slot templates, app screens).
- `docs/features.md` — the feature wishlist with its verdicts, `docs/bugs.md` the record of every
  fault this project actually had and what it cost to find. Both are load-bearing: code comments
  cite them constantly.

Project docs and commit messages are in German; code identifiers and comments are in English.

## Build, lint, test

Run from the repo root (Gradle wrapper). On Windows use `gradlew.bat`; `gradlew` (bash) also works in this environment.

```
./gradlew.bat assembleDebug          # build the app
./gradlew.bat test                   # run all JVM unit tests (app/src/test)
./gradlew.bat test --tests "com.hannes.bikecomputer.navigation.RouteSimplifierTest"   # single test class
./gradlew.bat test --tests "*.RouteSimplifierTest.reduces a nearly straight line*"    # single test method
```

There is no configured lint/ktlint/detekt task beyond the default Android Gradle Plugin `lint` task (`./gradlew.bat lint`). Toolchain: JDK 21 (see `gradle/gradle-daemon-jvm.properties`), Kotlin 2.3.21, AGP 9.3.0, compileSdk/targetSdk 36, minSdk 29.

Tests are plain JUnit4 with `unitTests.isReturnDefaultValues = true` (otherwise every `android.util.Log` call in an otherwise pure class throws "not mocked" — removing the logging instead would cost the `RideRecorder` lines that are the first source in any history investigation), no instrumented/androidTest suite exists — everything testable (BLE payload encoding, GPX parsing, route simplification) is written as pure JVM logic to keep it unit-testable without an emulator.

### Firmware (ESP-IDF)

Requires **ESP-IDF v5.4.x** on the machine (v5.4+ is mandatory: both Waveshare's official display BSP and the `esp_lcd_sh8601` panel driver require it). Source its environment script first (`export.ps1` on Windows, `export.sh` elsewhere) so `idf.py` is on PATH — Git Bash/MSYS is **not** supported by ESP-IDF's tooling, use PowerShell/cmd (or WSL) instead.

```
idf.py set-target esp32s3      # once per fresh build dir
idf.py build
idf.py -p <PORT> flash monitor # <PORT> e.g. COM3 on Windows; board uses USB-Serial/JTAG, no external adapter needed
```

Dependencies (`waveshare/esp32_s3_touch_amoled_1_75` BSP, `lvgl/lvgl`) are declared in `firmware/main/idf_component.yml` and auto-fetched into `firmware/managed_components/` by the ESP-IDF Component Manager on first configure — needs network access; never hand-edit files under `managed_components/`, they get overwritten.

## Architecture

The app is intentionally split so that BLE wire format, GPS/ride math, and route processing are pure, testable Kotlin with no Android UI dependency, while `ui/` wires them together with Compose.

- `ble/`
  - `BikeComputerBleUuids` + `BleProtocol.kt` — GATT service/characteristic UUIDs and payload encoding (`RideState.toRideDataPayload()`, `navStatusPayload()`, `phoneStatusPayload()`) and decoding (`decodeControlEvent()`, `decodeDeviceStatus()`). Byte layout **must** match `docs/fahrradcomputer-ble-protokoll.md` exactly (little-endian, fixed field offsets) — update the doc first when changing the wire format, then the code. `RideData` is at **v3** (33 bytes): the former `altitude_dm` field at bytes 8–9 carries **cumulative ascent in whole metres** since v2 (the absolute altitude sat unchanged for a whole evening loop; the meaning moved rather than a second field being appended), `max_speed_cms`/`elapsed_time_s` were appended in v2 for the configurable board slots, and v3 appends `altitude_m` (int16, the calibrated altitude also used for GPX export; sentinel `INT16_MIN` = unknown, because 0 m is a legitimate altitude) plus `descent_m` (uint16) — the absolute altitude came *back* as an appended field once the configurable slots made it selectable again (`docs/features.md`). The first 23 bytes stay field-identical with v1 and the firmware checks for "at least v1", so neither side breaks on a version mismatch. `NavStatus`'s `turn_direction`/`distance_to_turn_m` come from `navigation/TurnDetector.kt` (route geometry), not from a routing API — `TurnDirection.STRAIGHT` together with `distanceToTurnMeters = 0` is the agreed "nothing to show" and makes the board hide its turn arrow. `PhoneStatus`'s `routing_status` is still always `IDLE` (no routing API integrated). `setTimePayload()` builds `SetTime` (App→Board, Write with response) — sends `System.currentTimeMillis()` already shifted by the phone's current timezone offset (`TimeZone.getOffset()`), not the raw UTC epoch, since the board's RTC has no timezone concept and just displays whatever wall-clock value it's given.
  - `RoutePayload.kt` — builds the chunked `RouteData` packet sequence (header → point chunks → complete). First point of the whole route is absolute (`float32` lat/lon); every subsequent point is a `int16` delta (1/100000°) from the previous point, carried across chunk boundaries. See the doc for why (MTU limits, rounding-error avoidance).
  - `BleScanner.kt` — one-shot BLE scan as a suspend function (`scanForBikeComputer`), filtered by service UUID; a `preferredAddress` argument turns it into a strict filter (no silent fallback to "any board" — otherwise a failed scan would quietly connect to someone else's board). `scanForBikeComputers` is the continuous variant feeding the device picker, emitting the full RSSI-sorted list on every hit.
  - `BoardDisplayConfig.kt` + `DisplayConfigPreferences.kt` — the `DisplayConfig` characteristic, at **v2** (13 bytes; the firmware still accepts the 8-byte v1): six freely assignable metric slots on board Screen 1, font scale, two toggles, plus the energy fields `brightnessPercent` (10–100, clamped app- and firmware-side — a 0 % display could not be touch-recovered), `screenOffSeconds` and `deepSleepSeconds` (both 0 = never; both apply **only without** a BLE connection). `displayConfigPayload()` silently drops metrics whose `boardSupported` is false — the board has no `RideData` field for GPS accuracy, and a slot showing a permanent dash is worse than an empty one (altitude and descent *are* selectable since RideData v3; board/phone battery need no field at all — IDs 21/22 from `docs/gestaltung.md`, the board knows its own battery and gets the phone's via `PhoneStatus`). **The phone is the single source of truth**: the board does not persist the config, it is rewritten after every connect (a second persistent copy is a second place where something different can stand — exactly the construction that produced a threefold-wrong odometer, see `DeviceCommand.SET_ODOMETER`). The board's Screen 6 brightness buttons fit this rule via a round trip: the board applies the step locally at once (sun on the handlebars must not wait for radio), sends `ControlEvent` 9/10, and the app updates+re-pushes the stored config — `BRIGHTNESS_STEP_PERCENT` must match `display.c`'s define or local and stored values drift apart per press.
  - `RideSummaryPayload.kt` — the `RideSummary` characteristic: last finished ride plus lifetime and this-week aggregates for the board's statistics screen. `justFinished` is what makes the board bring that screen to the front; the routine push after a connect deliberately does not, or it would take the data screen away mid-ride. That routine push has no ride id (it happens because of a connect, not because of a ride), so `pushRideSummary()` resolves the newest finished ride itself via `RideDao.lastFinishedRide()` — ordered by `endedAt`, not `startedAt`, since a backfilled ride lies in the past but was created just now. Without that lookup the board showed "Noch keine Fahrt" next to a lifetime total of 35 rides, and only filled in if a ride happened to be finished in the same session. A **passed** id that no longer resolves deliberately does *not* fall back: that means the ride was just discarded as too short, and `justFinished` would then push an older ride to the front of a board nobody just rode.
  - `BoardCompanion.kt` — starts the app by itself once the board comes into range, via `CompanionDeviceManager` (API 31+): the board is associated once through a system dialog (`requestAssociation()`, filtered by the same service UUID the normal scan uses), after which Android launches `BoardCompanionService` and thereby `RideForegroundService` — **even from a process that isn't running**, i.e. after a phone reboot or after "App beenden". A background scan of our own is not an alternative: an app that isn't running cannot scan, and Android kills exactly that kind of permanent scanner. What starts is deliberately the service, not the UI — Android has blocked background activity starts since version 10, and during a ride what counts is that GPS and the BLE link are up. **The association dialog only sees *advertising* devices, and a connected board does not advertise** — so `SettingsScreen` pauses the reconnect (`setAutoConnectPaused(true)`, the same lever `BoardPickerScreen` pulls) and calls `bleManager.disconnect()` before opening it, waiting `COMPANION_ADVERTISE_DELAY_MILLIS` for the board to come back on air. Without that the picker stays empty precisely when everything is working (confirmed on hardware); the auto-connect is released again from both the launcher result and `onFailure`. The association lives in the system service and is read back from it (`associatedAddresses()`) rather than mirrored into `SharedPreferences`: the user can delete it in the system settings without this app noticing, so a second copy would be a second truth. Needs three install-time permissions (no dialog), and the easy one to miss is **`REQUEST_OBSERVE_COMPANION_DEVICE_PRESENCE`**: without it `startObservingDevicePresence()` is rejected by the system service (`legacyStartObservingDevicePresence_enforcePermission`), the association stands but is never watched, and nothing in the app looks wrong — that is exactly how the first hardware attempt failed. `startObserving()` therefore returns a Boolean and `SettingsScreen` shows a plain "association stands, but Android doesn't report the board" row instead of a green "aktiv"; `dumpsys companiondevice`'s `mNotifyOnDeviceNearby` is the ground truth. Also `REQUEST_COMPANION_RUN_IN_BACKGROUND` plus `REQUEST_COMPANION_START_FOREGROUND_SERVICES_FROM_BACKGROUND` — without the latter the woken process may not start a foreground service at all. `startObserving()` is re-armed on every `RideForegroundService.onCreate()` because it is idempotent and an autostart that silently stops working would be worse than none. **Not yet exercised on the device.**
  - `BoardPreferences.kt` — remembers which board to connect to (`SharedPreferences`, exposed as a `StateFlow`). Set automatically on the first-ever successful connect so the single-board case needs no setup, and changeable in `BoardPickerScreen`. Without it `attemptConnect()` took the first scan hit, which is a coin flip within radio range of a second SyncRider.
  - `BikeComputerBleManager` — Nordic `BleManager` subclass; phone is GATT **Central**, board is GATT **Peripheral/Server** (this direction matters — e.g. `RideData`/`RouteData`/`NavStatus`/`PhoneStatus` are phone→board Writes, never Notifies from the phone; `ControlEvent`/`DeviceStatus` are the board→phone direction, both `Notify`). Exposes connection state as a `StateFlow<BleConnectionState>`, board-originated `ControlEvent`s as a `SharedFlow<ControlEvent>` (`controlEvents`), and the board's own status as a `StateFlow<DeviceStatus?>` (`deviceStatus`, null until the first Read/Notify arrives) — subscribed via `setNotificationCallback(...).with { }` + `enableNotifications(...).enqueue()` in `initialize()`; `DeviceStatus` additionally does an explicit `readCharacteristic(...).with{}.enqueue()` on connect so the value doesn't have to wait for the board's first periodic Notify. `isRequiredServiceSupported()` calls `refreshDeviceCache()` when the expected characteristics aren't found — Android caches the GATT service table per device address, so after reflashing firmware with a changed characteristic list, the next connection otherwise keeps returning the stale (pre-flash) list and fails this check every time; `refreshDeviceCache()` forces real re-discovery and the check re-runs automatically.
- `ride/BarometricAltimeter.kt` — `Sensor.TYPE_PRESSURE` wrapped as a **median-filtered** altitude reading (`PressureMedianWindow`, 15 s trailing window). Its **absolute** value is unusable (computed against the standard atmosphere, so weather puts it up to three digits of metres off); only the *change* matters for climb metres. **Do not assume the barometer is the cleaner sensor** — measured against simultaneously recorded Komoot tracks (`docs/bugs.md`), the raw sensor on a moving bike jumped a median of 1.20 m per second versus 0.10 m for GPS altitude, i.e. twelve times worse, because it sees airflow and pocket pressure. Unfiltered plus the old 1.5 m hysteresis that turned a 3 m commute into 529 m. The filter is a **median, not a mean**, and that is the whole point: a 20 s moving average also fixes the commute but destroys real climbs (Komoot's own elevation model drops 177 m → 77 m), while the median keeps 162 of those 177 m. Started/stopped alongside the location updates in `RideTracker`'s `callbackFlow`, so the sensor only runs when someone is collecting ride data.
- `ride/RideTracker.kt` — wraps `FusedLocationProviderClient` as a `RideState` `SharedFlow` (`rideUpdates`, via `shareIn`/`WhileSubscribed`, replay=1), computing speed/distance/avg-speed/altitude/ride-time/lat-lon/heading/GPS-accuracy from raw location updates. Shared rather than a cold flow so every collector (currently `MainActivity` + `RideScreen`) rides the same GPS callback instead of each registering its own and double-mutating the tracker's instance state (distance, etc.). No BLE or UI knowledge. Passes `Looper.getMainLooper()` explicitly to `requestLocationUpdates()` (not `null`) — with `null`, the call falls back to the calling thread's Looper, which crashes with `NullPointerException: invalid null looper` once the producer runs inside `shareIn`'s `Dispatchers.Default`-backed scope (a thread pool has no Looper). **GPS noise handling** (docs/bugs.md) is the most-revised part of this file and rests on three independent vetoes, all of which must pass before a fix counts as movement. (1) The implied speed — position delta over the fix interval, *not* `location.speed` — must reach `MOVING_THRESHOLD_KMH` (2 km/h) and stay under `MAX_PLAUSIBLE_SPEED_KMH`. (2) The **net** displacement over a `STATIONARY_WINDOW_MILLIS` window must exceed `STATIONARY_RADIUS_METERS`, which exploits the fact that noise oscillates around a point while real movement travels. (3) `hasConfidentSpeed()` requires the chip's Doppler speed to reach `SPEED_CONFIDENCE_FACTOR` × its own reported `speedAccuracyMetersPerSecond`. Veto 3 exists because 1 and 2 were calibrated on an outdoor ride and do not hold at indoor reception: measured on a resting phone (hAcc median 22.8 m), 90 % of fixes cleared the 2 km/h threshold and the 8 m window veto only fired 71 % of the time, so a ride auto-started about once a minute. The chip's own uncertainty separates the two cases cleanly — at rest the reported speed never exceeded 1.37× its uncertainty, while riding puts that ratio around 18. **Do not** replace any of this with a per-fix "delta > `location.accuracy`" test: that compares a one-second displacement against a *position* uncertainty, so the effective speed threshold moves with reception (18 km/h at 5 m accuracy, 28.8 km/h at 8 m) and it once cost two thirds of the real distance. Speed against speed-uncertainty has no such scale mismatch. Separately, the *displayed* speed is EMA-smoothed (`SPEED_SMOOTHING_ALPHA`) from the chip value and gated by `displayRiding`, a hysteresis over the same movement verdict — display and distance want opposite things (steady at rest vs. catching every real metre), so they are deliberately separate. The movement verdict drives both distance accumulation and automatic recording start/pause: `recording` (`RideState.recording`, feeds `RideData`'s flag bit 0) auto-starts after `AUTO_START_CONSECUTIVE_MOVING_UPDATES` consecutive moving updates and auto-pauses after `autoPauseSeconds` consecutive stationary ones (a user setting since `docs/features.md`'s "Zeit bis 'Fahrt pausiert'": stored in `ride/RecordingPreferences.kt`, surfaced in SettingsScreen's Aufzeichnung section, pushed into the tracker by a service collector; fixes arrive at 1 Hz so one update ≈ one second), alongside manual `startRecording()`/`stopRecording()` (`RideScreen`'s button). Only `startRecording()` resets `distanceMeters`/ride time to zero — auto-pause/resume and manual `stopRecording()` freeze and later continue the same ride instead, so a stoplight pause can't silently wipe out accumulated distance. Active ride time is tracked as accumulated-segments-plus-current-segment (not wall-clock since first start) specifically so it freezes during any pause instead of continuing to tick. `elapsedTimeSeconds` (total time *including* pauses) uses the same segment model with one deliberate difference: an auto-pause at a traffic light does **not** freeze its segment, only a manual `stopRecording()` does — and the auto-start path only opens a new elapsed segment when none is running, otherwise resuming after an auto-pause would double-count. `maxSpeedKmh` is the fastest 5 s window over the accumulated distance (`MaxSpeedWindow`, the same rule the importer uses so live and backfilled rides stay comparable), not the instantaneous value — a single GPS glitch in a maximum would otherwise stand for the rest of the ride. That window is only as clean as the distance feeding it, which is why **`MIN_FIX_INTERVAL_MILLIS` matters most here**: fixes arriving closer together than that carry no new solution, only its scatter, and are skipped whole — including the `lastLocation` update. Letting a rejected outlier become the next reference point was worth up to 13 m of phantom distance per event; over a whole ride that vanishes in the total but lands squarely in the maximum, which is exactly what an extremum does. Measured on one commute: 1.2 % of fixes came in under 0.5 s apart with jumps up to 14 m, and the stored peak read 51.7 km/h where the recorded track itself supports only 37.5 (average 24.3). Both values are persisted alongside distance/ride-time. Also persists distance/ride-time/`recording` to `SharedPreferences` (`PREFS_NAME`) so a killed process resumes instead of losing an in-progress ride (`restoreState()` in `init`; a restored `recording=true` starts a fresh segment rather than counting the downtime). **Persist calls are throttled to `PERSIST_INTERVAL_MILLIS` (5s), not called on every location update** — doing it at the GPS callback's full ~1 Hz rate starved the `Dispatchers.Default` pool shared with `RideForegroundService`'s write-loop coroutine badly enough to silently stall all BLE writes after ~15s (no exception, the write coroutine just never resumed); see `docs/bugs.md`. `startRecording()`/`stopRecording()` still persist immediately (unthrottled) since those are one-off calls, not per-update. `resumeRecording()` continues a paused ride without resetting anything — needed only for a deliberate "resume" press (board Screen 4); simply riding on triggers the automatic start anyway. **Elevation** (`RideState.ascentMeters`/`descentMeters`) is accumulated here rather than in `RideRecorder`, because the board shows it live and a second counter elsewhere would produce a second, slightly different number: raw barometric altitude (falling back to GPS altitude, with the coarser hysteresis) feeds an `ElevationAccumulator`, and only while `recording` — otherwise a night of weather drift on the desk would be the next morning's ascent. The *displayed* altitude is that same barometric value plus an offset tracked very slowly against GPS altitude (`BARO_OFFSET_ALPHA`); the climb metres deliberately use the **uncalibrated** value, since the offset's slow drift would otherwise be a creeping phantom ascent.
- `data/` — the ride history (Room 2.8.4 + KSP 2.3.10; KSP works against AGP 9's built-in Kotlin support, no separate Kotlin plugin is applied in this project).
  - `Entities.kt` — `RideEntity` keeps its aggregates **redundantly** so the statistics overview never has to aggregate over tens of thousands of track points just to show a weekly total; `endedAt == null` marks the single in-progress ride. `TrackPointEntity` stores the *cumulative* ride distance per point, which is what lets charts and splits use the **distance axis** — on a bike ride that is far more informative than the time axis, where one traffic-light stop squashes half the graph.
  - `AppDatabase.kt` — deliberately **no** `fallbackToDestructiveMigration()`: the ride history is the one dataset in this project that cannot be reconstructed, so schema changes need real migrations. Currently at **version 2**; `MIGRATION_1_2` adds `saved_routes` and touches nothing else. When hand-writing such a migration, the column types must match exactly what Room would generate for the entity (`Double` → `REAL NOT NULL`, `Boolean` → `INTEGER NOT NULL`, nullable `Long` → `INTEGER`), or the schema check fails on open.
  - `SavedRoute.kt` / `SavedRouteRepository.kt` — the tour library (planned GPX routes, as opposed to ridden tracks in `RideEntity`). Points live as a `lat,lon;…` text column rather than a second table: at ≤500 points per route that is ~12 kB per row, too little to justify a foreign key, index and cascade — the ride's track points are tens of thousands, which is exactly why *those* have their own table. `encodeRoutePoints()` formats with `Locale.ROOT`; a German default locale would emit decimal commas and the string would not decode again (same trap as `GpxExporter`).
  - `RideRepository.kt` — the important part is the dispatcher. Everything runs on `Dispatchers.IO.limitedParallelism(1)`, never on `Dispatchers.Default`: `docs/bugs.md` records a case where 1 Hz `SharedPreferences.apply()` starved that shared pool until the BLE write coroutine silently stopped resuming. DB writes are the same pattern, only more expensive.
  - `RideImport.kt` — backfilling the history (`docs/bugs.md`). `RideImporter` turns a recorded GPX track into a finished `RideEntity`, `ManualRideImporter` does the same from a bare distance for days with no track at all (the checklist page `docs/fahrten-nachtragen.html` produces that list as JSON). Both compute their aggregates by the **same rules as a live recording** — moving time only above 2 km/h, peak as the fastest 5 s window via `MaxSpeedWindow`, position jumps over `MAX_PLAUSIBLE_SPEED_KMH` contributing neither distance nor time — otherwise backfilled and real rides would not be comparable in the statistics. The manual path assumes only a duration (`MANUAL_RIDE_SPEED_KMH`, the measured median over 16 of this user's own commutes) and deliberately leaves peak speed and elevation at 0 rather than inventing values that would sit in the records forever. `TrackElevation` is the single place where elevation samples become ascent/descent, shared by the importer and `RideRepository.recalculateElevation()` so a ride's climb cannot depend on which path put it into the database; `recalculateElevation()` exists because rides recorded before the barometer fix carry three-digit phantom ascents while their **track points are fine** — only the derived sum was wrong, so it can be rebuilt. Duplicate protection lives in `RideRepository.importRide()`: an overlapping time range is rejected, because the same ride commonly exists in two files (Komoot *and* MiBand recorded simultaneously) and a second row would silently double the very number the backfill is meant to fix. `RideAggregates.fromTrackPoints()` is the repair for the inherited-odometer bug above, and it deliberately does **not** reuse `RideImporter`'s geometry: it rebuilds distance/moving time/peak from the stored **cumulative distance per track point**, which has already passed the tracker's three movement vetoes, so the inherited offset cancels in the difference while a geometric recompute would hand back the GPS noise of every traffic light as distance. Every ride deletion in this class logs id, date and kilometres via `logDeletion()` on `warn` — added after five short rides vanished on 2026-08-31 with no way to tell which call removed them (`docs/bugs.md`); the ride table is the one dataset here that cannot be rebuilt, so it must never shrink silently. `RideRepository.recalculateRides()` touches only rides that provably carry the fault — first track point above `INHERITED_DISTANCE_THRESHOLD_METERS` (100 m, the same floor as a ride's minimum distance) — since a healthy ride does not start at exactly 0 m either (auto-start books the three triggering fixes, ~40 m at speed) and below that the error is smaller than the risk of replacing correct numbers. Rides that fall under 100 m afterwards are the false auto-starts; they are listed and only deleted on a second, explicit press.
  - `RideStatistics.kt` / `RideSplits.kt` / `GpxExporter.kt` — pure functions on plain data classes, no Android or DB dependency, so the fiddly parts (week boundaries, DST, weighted averages, GPX escaping/locale) are covered by JVM tests. Two `GpxExporter` traps have tests: timestamps must be **UTC** (unlike `SetTime`, which deliberately carries local wall-clock time), and coordinates must be formatted with `Locale.ROOT` or a German default locale emits commas no GPX reader accepts.
- `metrics/Metric.kt` — the metric catalog from `docs/gestaltung.md`. Each entry has a **stable,
  cross-device `id`**: the same number identifies the metric in the planned `DisplayConfig` (which
  metric sits in which board slot) and in `BoardInfo.metric_mask` (which metrics the firmware knows).
  IDs are append-only — renumbering one would silently show the wrong metric on a board running older
  firmware. `format(MetricSnapshot)` is pure (the snapshot carries `nowMillis` explicitly rather than
  reading the clock, so clock/arrival-time formatting is deterministic in tests).
- `navigation/`
  - `GpxImporter` — parses `trkpt` (falls back to `rtept`) from a GPX `InputStream` into `GpxRoute`/`GpxPoint`, plus the first non-empty `<name>` in the document. Callers prefer that name over the SAF display name: export services strip the *filename* to ASCII, so "Köln–Brühl" arrives as `K_ln_Br_hl`, while the XML carries it intact.
  - `RouteSummarizer` — length/ascent/descent of a route for the UI. Ascent/descent use a 3 m
    hysteresis: summing raw positive elevation deltas accumulates noise in one direction only, so a
    flat route otherwise reports hundreds of phantom metres. `RouteSummary.hasElevation` distinguishes
    "no `<ele>` tags in the GPX" from "actually flat" — the UI must not render the former as `0 m`.
  - `RouteSimplifier` — Douglas-Peucker simplification (iteratively increasing epsilon) down to a target point count (default 500) before a route is sent over BLE, since `RoutePayload` chunking and the board's rendering budget assume a simplified route.
  - `RouteProgress.kt` (`RouteProgressCalculator`) — projects the current position onto the loaded (simplified) route (nearest point on a segment) to derive remaining distance to the route's end and lateral distance to the route. Pure geometry, no routing API — feeds `RideData`'s `dist_to_dest_m`/`time_to_dest_s` and `NavStatus`'s `off_route` flag. Also returns `totalDistanceMeters` (it falls out of the remaining-distance computation anyway) so `fractionComplete` doesn't need a second pass over the route at 1 Hz, and `distanceAlongRouteMeters` (total minus remaining), which is the common yardstick shared with `TurnDetector`'s maneuver positions.
  - `TurnDetector.kt` — derives turn-by-turn maneuvers (`TurnDirection`, matching `NavStatus.turn_direction`'s numbering) from the route polyline alone, since no routing API with maneuver steps is integrated. The bearing change at a vertex is measured over a **±`BEARING_WINDOW_METERS` (30 m) window**, not between adjacent points: that is what separates a junction from a bend, since a 90° curve spread over 300 m yields only a few degrees per window and falls below `MIN_TURN_ANGLE_DEGREES` (35°). Corners split across several GPX points collapse to one maneuver via non-maximum suppression within `SUPPRESSION_RADIUS_METERS`. Runs on the **simplified** route (the one the board also has), so maneuver distances share a yardstick with `RouteProgressCalculator`. Deliberately provides no street names and no roundabout exits — those need real map data. Every route ends with a synthetic `DESTINATION` maneuver.
  - `KomootInstruction.kt` (`KomootNotificationParser`) + `KomootNavigationRelay.kt` — turn hints read out of Komoot's running navigation, for users who navigate with Komoot anyway. `TurnDetector` cannot in principle tell a junction from a bend and knows nothing about rerouting; Komoot knows both, and the answer is already on the device. Format measured on real hardware: `android.title` = `"20 m • Geradeaus · Roonstraße, B 55"` (bullet U+2022 between distance and maneuver, middle dot U+00B7 before the street), with the distance repeated unsplit in `android.shortCriticalText` (Android 16's "Live Update" field), which is why the parser prefers that field — one text cut fewer that can break. Street names are deliberately **not** forwarded: LVGL's Montserrat is ASCII-only, so "Roonstraße" would render as placeholders. **This interface is undocumented and German-language, so it must never be load-bearing:** an unrecognised maneuver word makes the parser return `null` and `RideForegroundService` falls back to `TurnDetector`, so a Komoot update costs the improvement and not the function. Unrecognised words are logged and surfaced in `SettingsScreen` so the mapping table can be extended without standing next to the machine. The relay is a singleton because `NotificationListenerService` is instantiated by Android, not by us; it ages instructions out after 2 minutes so a Komoot process death can't leave a stale arrow on the board for the rest of the ride.
  - `HeadingFilter.kt` — smooths `Location.getBearing()` before it goes out as `NavStatus.heading_deg` and rotates the board's map. Below `minSpeedKmh` the last valid heading is held: at a standstill the GPS chip derives the bearing from noise, and the heading-up map would spin at every traffic light. The EMA runs over the **shortest angular difference**, not the absolute value — averaging 350° and 10° the naive way gives 180°, i.e. the opposite direction.
- `media/` (Phase 10 — music remote control, board has no audio output itself, only sends button presses):

Registered in the manifest with `BIND_NOTIFICATION_LISTENER_SERVICE`, enabled by the user via `Settings.ACTION_NOTIFICATION_LISTENER_SETTINGS` (launched from `SettingsScreen.kt`). **(2)** It reads Komoot's live-navigation notification and forwards the maneuver to `navigation/KomootNavigationRelay` (see `navigation/KomootInstruction.kt` for the wire format and why this is only ever a layer on top of `TurnDetector`, never load-bearing). - `strava/` — Strava connection (`docs/features.md`). `StravaAccount.kt` holds the tokens and reads client id/secret from `BuildConfig`, filled at build time from `strava.properties` in the repo root (gitignored; a copy-me template sits next to it). Without them `isConfigured` stays false and the settings row says so instead of offering a button that would only end in an error page from Strava. `StravaClient.kt` does the OAuth token exchange/refresh and the multipart GPX upload over plain `HttpURLConnection` — three calls do not justify an HTTP library — always on `Dispatchers.IO`, never on `Dispatchers.Default` (that pool is shared with the GPS/BLE path, see `RideRepository`). `StravaAuthActivity` catches the `syncrider://strava/callback` redirect; it is its own invisible activity because the redirect can arrive while the app is not running, and making `MainActivity` `singleTask` for this one case would have changed its whole lifecycle and service binding. **Not yet exercised against the real API** — needs the user's Strava app credentials.
- `ride/RideRecorder.kt` — writes the running ride into the database. Ride boundaries are derived from `RideState` rather than giving `RideTracker` its own event API: a ride **starts** when `recording` goes true with none open, **ends** when `distanceMeters` drops (only `startRecording()` can cause that — auto-pause/resume freeze and continue, never reset; the firmware's `odometer.c` uses the same detection) or after 15 minutes of continuous pause. An auto-pause at a traffic light therefore does *not* end the ride — the same confusion that would make the board-side summary unusable. **Two of those three endings reset the tracker's counters and the third must too** (`onRideExpired`, wired to `rideTracker.resetAll()` by the service): "Fahrt beenden" and starting a new ride reset by themselves, but the 15-minute expiry — the one ending nobody triggers — did not, so the next ride began at the previous ride's odometer reading and was credited its distance a second time on finish. Over a chain of such rides that compounds, and a false auto-start indoors inherits enough kilometres to slip past `deleteIfTooShort`'s 100 m floor and stand in the history as a full copy of the last ride (`docs/bugs.md`, `RideRecorderTest`). The callback fires **only** on the expiry path: on the other two the tracker has just reset itself, and resetting again would wipe the ride that was just started. The expiry itself is **route-aware**: while a loaded route's destination is still ahead (`routeUnfinished()` in the service, measured against `ROUTE_DESTINATION_REACHED_METERS`), the pause tolerance grows from 15 min to `AUTO_FINISH_WITH_ROUTE_MILLIS` (3 h) — a quarter hour fits a commute, not a tour, and it split three tour days into 3–4 rides each (`docs/bugs.md`). Deliberately not "never": a multi-day tour keeps the route loaded overnight, and a ride that never ends grows unnoticed. `data/RideMerge.kt` repairs the rides that were already split — it groups **by route name**, never by time alone, since two commutes without a route could not be told apart, and `RideRepository.mergeRides()` rebuilds one continuous track from the segments (each segment's cumulative distance restarts at its own zero, so they are chained by delta, not concatenated). That call is the one place wrapped in `inTransaction`: it deletes the source rides before their points hang on the target. Track points are buffered in memory and flushed in batches every 30 s (a process kill loses at most that window, the same trade-off as `ODOMETER_PERSIST_EVERY_N_WRITES`); a ride left open by a process kill is *adopted* rather than duplicated, replaying its stored points through the `ElevationAccumulator` so the climb total doesn't reset to zero mid-ride. `ride/ElevationAccumulator.kt` holds the shared hysteresis (raw elevation noise summed one-directionally invents hundreds of phantom metres) used by both the recorder and `RouteSummarizer`.
- `ride/RideForegroundService.kt` — a `Service` (not `MainActivity`) now owns the single `RideTracker` and `BikeComputerBleManager` instances plus the loaded-route `MutableStateFlow<List<GpxPoint>?>`, and runs the scan/connect + write loop (previously in `MainActivity`) in its own `CoroutineScope`. Exists so GPS tracking and the BLE connection survive the screen locking or the app going to background (confirmed on hardware: RideData/NavStatus keep updating on the board with the phone screen off) — without this, Android's background execution limits killed GPS/BLE, a risk called out in `docs/wiki/10-innen.md`. Started via `ContextCompat.startForegroundService()` + `startForeground(...)` with a low-priority persistent notification. **The foreground-service type is negotiated, not fixed**: `location` is a while-in-use permission, so a `location`-typed FGS may not start while the app is in the background — which is exactly the state `BoardCompanion` wakes it in, and it threw `SecurityException` from the service's own `onCreate`, i.e. a crash loop precisely when the autostart was supposed to work (seen on hardware, targetSdk 36). `startForegroundNotification()` therefore tries `location|connectedDevice` and falls back to `connectedDevice` alone (that type has no such restriction, and `BLUETOOTH_CONNECT` covers it), with `promoteToLocationType()` retried from `onBind()`/`onStartCommand()` — both of which only happen once the app is in front. So the BLE link always comes up; GPS recording from a background start additionally needs `ACCESS_BACKGROUND_LOCATION`, which `SettingsScreen` asks for with a row that appears only while an association exists and the permission is missing (`ic_notification.xml`, `strings.xml`); requires the `FOREGROUND_SERVICE`/`FOREGROUND_SERVICE_LOCATION`/`POST_NOTIFICATIONS` manifest permissions (the last one also needs a runtime request on API 33+, added to `MainActivity.requiredPermissions`). The write loop itself (`RideData`/`NavStatus`/`PhoneStatus`, throttling, `gpsFixQualityFrom()`) is unchanged from before, just relocated. Connection is kept alive by `connectLoop()`, a periodic (`RECONNECT_CHECK_INTERVAL_MILLIS`, 5s) watchdog that scans+connects (`useAutoConnect(false)`, active/fast since a scan just confirmed the device is in range) whenever `bleManager.connectionState` is `Disconnected` — replaces a one-shot `connect().enqueue()` that never retried if the initial scan missed the board (e.g. board still booting) or the link later dropped, leaving the app stuck on "getrennt" indefinitely; see `docs/bugs.md`. `pushLoadedRoute()` re-sends the loaded route (`RouteData`) after **every** connect, not just when a tour is picked in `RoutesScreen` — the board keeps the route in RAM only, so a board reboot or a dropped link loses it, and since the Navigation screen now disappears entirely without a route on the board, it would otherwise stay gone until the next tap in the tour screen. The running `route_id` lives in the service for the same reason the odometer total does: two counters would be two places the same number can differ, so `RoutesScreen` calls this method through an `onSendRoute` lambda instead of reaching for `bleManager.sendRoute()` itself. `attemptConnect()` also fires `bleManager.writeSetTime(System.currentTimeMillis())` once right after every successful connect (not just the first ever) — cheap, and keeps the board's displayed clock correct across a timezone change/DST without needing separate logic to detect that. `controlEventLoop()` (Phase 10, music remote control) collects `bleManager.controlEvents` for the lifetime of the service (independent of `RideScreen`'s own collector, which is UI-only) and maps `SHORT_PRESS`→`MediaRemoteController.togglePlayPause()`, `LONG_PRESS`/`TRACK_NEXT`→`skipToNext()`, `TRACK_PREVIOUS`→`skipToPrevious()`; `SWIPE_LEFT`/`SWIPE_RIGHT` are ignored here since those only drive the board's own screen switch. `POWER_OFF` (11, the board announcing its own shutdown) runs `shutDownWithBoard()`: `finishRide()` → `rideRecorder.flush()` → `quitRequests` → `stopSelf()`, strictly in that order, or the process dies with an `endedAt = null` ride that the next start would adopt as still running. Two exits because the UI may or may not be alive — `MainActivity` collects `quitRequests` and does the full `quitApp()` (unbind, stopService, `finishAndRemoveTask`), and `stopSelf()` covers the case where no Activity is bound; calling both is harmless. The flow deliberately has no `replay`, otherwise an Activity started later would immediately close itself. `mediaStatusLoop()` (Phase 10.1, music screen) collects `mediaRemoteController.playbackStatus` for the service's lifetime and writes every change to the board via `bleManager.writeMediaStatus()` (empty/`false` when no session is active); `attemptConnect()` additionally pushes the current `playbackStatus.value` once right after every successful connect (same pattern as `writeSetTime()`) so a freshly (re)connected board shows the current track immediately instead of waiting for the next metadata change.

`firmware/main/`
  - `ble_gatt_server.c`/`.h` — defines the Bike Computer GATT service as a NimBLE peripheral. `RideData` (`Write Without Response`), `RouteData` (`Write`, header/chunk/complete dispatch, delta-decodes points and tracks per-route receive state in file-static variables), `NavStatus` (`Write Without Response`, decodes position/heading/turn/off-route), `ControlEvent` (`Notify`, 2 bytes: source/event_type), `DeviceStatus` (`Read`+`Notify`, 2 bytes: board_battery_pct/ble_rssi), and `PhoneStatus` (`Write Without Response`, 3 bytes: phone_battery_pct/gps_fix_quality/routing_status, decoded and only logged — no display slot for it in the current screen mockup) are implemented. `ble_gatt_server_notify_control_event(source, event_type)` sends a `ControlEvent` Notify to the currently connected central via `ble_gatts_notify_custom()` (no-op if nothing's connected) — its value attribute handle comes from NimBLE populating `.val_handle` in the `ble_gatt_chr_def` at registration (simpler than parsing it out of `gatt_svr_register_cb`, which the other characteristics don't need since they're Write-only). `DeviceStatus` instead uses `ble_gatts_notify()` (not `_custom()`) from a dedicated FreeRTOS task (`device_status_notify_task`, 5s interval, 4096-byte stack — 2048 was too small for the deep call path into NimBLE's host internals and crashed with `assert failed: spinlock_acquire spinlock.h:142 (lock->count == 0)`, a boot loop that briefly manifested as a white display flash on reset and was initially misdiagnosed as a display bug, confirmed and fixed on hardware) so a Read and a Notify build the payload through the same `device_status_access_cb()` path rather than duplicating it; the payload combines `pmu_get_battery_percent()` (see `pmu.cpp`) and `ble_gap_conn_rssi()`. The active `conn_handle` is tracked via `ble_gatt_server_on_connect()`/`_on_disconnect()`, called from `main.c`'s `gap_event()`. `ControlEvent`'s `ble_gatt_chr_def` needs a (never-invoked) `access_cb` even though it's Notify-only and never Read/Written — NimBLE's `ble_gatts_chr_is_sane()` rejects any characteristic definition with a `NULL` access_cb regardless of its flags, which otherwise makes `gatt_svr_init()` fail and crashes the `assert(rc == 0)` in `main.c`'s `app_main()` into a boot loop (confirmed on hardware). `DisplayConfig` (`Write`, 13 bytes v2 / 8 bytes v1 — the callback accepts "at least v1" and fills the energy fields with the pre-v2 fixed values 100 %/300 s/never) decodes the six slot metric ids, font scale, two flags, brightness (clamped to ≥10 % — a 0 % display could not be touch-recovered), screen-off timeout and deep-sleep timeout and hands them to `display_set_config()`; `RideSummary` (`Write`, 25 bytes) decodes the last ride's aggregates plus the lifetime/week totals and hands them to `display_set_ride_summary()`. Both are **not** required by the app's `isRequiredServiceSupported()` check — they are extras, and making them mandatory would mean a newer app cannot connect to older firmware at all, losing the ride rather than just the extra display. `JunctionPreview` is documented in the protocol doc but not yet on the firmware side. `SetTime` (`Write` with response, 4 bytes) decodes a little-endian `uint32` local-epoch-seconds value and forwards it to `pcf85063_set_local_epoch_seconds()` (see `rtc.c`), returning `BLE_ATT_ERR_UNLIKELY` if that write fails so the app's `.suspend()` call surfaces the failure instead of silently succeeding. `MediaStatus` (`Write Without Response`, variable length, Phase 10.1 — music screen) decodes `is_playing` plus length-prefixed `title`/`artist` UTF-8 byte strings (max 60 bytes each, validated against the actual received length before `memcpy`, rejecting anything malformed with `BLE_ATT_ERR_INVALID_ATTR_VALUE_LEN`) and forwards them to `display_set_media_status()`. `log_ride_data()` (Phase 11) also calls `odometer_on_ride_distance(distance_m)` on every `RideData` write and passes the returned lifetime total through `display_ride_data_t.total_distance_m` to `display_set_ride_data()` — see `odometer.h` above. `RideData` decoding is length-tolerant across all three payload versions (23/29/33 bytes): v2 fields (max speed, elapsed time) and v3 fields (absolute altitude with `INT16_MIN` = unknown, descent) are only read when present.
  - `pmu.h`/`pmu.cpp` — thin `extern "C"` wrapper (`pmu_init()`, `pmu_get_battery_percent()`) around the vendored `XPowersLib` (C++) for the board's AXP2101 power-management IC, so the mostly-C firmware only sees two plain functions. Uses `bsp_i2c_get_handle()` to share the Waveshare BSP's already-initialized I2C bus (same one the touch controller uses) via XPowersLib's `begin(i2c_master_bus_handle_t, addr)` overload, rather than creating a second bus on separate pins — a separate bus (GPIO7/GPIO8, per Waveshare's standalone, non-BSP-based `examples/esp-idf/01_AXP2101` demo for this board) found no device on hardware; the shared bus works since the AXP2101 and touch controller are on the same physical bus. `#define CONFIG_XPOWERS_ESP_IDF_NEW_API` is mandatory before including `XPowersLib.h`: without it, the library additionally compiles an unused legacy-API member function that references the old `driver/i2c.h`, which conflicts with the BSP's new `i2c_master` driver at the first `i2c_new_master_bus()` call (`CONFLICT! driver_ng is not allowed to be used with this old driver`) and boot-loops the board (confirmed on hardware) — ESP-IDF allows only one of the two I2C driver generations per process. `pmu_get_battery_percent()` returns `false` (mapped to the `0xFF` "no battery" sentinel by `ble_gatt_server.c`) whenever `XPowersPMU::isBatteryConnect()` is false, which is the board's normal state during bench/USB-only testing without a battery wired in yet (per the spec, the battery is a not-yet-installed future hardware addition).
  - `rtc.h`/`rtc.c` — plain-C register-level driver for the board's external PCF85063 RTC chip (I2C address `0x51`, no vendor library available unlike the AXP2101, so this talks `driver/i2c_master.h` directly: `i2c_master_bus_add_device()` + `i2c_master_transmit()`/`_transmit_receive()`, timeout `-1`). Shares the BSP's I2C bus via `bsp_i2c_get_handle()` like `pmu.cpp` does, under the same "probably the same bus, no separate one documented" assumption — confirmed working on hardware (ACKs on `pcf85063_init()`, no boot loop). Public functions are prefixed `pcf85063_` rather than `rtc_` — a `rtc_init()` name collided at link time with ESP-IDF's own internal `esp_hw_support` symbol of the same name (`multiple definition of 'rtc_init'`, unrelated chip-clock subsystem, confirmed on hardware) — a naming trap worth remembering before reaching for `rtc_`-prefixed names for anything RTC-related in this codebase. `pcf85063_set_local_epoch_seconds()` takes a value that's already local wall-clock time (see `BleProtocol.kt`'s `setTimePayload()`) and writes it via `gmtime_r()` purely as a calendar-math helper — "UTC" is only the computation path, not a meaningful timezone here. `pcf85063_get_time()` returns `false` if the chip's own Oscillator-Stop flag (seconds register bit 7, set by the chip whenever backup power ever dropped) is set, meaning no valid time has ever been written since power was lost — this flag is what makes the RTC's across-reboot persistence self-verifying instead of relying on a volatile "have I set it" flag in RAM (confirmed on hardware: correct time still shown after a reset with the phone's Bluetooth deliberately left off, i.e. with no `SetTime` write involved).
  - `odometer.h`/`odometer.c` (Phase 11) — plain-C module tracking a lifetime (not per-ride) odometer, persisted in NVS (namespace `bike_computer`, key `total_dist_m`, `uint32_t` meters — good for ~4.29 million km, effectively unlimited for this use case). `odometer_on_ride_distance(ride_distance_m)` is called from `ble_gatt_server.c`'s `log_ride_data()` on every `RideData` write; it detects a new ride start by `ride_distance_m` *decreasing* versus the previous call — the only thing that resets `RideData.distance_m` to 0 is the app's `RideTracker.startRecording()` (auto-pause/resume and an app/process restart both freeze-and-continue instead, see `RideTracker.kt`), so a decrease reliably means the previous ride is over — and folds the just-finished ride's final distance into the saved total, persisting immediately (rare, meaningful event). Between resets it also persists a snapshot every `ODOMETER_PERSIST_EVERY_N_WRITES` (30) calls (~30s at RideData's ~1 Hz) so a power loss mid-ride only loses the last ~30s of that ride's distance from the lifetime total, not the whole ride — writing NVS on every single 1 Hz `RideData` write was avoided to limit flash wear. Returns the live total (saved + current ride) on every call for immediate display. `odometer_init()` (called once from `main.c`'s `app_main()`, after `nvs_flash_init()`) loads the saved total at boot, defaulting to 0 on first-ever boot (no stored key yet). No new BLE characteristic — purely firmware-side bookkeeping computed from `RideData.distance_m`, which the app already sends.
  - `summary_store.h`/`summary_store.c` — keeps the last `RideSummary` across a reboot in NVS (namespace `bike_computer`, key `ride_summary`, the `display_ride_summary_t` struct as a blob). The **second and last exception** to "the board persists nothing", and deliberately narrow: it stores only what was already on screen, `summary_store_save()` writes only when the numbers actually differ from the last write (the routine push after every connect usually repeats them, and flash wear is real), and the first live `RideSummary` overwrites it without comment. `summary_store_load()` refuses a blob whose size doesn't match the current struct — a grown struct would otherwise be read as garbage numbers — and sets `from_storage`, which makes `display_set_ride_summary()` append "Stand der letzten Verbindung" so nobody mistakes an old total for a current one. Without this the statistics screen said "Noch keine Fahrt" after every power-on until a phone connected, i.e. exactly when you are standing there with only the board.
  - `buttons.h`/`buttons.c` — the board's side BOOT button (GPIO0; a strapping pin only during boot, a normal input afterwards), polled at 20 ms rather than interrupt-driven since debounce/long-press need time measurement anyway: short press toggles the panel (`display_toggle_screen_power()`, BLE and recording keep running), long press (1.5 s, fires on reaching the hold time so the display going dark *is* the feedback) powers the board off via `buttons_power_off()` — deep sleep with `esp_sleep_enable_ext1_wakeup_io()` on the same button, waiting for release first so the still-held low level doesn't immediately re-trigger the just-armed wake source. `buttons_power_off()` is public because the timed power-off (`apply_idle_deep_sleep()` in `display.c`, DisplayConfig v2 `deep_sleep_s`) and Screen 6's "BOARD AUS" button reuse it — one place owns the wake-source configuration *and* the `ControlEvent` 11 ("board is shutting down") notify that makes the app finish the ride and quit. That notify is followed by a `POWER_OFF_NOTIFY_GRACE_MS` delay: `ble_gatts_notify_custom()` only hands the packet to the NimBLE host, so going to sleep immediately would put it on no radio at all. The `CONTROL_EVENT_*` field values consequently live in `ble_gatt_server.h`, not in `display.c` — two modules need them now. The RST and PWR side buttons stay untouched (hard reset / AXP2101 supply). Two defences against a button the **handlebar mount squeezes permanently**: a press that was already there at startup is ignored until the first release (`armed`), otherwise the hold counter reaches the 1.5 s power-off threshold on its own 1.5 s after every boot and the display goes dark with nobody having pressed anything; and the wait-for-release loop inside `buttons_power_off()` gives up after `RELEASE_WAIT_TIMEOUT_MS` and switches the screen back on instead of sleeping — a stuck button would otherwise either park that loop forever or, if it went to sleep anyway, immediately re-trigger its own `ESP_EXT1_WAKEUP_ANY_LOW` wake source. **Only GPIO0 can be defended this way**: RST sits on the ESP32-S3's EN pin, so a permanently held RST keeps the chip in reset and no firmware runs at all — that case is mechanical, not software. `buttons_discard_short_wake()` closes the matching gap on the way *in*: the chip's wake source only knows "level low" and cannot demand a duration, so a brief contact in a pocket switched the board on. It runs as the very first statement of `app_main()` — before `display_init()`, so a too-short press never even lights the panel — and goes straight back to deep sleep unless the button is still held after `WAKE_HOLD_MS`.
  - `main.c` — NimBLE host init, GAP advertising (flags + 128-bit service UUID in the primary packet, device name + TX power in the scan response — the full set doesn't fit in a legacy 31-byte advertising PDU), GAP event handling (connect/disconnect/MTU, forwards connect/disconnect to `ble_gatt_server.c` for `ControlEvent`/`DeviceStatus`'s conn_handle tracking), re-advertises on disconnect. Calls `display_init()` then `pmu_init()` early in `app_main` (a failed `pmu_init()` only logs a warning, doesn't block boot — display/BLE work fine without the PMU).
  - `display.c`/`.h` — Screen 1 (Datenübersicht) from the spec, live: via Waveshare's `bsp_display_start()` (SH8601 panel + LVGL 9 port), a black `lv_screen_active()` background with a big centered speed value (number and unit are separate labels so the unit can be smaller and dimmed) plus two rows of three slots. Those six slots are **freely assignable** via `DisplayConfig`: `s_config` holds a metric id per slot (defaulting to exactly the previously hardcoded assignment — whoever configures nothing should notice nothing), `format_metric()` renders the value and `apply_slot_layout()` the icon, font size and visibility. Redrawing an icon uses `lv_obj_clean()` on the existing holder plus `draw_slot_icon()` rather than creating a new holder: a new one would keep appending to the `MAX_SHIFTABLE_LABELS`-limited pixel-shift list on every reconfiguration. The six icon shapes cover fourteen metrics on purpose — at 24 px an icon can say what *kind* of number this is (distance, time, speed, altitude), not which one exactly, and whoever assigned the slots knows. Row/column offsets are named constants (`ROW1_LABEL_Y`, `COLUMN_X`, …) chosen against the round display's usable chord width `2·√(233² − Δy²)` — see `docs/mockups/syncrider-board-layouts.svg`. All slot labels are **ASCII only**: LVGL's built-in Montserrat fonts cover 0x20–0x7F plus the `LV_SYMBOL` glyphs, so umlauts and `Ø` would render as placeholders (hence "HOEHE"/"SCHNITT"). A `lv_arc` in the otherwise empty outer ring (270°, gap at the bottom where the clock sits) shows route progress; the total route length it needs isn't in the protocol, so `display_set_route()` computes it from the already-projected points. That arc **must** have `LV_OBJ_FLAG_CLICKABLE` cleared — at 452 px it would otherwise become the touch input's active object and swallow the screen's swipe gesture, killing the carousel. `display_set_phone_status()` renders `PhoneStatus` (previously log-only) as a colored GPS-quality dot plus a phone-battery warning that only appears below `PHONE_BATTERY_WARN_PERCENT`. A **"KEIN HANDY"** label shares that same centre slot in the status row (`display_set_ble_connected()` shows exactly one of the two, since the phone battery is meaningless without a link): a grey Bluetooth glyph at the edge is not a difference anyone notices while riding, and frozen values look exactly like standing still. It stays hidden before the first-ever connect — the splash already explains that case. The Screen 1 turn hint uses `montserrat_26` for the distance and a 6 px arrow stroke; it cannot grow much beyond that because it lives in the ~40 px band between `STATUS_ROW_Y` and the 80 px speed value, and the number is what gets read anyway. `align_static()` registers every fixed-position label in `s_shiftables` so `apply_pixel_shift()` (driven by `battery_poll_task`, every 3 min) can nudge them a few pixels against AMOLED burn-in — deliberately per-label rather than translating the screen object, since a shifted full-screen root leaves an edge strip that nothing repaints, and on a round display the edge midpoints *are* visible even though the corners aren't. The arrival time is computed from `s_clock_hour`/`s_clock_minute`, cached by `battery_poll_task`, rather than reading the RTC directly: `display_set_ride_data()` runs on the NimBLE host task at 1 Hz and must not add I2C traffic to that path (the bus is shared with the PMU and touch controller). `display_set_ride_data()` is the only mutation entry point — called from `ble_gatt_server.c`'s `log_ride_data()` on every `RideData` write, wraps its `lv_label_set_text()` calls in `bsp_display_lock()`/`unlock()` since it runs on the NimBLE host task, not the LVGL task. `UINT32_MAX`-sentinel remaining-distance/time render as `"--"`. The route-line object (`s_route_line`) is sized to the full screen, not a small anchor box: LVGL's line widget computes the region it actually flushes to the display from the object's own bounding box plus only the line width, not from the point coordinates, so a small object with `OVERFLOW_VISIBLE` renders the line into a buffer region that's never sent to the panel (confirmed on hardware — Screen 2 stayed black despite correct, on-screen point coordinates in the logs).

  **Screen 2 (Navigation)** has two modes. `display_set_route()` draws the whole route north-up as an overview — that is what you get right after an import, before any position is known. The first `display_set_nav_status()` replaces it with a **moving, heading-up map section** and there is no way back for that route. The reason is resolution, not taste: a 36 km tour drawn across `ROUTE_DRAW_SIZE` is ~95 m per pixel, enough for a recognisable scribble of the whole track but not enough to tell whether the next junction goes left or right; `NAV_VIEW_AHEAD_M` puts it at ~1.2 m per pixel. `nav_build_route_line()` finds the nearest route vertex by linear scan (deliberately not incrementally from the last hit — that would be wrong after a restart mid-tour or a shortcut), takes the index window `NAV_TRAIL_BEHIND_M` back to `NAV_CLIP_AHEAD_M` forward using the per-point cumulative distances `display_set_route()` precomputed into `s_route_cum_m`, extends it by one point at each end so the line runs off the edge instead of stopping in mid-air, and rotates it so the direction of travel points up (`forward = dx·sin h + dy·cos h`, `right = dx·cos h − dy·sin h`; screen y is inverted). The position dot sits **below** the centre at `NAV_POSITION_Y` — what lies behind you needs little room, what lies ahead needs a lot. Rebuilding is gated on `NAV_REDRAW_MIN_MOVE_M`/`NAV_REDRAW_MIN_HEADING_DEG`: `lv_line_set_points()` invalidates the screen-filling line object, so every change costs a full-screen redraw, and at a traffic light that would be per-second work for an identical picture. A compass rose (`update_compass()`, red half pointing north, the usual convention) keeps the cardinal direction available on the rotated map, and a turn arrow plus distance sits at the top; both get a dimmed backdrop because the white route line can otherwise run straight through them. The seven arrow symbols (`TURN_SHAPES` / `build_turn_arrow()`) are drawn once at init and stacked on top of each other, `nav_set_turn()` only toggles visibility — and they share a single holder object so that only one entry is spent on the `MAX_SHIFTABLE_LABELS`-limited pixel-shift list. The arrowhead is derived from the direction of the shaft's last segment instead of being hand-placed per symbol. `turn_direction == STRAIGHT` with distance 0 hides the whole hint (see the protocol doc). `gesture_event_cb()` also calls `ble_gatt_server_notify_control_event()` on every swipe (source is always "Touch-Swipe" — this board has no external buttons). Touch input works (confirmed on hardware) — see `firmware/components/` note below. Boot splash + BLE icon (Phase 7, animated splash added later): `display_init()` hides the Screen 1 ride-data labels and shows a centered "SyncRider" splash label instead, with a one-shot boot animation — `create_splash_bike()` builds a minimalist line-art bicycle (two `LV_RADIUS_CIRCLE` wheel outlines in white plus a classic two-triangle diamond frame — rear triangle, seat tube/fork, top tube, handlebar stem + bar — in the brand accent color `SPLASH_BIKE_COLOR`/`0x30a0ff`, same as the BLE icon/position dot; no image asset, everything drawn with LVGL shapes/lines like the rest of this file) as a container object that `splash_anim_exec_cb()` slides from `SPLASH_BIKE_X_START` to `_END` (off-screen-left to off-screen-right) over `SPLASH_ANIM_DURATION_MS`. The same callback derives a left-to-right text reveal from the bike's geometric position — `s_splash_text_cover` is a black rectangle sized/positioned to exactly cover the "SyncRider" label (measured via `lv_obj_update_layout()` + `lv_obj_get_x/y/width/height()` right after the label's alignment is resolved, since alignment isn't resolved until a layout pass), and each frame shrinks/shifts the cover so its left edge tracks the bike's **trailing** edge (`v − SPLASH_BIKE_TEXT_GAP`) — the text visibly "builds up behind" the bike with no separate timing to keep in sync. The reveal edge was originally the *leading* edge (`v + SPLASH_BIKE_WIDTH`), which necessarily put the bike on top of the letters it had just uncovered; anchoring to the rear wheel instead is what makes it ride ahead of the text rather than through it. `splash_anim_ready_cb()` hides the bike once the one-shot animation finishes, leaving a static "SyncRider" splash; `display_set_ble_connected(bool)` (called from `main.c`'s `gap_event()` on every `BLE_GAP_EVENT_CONNECT`/`_DISCONNECT`) recolors a `LV_SYMBOL_BLUETOOTH` icon on both screens (blue connected / gray disconnected) and, only on the first-ever connect, hides the splash (plus the bike/cover objects too, in case the boot animation is somehow still mid-flight on an unusually fast first connect) and reveals the ride-data labels — later disconnects/reconnects mid-ride just recolor the icon, they don't bring the splash back. **The 466×466 framebuffer is a physically round display** (1.75" AMOLED, see `docs/wiki/03-hardware.md`) — a rectangular-corner alignment (`LV_ALIGN_TOP_RIGHT` etc.) lands well outside the visible circle (radius 233px; a corner is ~315px from center) and renders invisible except for a flash mid-swipe-animation when screen content slides through the visible area (confirmed on hardware, docs/bugs.md); the BLE icon uses `LV_ALIGN_CENTER` with an offset instead, and any new fixed-position UI element must stay within ~230px of screen center. Battery display (Phase 8): `battery_poll_task` (started at the end of `display_init()`) polls `pmu_get_battery_percent()`/`pmu_is_charging()` every `BATTERY_POLL_INTERVAL_MS` (5s) independent of the BLE connection — unlike `ble_gatt_server.c`'s `device_status_notify_task`, which only reads the PMU when a phone is connected (it notifies over BLE), the on-board display should show battery state regardless. Renders a **drawn** battery (`create_battery_widget()`: outline, positive nub, a fill whose width is the charge level, and a `LV_SYMBOL_CHARGE` bolt inside while charging) plus the percentage as a label, mirrored on the opposite side of the BLE icon; hidden when `pmu_get_battery_percent()` returns false (no battery detected). The percentage text turns amber at `BATTERY_WARN_PERCENT` and red at `BATTERY_CRITICAL_PERCENT`. Deliberately no blinking or pulsing: an earlier pulsing opacity animation while charging was removed again — at the edge of the field of view it was unrest rather than information, and a permanently running animation means permanent redraws in the same spot on an AMOLED. Time display (Phase 9): the same `battery_poll_task` also calls `pcf85063_get_time()` (see `rtc.c`) each cycle and formats `HH:MM` into a label centered at the bottom of both screens (`LV_ALIGN_CENTER, 0, 170` — same "stay within the round visible area" constraint as the BLE/battery icons) — one shared task instead of a second one, since 5s resolution is more than enough for a minute-granularity clock and both values are equally cheap/independent-of-BLE to poll. Empty string when no valid time is available yet (fresh RTC that's never received a `SetTime` write). Music screen (Phase 10.1, third screen — `s_screen3`): shows title/artist (`display_set_media_status()`, fed by the new `MediaStatus` characteristic) plus three tappable symbol labels (`LV_SYMBOL_PREV`/`LV_SYMBOL_PLAY`-or-`_PAUSE`/`LV_SYMBOL_NEXT`, `montserrat_48` for a large enough touch target) that call `media_prev_click_cb()`/`media_play_pause_click_cb()`/`media_next_click_cb()` on `LV_EVENT_CLICKED`, sending `ControlEvent` `TRACK_PREVIOUS`(4)/`SHORT_PRESS`(0)/`TRACK_NEXT`(5). Title/artist labels use `LV_LABEL_LONG_MODE_SCROLL_CIRCULAR` with a fixed width so long track names auto-scroll instead of being clipped. Screen navigation is a **cross, not a single ring** (`s_screens[SCREEN_COUNT]` + `s_current_screen_index`, `SCREEN_COUNT` = 6). Horizontally, `HORIZONTAL_RING` holds the riding screens (Daten → Navigation → Fahrtsteuerung → Statistik, with wraparound); vertically, the two operating screens hang off **every** riding screen — brightness *above* (swipe down to pull it in, `MOVE_BOTTOM`), music *below* (swipe up, `MOVE_TOP`), with the opposite gesture returning to `s_vertical_origin_index`, i.e. exactly the screen the swipe started from rather than always the data screen. They are reachable everywhere because they are operation, not a destination: needing to swipe back to the overview first to dim the display or skip a track is the wrong cost at the handlebars. If the origin screen has meanwhile become unavailable (Navigation without a route), the return falls back to the data screen. Horizontal swipes on music/brightness deliberately do nothing, so you can't fall out of an operating screen along a third axis. `screen_is_available()` keeps Navigation out of the ring while `s_route_count == 0` — the loop skips unavailable entries rather than landing on them, because a screen that always leads nowhere is worse than no screen. That check uses the actually-received route and **not** `RideData`'s route-loaded flag: the app only sets that flag once a position fix also exists, so the map would vanish indoors despite a loaded tour. Only horizontal swipes still emit `SWIPE_LEFT`/`SWIPE_RIGHT`; the protocol has no vertical type and the app ignores swipes anyway. An earlier version additionally sent `ControlEvent` `SHORT_PRESS`/`LONG_PRESS` on a generic tap/long-press anywhere on Screen 1/2 (`tap_event_cb()`) — removed again: LVGL's long-press timer starts on touch-down, before it's known whether the touch will turn into a swipe, so a slower swipe on Screen 1/2 also fired the music action (confirmed on hardware — swiping interfered with playback). Music control is now exclusively the three Screen 3 buttons. **Screen 4 (Fahrtsteuerung)** and **Screen 5 (Statistik)**: Screen 4 has a pause/resume and a stop button with the current distance and ride time between them (without those, "end ride" is a decision made blind). The pause button turns into a play button purely from `RideData`'s recording flag — the board deliberately keeps **no** ride state of its own, which after a dropped connection could be wrong. The stop button only appears when there is a ride to end (`recording || distance_m > 0`) and the pause button then centres itself; the condition deliberately includes a *paused* ride with distance, since that is exactly when you press "done" at the handlebars — gating on `recording` alone would make a paused ride impossible to finish from the board. Stopping asks back, pausing does not: a pause is reversible, a finished ride cannot be un-finished at the handlebars. Screen 5 renders whatever `RideSummary` last delivered. Neither screen's labels join the pixel-shift list — they are on screen seconds a day, and burn-in needs hours in the same place. **Screen 6 (Helligkeit)**: big −/+ symbol labels (with `lv_obj_set_ext_click_area()` widened hit zones — gloves) around the current percentage. `brightness_step()` applies the change locally first (`apply_brightness()` + label), then notifies the app via `ControlEvent` 9/10 so it persists the same step in its stored `DisplayConfig` and re-pushes it — at the range limits nothing happens and nothing is notified. `BRIGHTNESS_STEP_PERCENT` (10) must match `BoardDisplayConfig.BRIGHTNESS_STEP_PERCENT` app-side. Deliberately only brightness here, no timeout values: time values are typed on the phone, the handlebars need exactly one setting (sun). It also carries the **"BOARD AUS"** button (with a confirm box built like Screen 4's, since powering off cannot be undone at the handlebars — the BOOT long-press stays unconfirmed because holding it 1.5 s *is* the confirmation): device operation belongs on the one screen that operates the device, not next to the ride controls. That button needs a **`POWER_OFF_HOLD_MS` hold** and sits at the **top** edge, both against the same trap: the gesture back out of Screen 6 is a swipe up, which starts at the bottom, so a tap-activated button down there lies exactly in its path and switched the board off during normal navigation (hit on hardware). The hold is timed by hand in `power_off_press_cb`/`_press_lost_cb`/`_release_cb` rather than via `LV_EVENT_LONG_PRESSED`, whose duration is a device-wide setting and whose timer starts on touch-down before it is known whether the touch becomes a swipe — the same mechanism that already made gestures and presses collide once. The required hold is written on the button itself, or a short tap would look like a broken one. It only calls `buttons_power_off()`, which owns both the wake-source configuration and the `ControlEvent` 11 notify that takes the app down with it. Battery management: `apply_brightness()` is the single place computing the actual panel brightness — the configured value (`s_config.brightness_pct`, DisplayConfig v2, clamped to ≥`BRIGHTNESS_MIN_PERCENT`) with `apply_battery_saver()`'s `BATTERY_SAVER_BRIGHTNESS_PERCENT` winning only when it is *darker* (on an AMOLED, power scales with brightness, so this is a real saving, and dimming beats switching off — riding in the dark on a low battery needs the display more, not less); `apply_idle_screen_off()` powers the panel down after `s_config.screen_off_s` (0 = never) without a touch, and `apply_idle_deep_sleep()` powers the whole board off after `s_config.deep_sleep_s` (0 = never, also the default) via `buttons_power_off()` — both **only while no phone is connected** — during a ride the display is the whole point of the device. `screen_press_cb()` (`LV_EVENT_PRESSED`, which only records, never triggers — hence free of the conflict that killed the earlier generic tap/long-press handlers) wakes it again and sets `s_swallow_next_click`, so the waking touch cannot also hit whichever button happened to be under the finger. One deliberate deviation from that copied config: `CONFIG_BSP_DISPLAY_LVGL_BUF_HEIGHT=16` (not the demo's default 100) — a larger buffer hit a known Espressif bug ([esp-bsp#716](https://github.com/espressif/esp-bsp/issues/716)) where `lv_disp_flush_ready()` fires after the first SPI chunk instead of the last, causing `spi transmit (queue) color failed` and visible white stripes on full-screen redraws.

`firmware/components/esp32_s3_touch_amoled_1_75/` — a locally patched fork of the Waveshare BSP, wired in via `override_path` in `main/idf_component.yml`. Four `PATCH`-commented fixes, all in `esp32_s3_touch_amoled_1_75.c`, that together stop the recurring `spi transmit (queue) color failed` / frozen-display failure (`docs/bugs.md`): (1) `bsp_display_lcd_init()` was declared **without a parameter list** but called as `bsp_display_lcd_init(cfg)` — legal C, the argument is silently dropped, so the buffer flags never arrived and `esp_lvgl_port` allocated with `MALLOC_CAP_DEFAULT`, landing in internal RAM or *silently in PSRAM* depending on boot-time heap state (hence the failure appeared to roll dice); (2) the flags are now actually forwarded; (3) the caller is flipped to `buff_dma = true`/`buff_spiram = false` — the original sets `buff_spiram = true`, so fixing only (1) would push the draw buffer *into* PSRAM and make it worse; (4) `lvgl_port_add_disp()` instead of `lvgl_port_add_disp_rgb()` — the latter is for RGB parallel panels, and for this QSPI panel it both skips registering `on_color_trans_done` and makes `lvgl_port_flush_callback()` call `lv_disp_flush_ready()` synchronously right after *queueing* the transaction. That is esp-bsp#716 itself, now fixed rather than worked around. Nothing crashed because the port ignores `esp_lcd_panel_draw_bitmap()`'s return value. (5) `sw_rotate = false` — with rotation flags all false it only made `esp_lvgl_port` allocate a **second** same-size draw buffer (`draw_buffs[2]`), and after (3)/(4) that one sits in scarce internal DMA RAM. Those 14 912 wasted bytes were exactly what starved the NimBLE host task: `nimble_port_freertos_init()` does not check `xTaskCreate()`, so the host silently never ran, `on_sync()` never fired, the board never advertised, and the app simply could not find it — no error, no crash. `main.c` now logs free/largest-block internal heap right before creating that task plus a "NimBLE-Host-Task laeuft" line inside it, because that failure is otherwise indistinguishable from broken BLE. **The margin is thin: ~16 KB free with an 8 192-byte largest block at that moment** (13 523 when this was first measured, then down to 12 067, at which point the BT *controller* — not the host — ran out and `ble_gap_adv_rsp_set_fields()` failed with `BLE_ERR_MEM_CAPACITY`; `sdkconfig.defaults` now switches off the unused Central/Observer roles and caps connections/activities at 1/2, which bought back ~4 KB) — anything sizeable newly placed in internal RAM will hit the same trap. Verified on hardware over identical 9 s windows: 14/1/2 errors → 0/0/0, plus 60 s under live 1 Hz `RideData` load (the case that previously failed once per second) with zero errors and a complete connect handshake. The boot's free-internal-DMA figure goes 117 331 → 101 967 bytes (= the one remaining draw buffer, which previously was not in internal RAM at all). **Do not** re-derive display fixes from `CONFIG_BSP_DISPLAY_LVGL_BUF_HEIGHT` alone — that value is a load margin, not the cause, and its original justification in the docs was wrong (3 → 1 chunks, not "2–3").

`firmware/components/esp_lcd_touch_cst9217/` — a locally patched fork of the `waveshare/esp_lcd_touch_cst9217` registry component, wired in via `override_path` in `main/idf_component.yml`. Unlike `managed_components/` (registry-fetched, gitignored, never hand-edit), this directory is committed and meant to be edited. The patch: the original driver returned `ESP_ERR_INVALID_RESPONSE` from `read_data()` whenever no touch was currently present (a normal, expected state, not a fault) — `esp_lvgl_port@2.8.0`'s touchpad-read callback wraps that call in an unconditional `ESP_ERROR_CHECK`, so every "no touch" reading crashed the whole firmware. Fixed at the root: "no ACK" now sets 0 touch points and returns `ESP_OK`, matching the `esp_lcd_touch` driver contract. If bumping the `lvgl/lvgl` or `waveshare/esp32_s3_touch_amoled_1_75` component versions ever pulls in a fixed upstream `esp_lcd_touch_cst9217`, this override (and its `.c` patch comment) can be dropped.

`firmware/components/XPowersLib/` — a vendored (not registry-fetched) copy of just the `src/` directory of [lewisxhe/XPowersLib](https://github.com/lewisxhe/XPowersLib) (MIT), unpatched. Auto-discovered as a build component because ESP-IDF scans `PROJECT_DIR/components` by default — no `idf_component.yml` entry needed, unlike `esp_lcd_touch_cst9217` (that one's `override_path` entry exists to replace a *registry* dependency pulled in transitively by the BSP; `XPowersLib` has no registry counterpart to replace). Only `src/` was copied (not `examples/`/`datasheet/`/`tools/`/`Micropython/`, all Arduino/PlatformIO/docs artifacts irrelevant to an ESP-IDF component) since the repo's own root `CMakeLists.txt` already registers exactly `src/` + `src/REG` as the component's sources/includes. Used by `firmware/main/pmu.cpp`.

### Current implementation state vs. spec

Phase 1 (MVP: BLE connection + live Screen 1 data) from the original phase plan is complete and confirmed end-to-end on real hardware (Waveshare ESP32-S3-Touch-AMOLED-1.75): BLE connect, MTU negotiation, live `RideData` decoded and rendered on the actual AMOLED display, touch input working. Phase 2's BLE/data side now also works end-to-end, confirmed on real hardware: full `RouteData` transfer (header → chunks → complete) is received and decoded and renders as a visible route line on Screen 2, `RideData`'s `dist_to_dest_m`/`time_to_dest_s` are populated from `RouteProgressCalculator` once a route is loaded (no longer always the sentinel), and `NavStatus` is implemented end-to-end — the app writes position/heading/off-route at ~1 Hz whenever a route is loaded, the board decodes it and shows a colored position dot on Screen 2. `ControlEvent` (board→phone `Notify` on touch swipes, taps, and long-presses) and `DeviceStatus`/`PhoneStatus` (board battery+RSSI, phone battery+GPS-fix-quality) are also implemented end-to-end and confirmed on hardware. `ControlEvent` now also drives real app behavior — the dedicated music screen's three buttons (Phase 10.1, Screen 3) control the phone's active media session via `media/` and `RideForegroundService.controlEventLoop()`, and the new `MediaStatus` characteristic feeds that screen's title/artist/play-state back the other way — though `DeviceStatus` still has no consumer beyond a UI label (no low-battery warning yet). `DeviceStatus`/`PhoneStatus` were originally a single mixed-ownership "DeviceStatus" characteristic in the spec doc — split into two (see `fahrradcomputer-ble-protokoll.md`) since a single GATT characteristic can't have some fields Read/Notify (board-authoritative) and others Write (phone-authoritative). Screen 2 is now a heading-up moving map with a compass rose and a turn arrow, and `turn_direction`/`distance_to_turn_m` carry real values derived from the route geometry (`TurnDetector`) rather than from a routing API. Verified on hardware down to the data layer — route transfer, `NavStatus` with turn direction/distance, and the redraw filter all confirmed in the board's log; the rendered picture itself has not been checked by eye yet. Still open: no routing API means no street names, no roundabout exits and **no rerouting** — leaving the route only turns the position dot red and suppresses the turn hint; `JunctionPreview` is not implemented on either side.

The remaining items of `docs/features.md` were implemented in one pass (2026-07-26): barometric climb metres replacing absolute altitude (`RideData` v2), board Screen 4 (ride control) and Screen 5 (statistics/summary) with the `RideSummary` characteristic, freely assignable Screen 1 slots and font size via `DisplayConfig`, board battery management (colour warning, brightness saver, idle screen-off with wake-on-touch), the tour library with favourites and preview (Room migration 1→2), and the Strava connection. **Verification status of that pass:** the firmware builds, flashes and boots cleanly on real hardware (no SPI errors, odometer restored from NVS), and the app builds with all JVM tests green — but nothing of it has been exercised over an actual BLE link or looked at on the display, because the phone was not attached during that session. Everything board-side is therefore "compiles and boots", not "seen working". Strava additionally needs the user's API credentials in `strava.properties` before it can run at all. What remains genuinely unimplemented from the feature list: sound output from the board (needs a driver bring-up for the unused audio codec, comparable in effort to the AXP2101 work) and any automatic tour sync with Komoot or Google Maps (no public API for either).

### BLE protocol conventions to preserve

- All multi-byte values little-endian.
- Phone is GATT Central/Client; board is GATT Peripheral/Server. Only the board can `Notify`; phone→board data is always `Write`/`Write Without Response`.
- MTU is requested at 247 on connect (`requestMtu(247)` in `BikeComputerBleManager.initialize()`); protocol payload sizes assume this succeeded, with 23-byte MTU as an untested fallback case.
